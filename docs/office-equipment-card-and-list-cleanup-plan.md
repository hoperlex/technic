Частичный индекс `service_requests_urgent_idx` ([schema.ts:3551](../apps/api/src/db/schema.ts#L3551))
написан **под снимаемую сортировку**: его условие (`is_urgent AND deleted_at IS NULL AND status NOT IN
('accepted','cancelled','on_hold')`) повторяет активную часть `urgentFirst`. Сам отбор шире: он
исключает только `on_hold`, но сохраняет закрытые срочные за выбранный период. После Р1 нынешний
индекс сможет помогать лишь запросам, которые дополнительно исключили закрытые статусы, но не
общему отбору `urgent=true`; это и есть основание переопределить его в Р2.

### 2.2. Объём работ сегодня обязателен ЛЮБОМУ ремонту, включая внутренний

Цепочка такая:

1. Предъявление открыто всякому исполнителю ремонтной заявки — `canSubmitServiceEstimate`
   ([service-requests.ts:1130](../packages/contracts/src/service-requests.ts#L1130)) спрашивает вид,
   статус и сторону, но не спрашивает, есть ли подрядчик.
2. Согласует его «Ведение» либо назначенный — `canApproveServiceEstimate`
   ([:1154](../packages/contracts/src/service-requests.ts#L1154)).
3. Закрытие работ требует **совпадения ревизий**
   ([service-requests.ts:6536–6545](../apps/api/src/routes/service-requests.ts#L6536)):
   `approvedEstimateRevision !== estimateRevision` → `409`.

У заявки, по которой объём работ ни разу не предъявляли, `estimate_revision = 0`, а
`approved_estimate_revision = NULL` ([schema.ts:3200](../apps/api/src/db/schema.ts#L3200)), то есть
`NULL !== 0` — **истина**. Значит внутренний ремонт сегодня закрыть, не пройдя предъявление и
согласование, нельзя вовсе (находка Н1). Заказчик просит убрать не «лишнюю кнопку», а обязательный
шаг.

Окно закрытия работ ([ServiceCompleteModal.tsx:139–210](../apps/web/src/features/service-complete/ui/ServiceCompleteModal.tsx#L139))
целиком построено вокруг сметы: плашка «Согласована ревизия N на X ₽», таблица строк с отметками
«выполнено», скидка по акту, счётный итог. У внутренней заявки всё это показывает нули.

Прецедент правила уже есть: закрывающий документ спрашивается функцией
`serviceRequestNeedsClosingDocument` ([service-requests.ts:2651](../packages/contracts/src/service-requests.ts#L2651))
по паре «вид заявки + назначенный контрагент» — ровно тот признак, который нужен и здесь.

Есть ещё два связанных места, которые нельзя оставить на старом признаке. Очередь «кого ждут»
считает любое непогашенное `estimate_pending_revision` ожиданием согласования, а переназначение
сбрасывает объём работ не при всяком появлении подрядчика. В частности, переход `NULL → service`
при сохранённых поимённых исполнителях не считается `handedOver` и может унаследовать старый
внутренний объём работ. Оба случая разобраны в Р7 и Р9.

## 3. Решения

### Р1. Сортировка «срочные первыми» снимается, остальное про срочность остаётся

Из `orderBy` уходит выражение `urgentFirst`, и список сортируется тем, что выбрал человек
(умолчание — `statusChangedAt`). Срочность остаётся **отбором и маркером**: пресет над таблицей,
галочка в шите, красный тег в строке, поле «Срочность» в карточке, приставка в теме письма.

Почему именно так, а не «убрать срочность из очередей вовсе»: подъём наверх — это решение за
человека, какую заявку брать следующей, и заказчик снимает именно его. Возможность **спросить**
«покажи срочные» решением за человека не является.

### Р2. Индекс срочности переопределяется под отбор

`service_requests_urgent_idx` теряет основного потребителя вместе с сортировкой (Н7), поэтому
миграция переписывает его условие на `is_urgent AND deleted_at IS NULL`. Отбор `urgent=true`
добавляет к нему остаточное условие `status <> 'on_hold'`; закрытые срочные по-прежнему входят в
результат. Колонка индекса остаётся `status_changed_at`: она совпадает с умолчательным порядком
списка, а выбранная пользователем другая сортировка всё равно главнее срочности.

Удалить индекс вовсе нельзя без измерения: отбор «только срочные» остаётся рабочим входом (Р1).
Перед миграцией фиксируются размер таблицы и `EXPLAIN` запроса `urgent=true` с умолчательной
сортировкой; после миграции план должен использовать новый индекс. Раннер миграций выполняет DDL в
транзакции, поэтому `DROP/CREATE INDEX` ставится в окно, достаточное для измеренного размера
`service_requests`.

### Р3. Слова про очередь уходят из окна снятия срочности

Заголовок «Заявка перестанет стоять первой в очередях и в письмах» после Р1 неправда наполовину
(Н2). Новый текст: «С заявки снимется отметка срочности»; описание перечисляет наблюдаемый эффект:
маркер исчезнет, заявка перестанет входить в отбор срочных, а **новые** письма уйдут без приставки
«СРОЧНО ·». Уже отправленные письма, разумеется, не меняются.

### Р4. «Нужен ли объём работ» — одна функция контрактов

Рядом с `serviceRequestNeedsClosingDocument` заводится

```ts
export function serviceRequestNeedsEstimate(request: {
  kind: ServiceRequestKind;
  serviceCounterpartyId: string | null;
}): boolean {
  return request.kind === 'repair' && request.serviceCounterpartyId !== null;
}

export function serviceRequestHasEffectivePendingEstimate(request: {
  kind: ServiceRequestKind;
  serviceCounterpartyId: string | null;
  estimatePendingRevision: number | null;
}): boolean {
  return serviceRequestNeedsEstimate(request) && serviceEstimatePending(request);
}
```

Вторая функция отделяет сохранённый сырой признак от действующего ожидания. Правило спрашивают три
предиката объёма работ, предикат назначения, четыре API-входа сметы, закрытие работ, вкладка и окно
закрытия, а также расчёт «кого ждут» для карточки и серверных очередей. Своей копии условия в
портале и обработчиках нет — иначе первым признаком расхождения станет карточка, где кнопка «Объём
работ» есть, а сервер на неё отвечает отказом, либо внутренняя заявка останется в очереди
согласования по историческому `estimate_pending_revision`.

SQL не может вызвать TypeScript-функцию на колонках, и **третьей оси перебора очередь не
получает** (Н16). Вместо этого меняется само понятие оси: поле `ServiceWaitingRequest`
`estimatePendingRevision: number | null` становится `estimatePending: boolean` — уже
**эффективным**, посчитанным вызывающим (`serviceRequestHasEffectivePendingEstimate` в карточке и
при сборке DTO, SQL-выражение в builder'е). Осей в `WAITING_AXES` остаётся две, маски по-прежнему
выводятся перебором через `serviceRequestWaitingOn`, а тест SQL-корреляции сторожит единственное
выражение. Это техническое представление того же правила, а не второй продуктовый ответ.

Тип строки для предикатов (`ServiceActionRequest`) уже наследует `ServiceExecutorsRow` с полем
`serviceCounterpartyId` ([service-requests.ts:702](../packages/contracts/src/service-requests.ts#L702)),
поэтому достаточно дополнить их `Pick`. В `ServiceRequestDto` отдельного
`serviceCounterpartyId` нет: портал передаёт `request.service?.id ?? null` через существующий
`serviceActionRow`, а не читает выдуманное поле DTO.

### Р5. Предикаты, четыре ручки объёма работ и вид документа спрашивают Р4

`canSubmitServiceEstimate`, `canApproveServiceEstimate`, `canReopenServiceEstimate` получают первым
условием `serviceRequestNeedsEstimate`; их `Pick` расширяется `kind` и
`serviceCounterpartyId`. Ручки `PATCH /:id/estimate/submit`, `PATCH
/:id/estimate/approval`, `PATCH /:id/estimate/reopen` и `PUT /:id/estimate` отказывают
`422` с текстом «Заявку ведёт свой сотрудник — объём работ по ней не составляют».

У `PUT /:id/estimate` отдельного контрактного предиката сейчас нет: портал открывает тот же
редактор через `canSubmitServiceEstimate`, а сервер проверяет замки вручную. Поэтому ручка
спрашивает Р4 явно до проверки ревизий; четвёртый почти одинаковый предикат ради одного серверного
вызова не заводится.

`canAssignServiceExecutors` и одноимённая серверная проверка заменяют сырой
`serviceEstimatePending` на `serviceRequestHasEffectivePendingEstimate`. Иначе историческое
предъявление внутренней заявки перестало бы требовать решения, но продолжило бы запрещать смену
исполнителя.

Вид документа `estimate` («Объём работ») в `SERVICE_FILE_KIND_POLICY` тоже следует за этапом (Н17):
его политика (`statuses: ['in_work']`, `attachedBySide: ['executor']`) не знает про подрядчика, и без
правки внутренний исполнитель подшивал бы к заявке документ с ценами, которых по ней не бывает.
Правило спрашивается в `canAttachServiceFile` ([:3721](../packages/contracts/src/service-requests.ts#L3721))
и в производном от него перечне формы `attachableServiceFileKinds` — то есть в единственной точке,
куда ходят и сервер, и портал; обеим функциям добавляется признак Р4 самой заявки (её `kind` уже
приезжает видом документа, нужен `serviceCounterpartyId`). **Видимость уже подшитого вида не отнимается**: у исторической
заявки документ остаётся читаемым — это тот же довод, что и у Р7.

Отказ, а не молчаливое игнорирование: заявка, у которой сняли подрядчика, могла остаться открытой в
чужом браузере, и «сохранилось, но не сохранилось» — худший из исходов.

### Р6. Закрытие внутренних работ: дата и комментарий

- После `lockRequest` и проверки стороны обработчик делится на три явные ветки: ремонт подрядчика,
  внутренний ремонт, расходники. Ветка подрядчика сохраняет сверку ревизий, строки факта, гарантии,
  скидку, итог и закрывающий документ; ветка расходников сохраняет списание склада.
- Внутренняя ветка **не вызывает** `estimateItems`, не меняет `service_request_items`, не считает
  `works/total`, не ставит гарантии и не вызывает `applyConsumableFacts`. Это важно для старых
  внутренних заявок, у которых строки уже есть: они остаются историей, а не превращаются в факт и
  стоимость внутреннего ремонта.
- `items` в `completeServiceRequestSchema` — обязательный массив, поэтому законное тело внутренней
  заявки содержит `items: []`. Сервер отвергает только **непустой** `items`, непустой
  `consumables`, непустую скидку или её причину: `422` «По этой заявке стоимость работ не
  фиксируется». Запрет самого поля `items` сделал бы внутреннее закрытие невозможным.
- В `applyTransition` пишутся дата выполнения (`completedAt` из `body.completedOn`, московские
  сутки) и необязательный `comment`; автора сохраняет аудит действия, как и сейчас. Поля
  `finalTotalAmount` и `finalAdjustmentAmount` остаются `NULL`, `finalAdjustmentReason` — пустым.
- Тем же патчем гасится **историческое** предъявление (`estimatePendingRevision → NULL`), если оно
  сохранилось у внутренней заявки (Н18). Иначе появится состояние, которого сегодня не бывает ни у
  одной заявки: закрытая с непогашенным предъявлением. Очереди его уже не увидят (Р7), но колонка
  остаётся сырым фактом, и первый же отчёт, прочитавший её напрямую, повторит ошибку Н11. Снимок
  согласования (`approved_estimate_revision`, автор, дата) при этом не трогается: он объясняет, на
  каком основании работали, и стирать его — значит терять прошлое. В metadata аудита внутреннего закрытия нет `revision`, `total`,
  `works`, `changes` и `grantedWarranties`: ноль тоже был бы зафиксированной суммой, а ревизия —
  следом упразднённого шага.
- Окно закрытия получает третий режим рядом с двумя имеющимися: дата выполнения + необязательное
  «Что сделали». Он отправляет `items: []`, не отправляет `consumables`, передаёт
  `adjustmentAmount: null` и пустую причину скидки.

### Р7. Вкладка «Объём работ» — только там, где он положен либо уже есть

Вкладка строится только для финансовой аудитории:

```ts
request.audience === 'finance' &&
  (serviceRequestNeedsEstimate(serviceActionRow(request)) || request.estimateRevision > 0);
```

Явная проверка `audience` обязательна: без неё заявителю вернулась бы скрытая ADR 0160 финансовая
вкладка у любой заявки подрядчика. Вторая половина выражения — про прошлое: до выпуска внутренние
заявки могли пройти согласование; спрятать их строки значило бы стереть основание уже принятого
решения. У свежей внутренней заявки ревизия нулевая, и вкладок в карточке остаётся три.

Исторический объём внутренней заявки только читается: кнопок решения и правки нет, а обычная
плашка состояния заменяется нейтральной строкой «Исторический объём работ; после перехода на
внутреннее исполнение решение по нему не требуется». Если старая ревизия была согласована, номер и
подпись остаются рядом; если в БД сохранился pending, он не подписывается «ждём решения». Это
отдельная ветка отображения, иначе пустая историческая ревизия соврала бы «объём собирает
исполнитель».

По той же причине ось предъявления становится эффективной (Р4): `serviceRequestWaitingOn` читает
готовое булево, а в builder'е переписываются **обе** половины оси —
`pendingHere` получает конъюнкцию с Р4, а `noPendingHere` становится её отрицанием, а не
`estimate_pending_revision IS NULL` (Н16). Половины оси обязаны покрывать все строки: оставь мы
`noPendingHere` прежним, внутренняя заявка с историческим предъявлением не подошла бы ни к одной из
них и выпала бы из очередей вовсе — в том числе из «ждёт исполнителя», куда её же отправляет
карточка.
Исторический признак остаётся в DTO и БД, но карточка, счётчик и фильтр `waitingOnMe` считают
внутреннюю заявку ожидающей исполнителя, а не согласующего; переназначение им тоже не блокируется.
Миграции данных и ручного возврата сметы в правку не требуется.

### Р8. Смешанный состав — объём работ нужен

Свой сисадмин плюс подрядчик — обычный случай (`AssignServiceModal`, Н5 набросков). Признак Р4
смотрит на контрагента, а не на «есть ли поимённые исполнители»: работа подрядчика оплачивается
независимо от того, помогал ли ему свой сотрудник.

### Р9. Появление подрядчика не наследует внутренний объём работ

Текущий `handedOver` сбрасывает объём работ при снятии поимённого исполнителя либо замене уже
назначенного подрядчика, но пропускает `NULL → service`, если свои исполнители остаются в составе.
Поэтому условие сброса расширяется до «снят хоть один поимённый исполнитель **или изменился
`serviceCounterpartyId`**». Первое назначение подрядчика также проходит это условие, но при нулевой
ревизии сбрасывать нечего.

Расширение вводит одну новую ветку отказа, и её надо назвать (Н19): сброс идёт через
`assertEstimateReplaceable`, а та запрещает менять состав объёма работ, по строкам которого уже
обратились по гарантии. Путь достижим — `accepted → done → in_work` административными откатами и
затем назначение подрядчика, — и такое назначение получит `409` с текстом про гарантийные
обращения. Это принятое поведение: строки, на которые ссылается гарантийная претензия, не стираются
ни при каких переназначениях, и сегодняшний `service → service` ведёт себя так же.

Так `свой → смешанный/подрядчик` начинает коммерческий этап с чистого объёма работ, а
`подрядчик → свой` по-прежнему обнуляет его. Добавление своего помощника при неизменном подрядчике
смету не трогает; остальные сегодняшние правила переназначения сохраняются. Переходы
`NULL → service`, `service → NULL`, `service A → service B` и неизменный подрядчик покрываются
отдельным db-тестом.

### Р10. «Рекомендована замена» получает второй вход — в окне отмены

Сегодня пометка `replacementRecommended` и поле `rejectionResolution` ставятся **только** отказом по
объёму работ ([EstimateApprovalModal.tsx:177](../apps/web/src/features/estimate-approval/ui/EstimateApprovalModal.tsx#L177)),
то есть у внутренней заявки после Р5 сказать «чинить нецелесообразно, аппарат под замену» станет
нечем (Н3). Поэтому одиночная отмена уходит из общего `ReasonModal` в отдельный
`ServiceCancelModal`: обязательная причина остаётся, а у ремонта рядом появляются необязательное
«Что делаем вместо ремонта» (`resolution`) и чекбокс `replacementRecommended`. При отмеченной
замене решение обязательно; у обычной отмены (дубль, ошибка, заявка потеряла смысл) оно не
требуется. У заявки на расходники эти поля не показываются.

`serviceStatusChangeSchema` расширяется этими двумя необязательными полями. `statusStep` принимает
их только при `status === 'cancelled'` **и `kind === 'repair'`**, записывает `resolution` в
`rejectionResolution` и добавляет оба значения/изменение решения в аудит тем же форматом, что отказ
по объёму работ. На
административном откате непустые значения дают `422`, а не молча игнорируются; возврат отменённой в
«Новую» по-прежнему чистит оба поля матрицей сброса.

Массовая отмена остаётся действием с одной общей причиной: её схема и окно не меняются вовсе, а
вызов `statusStep` новых полей не передаёт — отсутствие необязательного поля сервер трактует как
«замена не рекомендована» и пустое решение. Одна галочка на пачку не должна
помечать все аппараты как рекомендуемые к замене.

Без этого пункта волна закрыла бы этап вместе со списком «что пора менять», который по нему
собирают.

### Р11. Подсказки: одно правило, один компонент

- В контрактах — `canCoordinateServiceRequests(subject)` = `can(subject, 'serviceRequests.assign')`.
  Отдельной функцией, а не строкой `can(...)` в десяти компонентах: правило «кому положены пояснения»
  обязано меняться в одном месте.
- В портале — чистый компонент `ServiceHint` в `entities/service-request`, экспортированный
  публичным `index.ts`; его входы — `coordinator`, `level`, `title`, `description`. В `features` его
  класть нельзя: он нужен другим feature-слайсам, а границы проекта запрещают `feature → feature`.
  Компонент сам не импортирует `AuthContext`: вызывающий получает `user`, считает
  `canCoordinateServiceRequests(user)` и передаёт булево. Координатору компонент рисует нынешний
  `Alert` без изменения текста и уровня; всем остальным `info` и `success` не рисует вовсе, а
  `warning` отдаёт одной мелкой строкой `Typography.Text type="secondary"` с заголовком без
  описания.
- Причины блокировки («правка закрыта предъявлением», «нет закрывающего документа») тоже идут как
  `ServiceHint warning`: для некоординатора они компактны, но не исчезают. Только фактические ошибки
  сервера (`failure`, `error`) и ошибки валидации остаются полноценными и через `ServiceHint` не
  проходят.

Почему компонентом, а не правкой каждого места: правок по таблице §2.3 одиннадцать, и через полгода
двенадцатая плашка появится в новом окне мимо любого списка. Компонент делает решение видимым в
типах.

### Р12. Состав правок по плашкам

Ровно таблица §2.3, столбец «Решение»: в строках, переведённых на `ServiceHint`, держатель
`serviceRequests.assign` видит прежнюю плашку, а остальные получают поведение Р11. Отдельно серая
строка «Заявка объектная: отдел у неё не указан» убирается для всех — она объясняет пустоту,
которой в карточке не видно. Координаторские окна из предпоследней строки таблицы и все ошибки не
меняются.

### Р13. Вкладка «Номенклатура» становится «Расходниками»

Переименование в интерфейсных подписях: вкладка карточки, заголовок окна правки («Расходники заявки
СО-14»), уведомление «Состав расходников сохранён», подписи пункта действий («Заполнить расходники»
/ «Изменить расходники»), строка истории «Состав расходников» и соответствующие макеты/инструкции
в памятках.

Лексическая граница жёсткая: меняется название **состава одной заявки**, но не термин
«номенклатура» в предметном смысле. «Код номенклатуры», набор «Оргтехника: номенклатура», права
ведения справочника, комментарии модели и названия разделов справочника не переименовываются.
Глобальная замена слова по репозиторию была бы ошибкой.

Коллизия имён (Н6): вкладка **раздела** «Расходники»
([ServiceRequestsPage.tsx:62](../apps/web/src/pages/service/ServiceRequestsPage.tsx#L62)) ведёт
справочник позиций и остаток, вкладка **карточки** — состав одной заявки. Разводить их прилагательными
(«Расходники заявки») план не станет: контекст разный — раздел и карточка, — а в карточке рядом стоит
вкладка «Объём работ», и пара «Объём работ / Расходники» читается как ответ на один и тот же вопрос
«что по заявке пойдёт».

### Р14. Таблица расходников читается без объяснений

- Колонки «Выдано» и «Причина расхождения» появляются, только когда есть хоть одна отметка о выдаче.
  До выезда исполнителя они показывают «не отмечено» и «—» во всех строках — то есть занимают
  половину ширины, ничего не сообщая.
- Заголовки становятся вопросами: «Сколько просили» и «Сколько выдали» вместо «Просили»/«Выдано».
- Пустой состав — строка словами: «Состав ещё не собран: позиции заполнит исполнитель, которому
  везти» вместо пустой таблицы antd.
- Код позиции остаётся второй строкой мелким — по нему сверяют со складом.

### Р15. Памятки и руководства правятся вместе с кодом

`generate-office-equipment-guides.mjs` (перечни вкладок и действия заявки),
`generate-office-equipment-it-guide.mjs` (макет окна), `generate-office-equipment-manual.mjs`
(перечень вкладок карточки) и `generate-office-equipment-requester-guide.mjs` (обещание «срочные
разбирают вне очереди», строки 533 и 1013 — найдено при реализации Э0) — только интерфейсные подписи из Р13; там же снимается обещание
«срочные показываются первыми» и добавляется внутреннее закрытие без объёма работ там, где описан
цикл. Все артефакты, которые производят изменённые генераторы, пересобираются и проверяются, а не
перечисляются заранее неточным числом PDF/PPTX.

## 5. Этапы

Ниже — порядок реализации и проверки. Граница деплоя намеренно проходит внутри Э1–Э3 ради
совместимости старого и нового web; точная нарезка описана в §8.

### Э0. Срочность в общем порядке (п. 1)

1. `urgentFirst` уходит из `orderBy` вместе с комментарием, объясняющим подъём.
2. Комментарий индекса в `schema.ts` и сам индекс переписываются (Р2); миграция

## 7. Границы

- **Гарантии внутреннего ремонта** (Н4) в этой волне не заводятся: новые внутренние работы не
  создают строк факта, а старые строки внутренняя ветка не закрывает. Файл гарантийного талона можно
  хранить в документах, но сам по себе он не создаёт запись реестра «Гарантии»; для такого учёта
  нужна отдельная модель, смыкающаяся с п. 14 backlog'а.
- **Суммы новых внутренних заявок** не переносятся никуда: заказчик просил их не фиксировать, а не
  «фиксировать в другом месте». Уже записанная историческая оценка остаётся читаемой по Р7, но
  итогом выполнения не становится.
- **Аудитории DTO** (`finance`/`requester`) не трогаются: п. 3 меняет форму подачи текста, а не
  состав данных, который сервер отдаёт читателю.
- **Пресет «Срочные» и письма** остаются (Р1) — просьба про порядок списка, а не про срочность как
  таковую.
- **Исторические заявки** с объёмом работ при внутреннем исполнителе остаются читаемыми (Р7); ни
  чистки данных, ни миграции содержимого волна не делает. Их pending перестаёт быть рабочим
  ожиданием, но само сохранённое значение не переписывается.
- **Массовая отмена** не получает общей галочки «Рекомендована замена»: решение относится к одному
  аппарату и вводится только в его карточке (Р10).

## 8. Порядок выката

Выкат делится на два объявляемых выпуска по границе «меняется ли цикл»:

1. **Первый выпуск — Э0, Э4, Э5, Э6** (порядок списка, тише подсказки, «Расходники», памятки).
   Цикл заявки не меняется. Вместе с кодом уезжают новый индекс Р2 и своя запись выпуска, поэтому
   это не «откат только кодом»: при откате кода более широкий индекс можно безопасно оставить —
   старый запрос им не пользуется хуже, чем прежде, — а обратный DDL ради отката не нужен.
2. **Второй выпуск — Э1–Э3, Э7** (внутренний ремонт без объёма работ). Одновременный выкат сервера
   и портала не считается механизмом совместимости: ни один порядок двух несовместимых версий не
   безопасен. Выпуск проходит тремя фазами:

   1. **A — расширяющий API.** Сервер уже принимает новое простое закрытие внутреннего ремонта
      (`items: []`, без денег) и сохраняет старый путь для тела старого портала с заполненными
      строками. В эту же фазу входят новые необязательные поля одиночной отмены, эффективное
      ожидание Р4/Р7 и безопасный сброс при переназначении Р9. Четыре ручки объёма работ пока не
      запрещаются. Это временная ветка совместимости: действия старого портала ещё не получают
      транспортных отказов, новый портал уже может работать.
   2. **B — портал.** Уезжают Р7, простой режим закрытия и отдельное окно отмены. Он работает с API
      фазы A; свежие внутренние заявки больше не предлагают объём работ.
   3. **C — ужесточение API.** После того как старая web-сборка перестала раздаваться и истёк
      принятый для открытых вкладок период совместимости, включаются отказы Р5 и строгий запрет
      непустых строк/денег Р6, а временная старая ветка удаляется. Залежавшаяся старая вкладка
      получает объяснимый `422` и после обновления страницы переходит на новый сценарий.

Фазы A и C должны быть отдельными коммитами/деплоями: временная совместимость не остаётся
бессрочной. Проверяются четыре пары версий: старый web → A, новый web → A, новый web → C и старая
открытая вкладка → C с ожидаемым `422`.

Незакрытые заявки данными волна не переписывает. Исторический объём остаётся видимым только на
чтение, а Р7 исключает его pending из рабочих очередей; согласовывать или возвращать его вручную не
нужно. Перед вторым выпуском количество таких строк фиксируется как контрольная величина для
проверки после выката:

```sql
SELECT
  count(*) AS with_estimate,
  count(*) FILTER (WHERE estimate_pending_revision IS NOT NULL) AS with_pending
FROM service_requests
WHERE kind = 'repair' AND service_counterparty_id IS NULL
  AND deleted_at IS NULL AND status NOT IN ('accepted', 'cancelled')
  AND (estimate_pending_revision IS NOT NULL OR estimate_revision > 0);
```

После фазы C эти строки остаются на месте, но не входят в «Ждёт согласования»/`waitingOnMe`,
закрываются простым сценарием и не получают `final_total_amount` либо гарантий по старым строкам.
