# Этап 3 — page/widget-слайсы, разрез монолитов и загрузка по требованию

План продолжает [этап 2](frontend-fsd-stage-2.md) и заменяет для этой работы разделы Р5 и Р7
[плана доработок фронтенда](frontend-followup-plan.md). Общие решения о направлении слоёв,
публичных входах и владельцах сценариев остаются из
[исходного FSD-плана](frontend-fsd-plan.md); состояние системы определяет код, а этот документ —
только порядок будущей работы.

**Baseline:** `origin/main` на 30.09.2026, коммит `8527e63d`. Этап объединяет две связанные
программы: сначала страницы получают устойчивые `page`/`widget`-границы и перестают быть
монолитами, затем эти же публичные входы становятся точками ленивой загрузки. Делать наоборот
нельзя: динамический импорт внутреннего файла узаконит временный путь и привяжет маршрутизацию к
деталям монолита.

Каждая волна рассчитана на **1,5–4 часа вместе с тестами, интеграцией и фиксацией бюджета**. Если
проверки не помещаются в окно, волна не считается завершённой и следующая не начинается.

## 2. Архитектурный контракт этапа

### 2.1 Что считается слайсом

- `pages/<route>/index.ts` — публичный вход маршрута. Слайс страницы знает адрес, права, вкладки и
  композицию, но не содержит форму, таблицу на сотни строк или мутацию сценария.
- `widgets/<block>/index.ts` — публичный вход самостоятельного блока экрана: списка с фильтрами,
  карточками и колонками либо хоста связанных окон. Виджет может собирать `features` и `entities`,
  но не импортирует соседний виджет.
- `features/<action>/index.ts` — пользовательское действие: создать, назначить, сменить статус,
  исправить маршрут. Здесь живут форма, команда, мутация и её эффект на кэш.
- `entities/<entity>` остаётся владельцем API, ключей запросов, подписей полей и чистых доменных
  представлений. Перенос из страницы не даёт права скопировать доменное правило наверх.

Каталог ради каталога слайсом не считается. У каждого нового слайса должен быть публичный вход,
хотя бы один внешний потребитель и boundary-фикстура, доказывающая запрет обходного импорта.

### 2.2 Инварианты разреза

1. Поведение, HTTP-контракты, права, query keys и форма URL не меняются. Поведенческая правка идёт
   отдельной задачей и отдельным коммитом.
2. Комментарий-инвариант переносится вместе с кодом. Комментарии не удаляются ради прохождения
   лимита и остаются на английском.
3. Новый файл — не длиннее 400 сырых строк. Цель — пустой `quality-budget.maxLines`, без новых
   исключений.
4. Страница импортирует виджет или feature только через `index.ts`; `app` импортирует только
   публичный вход page-слайса. Тесты переходят на те же входы, если проверяют публичное поведение.
5. Форма ключа TanStack Query сравнивается до и после. Каждая перенесённая мутация проходит
   `check:cache-invalidation` и сценарий «изменить → вернуться на ранее открытую вкладку».
6. Перемещение и изменение логики не смешиваются. Внутри волны допустимы два коммита: механический
   разрез, затем подключение/ратчет.

### 2.3 Инварианты загрузки

1. Новая точка `lazy()` ссылается только на публичный `index.ts` готового page/widget/feature-слайса.
2. Реестр `SHELL_SECTIONS` остаётся единственным перечнем разделов. Code splitting не создаёт
   второй список адресов, прав или страниц.
3. `Suspense` не снимает уже показанный каркас. Route fallback живёт внутри `AppLayout`, а fallback
   вкладки или окна занимает только её область.
4. Недоступный роли раздел не скачивается до перехода. Скрытая правами вкладка не импортируется
   «для удобства» статически.
5. `manualChunks` не вводится до route splitting и измерения manifest: ручная группировка легко
   уменьшает имя entry-файла, не уменьшая фактическое синхронное замыкание.
6. Ошибка загрузки чанка после выката имеет понятный экран и повтор через обновление версии, а не
   бесконечный `Spin`.

Корректировка после волны 2: `VehicleRequestsTab` сократился с 2 805 до 1 941 строки, но явный

Уточнение по реализации волны 3а: хост редактора стал widget, а не feature, поскольку он собирает

Уточнение по реализации волны 3б: lifecycle-хост стал widget по той же причине, что и редактор —

## 4. Бюджет загрузки

Носитель расчёта — `scripts/bundle-size.mjs`: только он обходит manifest и считает gzip
синхронного замыкания. Новый budget-файл хранит результаты этого расчёта, но не реализует второй
алгоритм. `quality-budget.json` продолжает отвечать только за исходники и не требует production
build в быстром `pretest`.

Минимальные критерии этапа:

- начальное синхронное замыкание — не более **60 %** baseline, то есть **555,7 КБ gzip**;
- цель 50 % (**463,1 КБ**) остаётся stretch: её нельзя достигать переносом общего кода в
  предзагружаемый vendor chunk;
- каждый раздел и тяжёлая вкладка имеют отдельный динамический корень в manifest;
- переход в один раздел не загружает код другого раздела;
- сумма entry + выбранный маршрут измеряется отдельно, записывается после волны 16 и дальше может
  только уменьшаться;
- бюджет проверяется свежей сборкой с постоянным `BUILD_ID`, а не содержимым старого `dist`.

Если после волны 16 entry не достигает 555,7 КБ, сначала строится отчёт «какой статический импорт
удерживает модуль». `manualChunks`, замена библиотеки и переписывание UI не считаются допустимым
ответом без этого отчёта.

## 5. Проверки внутри каждой волны

Минимальный набор до коммита:

1. `git status --porcelain -- <пути волны>` до правки: чужой dirty-файл исключается либо работа
   переносится.
2. Typecheck web-пакета, ESLint и Prettier по своим файлам.
3. Целевые тесты сценария, чьи границы менялись.
4. `pnpm --filter @technic/web check:cache-invalidation` для волны с мутациями.
5. `pnpm --filter @technic/web quality:check`; после честного сокращения владелец запускает
   `quality:update` в том же коммите.
6. Boundary и layout-тесты при появлении/перемещении слайса.
7. Полный web-набор в конце каждой волны; root `pnpm check` — в волнах 0, 6, 10, 14 и 19.
8. Начиная с волны 15 — свежая production build и bundle-budget.

Три полных web-прогона подряд нужны в конце контуров M и L, а не после каждого механического
переезда. Плавающий тест перепроверяется отдельно, но красный результат не объявляется флаком без
повторяемого доказательства.

## 6. Точки пересмотра

- **После волны 0:** уточнить baseline после интеграции ожидающей ветки и проверить, не появились
  новые файлы в `maxLines`.
- **После волны 6:** проверить, действительно ли выбранные interfaces widgets сократили связанность,
  а не превратили props в копию всего page-state. При необходимости порядок волн 7–13 меняется.
- **После волны 14:** утвердить фактическую карту динамических корней и численные бюджеты маршрутов;
  до этого глубина code splitting не считается решённой.
- **После волны 17:** по manifest решить, нужны ли ленивые окна волны 18 все сразу; уже отдельный и
  маленький чанк не дробится ради количества чанков.

## 7. Критерий готовности этапа

1. В `apps/web/src` нет файла длиннее 400 сырых строк; `quality-budget.maxLines` пуст.
2. Page-слайсы содержат маршрутизацию и композицию, widgets — самостоятельные блоки, features —
   действия; внешние импорты идут только через публичные `index.ts`.
3. Все boundary-правила работают как `error`, включая page/widget fixtures.
4. Query keys, права, URL, кэш-эффекты и пользовательское поведение совпадают с baseline.
5. Анализатор не пропускает неизвестную пишущую мутацию; его остаток либо ноль, либо состоит
   только из поимённо доказанных read/control-вызовов.
6. Начальный JS не превышает 555,7 КБ gzip; чужие разделы отсутствуют в его синхронном замыкании.
7. Прямые ссылки, back/forward, скрытые правами вкладки, route modal и обновление после релиза
   работают при холодном и тёплом кэше чанков.
8. `pnpm check`, `pnpm check:docs`, production build и три последовательных полных web-прогона
   зелёные на финальном коммите.

## 8. Вне этапа

- изменение бизнес-поведения, API, контрактов и модели доступа;
- профили `staleTime`, дебаунс запросов и ленивая загрузка данных справочников — это отдельная
  оптимизация запросов, а не code splitting;
- погашение 17 употреблений устаревшего API antd, если конкретный компонент не затронут волной;
- перенос модулей ради красивого дерева без уменьшения связанности или появления публичного
  контракта;
- ручное дробление vendor-чанков без доказанного статического импортера.

Работа ведётся короткими ветками по одной волне. Горячие файлы не живут в долгой ветке: перед
каждой волной она обновляется от `origin/main`, а завершённая волна сразу интегрируется и затягивает
бюджет. Так следующий исполнитель начинает с нового факта, а не с обещания большого финального
слияния.
