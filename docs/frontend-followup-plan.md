**CI в репозитории нет вообще** — ни `.github/workflows`, ни git-хуков.

Отсюда порядок: барьеры **первыми**, до любой миграции. Иначе повторится история недельных заявок —
~100 строк нового API дописаны прямо в `resources.ts`

## 4. Барьеры (Р1) — до всего остального

Пять барьеров. Каждый обязан **падать**, а не сообщать.

### Б1. Проверки запускаются — и не пишут в дерево молча (1 ч)

CI нет; заводить его этой работой — не задача плана. Проверки вешаются на то, что и так зовут.

Две раздельные цели, чтобы обычный `pnpm test` не менял рабочее дерево:

| Цель             | Что делает                                                      |
| ---------------- | --------------------------------------------------------------- |
| `quality:check`  | только читает; падает при росте **и при незаписанном снижении** |
| `quality:update` | явно переписывает бюджеты и инвентари                           |

`pretest` пакета `@technic/web` зовёт **только** `quality:check` (корневой `pnpm test` →
`pnpm -r test`). Улучшил код — запусти `quality:update`, и правка бюджета попадёт в тот же коммит.
Молчаливая запись при зелёном прогоне отпадает: её слишком легко не закоммитить.

Появится CI — менять нечего, он зовёт те же цели.

### Б2. Бюджеты **и** инвентари (2 ч)

Числа контролируют общий долг, но **не запрещают новые исключения**: ключ в уже «грязном» файле не
поднимет `rawKeyFiles`, метод внутри существующего объекта не поднимет `resourcesApiObjects`, а
добавление может компенсироваться чужим удалением. Поэтому механизма два.

**Бюджеты** — `apps/web/quality-budget.json`, числа только вниз:

```json
{
  "legacyFiles": { "hooks": 6, "utils": 4, "components": 23 },
  "rawKeyFiles": 40,
  "bundleGzipKb": 604,
  "maxLines": { "src/pages/WasteRequestsPage.tsx": 2003, "…": 0 }
}
```

**Инвентари** — `apps/web/quality-inventory.json`, нормализованные сигнатуры того, что разрешено
существовать в legacy (собираются AST-обходом, см. Б3, Б4):

- методы legacy-API: `resources.filesApi.upload`, `auth.login`, …;
- сырые ключи: `src/pages/admin/MailingSchedulesBlock.tsx → ['mailing-schedules']`.

Правило: **новая сигнатура — ошибка**; исчезнувшая пропадает из инвентаря при `quality:update`.
Компенсация удалением здесь не работает: сравниваются имена, а не количества.

`maxLines` дополнительно: **любой новый файл длиннее 400 строк, которого нет в карте, — ошибка.**
`max-lines` в ESLint остаётся предупреждением: он про порог, бюджет — про рост.

Это же закрывает лазейку с allowlist: дописать файл в список можно, но `legacyFiles` не даст числу
вырасти — придётся либо разложить файл, либо поднять бюджет отдельной строкой в диффе.

### Б3. Новое API — только в `entities` (1,5 ч)

`resources.ts` и `auth.ts` заморожены на уровне **сигнатур методов** (инвентарь Б2), а не только
длины. Новая ручка — в слайс. Это прямой ответ на историю недельных заявок: там добавляли методы в
существующий объект, и счётчик объектов бы промолчал.

### Б4. Ключи — AST, а не регулярка (3 ч)

`typescript` уже в зависимостях. `check:query-keys` обходит AST и собирает:

- свойства `queryKey` в объектных литералах;
- первые аргументы `invalidateQueries`, `setQueryData`, `getQueryData`, `removeQueries`,
  `cancelQueries`, `prefetchQuery`, `fetchQuery`, `ensureQueryData`;
- объявления переменных, чьё значение — массив со строковым первым элементом (ловит `SCHEDULES_KEY`
  и родню).

Файл владеет сырым ключом, если значение — литеральный массив, а не выражение из `@entities/*`.
Результат идёт и в бюджет (число файлов), и в инвентарь (файл + сам ключ).

**Скрипт падает, если не смог разобрать конструкцию.** Молчаливый пропуск непонятного — ровно тот
дефект, из-за которого нынешняя проверка даёт ложное спокойствие.

Точное число замеряется при внедрении: регулярка видела 40, реальных больше минимум на четыре.

### Б5. Границы для `features` — с переносом, а не «бесплатно» (2,5 ч)

**Поправка редакции 2.** Я написал, что стоимость нулевая, «пока каталогов нет». Каталог `features`
уже есть — 19 файлов, шесть слайсов. И одно нарушение в нём уже живёт:
[EstimateApprovalModal.tsx:12](../apps/web/src/features/estimate-approval/ui/EstimateApprovalModal.tsx#L12)
тянет `components/FileLinks`. Включение `no-unknown-dependencies` даст красный сразу.

Порядок работы:

1. **Слайс `file`** — `filesApi` из `resources.ts` (около 30 строк, самодостаточен) и `FileLinkList`
   из `components/FileLinks.tsx` (342 строки, 10 потребителей). Слайс и так стоял в очереди Р6, а
   здесь он снимает единственное препятствие.
2. **Включить** `no-unknown-dependencies` для `src/features/**`, `src/widgets/**`, `src/app/**`.

Запасной вариант, если `filesApi` окажется связаннее, чем выглядит: включить правило с одним
поимённым исключением на `estimate-approval` и датой снятия — но переезд предпочтительнее, он
закрывает долг, а не переносит его.

**Оценка Р1: 10 часов (≈1,5 дня).** Пять независимых коммитов.

## 5. Работы

### Р2. Инвалидация журнала путевых листов — 2 ч

`waybills` пишется сервисом ЭСМ-2
([waybill-esm2.ts:364,481](../apps/api/src/services/waybill-esm2.ts#L364)) из четырёх ручек
([vehicle-requests.ts:2816,3162,3268,3379](../apps/api/src/routes/vehicle-requests.ts#L2816)).
На фронте `waybills` не гасит ни одна:

| Ручка                   | Где на фронте                                                                           | Что гасит                            |
| ----------------------- | --------------------------------------------------------------------------------------- | ------------------------------------ |
| `PATCH /:id/status`     | [VehicleRequestsTab.tsx:758](../apps/web/src/pages/vehicle/VehicleRequestsTab.tsx#L758) | `vehicle-requests`, `vehicle-routes` |
| `PATCH /:id/assignment` | [VehicleRequestsTab.tsx:663](../apps/web/src/pages/vehicle/VehicleRequestsTab.tsx#L663) | `vehicle-requests`, `vehicle-routes` |
| `POST /:id/early-end`   | [shared.tsx:544](../apps/web/src/pages/vehicle/shared.tsx#L544)                         | **только `vehicle-requests`**        |
| `PATCH /:id/early-end`  | [shared.tsx:544](../apps/web/src/pages/vehicle/shared.tsx#L544)                         | **только `vehicle-requests`**        |

Обе ручки досрочного завершения ходят через общий локальный `invalidate()` в `useEarlyEnd` — в
редакции 2 я приписал им и `vehicle-routes`, чего там нет. Реестр Р3 должен стартовать с точных
фактов, поэтому таблица выше — часть его исходных данных.

Окно неконсистентности ≤10 с: `staleTime` в проде — 10 секунд
([main.tsx:19](../apps/web/src/main.tsx#L19)). Дефект настоящий, но уже, чем сказано в редакции 1;
значение вырастет вместе с профилями актуальности.

**Методика теста.** Тестовый `QueryClient` живёт с `staleTime: 0`
([render.tsx:40](../apps/web/test/render.tsx#L40)), поэтому наивный тест «перешли в журнал после
мутации» перезапросит данные сам и **пройдёт без исправления**. Правильно: один `QueryClient` на
сценарий; журнал заранее в кэше с большим `staleTime`; выполняется переход; проверяется
`isInvalidated` либо новый HTTP-запрос счётчиком `mockHttp`. Тест обязан быть проверен на падение
без исправления.

### Р3. Реестр эффектов — прототип, потом решение (2 дня)

Точечный тест закрывает известную связь, а дефект журнала родился из **неизвестной**. Нужен реестр
в коде — но оценка редакции 2 в четыре часа была занижена.

**Непрямые формы мутаций уже есть**, вопреки моей фразе «вынесенных в хелперы нет»:

| Форма                                      | Пример                                                                                |
| ------------------------------------------ | ------------------------------------------------------------------------------------- |
| ручка приходит параметром хука             | [usePurgeAction.ts:51](../apps/web/src/hooks/usePurgeAction.ts#L51)                   |
| `mutationFn` — локальная функция           | [WeeklyRequestPage.tsx:159](../apps/web/src/pages/vehicle/WeeklyRequestPage.tsx#L159) |
| два вызова API в одной мутации             | [WasteRequestsPage.tsx:956](../apps/web/src/pages/WasteRequestsPage.tsx#L956)         |
| инвалидация через локальный `invalidate()` | [shared.tsx:544](../apps/web/src/pages/vehicle/shared.tsx#L544)                       |

Плюс `setQueryData` и `onSettled`. Межфайловый анализ всего этого хрупок, поэтому порядок такой:

1. **Аудит бэка (3 ч)** — для каждой мутирующей ручки, в какие сущности она пишет. Чтением фронта
   это не выводится в принципе.
2. **Прототип проверки (3 ч)** на всех 100 текущих мутациях: сколько разбирается автоматически,
   сколько попадает в «не понял». **Развилка:** если непонятых больше четверти — проверка
   переводится на явную метадату, а не на углубление анализа.
3. **Явная метадата для сложных случаев** — аннотация над мутацией (`@affects waybill,
vehicle-route`), которую скрипт читает как истину. Дешевле и честнее хрупкого вывода.
4. **Таблица «ручка → сущности»** в `apps/web/test/invalidation-map.ts` и падающая проверка.

Проверка падает на неразобранной мутации без метадаты — иначе она снова даст ложное спокойствие.

### Р4. Расщепление `format`/`date` — 3 ч

Домен распределяется по владельцам (`user`, `session`, `counterparty`, `request`), как решал
[этап 2, §2.4](frontend-fsd-stage-2.md), — не сваливается в `request`.

Слайс `request` **API не имеет** (`RequestHistory`, `ResponsibleFields`, `TimeInput`, правила дат,
подписи общих полей), разрезания страниц не требует и делается сразу. Не делаем `waste-request` и
`vehicle-request` — те, что с API.

Объём ограничен честно: переезжает общее ядро (`shared/lib`) и то доменное, чей владелец уже есть.
Подписи `user`/`session`/`counterparty` ждут своих слайсов. Критерий «`utils` исчез» снят как
недостижимый (`formErrors.ts`, `links.ts` остаются) — взамен `legacyFiles.utils` с 4 до 2.

### Р5. Производительность — отдельный трек (1,5 дня)

Бандл вырос с 526,2 до **603,5 КБ** gzip (+15 %).

| Работа                               | Зависит от разрезания страниц? | Оценка |
| ------------------------------------ | ------------------------------ | ------ |
| Детерминированный замер (см. ниже)   | нет                            | 1 ч    |
| `React.lazy` по маршрутам            | **нет**                        | 4–6 ч  |
| Ленивые справочники фильтров и формы | частично                       | 4 ч    |

**Замер должен быть детерминированным до того, как попадёт в бюджет.** Сейчас `bundle-size.mjs`
читает существующий `dist` ([стр. 22](../apps/web/scripts/bundle-size.mjs#L22)), а локальная сборка
вшивает таймстамп ([vite.config.ts:6](../apps/web/vite.config.ts#L6)) — замер будет то устаревшим,
то плавающим, и авторатчет начнёт дрожать. Нужно: обязательная сборка перед измерением и
фиксированный `BUILD_ID=quality-check`.

**После `lazy` — проверить поиск чанка маршрута:** `includes(routeHint)` регистрозависим
([стр. 74](../apps/web/scripts/bundle-size.mjs#L74)), и аргумент `waste` не найдёт
`WasteRequestsPage.tsx` — замер молча покажет один entry-чанк. Ловушка ровно того же рода, что и
зелёная проверка раскладки.

**Цель ≤3 запросов требует ленивых фильтров, а не только формы.** На первом экране шесть запросов, и
типы контейнеров с операторами нужны **фильтрам**
([WasteRequestsPage.tsx:1372,1379](../apps/web/src/pages/WasteRequestsPage.tsx#L1372)), а не только
форме. Поэтому справочники грузятся при первом раскрытии `Select` — и фильтра, и формы. Иначе
заявленный результат из работ не следует.

Цели baseline: gzip первого экрана **≤300 КБ**, запросов до первого взаимодействия **≤3**.

### Р6. Попутная миграция — правило, а не бесплатность

1. **Жёсткое, обеспеченное проверками:** новое API и новые ключи в legacy не добавляются — никогда,
   даже если старое пока остаётся (Б3, Б4 — на уровне сигнатур).
2. **Мягкое, с лимитом:** миграция существующего слайса — отдельная подзадача с оценкой. Больше
   часа сверх продуктовой задачи — выносится отдельным заданием.

Очередь: `driver`, `waybill`, `vehicle-route`, `user`, `session`, `vehicle`, `vehicle-type`,
`counterparty`. Слайс `file` уходит в Р1 (Б5).

### Р7. Монолиты — под бюджетом, разрезание по мере задач

27 файлов длиннее 400 строк; топ-3 — 5414 строк. Бюджет `maxLines` (Б2) останавливает рост в день
внедрения: `max-lines` предупреждением не блокирует ничего
([eslint.config.mjs:148](../eslint.config.mjs#L148)), и после редакции 1 два файла из трёх выросли
снова.

Разрезание — 3–4 дня, отдельным решением. Рекомендация: браться за `WasteRequestsPage`, когда
очередная задача по вывозу мусора и так потребует в неё лезть.

## 6. Порядок

```text
Р1 барьеры (1,5 д)  →  Р2 дефект (2 ч)  →  Р3 реестр (2 д)  →  Р4 utils (3 ч)
                    ↘  Р5 производительность (1,5 д) — независимая, можно параллельно
Р6 попутно, Р7 отдельным решением
```

Р1 первым не из аккуратности: без барьеров любая следующая работа снова растворится в росте.
Внутри Р1 первым идёт Б5 — он тянет за собой слайс `file`, и делать его после остальных барьеров
значит чинить красный лес.

## 7. Критерии

| Признак                                | Как меряем                                                     |
| -------------------------------------- | -------------------------------------------------------------- |
| Проверки реально запускаются           | `pnpm test` падает при искусственном нарушении каждого барьера |
| Обычный прогон не трогает дерево       | после `pnpm test` рабочее дерево чистое                        |
| Новых исключений не появляется         | инвентарь: новая сигнатура API или ключа — красный             |
| Legacy не растёт                       | `quality-budget.json` — все числа только вниз                  |
| Дефект журнала закрыт                  | тест проверен на падение без исправления                       |

## 9. Журнал правок

**Редакция 3 (10.08.2026)** — по второму ревью. Приняты все шесть уточнений:

1. **Б5 не бесплатен** — `features` уже 19 файлов, и `estimate-approval` тянет `components/FileLinks`.
   Б5 переписан: сначала слайс `file`, потом включение правила; +2,5 ч.
2. **Числа не запрещают новые исключения** — добавлены инвентари сигнатур (Б2, Б3, Б4). Метод внутри
   существующего объекта и ключ в «грязном» файле теперь ловятся. Для `maxLines` — новый файл >400
   строк вне карты тоже ошибка.
3. **`pretest` не должен писать в дерево** — цели разделены на `quality:check` и `quality:update`;
   авторатчет из прогона тестов убран.
4. **Р3 недооценён** — непрямые формы мутаций перечислены поимённо; порядок теперь «аудит →
   прототип на 100 мутациях → развилка → метадата для сложного»; 4 ч → 2 дня.
5. **Неточность в Р2** — обе ручки досрочного завершения гасят только `vehicle-requests` (общий
   `invalidate()` в `useEarlyEnd`), а не `vehicle-requests` + `vehicle-routes`. Таблица исправлена и
   становится исходными данными реестра.
6. **Замер бандла недетерминирован** — обязательная сборка и `BUILD_ID=quality-check` до внесения в
   бюджет; отмечена регистрозависимость поиска чанка маршрута.
7. **Цель ≤3 запросов** — добавлена ленивая загрузка справочников фильтров (контейнеры и операторы
   нужны именно им), иначе результат из работ не следовал.
