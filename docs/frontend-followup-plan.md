# План доработок фронтенда после остановки FSD-рефакторинга

Заменяет незавершённые части [этапа 2](frontend-fsd-stage-2.md) и пересматривает
[общий план](frontend-fsd-plan.md) под новую обстановку. Составлен 06.08.2026, после того как
рефакторинг был остановлен 05.08.2026 на безопасной границе.

## 1. Что изменилось с 31.07

| Обстоятельство            | Тогда                                  | Сейчас                                              |
| ------------------------- | -------------------------------------- | --------------------------------------------------- |
| Окна сверки               | по 20–30 минут на каждую группу        | **не нужны**: параллельной правки тех же файлов нет |
| Схема работы              | короткие ветки, порядок «от холодного» | правки идут сразу, в общий поток                    |
| Тестов                    | 45 файлов / 327                        | **58 файлов / 414**                                 |
| Потребителей `resources`  | 39                                     | **45**                                              |
| Строковых ключей запросов | 137                                    | **122**                                             |
| Слайсов `entities`        | 0                                      | **7**                                               |

Отмена окон — главное изменение: именно они делали переезд дорогим. Из этого следует, что и план
должен быть другим, а не «продолжением с того же места».

## 2. Что уже получено и работает

Это не задел «на будущее», а действующие правила, которые за 16 последующих коммитов не дали ни
одного нарушения:

- **границы слоёв** — `shared` не знает правил портала, `entities` не видит соседей и legacy, вход
  только через `index.ts`; проверено четырнадцатью фикстурами;
- **сеть безопасности** — 414 тестов, включая сценарные потоки заявок; моков модулей приложения не
  осталось, новые тесты пишутся на HTTP-моках;
- **`shared`** — ui-kit, хуки, транспорт, сессия с проверкой поколения, фабрики ресурсов, реестр
  ключей, контракт ошибок;
- **7 слайсов** — объекты, отделы, склады, типы контейнеров, типы мусора, тарифы, адрес;
- **измеримость** — `check:stage1-layout`, `check:stage2-layout`, `bundle:size`, счётчик запросов
  первого экрана.

Продолжать ради этого нечего: оно уже приносит пользу на новом коде.

## 3. Что осталось незакрытым — и чем это грозит

### 3.1 Долг раскладки: проверка стала красной

За сутки в старых каталогах появилось шесть файлов, которых нет ни в одном списке:
`usePurgeAction`, `useWasteObjectScope`, `useVehicleClassificationFilter`, `PhoneInput`,
`SupportContactsModal`, `utils/links`.

Красная проверка, которую все привыкли видеть красной, перестаёт быть сигналом — это худший исход
для инструмента, заведённого ради сигнала.

### 3.2 Настоящий дефект: журнал путевых листов не обновляется

Перевод заказа техники в работу выписывает путевой лист (ADR 0037), но `waybills` при этом никто не
инвалидирует: проверено — ключ трогают только сама страница листов и окно вложений. Диспетчер,
открывший журнал после перевода, видит его без нового листа, пока не обновит страницу вручную.

Это единственная поведенческая поломка, найденная разбором, и она не зависит от того, продолжается
рефакторинг или нет.

### 3.3 Монолиты растут быстрее, чем разбирались

| Файл                     | 31.07 | 06.08 | Прирост |
| ------------------------ | ----- | ----- | ------- |
| `WasteRequestsPage.tsx`  | 1588  | 2003  | +415    |
| `VehicleRequestsTab.tsx` | 1364  | 1919  | +555    |
| `VehicleAssignModal.tsx` | 952   | 1351  | +399    |

Три файла набрали 1369 строк за неделю. Это и есть исходная боль, ради которой затевался
рефакторинг, — и она усилилась, а не ослабла.

### 3.4 Мелкий долг

- `api/resources.ts` — 657 строк и самый правимый файл фронта (6 правок за два дня);
- расщепление `format`/`date` не сделано: доменные словари и правило «заявку не раньше сегодня»
  по-прежнему в `utils`;
- `usePurgeAction` живёт в `pages/directories`, хотя им пользуются четыре вкладки.

## 4. Принцип нового плана: попутно и узко

Прежний план был проектом на 20 дней с окнами и очередью слайсов. Новый — набор узких работ,
каждая из которых окупается сама по себе:

1. **Попутный переезд.** Слайс делает та задача, которая и так открывает этот экран. Накладные на
   синхронизацию — ноль: файл правится один раз и сразу в новой структуре.
2. **Целевые работы** — только там, где есть измеримая польза сегодня: починка дефекта, разрезание
   растущего монолита, восстановление сигнала проверки.
3. **Никаких «переездов ради стройности».** Слайс, который никто не открывает, ждёт своей задачи
   сколько угодно долго: `resources.ts` реэкспортирует, всё работает.

## 5. Работы

### P1 — сделать в ближайшие дни (≈6 часов)

| #   | Работа                                                                     | Почему сейчас                                              | Оценка |
| --- | -------------------------------------------------------------------------- | ---------------------------------------------------------- | ------ |
| 1   | Инвалидация журнала листов при переводе заказа в работу + тест             | настоящий дефект, виден диспетчеру                         | 1 ч    |
| 2   | Актуализировать списки в `check:stage2-layout`, разложить шесть файлов     | иначе проверка перестаёт быть сигналом                     | 1,5 ч  |
| 3   | `usePurgeAction` → `features/purge-record`                                 | общий сценарий четырёх вкладок лежит в папке одной из них  | 1 ч    |
| 4   | Расщепить `format`/`date`: ядро в `shared/lib`, домен в `entities/request` | последний кусок, из-за которого `utils` не может исчезнуть | 2,5 ч  |

### P2 — попутно, без отдельного времени

| Что                                         | С какой задачей едет                          |
| ------------------------------------------- | --------------------------------------------- |
| Слайсы `driver`, `waybill`, `vehicle-route` | ближайшая правка путевых листов или рейсов    |
| Слайсы `user`, `session`                    | правка учёток, входа или прав                 |
| Слайсы `vehicle`, `vehicle-type`            | правка справочника техники или классификатора |
| Слайсы `counterparty`, `file`               | правка контрагентов или вложений              |
| Ключи экрана — на реестр сущности           | всякий раз, когда экран и так открыт          |

Правило простое: **открыл файл ради задачи — забери его слайс с собой.** Не открыл — не трогай.

### P3 — разрезание монолитов, отдельным решением

Три страницы на 5273 строки — самостоятельная работа, которая не сводится к переезду: там нужны
`features` (форма заявки, смена статуса, назначение) и единое описание фильтров. Это 3–4 дня и
имеет смысл, только если разработка этих экранов на время замедлится.

**Моя рекомендация:** взяться за `WasteRequestsPage`, когда очередная задача по вывозу мусора
потребует в неё лезть, и разрезать её тогда же — по горячему, а не отдельным заходом.

### Чего не делаем

- Слайсы `waste-request`, `vehicle-request`, `request` — до разрезания самих страниц смысла мало:
  api там переедет, а полторы тысячи строк экрана останутся.
- Этапы 3–7 общего плана в прежнем виде: `useCrudMutations`, единые фильтры, стили, `lazy`-маршруты.
  Они предполагали, что к тому моменту страницы уже разобраны.
- Матрица инвалидаций как отдельный документ: вместо неё — точечные проверки на реальные связи
  (первая из них — работа P1 №1).

## 6. Как поймём, что не зря

| Признак                         | Как меряем                                            |
| ------------------------------- | ----------------------------------------------------- |
| Проверка раскладки снова сигнал | `check:stage2-layout` зелёная, красная = разбираемся  |
| Дефект журнала закрыт           | сценарный тест на связку «перевод в работу → журнал»  |
| `utils` исчез                   | каталога нет, ядро в `shared/lib`, домен в `entities` |
| Монолиты перестали расти        | `max-lines` в трёх файлах не увеличивается неделю     |
| Новый код пишется по слоям      | ноль нарушений границ за неделю (сейчас так и есть)   |

## 7. Оценка и риск

P1 — около 6 часов, разбивается на четыре независимых коммита, окон не требует.
P2 — нулевая: работы растворены в задачах.
P3 — 3–4 дня, отдельным решением.

Главный риск обратный прежнему: не «сломаем при переезде», а **«так и останется наполовину»**.
Смягчение — P1 №2: пока проверка раскладки зелёная и списки точны, любой новый файл требует
решения, куда он относится. Это дешевле любого плана и работает без напоминаний.
