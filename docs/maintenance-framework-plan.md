## 2. Решения

**Р1. Рантайм — `.maintenance/` в корне, целиком в `.gitignore`.** Концепт называет каталог
`.convergence/`, постановка — `.maintenance/`; берётся имя из постановки, потому что спорить о нём
дороже, чем оно стоит. Внешнее хранилище (`~/.vibe-maintenance/<project-id>/`) не делается: здесь
один репозиторий на одной машине, а интерфейс `StateStore` переезд обеспечит и потом.

**Р2. Политики — новый корневой `architecture/`, решения остаются в `docs/adr/`.** Перенести 189
файлов и все ссылки на них нельзя: на «ADR 0085» ссылаются 320 мест, включая неизменяемые сообщения
коммитов. Поэтому `architecture/` содержит только машинный слой и **ссылается** на тексты решений.

**Р3. Карта модулей не копируется, а читается.** `architecture/modules.yaml` не перечисляет пути
доменов заново — он даёт зонам обслуживания идентификаторы и правила, а состав домена берётся
разбором `docs/code-map.md`. Вторая карта разошлась бы с первой в первую же неделю, и проверка
`check:docs` о расхождении не узнала бы.

**Р4. `eslint.config.mjs` остаётся профилем `vibe` без единой правки; `release` — надстройка.**
Переносить действующий конфиг в `eslint/vibe.config.mjs` значит трогать общий файл, от которого
зависят ворота качества и незакрытый [план вычистки линта](lint-debt-plan.md). Release-профиль
живёт отдельным файлом, импортирует действующий и добавляет свои правила поверх. Ни одно правило из
профиля `vibe` не снимается — иначе базовая линия §0 перестала бы сравниваться с историей.

**Р5. Ядро — TypeScript, исполняется штатным Node без сборщика.** Node 22.23 снимает типы сам
(`node tools/maintenance/cli/main.ts`), поэтому `tsx` в корень не добавляется. Ограничение
понятное: только стираемый синтаксис (никаких `enum` и `namespace`), относительные импорты — с
расширением `.ts`.

**Р6. Единственная новая зависимость — `yaml` в корень.** Политики правит человек, и им нужны
комментарии «почему»: в JSON их нет, а конфиг-как-код (`.ts`) исполняется и потому не годится на
роль данных, которые читает и правит агент. Пакет без собственных зависимостей, типы свои.

**Р7. Verifier переиспользует существующие ворота, а не заводит свои.** Быстрый уровень —
`pnpm check` (типы, линт, тесты кроме db). Уровень с базой — `pnpm check:db`, по умолчанию
**выключен**: ему нужна своя свежая база, а на общей он даёт ложные падения (см. память проекта о
загрязнении общей базы). Включается флагом для прогонов, трогающих `apps/api/src/db` и сервисы.

**Р8. Агент — только `ManualVsCodeAdapter`.** Framework пишет `.maintenance/task.md`, человек
отдаёт его Claude/Codex, framework читает `.maintenance/results/*.json`. Никаких недокументированных
API плагинов IDE.

**Р9. Защищённые области этого проекта** (Э5): миграции и схема, права и предикаты контрактов,
почта, печатные формы и ЭСМ-2, деплой, ворота качества, тексты решений. Формы три — `allowed`,
`manual-review`, `forbidden`.

## 3.1. Что сделано на ЭA (14.09.2026)

Фундамент стоит и проверяется одной командой: `pnpm maintain doctor` читает конфиг, все четыре
файла политик и карту модулей, создаёт рабочий каталог и убеждается, что git его игнорирует.
Сегодняшний ответ: 10 правил (8 жёстких, 1 мягкое, 1 совещательное), 7 защищённых областей,
16 доменов — взятых разбором карты кода, а не переписанных в отдельный список.

Проверяется не только форма файлов. `doctor` роняет прогон, если носитель правила или ссылка на
решение не существует в дереве, если каталог пакета исчез, если рабочий каталог перестал быть
игнорируемым и если ни один уровень проверки поведения не включён — то есть если доказывать
сохранение поведения стало нечем.

**Профиль `release`.** `pnpm lint:release` = действующий профиль плюс сигнальные правила. Замер
14.09.2026: **0 ошибок, 442 предупреждения** (сложность 145, длина файла 154, длина функции 129,
глубина 1, число параметров 4, плюс 9 неиспользуемых имён из повседневного профиля). Пороги взяты
из распределения этого дерева, а не из учебника: при пороге функции в 200 строк нарушителей 273 при
медиане нарушителя 289 — то есть 200 здесь означает «обычно», а не «длинно»; при 300 остаётся 129,
и это уже хвост. `no-warning-comments` даёт ноль: TODO и FIXME в `apps`, `packages` и `scripts` нет
ни одного, и правило стоит ради первого появившегося, а не ради уборки.

**Базовая линия не сдвинулась.** После всех правок: `pnpm typecheck` зелёный, `eslint .` — 0 ошибок
и те же 26 предупреждений, `check:docs` — 0 ошибок. Ни одно правило повседневного профиля не снято,
ни один файл приложения не изменён.

**Про один красный прогон.** Первый полный `pnpm check` после этапа показал падение шага «фронт:
тесты»; повторный прогон того же дерева зелёный целиком, и отдельный прогон фронта — 225 файлов,
2049 тестов, ноль падений. Назвать упавший тест нечем: вывод первого прогона был обрезан при
снятии, и это ошибка снятия, а не находка. Класс падения известен и записан раньше — тесты
обновления сессии плавают именно в полном прогоне.

**Чего на ЭA сознательно нет.** Ни одного анализатора, ни одной находки, ни одной правки кода:
система пока умеет только отвечать на вопросы о правилах. Это и есть смысл этапа — сначала
устойчивый набор правил, потом рассуждение поверх него.

Переносимо (будущая внешняя библиотека): всё в `tools/maintenance/core`, `analyzers`,

## 6. Риски

1. **Общее рабочее дерево.** Транзакция git на этапе ЭC обязана откатывать только свои файлы.
   Откат «всего дерева» унёс бы чужую незакоммиченную работу — это самый дорогой риск плана, и
   поэтому checkpoint делается по списку файлов партии, а не `git checkout .`.
2. **Ворота качества чужие.** `pnpm check` ведётся ADR 0147 и планом вычистки линта. Verifier его
   только зовёт и никогда не правит.
3. **Агент как источник истины.** Находка без структуры и отпечатка превращается в прозу, которую
   нечем сравнить с прошлым прогоном. Поэтому схема finding появляется на ЭB, раньше цикла.
4. **Соблазн массового рефакторинга.** Ни один этап этого плана не правит код приложения; первая
   правка кодовой базы делается уже готовым циклом, под откатом и на согласованной области.

## 7. Что сознательно откладывается

Characterization-тесты (F14) — до ЭC, и только если Behavior Lock окажется дырявым на выбранной
области. SQLite под журнал находок — до тех пор, пока JSON не станет тесен. Автономные адаптеры
агентов — до ЭG. Перенос `eslint.config.mjs` в `eslint/vibe.config.mjs` — не делается вовсе, пока
не закрыт план вычистки линта. Полномочия и раздел портала не заводятся: система живёт в командной
строке разработчика и наружу не показывается.
