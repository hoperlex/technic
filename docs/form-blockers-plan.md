## 1. Постановка

Нажатие «Сохранить»/«Перевести в работу»/«Закрыть работы» может не пройти. Сейчас человек узнаёт об
этом тремя разными способами, и два из трёх не показывают, **какое поле** править:

| Способ                 | Что видно                                       | Где                  |
| ---------------------- | ----------------------------------------------- | -------------------- |
| правила `Form.Item`    | красная рамка и подстрочник у поля              | 128 правил           |
| `message.warning(...)` | тост в углу, поле не помечено, прокрутки нет    | **17 мест**          |
| дизейбл/пустое условие | ничего: кнопка нажимается, окно молчит          | 1 место              |
| ошибки полей с сервера | красная рамка без прокрутки — можно не заметить | 7 вызовов в 6 файлах |

Требуется одинаковое поведение во всех четырёх случаях: целевые поля красные, под каждым —
причина, экран прокручен к первому блокеру, и на каждом нажатии кнопки (первом и повторных) поля
блокеров дают вспышку от тёмного к целевому красному.

## 3. Что должен увидеть человек

1. Нажал кнопку — окно **не закрылось**, тоста нет (тост остаётся для сетевых и серверных ошибок
   без привязки к полю).
2. Все поля-блокеры красные, под каждым — своя причина в подстрочнике.
3. Экран прокручен так, что **первый** блокер по порядку формы — в середине видимой области
   (внутри тела окна на десктопе, внутри шита на телефоне), фокус — в нём.
4. Поля-блокеры дают вспышку: тёмно-красный → целевой красный, ~400 мс, один раз на нажатие.
5. Повторное нажатие с теми же блокерами повторяет вспышку и прокрутку — иначе второе нажатие
   выглядит как «кнопка не работает».
6. `prefers-reduced-motion` — вспышки нет, всё остальное есть.

## 4. Устройство

Ядро — один примитив, три точки входа. Точки входа разные, поведение одно; иначе прокрутка
«по правилам» и прокрутка «по имперактивной проверке» разъедутся в первый же месяц.

```text
                    правила Form.Item ──► onFinishFailed ─┐
   проверки в onFinish ──► raise([...]) ─────────────────┼──► showBlockers()
   ошибки полей с сервера ──► fromApi(error) ───────────┘        │
                                                                 ├─ form.setFields (рамка + подстрочник)
                                                                 ├─ scrollToField(первый, block:center, focus)
                                                                 └─ вспышка на полях с ошибкой
```

Предлагаемое размещение (слой `shared`, домена не знает):

```text
apps/web/src/shared/ui/formBlockers.ts   useFormBlockers(form) → { formProps, raise, fromApi }
apps/web/src/styles.css                  @keyframes вспышки + .ant-form-item-has-error
```

Подключение в окне — две строки:

```tsx
const blockers = useFormBlockers(form);
…
<FormModal onSubmit={() => form.submit()} …>
  <Form form={form} layout="vertical" onFinish={submit} {...blockers.formProps}>
```

и в самой проверке вместо тоста:

```tsx
if (!v.vehicleId) return blockers.raise({ vehicleId: 'Выберите технику' });
```

Тексты причин **берутся существующие** — те же, что сейчас в тостах и в `message` правил. Общий
словарь умолчаний («Поле обязательно к заполнению», «Поле заполняется только цифрами») подставляется
только там, где своего текста нет (§2.3), через `ConfigProvider form={{ validateMessages }}` в
[main.tsx](../apps/web/src/main.tsx) — одно место на портал.

### 4.1 Прокрутка

`antd` 6 даёт готовое: `form.scrollToField(name, { block: 'center', focus: true })` (внутри —
`scroll-into-view-if-needed`) и `form.focusField(name)`. Тело `Modal` и
тело `Drawer` — скроллящиеся контейнеры, библиотека их находит сама, ветвления «десктоп/телефон» не
нужно.

Две тонкости, из-за которых прокрутку лучше звать самим, а не через `scrollToFirstError`:

- прокрутка должна идти **после** отрисовки подстрочников, иначе цель смещена на их высоту —
  примитив откладывает вызов на кадр (`requestAnimationFrame`);
- `scrollMode` у antd по умолчанию `'if-needed'`: поле, уже видимое с краю, не центрируется. Что
  выбрать — развилка Р3.

### 4.2 Вспышка

Чистый CSS в `styles.css`, никаких библиотек (бюджет бандла — §8):

```css
@keyframes blocker-flash-a { from { border-color: #a8071a; background: #fff1f0 } to { …целевые… } }
@keyframes blocker-flash-b { /* тело то же */ }
```

Перезапуск на повторном нажатии: класс на `<Form>` чередуется `is-flash-a` ⇄ `is-flash-b` по
чётности счётчика нажатий. Два одинаковых набора кадров под разными именами нужны именно для этого:
если имя `animation-name` не изменилось, браузер анимацию не перезапускает. Альтернатива — снимать
класс и форсировать reflow из хука; это короче в CSS, но означает ручную работу с DOM (развилка Р4).

Цвета — константами с комментарием: `#ff4d4f` (целевой красный antd) и `#a8071a` (тёмный из той же
палитры). Токенов CSS у antd нет: `cssVar` в [theme.ts](../apps/web/src/theme.ts) не включён.

### Р1. Где живёт механика

| Вариант                                                                                                                     | Плюсы                                                        | Минусы                                                                                                |

оставить и дописать. Рекомендую замену.

### Р3. Как прокручивать

- **`scrollMode: 'if-needed'` + `block: 'center'`** (по умолчанию у antd): уже видимое поле не
  дёргается. Риск: поле видно «краем» у самого низа под кнопками — центровки не будет.
- **`scrollMode: 'always'`**: центрирует всегда, движение предсказуемо, но экран прыгает даже когда
  всё и так на виду.

Рекомендую `'always'` + `behavior: 'smooth'`: в задаче сказано «прокручивать к/центровать», и на
шите телефона кнопки перекрывают низ тела — «видно» и «доступно» там не совпадают.

Смежное: `focus: true` фокусирует первое поле. Для `Input` это хорошо; у `DatePicker` фокус может
открыть панель календаря поверх подстрочника — проверить на `VehicleEarlyEndModal` и решить,
не отключать ли фокус для полей даты.

### Р4. Перезапуск вспышки

- **CSS-чередование двух наборов кадров** — без работы с DOM, но в стилях лежит дубль кадров;
- **снятие класса + reflow из хука** — короче в CSS, но React-компонент трогает DOM руками.

Рекомендую первое: дубль кадров виден и объясним комментарием, ручная работа с DOM — нет.

### Р5. Что именно вспыхивает

- только рамка поля;
- рамка + светлая заливка;
- рамка + заливка + подпись поля красным.

Рекомендую второе. Подпись красным — отдельное решение по всему порталу: сейчас antd красит только
рамку и подстрочник, и менять это ради вспышки не стоит.

### Р6. Барьер, чтобы правило не забылось

По духу [Р1 плана доработок](frontend-followup-plan.md) («проверка обязана падать, а не сообщать»):

- **есть барьер**: проверка (AST по `src`), что `message.warning` не вызывается в функции отправки
  окна и что окно с `<Form>` внутри `FormModal` подключает `useFormBlockers`; +2 ч;
- **нет барьера**: договорённость в ADR и ревью.

Рекомендую барьер минимальной формы — только запрет `message.warning` в отправке; проверку
«подключён ли декоратор» надёжно выразить сложнее, чем она стоит.

### Р7. Объём первой очереди

- **только заявки** (новая заявка на автотехнику, на вывоз, на обслуживание + движения статусов) —
  9 файлов из §2.2, остальное попутно по правилу Р6 плана доработок;
- **весь портал сразу** — плюс справочники, учётки, рассылки; +1 день, риск задеть 33 окна разом.

Рекомендую первое: механика ядра всё равно ставится глобально, а конверсия тостов идёт по модулям.

## 9. Риски

1. **Блокер на скрытой вкладке.** `VehicleRequestsTab`, `UsersTab`, `WasteRequestsPage` содержат
   `Tabs`; если поле-блокер окажется на неактивной вкладке, прокрутка не приведёт никуда, и человек
   увидит «кнопка не работает» в чистом виде. Проверить, есть ли такие поля **внутри** форм окон;
   если есть — примитив обязан сначала открывать вкладку с первым блокером.
2. **Фокус на `DatePicker`** открывает панель поверх подстрочника (Р3).
3. **Смещение раскладки.** В `FormGrid` появление подстрочника растит строку сетки — соседняя
   колонка «прыгает». Прокрутка на следующем кадре это учитывает, но при нескольких блокерах
   форма всё равно подрастает. Резервировать место под подстрочник у всех полей — дорого по высоте;
   предлагаю принять смещение.
4. **Порядок причин.** Имперактивные проверки идут цепочкой с `return` на первой же (§2.2,
   `VehicleAssignModal`): человек чинит одно поле, жмёт снова — загорается следующее. `raise`
   должен принимать **все** нарушенные условия сразу, иначе поведение остаётся прежним, просто
   красным вместо тоста. Это требует переписать цепочки в список проверок — учтено в Э3.

## 10. Что решить до реализации

Р1 (устройство), Р2 (окна без формы), Р3 (режим прокрутки и фокус на датах), Р6 (нужен ли барьер),
Р7 (объём первой очереди). Остальные развилки — внутренние, решаются при реализации.
