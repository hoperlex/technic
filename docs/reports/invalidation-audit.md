# Реестр эффектов мутирующих ручек API

Вход для работы Р3 из `docs/frontend-followup-plan.md`. Снято 10.08.2026 по `main` (78562d3).

## Зачем

Фронт гасит кэш React Query по имени сущности, которую «очевидно» правит ручка. Но часть ручек
пишет в чужие таблицы через сервисы, и со стороны фронта это не видно в принципе. Показательный
случай: `PATCH /vehicle-requests/:id/status` вызывает `syncEsm2Waybills`, который делает
`.insert(waybills)` (`apps/api/src/services/waybill-esm2.ts:364`) и `.update(waybills)` (там же,
`:481`) — а фронт после мутации сбрасывает только `vehicle-requests` и `vehicle-routes`. Таблица
ниже перечисляет все найденные такие связи.

## Как снято

1. Все `r.post` / `r.patch` / `r.put` / `r.delete` из `apps/api/src/routes/*.ts` — найдено
   **125 обработчиков** (плюс семейство `DELETE /:id/purge`, см. ниже).
2. Для каждого обработчика собраны `.insert(X)` / `.update(X)` / `.delete(X)` в его теле —
   границей тела считается следующая регистрация маршрута в файле.
3. Локальные хелперы файла маршрутов (`attachToRoute`, `detachOnStatus`, `applyTransition` и т. п.)
   разобраны отдельно, и по каждому обработчику проверено, какие из них он зовёт.
4. Сервисы из `apps/api/src/services/**` разобраны на уровне экспортируемых функций; переход
   сервис → сервис пройден вручную для цепочек глубины 2–3 (`afterWorkPeriodChanged` →
   `syncEsm2Waybills` → `takeNextNumber`; `applyWeeklyRequest` → `createSpecialEquipmentRequest` /
   `extendSpecialEquipmentPeriod` → `syncEsm2Waybills`).
5. Приоритет обхода: `vehicle-requests.ts`, `vehicle-routes.ts`, `waste-requests.ts`,
   `waybills.ts` — разобраны полностью и вручную. Остальные файлы разобраны машинно с ручной
   проверкой только тех мест, где нашлась запись в чужую таблицу.

Скрипты обхода одноразовые, лежат в скрэтчпаде и в репозиторий не попадали.

### Что вынесено за скобки

Не считаются кросс-сущностным эффектом и в таблицах отмечаются сноской, а не отдельной колонкой
инвалидации:

- **Аудит.** `writeAudit(...)` → `audit_log`; есть почти в каждой мутирующей ручке. На фронте
  отдельная вкладка «Аудит», её кэш логичнее гасить по времени, а не по каждой мутации.
- **История.** `vehicleRequestStatusHistory`, `requestStatusHistory`, `serviceRequestStatusHistory`,
  `weeklyVehicleRequestHistory` — пишутся ровно тем обработчиком, который меняет свою сущность,
  и читаются во вкладке истории той же карточки.
- **Файлы.** `files`, `jobs` и связки `*_files`. `markFilesActive` (`files[update]`),
  `scheduleFilesDeletion` (`files[update]` + `jobs[insert]`), `hardDeleteFiles` (`files[delete]` +
  `jobs[insert]`) — из `apps/api/src/services/request-files.ts`. Списки файлов приходят внутри DTO
  карточки, отдельного ключа кэша у них нет.

## Не разобрано

Честный список пробелов — важнее полноты.

1. **`service-requests.ts` разобран поверхностно.** 18 обработчиков, из них 12 — переходы статуса
   через `applyTransition`. Проверено, что переходы пишут в `service_requests`,
   `service_request_items` и историю, но **не проверено**, трогают ли отдельные переходы
   (`/complete`, `/accept`, гарантийные претензии через `resolveWarrantyClaim`) орг.технику
   (`office_equipment`) или склад. Здесь вероятен ещё один кросс-эффект уровня
   `vehicle-requests/status`. Первое место, куда идти дальше.
2. **`weekly-vehicle-requests.ts`, 4 ручки — разобрана только цепочка `applyWeeklyRequest`.**
   Внутри `weekly-request-apply.ts` есть ветки (`extendSpecialEquipmentPeriod`,
   `createSpecialEquipmentRequest`, отказ), и какая ветка при каком решении визы срабатывает,
   не прослежено. Список таблиц в таблице выше — объединение всех веток, то есть верхняя оценка.
3. **`users.ts` `PATCH /:id`** — самый длинный обработчик (220 строк) с ветками по ролям. Разобран
   машинно; ветки со сменой роли и с назначением руководителя отдела вручную не прочитаны, там
   возможна запись в `user_departments` не только через `replaceUserDepartments`.
4. **`drivers.ts`** — `POST /:id/licenses` и импорт водителей (`driver-import-apply.ts`,
   `applyDriverImport` → `persons`, `person_credentials`, `person_employments`,
   `person_specializations`, `person_credential_categories`) не сопоставлены с конкретными
   ручками: где именно вызывается `applyDriverImport`, не проверено.
5. **`directory-transfer.ts` `POST /:key/import`** — перечислены таблицы всех `defs/*.ts`, но
   соответствие «ключ справочника → набор таблиц» не выписано. Для точной инвалидации нужно
   раскрыть `defs/index.ts`.
