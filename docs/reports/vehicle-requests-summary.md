# Модуль «Заказ ТС» — сводка реализации (каркас)

Вертикальный срез БД → контракты → REST → frontend для заявок на технику двух типов
(заказ спецтехники / грузоперевозки). Обоснование — [ADR 0004](../adr/0004-vehicle-requests.md).
Реализовано по утверждённому плану с осознанной «скидкой на каркас».

## Что сделано (по коммитам)

| Шаг | Коммит | Содержание |
|---|---|---|
| 1. БД | `c33c7d8` | enum + `vehicle_requests` + 2 detail + files/history + индексы; миграция 0012 |
| 2. Контракты | `993d329` | discriminatedUnion create/update (.strict()), DTO-union, list, номер; 15 тестов |
| 3. Backend | `29a8a0f` | файловый сервис, обобщение access/files, порт «Мусора», роут vehicle-requests |
| 4. Frontend | `ebdf44d` | раздел /vehicle-requests, 3 вкладки, 2 формы/таблицы, зависимые Select |

## Критерии завершения (§36)

1. ✅ Три вкладки (спецтехника / грузоперевозки / на объекте).
2. ✅ Типы не смешиваются (отдельные таблицы/формы, `requestType` в списке обязателен).
3. ✅ Номер «ТС-xxxxxx» (`formatVehicleRequestNumber`, поиск через parse).
4. ✅ Единая base-таблица + разные detail.
5. ⚠️ Корректность деталей — сервисной транзакцией (constraint-триггер в бэклоге).
6. ✅ Подтип валидируется backend (вид/активность/выбираемость).
7. ✅ Файловая подсистема учитывает оба модуля (общий сервис).
8. ✅ Один файл нельзя прикрепить к двум заявкам (сервис + `FOR UPDATE` + UNIQUE в таблице ТС).
9. ✅ Access-helper параметризован (`requestVisibilityWhere(p, objectIdColumn)`).
10. ✅ Статусы/версии/история/удаление/восстановление.
11. ✅ Даты: спец — date-only; freight — timestamptz + Europe/Moscow.
12. ✅ numeric → Number в DTO.
13. ✅ Старые заявки показывают актуальные названия типов (без snapshot).
14. ✅ «На объекте» — `Empty`, без запросов.
15. ✅ «Вывоз мусора» — регрессия контрактов/типов зелёная (53/53).

## Отложено — PG-интеграция (§34) и триггер

Тестовой инфраструктуры на реальном PostgreSQL нет — не проверены автоматически:
constraint-триггер деталей (не реализован), файловая конкурентность и кросс-модульная
уникальность (`FOR UPDATE`), timezone-фильтр грузоперевозок, регрессия «Вывоза мусора» после
рефакторинга файлового сервиса. Логика покрыта контракт/unit-тестами; полноценные PG-тесты —
в бэклоге (требуют Testcontainers или гейт по `TEST_DATABASE_URL`).

## Ручной acceptance-чеклист (frontend, Playwright-раннера нет)

- [ ] Три вкладки; активная сохраняется в URL (`?tab=`).
- [ ] Списки спецтехники и грузоперевозок не смешиваются.
- [ ] Поля и колонки соответствуют вкладке; в форме нет поля requestType.
- [ ] Зависимый Тип→Подтип: смена типа очищает подтип; подтип недоступен до выбора типа.
- [ ] Спецтехника: период date-only; грузоперевозка: дата+время (МСК), объём/масса (≥1),
      места погрузки/разгрузки обязательны.
- [ ] Файлы: загрузка/удаление; прикреплённый файл нельзя удалить через прямой DELETE (409).
- [ ] Статусы (переходы по ролям), редактирование с version, hard/soft delete, restore (admin).
- [ ] «На объекте» не делает сетевых запросов; ошибки backend показываются пользователю.
- [ ] «Вывоз мусора» работает как раньше (создание/файлы/статусы/удаление).
