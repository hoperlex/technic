## 0.1 Алиасы путей

Vite 8 читает `paths` прямо из `tsconfig.json` (`resolve.tsconfigPaths` — поле есть в типах
установленной 8.1.5), поэтому источник истины один и три копии алиасов не разъедутся:

| Файл                        | Что добавить                                                                                                            |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `apps/web/tsconfig.json`    | `compilerOptions.paths`: `@app/*`, `@pages/*`, `@widgets/*`, `@features/*`, `@entities/*`, `@shared/*` → `src/<слой>/*` |
| `apps/web/vite.config.ts`   | `resolve: { tsconfigPaths: true }`                                                                                      |
| `apps/web/vitest.config.ts` | то же (у vitest свой конфиг, resolve берётся оттуда)                                                                    |

Если `tsconfigPaths` не сработает (выяснится первым прогоном) — запасной вариант: явные
`resolve.alias` с **абсолютными** путями и ключами без `/*`
(`'@shared': path.resolve(__dirname, 'src/shared')`): формат alias у Vite не совпадает с шаблонами TS.

### Проверка тремя инструментами — с настоящим импортом в приложении

### Фикстуры границ — со своим конфигом

Ключевая деталь: production-конфиг описывает элементы по путям `src/entities/*`, `src/features/*` и
т. д. Файлы фикстур лежат вне `src/`, поэтому **этим конфигом они не классифицируются**: правило
вернёт ноль сообщений, и «зелёный» тест будет означать лишь, что boundaries ничего не понял про
фикстуры. Поэтому у фикстур собственный конфиг с собственным `boundaries/elements`, чей корень —
каталог фикстур, и собственный `tsconfig` с теми же алиасами для резолвера.

```text
apps/web/test/fixtures/boundaries/
  eslint.config.mjs                  свой boundaries/elements с корнем этого каталога
  tsconfig.json                      те же @-алиасы, но на это дерево
  shared/ui/index.ts
  entities/object/index.ts           export * from './api'
  entities/object/api/index.ts
  entities/object/api/internal.ts
  entities/object/bad-up.ts          import '@features/x'                                    → ошибка
  entities/object/bad-sibling.ts     import '@entities/user'                                 → ошибка
  entities/user/index.ts
  features/x/index.ts                публичный вход слайса — без него @features/x не резолвится
  features/x/ok-down.ts              import { objectsApi } from '@entities/object'           → ok
  features/x/bad-deep.ts             import { secret } from '@entities/object/api/internal'  → ошибка
```

`apps/web/test/boundaries.test.ts` прогоняет ESLint через Node API — `new ESLint({ overrideConfigFile: '<путь к конфигу фикстур>' })`
(флаг `--no-eslintrc` относится к eslintrc-эпохе и в flat config не применяется) — и проверяет
**конкретный `ruleId`** (`boundaries/dependencies`), а не наличие любого сообщения: правило,
проверенное «хоть какой-нибудь ошибкой», молча деградирует при смене конфига.

Каталог фикстур добавляется в `ignores` основного `eslint.config.mjs`: заведомо плохие импорты не
должны красить обычный `pnpm lint`.

Чтобы «зелёный» `ok-down` действительно что-то означал, в конфиге **фикстур** (и только там)
`boundaries/no-unknown` включён как `error`: неклассифицированный файл тогда падает с этим
правилом, а не молча проходит. Тест проверяет для `ok-down` отсутствие обоих `ruleId` —
и `boundaries/dependencies`, и `boundaries/no-unknown`.

**Done:** `pnpm lint` зелёный; `boundaries.test.ts` зелёный: три отрицательных случая падают именно
с `boundaries/dependencies`, положительный не падает ни с ним, ни с `boundaries/no-unknown`.

## 0.3 Тестовая инфраструктура: HTTP-моки, сброс состояния, фабрики

Семь существующих тестов мокают модуль `../src/api/resources` целиком — после разбора на слайсы
такой мок превращается в шестнадцать. Новые тесты мокают **сеть**: переезд модулей их не трогает, а
проверяют они то, что ломается при неверной инвалидации и ленивости — какие запросы уходят.

### `apps/web/test/http.ts`

```ts
/** Ответ маршрута: статус задаётся явно — от него зависит ветка обработки в apiFetch. */
export interface MockResponse {
  status: number;
  body?: unknown;
  headers?: Record<string, string>;
}

export const json = <T>(body: T, status = 200): MockResponse => ({ status, body });
export const noContent = (): MockResponse => ({ status: 204 });
/** Ошибка в формате портала: `fields` разбирает applyApiFieldErrors. */
export const apiError = (
  status: number,
  body: { code: string; message: string; fields?: Record<string, string> },
): MockResponse => ({ status, body });

export type RouteHandler = (ctx: {
  params: Record<string, string>;
  query: URLSearchParams;
  body: unknown;
}) => MockResponse | Promise<MockResponse>;

/** Ключ: 'GET /waste-requests', 'PATCH /waste-requests/:id/status'. */
export type RouteMap = Record<string, RouteHandler>;

export interface HttpMock {
  calls: { method: string; path: string; query: URLSearchParams; body: unknown }[];
  countOf: (route: string) => number;
  /** Дописать/переопределить маршруты по ходу теста (второй пользователь, изменившийся список). */
  use: (routes: RouteMap) => void;
}

export function mockHttp(routes: RouteMap): HttpMock;
```

Требования:

- **автоматическое восстановление `fetch`** в `afterEach` из `test/setup.ts` — упавший тест не
  утаскивает за собой следующие;
- сопоставление пути с префиксом `/api/v1` и параметрами (`:id`);
- незаданный маршрут → падение с внятным текстом («нет мока для `GET /objects`»), а не пустой ответ;
- поддержка `PUT` на внешний presigned-URL — иначе тесты с вложениями не соберутся;
- журнал `calls` — основа проверок «сколько запросов ушло» и «что перезапрошено после мутации».

### Два helper'а рендера

Смешивать настоящий `AuthProvider` с моком `useAuth` в одном helper'е нельзя: `vi.mock` поднимается
на верх модуля и не переключается между тестами одного файла.

```ts
/** Обычный тест: пользователь подставляется значением контекста, сеть — по мокам. */
export function renderWithUser(
  ui: ReactNode,
  opts?: {
    user?: Partial<AuthUser>; // по умолчанию — диспетчер
    viewport?: Viewport;
    queryClient?: QueryClient;
  },
): RenderResult & { queryClient: QueryClient };

/** Тест сессии: настоящий AuthProvider, вход и выход идут через сеть. */
export function renderWithSession(
  ui: ReactNode,
  opts?: {
    viewport?: Viewport;
    queryClient?: QueryClient;
  },
): RenderResult & { queryClient: QueryClient };
```

Оба оборачивают дерево в одну и ту же оболочку — порядок важен и не отдаётся на догадку
исполнителя:

```text
ConfigProvider(locale=ru_RU, theme=themeFor(isMobile))
  └─ AntApp                     // App.useApp(): message и modal, без него формы падают
      └─ QueryClientProvider    // свежий клиент, retry: false
          └─ MemoryRouter       // страницы используют навигацию и Outlet
              └─ AuthContext.Provider (renderWithUser) | AuthProvider (renderWithSession)
                  └─ ui
```

`renderWithUser` подставляет значение через `AuthContext.Provider` — для этого `AuthContext`
экспортируется из `src/auth/AuthContext.tsx` (одна строка, поведение не меняется). Моков модулей
приложения нет ни в одном из helper'ов.

**Что в каком коммите.** `mockHttp`, `renderWithUser` и фабрики — коммит №3, он не трогает
auth-код вовсе. `renderWithSession`, сбросы auth-состояния (`__resetAuthBootstrap`,
`__resetSession`) и generation token появляются в коммите №7 вместе с исправлением 0.6a: они
требуют правок `AuthContext`/`api/client`, а на них назначено окно сверки A. Описаны здесь вместе,
чтобы helper'ы читались как одна поверхность.

### Сброс состояния между тестами

В `afterEach` (`test/setup.ts`) сбрасывается всё, что живёт в модулях. Сами сбросы вводятся
**коммитом №7** (правки `AuthContext`/`api/client` идут в окно A):

| Что                         | Где сейчас             | Как сбрасывать                                          |
| --------------------------- | ---------------------- | ------------------------------------------------------- |
| `bootstrapPromise`          | `auth/AuthContext.tsx` | `__resetAuthBootstrap()`                                |
| `lastAuthenticatedUserId`   | вводится в 0.6a        | тем же `__resetAuthBootstrap()` — обе переменные вместе |
| `accessToken`               | `api/client.ts`        | `__resetSession()`                                      |
| `refreshing` (in-flight)    | `api/client.ts`        | см. ниже — не простым `null`                            |
| обработчик `sessionExpired` | `api/client.ts`        | `setSessionExpiredHandler(null)`                        |

**In-flight refresh нельзя сбросить присваиванием `null`:** уже запущенный promise завершится позже
и установит токен уже в следующем тесте. Нужен **generation token** — счётчик, увеличивающийся при
сбросе; результат refresh применяется, только если его поколение совпадает с текущим. Тот же приём
переезжает в `shared/api/session` в этапе 1 и там же закрывает гонку в реальном приложении (быстрый
logout во время висящего refresh).

### Фабрики тестовых данных — до параллели

Общий `test/factories.ts` стал бы точкой одновременной записи для трёх авторов сценариев. Поэтому
фабрики разделены по доменам и фиксируются **в этом, последовательном блоке**:

| Файл                        | Что даёт                                                        |
| --------------------------- | --------------------------------------------------------------- |
| `test/factories/auth.ts`    | `authUser()`, ответы `/auth/login`, `/auth/me`, `/auth/refresh` |
| `test/factories/waste.ts`   | `wasteRequest()`, сводка, справочники вывоза                    |
| `test/factories/vehicle.ts` | `vehicleRequest()`, сводка, классификатор, назначение           |

Фабрики фиксируются целиком **до** начала параллели. После этого авторы сценариев их **не

Если сценарию не хватает поля — оно добавляется отдельным коммитом до параллели, а не по ходу.
Общие поля DTO приходят из `@technic/contracts`.

## 0.6 Исправления, которые не ждут этапов

### a. Очистка кэша при смене и истечении сессии (дефект §1.3 плана)

Сравнения `user.id` при `login` недостаточно: обработчик `sessionExpired`
([AuthContext.tsx:68](../apps/web/src/auth/AuthContext.tsx)) сначала обнуляет `user`, и следующий
вход сравнивал бы нового пользователя с `null` — данные предыдущего остались бы в кэше.

Решение: отдельная переменная `lastAuthenticatedUserId`, не зависящая от состояния React, и очистка
во всех четырёх точках:

| Событие                                      | Действие                                                                     |
| -------------------------------------------- | ---------------------------------------------------------------------------- |
| `logout`                                     | `queryClient.clear()`, `lastAuthenticatedUserId = null`                      |
| `sessionExpired`                             | `queryClient.clear()`, `lastAuthenticatedUserId = null`                      |
| `login`                                      | `res.user.id !== lastAuthenticatedUserId` → `clear()`; затем запомнить новый |
| `refreshUser` / bootstrap вернул другой `id` | то же                                                                        |

Тем же коммитом вводится generation token для in-flight refresh (0.3) — иначе висящий refresh
установит токен уже после очистки.

Полная схема с выносом в `shared/api/session` — этап 1, §4.1 плана.

Коммит включает тесты 0.4д и 0.4е — так каждый коммит остаётся зелёным.

### b. `StatusCell` из тела компонента (дефект §1.1 плана)

Это не правка на пару строк: [WasteRequestsPage.tsx:720-801](../apps/web/src/pages/WasteRequestsPage.tsx) —
82 строки, зависящие от `user`, `isMobile`, `statusMut` и `requestStatusChange`.

### Алгоритм `bundle-size.mjs`

Считает не «entry + чанк маршрута», а **транзитивное замыкание синхронных импортов** — иначе после
`lazy`-разбиения (этап 5) у чанка маршрута появятся собственные shared-импорты, и сравнение «до/после»
окажется нечестным в свою пользу:

1. найти entry-чанк (`isEntry: true`);
2. найти чанк маршрута `/waste` — по `src` страницы среди `dynamicImports` entry (после этапа 5) либо
   как часть замыкания entry (сейчас, пока разбиения нет);
3. от обоих рекурсивно обойти `imports` (только синхронные; `dynamicImports` не считаются);
4. дедуплицировать по имени файла;
5. просуммировать **gzip**-размеры.

Одна и та же функция применяется к baseline и к финальному замеру — сравнение считается одинаково.

Тест счётчика запросов — живой критерий: в этапе 5 ожидания меняются на ≤3, и регрессия становится
красным тестом, а не наблюдением в devtools.

**Done:** отчёт закоммичен с числами; `bundle-size.mjs` воспроизводит число одной командой;
тест-счётчик зелёный на текущих ожиданиях.
