# Runbook (эксплуатация)

Прод: VPS `89.232.188.170`, каталог `/opt/portals/technic`, compose-проект **`technic`**,
публичный URL **https://auto.su10.ru**. Edge: контейнер `infra-nginx` + vhost
`/opt/infra/nginx/conf.d/technic.conf`. Секреты: `/etc/technic-portal/prod.env`
(вне git). На VPS есть другие проекты — не трогать их compose/vhost и не запускать
глобальные destructive-команды.

## Деплой (`deploy-auto`)

Штатный деплой — одной командой `deploy-auto` (из любого каталога VPS; симлинк в
`/usr/local/bin`, скрипт — `deploy/deploy-auto.sh`). Делает: `git pull` ветки **main**
(с проверкой `HEAD == origin/main`) → сборку `technic-*:<sha>` → бэкап БД перед миграциями →
авто-накат новых миграций → `up -d` → health-гейт `:latest`. Portal-scoped: соседние
порталы/`infra-nginx` не трогает, `docker rmi` — только по whitelist `technic-*`, без
`docker system prune -a`/`down --volumes`.

```bash
deploy-auto                 # обычный деплой (main): pull → build → миграции → up → health
deploy-auto --skip-migrate  # деплой кода без наката миграций (даже если есть pending)
deploy-auto --previous      # быстрый откат кода на предыдущий SHA (без пересборки); схему НЕ трогает
deploy-auto --restore-db    # восстановление БД из последнего дампа (destructive, TTY-подтверждение)
deploy-auto --status        # read-only: релизы, образы, статус миграций, бэкапы, диск
deploy-auto --no-prune      # без чистки образов/кэша (ротация бэкапов — всегда)
deploy-auto --cutover       # необратимый выкат с остановкой записи (протокол, см. ниже)
deploy-auto --cutover-revert # откат незавершённого cutover, пока граница не записана
```

**Git-流:** деплоится только ветка **main**; перед деплоем код должен быть в `origin/main`
(скрипт откажет при ветке ≠ main или `HEAD ≠ origin/main` → `git checkout main` + push).

**Обновление самого скрипта:** `deploy-auto` стоит симлинком в рабочее дерево и пуллит сам
себя, поэтому после pull он перезапускается новой версией и продолжает деплой ею — правки в
`deploy/deploy-auto.sh` вступают в силу тем же деплоем. Без перезапуска запущенный bash дочитывал
бы старый файл через открытый дескриптор (git обновляет файл заменой inode), и деплой, привёзший
новый шаг, шёл бы по предыдущей версии — молча, без единой ошибки в выводе.

**Бэкапы (keep-2):** перед накатом миграций — `pg_dump -Fc` в
`/var/lib/technic/deploy/db-backups` (2 последних `<utc>-<sha>.dump` + `.meta`, плюс 1
аварийный `prerestore-*`); снимок `prod.env`+CA+vhost в `config-backups` (2 последних).
Ротация идёт всегда, даже при `--no-prune`. Бэкапы содержат ПДн/секреты — каталоги 700/600.

`.meta` несёт не только метки времени и коммита, но и **точный состав применённых миграций**
(`migrations_count`, `migrations_sha256` и строки `migration=`) — по нему сверяется дамп при
восстановлении (см. «Гейты отката»). Дамп с файлом `<дамп>.pin` рядом **закреплён**: его ставит
`--cutover` на предмиграционный дамп, и keep-2 такой дамп не считает и не удаляет. Снимать
закрепление руками (`rm <дамп>.pin`) можно только осознанно: это единственный дамп, к которому
откат ещё разрешён. Рядом с закреплённым дампом лежат `<дамп>.release.state` и
`<дамп>.schema-floor.state` — снимок состояния на момент записи границы.

**Откат:** `--previous` возвращает прошлый код без пересборки, но схему НЕ откатывает;
согласованный откат — `deploy-auto --previous --restore-db`. Важно: `pg_restore --clean`
не гарантирует полный откат схемы (объекты новее дампа могут остаться) — authoritative
schema-откат — **Yandex Managed PG PITR** (метку времени печатает `--restore-db`). Отсюда
правило: **миграции backwards-compatible** — после применённых миграций/`up -d` скрипт
авто-отката кода НЕ делает.

**Гейты отката (протокол выката §4–§5).** Оба разрушительных режима теперь fail-closed и молча не
проходят:

- **нет или повреждён `/var/lib/technic/deploy/schema-floor.state`** — `--previous` и `--restore-db`
  отказывают целиком. Файл заводится **однократно** обычным деплоем и дальше только дополняется,
  поэтому его отсутствие означает потерю границы, а не «границ не было». Чинится восстановлением из
  снимка конфига (`config-backups/config-*.tar.gz`, файлы лежат в корне архива), а не
  переинициализацией — её нет ни под каким флагом;
- **`--previous` ниже границы** — если целевой образ не содержит какой-то миграции из `floors`,
  откат отклоняется навсегда: этот код не умеет жить с такой схемой;
- **`--restore-db`** принимает только дамп, чей состав миграций **в точности равен** составу
  целевого образа, содержит все границы и не старше текущей схемы. Дамп без `.meta` (снят версией
  скрипта до протокола) не принимается вовсе — для него остаётся PITR.

Текущее состояние обоих файлов показывает `deploy-auto --status` (строки `cutover` и `схема`).

### Необратимый выкат (`--cutover`)

Режим для миграций, которые **меняют смысл данных** и потому не переживают «старый код на новой
схеме»: обычный деплой накатывает миграции до перезапуска, и старый код какое-то время пишет по
старым правилам. Нормативное описание — [протокол выката](schema-cutover-protocol.md); здесь только
команды. Параметры своего релиза (какая миграция, какой верификатор, какой teardown) даёт план этого
релиза.

Что обязано быть сделано **до** запуска:

1. **репетиция на копии базы** по чек-листу протокола §9 — без неё выкат не начинается;
2. в релизе ровно **одна** неприменённая миграция (§6): чужая рядом — отказ ещё до остановки
   сервисов, её выкатывают обычным деплоем первой;
3. релиз привёз `apps/api/teardown/<миграция>.sql` (обратная миграция) и
   `apps/api/teardown/<миграция>.sql.verify` (строка с командой-верификатором). Нет любого из них —
   отказ до остановки сервисов: без верификатора не проверить данные, без teardown невозможен откат.

```bash
deploy-auto --cutover        # pull → build → сверка бандла → стоп api/worker → дамп (закреплённый)
                             # → миграция → верификатор → ГРАНИЦА → up -d → health → архив состояния
deploy-auto --status         # где мы сейчас: строка cutover показывает фазу
```

Идёт всё **с остановкой записи**: `technic-api` и `technic-worker` лежат от дампа до подъёма,
снаружи это 502. `technic-web` остаётся поднятым намеренно — честная ошибка лучше белого экрана.

**Повтор безопасен и является штатным способом продолжить.** После любого обрыва (упал верификатор,
умер контейнер, Ctrl-C, разорвался ssh) повторный `deploy-auto --cutover` сверяет журнал миграций,
границу и фазу и пропускает сделанное. Продолжают **тем же коммитом**: чужой SHA — отказ.

Что делать по фазе, если что-то пошло не так:

| Фаза в `--status`      | Где мы                       | Что делать                                                                         |
| ---------------------- | ---------------------------- | ---------------------------------------------------------------------------------- |
| `migrating`            | миграция накатывается        | повторить `--cutover`                                                              |
| `migrated`             | схема новая, границы ещё нет | вперёд — `--cutover`; назад — `--cutover-revert` (единственное окно для отката)    |
| `irreversible`, `done` | граница записана             | только вперёд: `--cutover` (повторит health) либо обычный `deploy-auto` нового SHA |
| нет активного выката   | всё закрыто                  | обычный `deploy-auto`                                                              |

**Health не подтвердился — выкат не заперт.** Схема уже новая, поэтому обычный `deploy-auto` с
исправленным кодом разрешён и ничего не обходит: он выкатывает следующий код на ту же схему и
закрывает состояние выката как `superseded`. Повтор `--cutover` прогоняет health заново.

**Откат — только до записи границы:**

```bash
deploy-auto --cutover-revert   # teardown релиза + возврат сервисов на прежний тег
```

Разрешён тогда и только тогда, когда фаза ровно `migrated` **и** миграции ещё нет в
`schema-floor.state`. Дополнительно проверяются: сервисы остановлены, применённый набор совпадает с
бандлом, посторонних миграций нет, закреплённый дамп на месте, образ кандидата не вычищен
ретеншном. После `irreversible` откат отклоняется навсегда — дальше PITR либо ремонт вперёд.

**Граница совместимости** живёт в `/var/lib/technic/deploy/schema-floor.state` и переживает всё:
архивирование состояния выката, следующие релизы, перенос площадки (файл едет в снимке конфига).
Она и есть «ниже этой миграции откатываться нельзя» — см. «Гейты отката» выше. Руками файл не
правят.

**Teardown руками не запускают.** `pnpm --filter @technic/api db:cutover-down <миграция.sql>` не
проверяет ни фазы, ни границы — он снимает схему и запись журнала одной транзакцией и предназначен
`deploy-auto` и репетиции на копии базы. У человека для этого есть `--cutover-revert`.

### Ездки и точки маршрута: параметры выката (ADR 0108, миграции `0136` и `0146`)

Релиз, ради которого заводился `--cutover`: миграция `0136` переносит адреса, количество и контакты
с заявки на **ездку** и удаляет колонки-источники, то есть меняет смысл данных. Параметры, которые
протокол спрашивает у релиза:

| Параметр      | Значение                                                                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| бандл         | одна миграция `0136`: три таблицы, `waybill_trips`, `issue_warnings`, бэкфил и запись выпуска (`seq 19`, версия `0.1.18.0108`) — всё в ней          |
| верификатор   | `apps/api/teardown/0136_route_trips.sql.verify` → `pnpm --filter @technic/api backfill:trips --check` (read-only, ненулевой код на любом нарушении) |
| teardown      | `apps/api/teardown/0136_route_trips.sql` — возвращает колонки заявки из **первой** ездки и снимает новые таблицы                                    |
| граница floor | `0136` — ниже неё откат запрещён навсегда                                                                                                           |

**Два предохранителя миграции стоят до первого изменения схемы, и разбирают их заранее** — выкат
идёт с остановкой записи, и разбираться по ходу означает держать портал лежащим:

- грузовая заявка **без строки деталей**: бэкфил ездок идёт от деталей, и такая заявка осталась бы
  без адресов вовсе;
- день линейного заказа, у объекта которого **нет ни наименования, ни адреса**: точке маршрута
  нечего записать адресом, а CHECK упал бы кодом `23514` без единого слова о том, у какого объекта
  дыра.

Оба запроса можно прогнать заранее на проде — они только читают. Остальные три предохранителя
сверяют числа после бэкфила (ездка на каждую строку деталей; две роли на грузовую строку состава и
одна на линейный день; строка `waybill_trips` на каждый талон грузовой заявки) и роняют транзакцию
целиком, ничего не оставляя.

**Миграция `0146` (порядок ролей внутри точки) в бандл выката не входит и войти не может**: протокол
§6 требует в релизе ровно одну неприменённую миграцию, а чужая рядом — отказ ещё до остановки
сервисов. Значит она выкатывается **отдельным обычным деплоем**, и у этого деплоя есть своё окно:
`ALTER TABLE … SET NOT NULL` накатывается **до** перезапуска API, а предыдущая версия кода про
колонку `position` не знает и на заведении роли получит отказ. Окно короткое (миграция → `up -d`),
но приходится оно ровно на сборку маршрутов, поэтому деплой ставят в нерабочее время и не
совмещают с чем-то ещё. Порядок обратный невозможен: `0146` правит таблицу, которую заводит `0136`.

После подъёма проверяют три вещи, и все три — на живых данных: карточка старой заявки открывается и
показывает одну ездку с прежними адресами и количеством; собранный до релиза маршрут показывает по
две точки на грузовую строку и по одной на линейный день; повторная печать ранее выданного листа
даёт **тот же** документ (он печатается из снимка и миграцией не трогается).

### Разовый шаг: перенос истории в маршруты (ADR 0050)

Маршруты — рейс машины на дату между заявкой и путевым листом (ADR 0050) — выкатываются двумя
релизами, и между ними нужен ручной прогон. Порядок обязателен: миграция `0074` начинается
предохранителем и **прервёт деплой**, если история не перенесена (схема при этом не пострадает —
падение происходит до первого изменения).

```bash
# 1. Релиз с миграцией 0072 уже выкачен (таблицы рейсов, waybills.route_id nullable).
docker compose -p technic exec api pnpm backfill:routes --check   # отчёт, база не меняется
# 2. Разобрать блокирующие пункты отчёта:
#    · заявки сразу в нескольких действующих листах — аннулировать лишний бланк в журнале;
#    · заявка и на действующем листе без рейса, и уже в рейсе — аннулировать лист либо вынуть её.
docker compose -p technic exec api pnpm backfill:routes           # перенос: рейс на пару «машина + дата»
docker compose -p technic exec api pnpm backfill:routes --check   # «Листов без рейса: 0»
docker compose -p technic exec api pnpm backfill:routes --clear-orphan-drivers
#    ↑ обнуляет водителей в назначениях, где рейса не бывает (аренда, спецтехника): без этого
#      предохранитель миграции 0074 тоже не пропустит.
# 3. Только теперь деплой релиза с миграцией 0074 (NOT NULL, «один лист на рейс», снятие
#    старого UNIQUE, удаление driver_person_id у назначений).
```

Если релиз с `0074` уже в `main`, а перенос не сделан — деплойте `deploy-auto --skip-migrate`,
прогоните шаги выше и повторите обычный `deploy-auto`. Скрипт переноса идемпотентен: повторный
запуск ничего не дублирует.

### Разовый шаг: перенос полномочий из надстроек роли (ADR 0106)

Два системных полномочия — «Оператор (оргтехника)» и «Согласование ИТ» — переезжают из
`user_role_addons` в `grants`/`user_grants` пятью шагами expand/contract (ADR 0106 §9, план
реструктуризации §13). Шаги 1a и 1e — релизы с миграцией, 1c и 1d — релизы без миграций, а между
1a и 1c обязателен ручной прогон. Скрипт `backfill:grants` **приезжает релизом 1a**: до его выката
команды в образе нет.

```bash
# 1. Релиз 1a выкачен: новые таблицы, два системных набора с нынешним составом прав, двойная
#    запись выдач и отзывов. Чтение по-прежнему из user_role_addons, user_grants пуста.
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api backfill:grants --check || true   # отчёт, база не меняется
#    ↑ до переноса расхождение ненулевое и это нормально: в новой таблице нет ничего, что выдали
#      до старта двойной записи. Цифра нужна как точка отсчёта — с ней сверяют результат.
#      Код возврата здесь ожидаемо 1 — отсюда и `|| true`: под `set -e` чек-лист оборвался бы на
#      правильном ответе скрипта. Это единственный шаг, где единица ожидается; ниже она означает
#      отказ. Ноль на этом шаге — тоже сигнал: переносить нечего, проверьте, та ли база и вправду
#      ли выкачен 1a.
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api backfill:grants           # перенос: INSERT … SELECT в одной транзакции
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api backfill:grants --check   # обе стороны по нулям, код возврата 0
# 2. Только теперь релиз 1c (переключение чтения на новые таблицы). Сверку повторить
#    непосредственно перед выкатом: между переносом и релизом могли выдать полномочие.
# 3. Релизом позже — 1d (прекращение записи в user_role_addons, таблица остаётся живой).
# 4. Ещё релизом позже — 1e (миграция удаляет user_role_addons).
```

**Признак, по которому идут дальше, — нулевой двусторонний diff**: пусто и «есть в
`user_role_addons`, нет в `user_grants`», и обратное. Перенос сериализован с выдачей и отзывом
(`LOCK TABLE user_role_addons IN SHARE MODE` на время вставки и сверки, `ON CONFLICT DO NOTHING`),
поэтому ноль означает именно совпадение назначений, а не удачный момент замера.

**Код возврата по шагам.** Первый `--check` — единственное место, где единица ожидается и ничего не
значит, кроме «переносить есть что»; в чек-листе он и запускается с `|| true`, а решение принимают
по отчёту. У переноса и у второго `--check` единица означает отказ: дальше не идти. Обратная
сторона сверки ограничена кодами двух переезжающих наборов, поэтому пользовательские наборы этапа 3
её не поднимают — расхождение здесь всегда про переезд.

**Третья строка отчёта — «права совпали, история выдачи разошлась».** Пара есть в обеих таблицах, а
`granted_by` или `granted_at` разные: так выглядит откат до версии без двойной записи, в котором
полномочие отозвали и выдали заново (`ON CONFLICT DO NOTHING` сохранил прежнюю строку назначения).
Доступ от этого не меняется, и переключение чтения такое расхождение **не** запрещает — но `--check`
из-за него возвращает 1, чтобы шаг чек-листа остановился и человек посмотрел отчёт. Перенос его не
чинит (повторять его незачем) и чинить не берётся: с шага 1d старая таблица отстаёт, и копирование
истории из неё затирало бы верную. Правится руками и только пока двойная запись работает — то есть
до 1d; после 1e восстанавливать историю будет уже не из чего:

```sql
UPDATE user_grants ug
   SET granted_by = ura.granted_by, granted_at = ura.granted_at
  FROM user_role_addons ura
  JOIN grants g ON g.code = ura.addon::text
 WHERE ug.user_id = ura.user_id AND ug.grant_id = g.id
   AND (ug.granted_by IS DISTINCT FROM ura.granted_by
     OR ug.granted_at IS DISTINCT FROM ura.granted_at);
```

**Почему перенос — ручной шаг, а не часть миграции 1a.** Миграции накатываются **до** перезапуска
приложения (`deploy-auto`: накат идёт перед `up -d`). Скопируй их миграция — между копированием и
стартом нового кода продолжает работать старая версия, пишущая только в `user_role_addons`: выдача
или отзыв полномочия в это окно не попали бы в новые таблицы и потерялись бы навсегда, потому что
второй раз копировать никто не будет. Порядок «сперва двойная запись, потом перенос» закрывает окно
целиком: всё после старта двойной записи уже в новых таблицах, всё до — доберёт перенос.

**Почему между 1d и 1e обязан пройти целый релиз.** Удали таблицу тот же релиз, что прекращает в
неё писать, — миграция снесёт `user_role_addons` до перезапуска, и работающий код предыдущей версии,
продолжающий двойную запись, начнёт падать на каждой выдаче полномочия. Релиз 1d поэтому оставляет в
базе живую, но никем не используемую таблицу, и только следующий её удаляет.

**Предохранителя в миграции здесь нет** — в отличие от маршрутов (`0074`), где непереносённая
история прерывает деплой. У 1c и 1d миграций нет вовсе, останавливать деплой нечем, и решение «идти
дальше» целиком на человеке с отчётом `--check` в руках. Если 1c выкачен раньше переноса, держатели
полномочий теряют доступ (читается пустая `user_grants`); чинится это прогоном
`backfill:grants`, а не откатом: права читаются из базы на каждый запрос, и доступ возвращается со
следующего.

**`--check` показал ненулевой diff после переноса — чтение не переключать.** Разница означает, что
двойная запись где-то не сработала, и релиз 1c в таком состоянии закрепил бы расхождение. Порядок
разбора: скрипт печатает обе стороны с примерами строк — посмотреть, в какую сторону разошлось и на
каких учётках, найти причину (выдача мимо `replaceUserAddons`, ручная правка `user_role_addons` в
базе), затем повторить перенос. Он идемпотентен: повторный запуск ничего не дублирует и совпадающие
назначения не пересоздаёт.

**Откат по шагам — неоднородный:**

| Откат                | Безопасен | Почему                                                                  |
| -------------------- | --------- | ----------------------------------------------------------------------- |
| `1c → 1b`, `1b → 1a` | да        | двойная запись работает, обе таблицы согласованы                        |
| `1d → 1c`            | да        | старая таблица уже отстала, но обе версии читают новые                  |
| **`1d → 1b`**        | **нет**   | версия читала бы `user_role_addons`, отставшую на всё выданное после 1d |
| `1e → 1d`            | да        | версия 1d старую таблицу не читает и не пишет                           |
| **`1e → 1c`**        | **нет**   | таблицы больше нет, а те версии её читают                               |

До 1d откат безопасен в любую сторону. Возврат к чтению `user_role_addons` после 1d допустим только
после **обратной сверки** — переноса из `user_grants` в старую таблицу; без неё откат молча отберёт
доступ у всех, кому его выдали после прекращения записи, и заметят это не в деплое, а по жалобе
«пропала кнопка». После 1e откатываться некуда: таблицы нет, и вернуть её может только PITR
(см. «Гейты отката»).

#### Что входит в релизы 1d и 1e (подготовлено 18.08.2026, не выкачено)

Оба шага расписаны заранее, потому что порознь они выглядят безобидно, а порядок между ними —
единственное, что отделяет их от падения на каждой правке учётки.

**Релиз 1d — только код, миграций нет.** Правки в `apps/api/src/services/user-scopes.ts`, две и
неразделимые:

1. `replaceUserAddons` перестаёт писать в `user_role_addons`: убираются `tx.delete(userRoleAddons)`
   и `tx.insert(userRoleAddons)`, вызов `mirrorAddonGrants` остаётся. Единственный писатель старой
   таблицы — эта функция, других в коде нет;

Это последний момент, когда двусторонний ноль вообще достижим: с 1d старая таблица начинает

таблицу никто не пишет; единица от `--check` там штатна и признаком беды больше не служит. Смысл с

### Выкат полномочий в окне учётки (ADR 0119)

Полномочия выдаются прямо в карточке учётки — тем же решением, что рассматривает заявку на
регистрацию. Миграций фича не требует, но выкат ступенчатый, и порядок не переставляется:

| Шаг | Что везёт                                                                               | Расширяет доступ            |
| --- | --------------------------------------------------------------------------------------- | --------------------------- |
| 1d  | прекращение записи в `user_role_addons` (см. раздел выше)                               | нет                         |
| 1а  | `writeAuditTx` — журнал событий доступа пишется в транзакции и роняет операцию при сбое | нет                         |
| 1б  | сервер принимает `grants` в теле учётки, каталог отбирается ролью                       | нет: тела ещё никто не шлёт |
| 2   | портал: поле «Полномочия» вместо «Надстроек»                                            | да — это и есть фича        |

**Перед 1б обязателен preflight** — он отвечает на два вопроса по живым данным:

```bash
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api check:grants-preflight
```

- **предел назначений.** Ненулевой код возврата означает одно: у кого-то назначений больше, чем
  `MAX_ASSIGNED_GRANTS`. Выкатывать в таком состоянии нельзя — карточка этого человека откроется
  в положении, из которого нельзя сохранить даже телефон. Лечится отзывом лишнего в реестре выдач
  либо поднятием константы новым релизом;
- **список держателей.** Ошибкой не считается, но его надо отдать администраторам до выката 1б:
  между 1б и 2 старый портал не сможет сменить роль тому, у кого от этой смены меняется действие
  назначения (400 «откройте карточку заново»). Такая правка в этом окне делается отзывом набора в
  реестре выдач и повторной выдачей после смены роли. Окно закрывается выкатом шага 2.

**Проверка после выката 2:** открыть карточку любой учётки с ролью, принимающей наборы, — поле
«Полномочия» показывает наборы, совместимые с ролью, а взведённые переводом ролей отмечены и
заблокированы. Если поле пришло заблокированным с сообщением о неполном списке — сервер не отдал
каталог целиком, и высказывание портал сознательно не отправляет; смотреть надо `GET /grants`, а не
форму.

### Выкат набора позиций в фильтре техники (ADR 0124)

Фильтр «Тип ТС» принимает несколько позиций сразу. Миграций нет, но релизы разведены и порядок не
переставляется:

| Шаг | Что везёт                                                                         | Меняет поведение        |
| --- | --------------------------------------------------------------------------------- | ----------------------- |
| A   | сервер принимает `classifications` наравне со старой парой; обе формы сразу — 400 | нет: портал ещё не шлёт |
| B   | портал: множественный выбор в «Заявках», «Истории», «На объекте», «Гараже»        | да — это и есть фича    |

Календарного окна между A и B не требуется: любое сочетание контейнеров согласовано, и откат

**Проверка после B:** в «Заявках» выбрать две позиции разных типов — в выдаче строки обоих, цифры
сводки над таблицей относятся к той же выборке; на телефоне тот же набор виден в шите «Фильтры» и
считается одним заданным фильтром.

### Разовый шаг: сверка перевода ролей (этапы 8 и 9, ADR 0113)

Упраздняемые роли переводятся тремя релизами каждая (план §13.2): **prepare** выдаёт замещающие
наборы держателям старой роли и закрывает вход в неё, **migrate** переводит учётки одним `UPDATE`,
**cleanup** убирает роль из кода. Выкачен пока prepare — миграции `0154` (снимок
`user_role_migration`), `0155` (площадка) и `0156` (отдел). Ручной шаг у него один и запускается
**дважды**:

```bash
# 1. Сразу после наката prepare: между миграцией и перезапуском работала версия, которая старую
#    роль ещё принимала, и заведённая в эти минуты учётка осталась без снимка.
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api check:role-migration
# 2. Непосредственно перед выкатом migrate — как условие выката: за релиз между шагами могли
#    отозвать взведённое назначение или сменить кому-то роль руками.
```

Скрипт считает по каждой учётке старой роли два субъекта — сегодняшний и завтрашний, — и печатает
разницу **поимённо**. Считает он рабочим кодом: права наборов берёт то же выражение, которым их
считает принципал, а складывает источники та же матрица; отличается второй субъект ровно одной
ролью. Код возврата 0 означает «перевод ничего не меняет ни у кого».

Виды отказа и решение по каждому:

- **снимка нет** — учётка заведена на старой роли после наката prepare (окно деплоя) либо роль
  правили в базе руками. Перевод идёт по снимку и такую учётку пропустит, а роль к тому времени
  уже никого не пустит. Лечится повторным накатом посевных запросов `0155`/`0156` — они
  идемпотентны (`ON CONFLICT DO NOTHING`) и добирают только недостающее;
- **права теряются** — взведённое назначение отозвали в реестре выдач. Вернуть выдачей набора не
  выйдет: старой роли набор не совместим намеренно (иначе визу объекта можно было бы выдать
  рядовому штабу), поэтому лечится тем же повторным накатом посева;
- **права появляются сверх объявленного** — расширение, которого заказчик не решал: разбирать до
  перевода. Объявленное расширение (комендант получает оргтехнику, решение №1) отказом не
  считается и печатается отдельной строкой с числом учёток;
- **снимок разошёлся с учёткой** — роль сменили руками между шагами. Перевод пропустит её по
  условию `WHERE u.role = m.role_before`; такие учётки разбираются поимённо, а не переписываются.

**Взведённые назначения выглядят в реестре выдач как «ждёт перевода роли», и это норма.** Права по
ним не идут — их даёт роль, — а гейт совместимости откроется в момент перевода. Отзыв такой строки и
есть единственный способ испортить перевод: сверка называет пострадавших поимённо.

**Откат prepare** — снятие посеянного, в порядке внешнего ключа: сначала `DELETE FROM user_grants
WHERE origin = 'migration'` по снимкам этапа, затем сами снимки. Прав это ни у кого не отнимает: до
перевода назначения не действуют. Откат кода безопасен сам по себе — снимок и назначения предыдущая
версия просто не читает.

#### Релиз migrate (этапы 8 и 9)

Файлы: `pending/stage8-migrate-site-role.sql`, `pending/stage9-migrate-department-role.sql`.
Ехать могут одним релизом или разными — этапы независимы, снимок различает их номером.

Условие выката, все три пункта:

1. **этап 7 выкачен** (адресация рассылок правом, ADR 0111) — иначе перевод трёх площадочных ролей
   в одну сольёт три аудитории рассылок в одну. Для этапа 9 пункт не нужен;
2. **prepare выкачен предыдущим релизом и приложение перезапущено**: вход в упраздняемые роли
   закрыт, новых держателей без снимка не появляется;
3. **сверка возвращает 0 — прогнанная сейчас, а не после prepare:**

```bash
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api check:role-migration
```

За релиз между шагами могли отозвать взведённое назначение или сменить кому-то роль руками; разбор
каждого вида отказа — в разделе про prepare выше. Ненулевой код — не выкатывать.

Что делает миграция: `UPDATE users SET role = m.role_after` по снимку с условием
`WHERE u.role = m.role_before`, отметка `migrated_at` тем же оператором через `RETURNING`, и
`auth_version + 1` переведённым. Права не меняются ни у кого, кроме объявленного расширения
(комендант получает оргтехнику, решение №1): наборы, которые их сохраняют, выданы релизом раньше и
начинают действовать ровно в момент смены роли.

**`auth_version + 1` — не разлогин.** Сервер роль из токена не берёт вовсе (принципал читает базу на
каждом запросе); гасится клиентский снимок роли и прав из `/auth/me`. Портал получает 401 «токен
устарел», молча дёргает `/refresh` и повторяет запрос — по одному лишнему обмену на переведённую
учётку. Без этого бывший комендант не увидел бы оргтехнику до истечения токена.

**Миграция роняет деплой, если на упраздняемой роли кто-то остался** (предохранитель после
`UPDATE`, прецедент — `0074`). Пройти мимо перевода может только учётка без снимка, заведённая в
минуты между накатом prepare и перезапуском. Лечение — повторный накат посевных запросов
`0155`/`0156` (идемпотентны, `ON CONFLICT DO NOTHING`), затем повторный деплой. Миграции катятся до
перезапуска, поэтому отказ оставляет работать прежнюю версию на прежней схеме — то самое состояние,
из которого шаг повторяют.

**Проверка после выката** — та же сверка плюс витрина «Права»: у каждой переведённой учётки набор
прав тот же, что был вчера, кроме объявленного расширения.

**Откат migrate** — тем же снимком и так же условно:

```sql
UPDATE users u SET role = m.role_before, auth_version = u.auth_version + 1, updated_at = now()
  FROM user_role_migration m
 WHERE m.user_id = u.id AND m.stage = 8 AND m.migrated_at IS NOT NULL
   AND u.role = m.role_after;
UPDATE user_role_migration SET migrated_at = NULL WHERE stage = 8;
```

Условие `u.role = m.role_after` обязательно: учётка, которой роль сменили руками уже после перевода,
в откат не попадает и разбирается отдельно. Взведённые назначения откат не снимает — они
принадлежат prepare и просто снова перестают действовать.

#### Релиз cleanup (этапы 8 и 9) — последний, и после него откат перевода невозможен

Файлы: `pending/stage8-cleanup-site-role.sql`, `pending/stage9-cleanup-department-role.sql`. **Едут
одним коммитом с правками кода** — половинки одного утверждения:

| Где                                        | Что                                                                                                                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `packages/contracts/src/enums.ts`          | `ROLES` без четырёх ролей; подписи из `roleLabels` → `ARCHIVED_ROLE_LABELS`; строки уходят из `roleColors`, `OBJECT_SCOPED_ROLES`, `DEPARTMENT_SCOPED_ROLES`                               |
| `packages/contracts/src/role-addons.ts`    | `shtab` уходит из `ROLE_ADDON_BASE_ROLES` обоих оргтехнических наборов                                                                                                                     |
| `packages/contracts/src/permissions.ts`    | строки упразднённых ролей из `ROLE_PERMISSIONS`, `ROLE_VEHICLE_REQUEST_TYPES`, `ROLE_STATUS_TRANSITIONS`                                                                                   |
| `packages/contracts/src/role-migration.ts` | модуль уходит целиком вместе с пятью читателями: `retiringRoleIssue` в `routes/users.ts`, `isRetiringRole` в `UsersTab.tsx`, `roleMigrationOf` в `grantModel.ts` и `userAccountLabels.tsx` |
| `apps/api/src/check-role-migration.ts`     | сверка и её строка в `package.json`: сверять больше нечего                                                                                                                                 |

Оставлять `ROLE_MIGRATIONS` пустым нельзя: пометка «ждёт перевода роли» в реестре выдач считается по
нему, а строки `user_grants` с `origin = 'migration'` живут вечно — после перевода они означают
действующий набор, и вечно-мёртвая ветка врала бы про них при первом же взгляде.

Составлять список руками не придётся: `Role` — закрытое объединение, и компилятор назовёт каждое
место сам. Портал списков ролей не держит вовсе — он берёт их из `ROLES`.

**Одно место компилятор назовёт, но решение оставит человеку — `roleEnum` в
`apps/api/src/db/schema.ts`.** Он описывает тип в базе, а тот значения сохраняет: на них держится
`user_role_migration.role_before`. Убрать их из `roleEnum` — значит типизировать снимок ложью;
оставить — значит получить объединение шире, чем `Role`, и ошибку компилятора на
`role: u.role` в `loadPrincipal`. Предпочтительно второе: `roleEnum` остаётся полным, а сужение
делается на границе «база → код» — тем же приёмом, которым `isPermission` отсеивает право-сироту
(`grantPermissionsByUserIds`). Подпись для значения, не прошедшего сужение, уже есть — `roleTitle`
в контрактах (заведён 18.08.2026 вместе с `ARCHIVED_ROLE_LABELS`).

Условие выката:

1. **migrate выкачен предыдущим релизом** и приложение перезапущено;
2. `SELECT count(*) FROM users WHERE role IN ('shtab','rukstroy','commandant','department_head')`
   — ноль (предохранитель миграции проверяет это сам и роняет деплой, но узнать заранее дешевле);
3. `SELECT count(*) FROM user_role_migration WHERE migrated_at IS NULL` — ноль либо разобранный
   поимённо список: это учётки, которым роль меняли руками, и после cleanup возвращать их будет
   некуда.

Что делает SQL: снимает строки `grant_roles` с упразднёнными ролями — и системные (две:
`office_equipment_operator` и `office_equipment_it_approver` × `shtab`), и пользовательские, куда
prepare дописал целевую роль рядом. Значения enum в базе **не удаляются** (`ALTER TYPE ... DROP
VALUE` не существует, а пересоздание типа задевает `users.role` и `mailing_schedule_roles.role` и
требует необратимого выката): они остаются мёртвыми, и на них держится
`user_role_migration.role_before` — единственный ответ на «кем человек был».

**Почему вычитание `grant_roles` не в migrate, хотя соблазн велик.** Какие пользовательские наборы
были собраны под старую роль, нигде не записано: prepare добавлял целевую роль, а не запоминал,
кому добавил. Сними строку раньше — и откат перевода вернул бы человека на `shtab` уже без прав его
набора, молча. Между migrate и cleanup откат ещё разрешён, поэтому вычитание ждёт релиза, в котором
роль исчезает насовсем.

**Откат cleanup** — обычный откат кода: схема после него ровно та же, ни одного значения enum не
удалено. Необратимо не хранилище, а знание: строки `grant_roles` восстановить неоткуда, поэтому
откат **перевода** после cleanup означает ручной разбор пользовательских наборов.

## Загрузка файлов (S3 / CORS)

Файлы грузятся **напрямую в cloud.ru** по presigned PUT: браузер (origin `https://auto.su10.ru`)
делает PUT на `https://s3.cloud.ru/<bucket>/<key>`. **nginx и Fastify в этом запросе не участвуют** —
preflight (OPTIONS) обрабатывает cloud.ru. Поэтому CORS настраивается **на бакете**
(`docs/setup-infra.md §3`), а не в nginx/Fastify. Архитектуру на проксирование файлов через API
не менять — файлы до 50 МБ идут прямо в S3.

Симптом `No 'Access-Control-Allow-Origin' header` при загрузке — обычно одно из:

1. **`S3_FORCE_PATH_STYLE=false`** → URL вида `https://<bucket>.s3.cloud.ru/...`. cloud.ru отдаёт на такой
   host `403 AccessDenied` вообще на всё, включая preflight, и **без** `Access-Control-*` заголовков —
   браузер показывает это как ошибку CORS, хотя политика бакета корректна. Поставить `true` (см. env ниже);
2. presigned URL содержит `x-amz-checksum-crc32` / `x-amz-sdk-checksum-algorithm` (авто-checksum AWS SDK) —
   **исправлено в коде** (`apps/api/src/lib/s3-client.ts`); убедиться, что задеплоена свежая версия;
3. на бакете нет/некорректна CORS-политика — настроить (`aws s3api put-bucket-cors`, см. setup-infra §3);
4. runtime использует не тот bucket/endpoint — проверить env (ниже).

Отличить (1) от (3) можно за один запрос: preflight на path-style URL отвечает `200` + CORS-заголовками,
на virtual-hosted — `403` без них (см. «Проверка preflight» ниже).

### Проверка runtime-окружения (без секретов)

```bash
docker exec technic-api sh -lc \
  'env | grep -E "^(PUBLIC_ORIGIN|S3_ENDPOINT|S3_REGION|S3_BUCKET|S3_FORCE_PATH_STYLE)="'
```

`S3_FORCE_PATH_STYLE` должен быть `true`. Если значения не совпадают с ожидаемыми — поправить
`/etc/technic-portal/prod.env`. **Изменение `prod.env` требует пересоздания контейнеров**
(restart/reload не перечитывает `env_file`):

```bash
docker compose -f deploy/docker-compose.yml -p technic up -d --force-recreate technic-api technic-worker
```

### Проверка preflight (CORS) напрямую к бакету

`$UPLOAD_URL` — presigned PUT из ответа `POST /api/v1/files/upload-session`:

```bash
curl -i -X OPTIONS "$UPLOAD_URL" \
  -H 'Origin: https://auto.su10.ru' \
  -H 'Access-Control-Request-Method: PUT' \
  -H 'Access-Control-Request-Headers: content-type'
```

Ожидаемый ответ (`200`/`204`) содержит:

- `Access-Control-Allow-Origin: https://auto.su10.ru`
- `Access-Control-Allow-Methods: PUT` (или список с PUT)
- `Access-Control-Allow-Headers: content-type`
- `Access-Control-Max-Age: 3600`

`403 AccessDenied` без `Access-Control-*` и с host `<bucket>.s3.cloud.ru` → virtual-hosted-style,
чинится `S3_FORCE_PATH_STYLE=true`. Ответ без CORS-заголовков на **path-style** URL → проблема
в CORS-политике бакета, а не в приложении.

### Метрики почты (`GET /metrics` на `technic-api:3000`)

Формат — текстовый Prometheus. Наружу маршрут не проксируется: снаружи проходит только `/api/`.

Почта — единственная часть портала, которая работает без человека: письмо составляется ночью,
отправляется фоном и о своей неудаче никому не рассказывает. Ошибку в интерфейсе кто-нибудь заметит
и позвонит; молчащую рассылку — нет, и узнают о ней тогда, когда водитель не приедет. Отсюда набор:

| Метрика                                     | Что показывает                                          | Когда тревожить                  |
| ------------------------------------------- | ------------------------------------------------------- | -------------------------------- |
| `technic_mail_messages{status="failed"}`    | Письма, которые уже не уйдут (без отладочных)           | любой рост                       |
| `technic_mail_messages{status="pending"}`   | Ждут очереди                                            | не убывает дольше получаса       |
| `technic_jobs{status="dead"}`               | Задачи, исчерпавшие попытки                             | любой рост                       |
| `technic_mailing_runs_24h{status="failed"}` | Упавшие запуски рассылок за сутки                       | больше нуля                      |
| `technic_mailing_schedules_overdue`         | Включённые расписания, чьё время прошло 10+ минут назад | больше нуля — планировщик молчит |

Последняя метрика — главная для рассылок: штатный запуск сдвигает время сразу, поэтому её рост
означает, что worker не тикает или не достучался до API (`INTERNAL_API_TOKEN`, `INTERNAL_API_URL`).

Отладочные письма (`is_test`) из счётчиков исключены: проверка вёрстки не должна читаться как сбой
доставки.

## Почта: очередь и разбор жалоб «письмо не пришло»

Письмо составляет API и кладёт в `mail_messages` вместе с задачей `send_email` — одной транзакцией.
Отправляет `technic-worker`: он же ограничивает частоту (`MAIL_MAX_PER_MINUTE`) и проставляет
результат. Тело письма хранится готовым, поэтому повтор отправляет ровно то, что было составлено.

Состояния письма: `pending` — ждёт очереди, `sent` — принято SMTP-сервером (в `sent_at` время, в
`provider_id` идентификатор у провайдера), `failed` — не уйдёт уже никогда.

```bash
# Что не отправлено прямо сейчас и почему
psql "$DATABASE_URL" -c "select kind, status, to_email, subject, last_error, created_at
  from mail_messages where status <> 'sent' order by created_at desc limit 20;"

# Письма конкретному человеку — первый вопрос при «мне ничего не приходило»
psql "$DATABASE_URL" -c "select kind, status, sent_at, provider_id, last_error
  from mail_messages where to_email = 'ivanov@example.ru' order by created_at desc limit 20;"

# Очередь отправки: задачи, которые ещё не выполнены
psql "$DATABASE_URL" -c "select status, count(*) from jobs where type = 'send_email' group by 1;"
```

Что означают состояния и что делать:

- **`pending` дольше нескольких минут, задача `pending` с далёким `next_run_at`** — упёрлись в
  потолок отправки: рассылка растянута во времени намеренно. Проверить `MAIL_MAX_PER_MINUTE` против
  тарифа провайдера.
- **`pending`, а задач `send_email` нет вовсе** — почта выключена (`MAIL_ENABLED=false`) либо worker
  не поднялся. Письма дождутся включения: задача откладывается, а не тратит попытки.
- **`failed` с текстом ответа SMTP 5xx** — окончательный отказ: адрес не существует, домен не
  принимает почту, отправитель отвергнут. Повторять бессмысленно, надо чинить адрес: у водителя — в
  карточке справочника, у пользователя — в его учётке.
- **`failed` после исчерпания попыток** — временные отказы не кончились: смотреть `last_error` и
  доступность провайдера.
- **письмо `sent`, но человек его не видит** — искать в спаме и проверять DNS домена отправителя
  (`docs/setup-infra.md`, п. 5.1): просроченный или отсутствующий DKIM/SPF выглядит именно так.

Секретов в журнале нет: тела auth-писем содержат ссылку с одноразовым токеном, поэтому доступ к
содержимому писем даётся отдельно от обычного администрирования, а в логи тело не пишется.

**Проверить доставку руками.** Администрирование → **Рассылки** → «Отладочная отправка»: тип
письма и получатель из числа действующих администраторов (право `mailings.manage`). Письмо уходит
по-настоящему — с пометкой `[ТЕСТ]` в теме и недействительными ссылками, — но помечено `is_test` и
в статистику запусков не попадает. Каждая отправка пишется в аудит как `mailing.test_sent`. Этим и
проверяется боевая настройка после правки DNS или смены SMTP-провайдера:

```bash
# Отладочные письма за сутки: что отправляли и чем кончилось
psql "$DATABASE_URL" -c "select kind, to_email, status, last_error, created_at from mail_messages
  where is_test and created_at > now() - interval '1 day' order by created_at desc;"
```

## Рассылки по расписанию

Расписания заводит администратор: **Администрирование → Рассылки** (право `mailings.manage`).
Часы держит `technic-worker`: раз в минуту (`MAILING_TICK_INTERVAL_MS`) он спрашивает у API, чьё
время наступило, и просит выполнить запуск — сборка письма живёт в API, где есть права и область
видимости получателя (ADR 0075).

Для этого worker'у нужны две переменные в `/etc/technic-portal/prod.env`: `INTERNAL_API_TOKEN`
(общий секрет, одинаковый у API и worker) и `INTERNAL_API_URL` (по умолчанию
`http://technic-api:3000`). Без токена планировщик молчит, а `/internal/mail/*` отвечает `401`.
Наружу этот префикс не проксируется — во фронтовом nginx стоит явный `return 404`.

Что важно знать при разборе:

- **Двойной рассылки не бывает** даже при двух worker'ах: запуск уникален парой
  «расписание + назначенное время», второй экземпляр получает отказ и не делает ничего.
- **Повтор запуска безопасен**: ключ письма включает идентификатор запуска, поэтому повторное
  выполнение не создаёт новых писем. Упавшую рассылку можно просто выполнить заново.
- **Границы данных зафиксированы** в самом запуске (`period_start`/`period_end`) — повтор возьмёт те
  же дни, а не пересчитает окно от момента повтора.
- **Статистика запуска** показывает не только отправленное: `withoutEmail` — водители с рейсами, но
  без адреса (пробел справочника), `excluded` — исключённые администратором, `empty` — те, у кого
  после вычета исключённых дат рейсов не осталось.

```bash
# Что и когда сработает дальше
psql "$DATABASE_URL" -c "select name, type, is_enabled, send_at, run_weekdays,
  window_from_days, window_days, next_run_at
  from mailing_schedules order by next_run_at nulls last;"

# История запусков с итогами
psql "$DATABASE_URL" -c "select planned_at, status, is_manual, stats, error
  from mailing_runs order by created_at desc limit 20;"

# Письма конкретного запуска
psql "$DATABASE_URL" -c "select to_email, status, sent_at, last_error
  from mail_messages where mailing_run_id = '<uuid>' order by created_at;"
```

Если рассылка не ушла: сперва `mailing_runs` (создан ли запуск и в каком он статусе), затем
`mail_messages` того же запуска (составлены ли письма), затем очередь `jobs` типа `send_email`.
Пустой `next_run_at` у включённого расписания означает, что срабатывать больше нечему — например все
дни выполнения попали в исключения.

### Ролевые сводки

Сводка (`role_digest`) собирается каждому получателю своя: таблицы одни и те же, а строки в них —
только те, что человек видит в портале под собой (ADR 0078, ADR 0093). Адрес в расписании отвечает
лишь на вопрос «кому отправлять» — и с ADR 0111 адрес этот **право**, а не имя роли
(`mailing_schedule_permissions`). Право считается эффективным: дала его должность или назначенный
набор (ADR 0106), для рассылки разницы нет.

- **Получатель обязан иметь подтверждённый адрес** — иначе он в рассылку не попадает вовсе.
- **Пустая сводка не отправляется** и считается в статистике запуска как `empty`: если эта цифра
  равна числу получателей, значит рассылка настроена на тех, кому нечего показать. А если в итогах
  нули по всем счётчикам сразу — получателей не нашлось вовсе, и первым делом надо смотреть, есть ли
  у расписания хоть одно право-адресат.
- **Содержание — две таблицы по действующим путевым листам**: перевозки (4-П и форма № 3, по дате
  рейса) и техника на объектах (ЭСМ-2, по пересечению недели листа с окном). Нет листа — нет
  строки: рейсы на арендной технике в сводке не видны ни строкой, ни счётчиком, потому что лист на
  неё выписывает арендодатель. На жалобу «в письме не все рейсы» смотреть надо сюда.
- **Окно смотрит вперёд**: `window_from_days` (0 — сегодня, 1 — завтра) и `window_days`. «За вчера»
  сводка больше не рассказывает — разделов событий нет.
- **Аудитория задаётся отбором, а не исключениями**: режимы `all`/`selected` в
  `scope_mode`/`recipient_mode` и перечни в `mailing_schedule_scopes` /
  `mailing_schedule_recipients`. Режим `selected` фиксирует набор: заведённая позже площадка и
  новый сотрудник в рассылку сами не попадут, их надо отметить руками.

**После выката миграции `0124` расписания сводок перечитать глазами.** Прежний период сводки был
ретроспективным («за вчера», «за прошлую неделю»), а содержание письма переписано целиком и говорит
теперь о будущем — сохранить смысл было нечем. Перенос выбрал умолчание по времени отправки:
утренние (до 12:00) — на сегодня, вечерние — на завтра, недельные — на 7 дней вперёд. Настройка
правдоподобная, а не эквивалентная: пока каждое расписание не перечитали, что именно уходит людям,
видно только из этой таблицы.

```bash
# Окно и аудитория каждой сводки после переноса
psql "$DATABASE_URL" -c "select name, send_at, run_weekdays, window_from_days, window_days,
  request_scope, scope_mode, recipient_mode, show_trips, show_onsite
  from mailing_schedules where type = 'role_digest' order by name;"
```

```bash
# Кому ушла сводка последнего запуска и с какой темой
psql "$DATABASE_URL" -c "select to_email, status, subject from mail_messages
  where kind = 'role_digest' and mailing_run_id = '<uuid>' order by created_at;"
```

#### Разовый шаг: сверка аудитории после переезда адресации на права (ADR 0111)

Миграция `0151` не только заводит `mailing_schedule_permissions`, но и **наполняет её по факту**:
для каждого расписания ищет право, дающее на живых данных ровно ту же аудиторию, что нынешний набор
ролей. Отдельным скриптом это сделать нельзя — он приезжает тем же образом, что и новый код, то есть
запустить его можно только после перезапуска, а до тех пор все расписания адресовались бы пустой
таблицей и молчали. Поэтому перенос идёт в миграции (она накатывается **до** перезапуска), а ручной
шаг после выката один — сверка:

```bash
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api check:mailing-audience
```

Скрипт считает «до» по прежним ролям, «после» по правам и сравнивает **поимённо**. Считает он рабочим
кодом рассылки, тогда как перенос считал то же равенство своим SQL: два независимых счёта одного
множества — в этом и смысл шага. Код возврата 0 означает «аудитория каждого расписания совпала».

Три вида отказа, и решение у каждого своё:

- **адресация не подобрана** — эквивалентного права нет, и расписание не пишет никому. Это не
  поломка переноса: аудитория роли выражается правом далеко не всегда («Штаб» как таковой не
  отделяется ни одним правом ни от «Отдела», ни от «Диспетчера»). Скрипт печатает, кому уходило до
  переезда, и ближайшие права с ценой каждого («потеряется N, добавится M»); **выбор — за
  заказчиком**, задаётся он в форме расписания. Приближение здесь означало бы менять список
  получателей молча;
- **аудитория разошлась** — право подобрано не то, письма пойдут не тем: имена обеих сторон в
  отчёте, править форму расписания надо до ближайшей вечерней рассылки;
- **право-сирота** — в таблице лежит строка вне словаря кода: адресация по ней молча не сработает.

Строку `отбор без гейта модуля изменился: −N / +M` отказом считать не надо: это люди, которым письмо
не составлялось и не составится (у них нет `vehicleRequests.read`), — счётчик кандидатов в форме
расписания из-за них станет другим, и знать об этом надо заранее.

`mailing_schedule_roles` миграция **не трогает**: пока строки на месте, откат этапа — обычный откат
кода, а сверка умеет сопоставить обе адресации. Удаляет таблицу отдельная миграция релизом позже.

## Подтверждение адреса при регистрации

Заявка на регистрацию заводится неподтверждённой, и письмо со ссылкой уходит в той же транзакции
(ADR 0072). Пока адрес не подтверждён, активация отклоняется — администратор видит это в колонке
«Адрес» списка пользователей.

- Ссылка подтверждения живёт `MAIL_VERIFY_TTL_SECONDS` (сутки), ссылка сброса пароля —
  `MAIL_RESET_TTL_SECONDS` (час). Оба значения в `/etc/technic-portal/prod.env`.
- Повторное письмо человек запрашивает сам на `/verify-email`: не чаще одного на учётку за пять
  минут и пяти запросов с адреса за десять.
- Заявка, не подтверждённая за `MAIL_REGISTRATION_EXPIRY_DAYS` (по умолчанию 7 дней), уходит в
  архив — адрес освобождается, и человек регистрируется заново. Ноль и меньше выключают закрытие.
- Ручного обхода подтверждения нет. Если письмо до человека не доходит, учётку заводит
  администратор — такая считается подтверждённой по факту создания.
- При `MAIL_ENABLED=false` саморегистрация отвечает `503`: заявку, которую невозможно подтвердить,
  портал не заводит.

```bash
# Заявки, ждущие подтверждения адреса
psql "$DATABASE_URL" -c "select email, created_at from users
  where deleted_at is null and role is null and email_verified_at is null order by created_at;"

# Ушло ли письмо конкретному человеку и что ответил SMTP
psql "$DATABASE_URL" -c "select kind, status, sent_at, last_error from mail_messages
  where to_email = 'ivanov@example.ru' order by created_at desc limit 5;"
```

## Срок хранения отклонённых заявок на регистрацию

`technic-worker` раз в час (`WORKER_CLEANUP_INTERVAL_MS`) сносит из архива учётки, которым отказали
в регистрации: те, что лежат в архиве дольше срока, без роли и неактивны (ADR 0063). Учётки
работавших сотрудников уборка не трогает — их держат внешние ключи, и срока хранения у них нет.

- `USER_REJECTED_REGISTRATION_TTL_DAYS` в `/etc/technic-portal/prod.env` — срок в днях, по
  умолчанию **7**. Ноль и меньше выключают уборку.
- Пока отказ в архиве, его можно вернуть в очередь: карточка учётки → **Восстановить** (право
  `archive.restore`). После уборки восстанавливать нечего.
- След остаётся в журнале: `user.purge_expired` с адресом и сроком, без актора — удалил срок, а не
  человек. Ручное удаление администратором пишется как `user.purge`.

```bash
# Сколько заявок ждёт уборки прямо сейчас
psql "$DATABASE_URL" -c "select count(*) from users where deleted_at < now() - interval '7 days' and role is null and is_active = false;"
```

## Наполнение справочника водителей

Кадровая выгрузка приезжает JSON-файлом и в git не попадает: ФИО, дата рождения и СНИЛС живых
людей в репозитории не хранятся (ADR 0037 п. 12–13).

**Наполняют только из портала, доступ к серверу не нужен** (ADR 0047). Справочники → Водители →
**Загрузить выгрузку**: портал разбирает файл и показывает, кого заведёт (база при этом не
меняется), заведение — вторым шагом. Право то же, что у заведения водителя руками
(`drivers.write`). Ошибка в файле объясняется дословно — «Петров Пётр: СНИЛС … не проходит
проверку контрольной суммы», — и чинится в самом файле. Формат файла, разбор отчёта и частые
отказы — в [инструкции](guide-staff-import.md).

Пути через сервер нет: файл на VPS не кладут, деплой справочник не наполняет и `seed:drivers`
больше не существует. Повторная загрузка того же файла ничего не дублирует — ключ человека
СНИЛС, заведённые пропускаются.

Загрузка заводит физлицо, специализацию «Водитель», трудовое отношение и удостоверение с
категориями. Серия, номер и сроки удостоверения в кадровой выгрузке отсутствуют — они остаются
пустыми, документ помечен `unverified`. Такой водитель в отбор под машину попадает (пустой срок
отбор читает как бессрочный), но графа «номер удостоверения» в путевом листе печатается пустой.
Реквизиты вносит администратор в карточке водителя: **Добавить удостоверение** с настоящими
данными, затем **Аннулировать** временное — иначе человек покажется в списке выбора дважды.
