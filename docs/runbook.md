# Runbook (эксплуатация)

Прод: VPS `89.232.188.170`, каталог `/opt/portals/technic`, compose-проект **`technic`**,
публичный URL **https://auto.su10.ru**. Edge: контейнер `infra-nginx` + vhost
`/opt/infra/nginx/conf.d/technic.conf`. Секреты: `/etc/technic-portal/prod.env`
(вне git). На VPS есть другие проекты — не трогать их compose/vhost и не запускать
глобальные destructive-команды.

## Деплой (`deploy-auto`)

Штатный деплой — одной командой `deploy-auto` (из любого каталога VPS; симлинк в
`/usr/local/bin`, скрипт — `deploy/deploy-auto.sh`). Делает: `git pull` ветки **main**
(с проверкой `HEAD == origin/main`) → сборку `technic-*:<sha>` → бэкап БД перед миграциями →
авто-накат новых миграций → `up -d` → health-гейт `:latest`. Portal-scoped: соседние
порталы/`infra-nginx` не трогает, `docker rmi` — только по whitelist `technic-*`, без
`docker system prune -a`/`down --volumes`.

```bash
deploy-auto                 # обычный деплой (main): pull → build → миграции → up → health
deploy-auto --skip-migrate  # деплой кода без наката миграций (даже если есть pending)
deploy-auto --previous      # быстрый откат кода на предыдущий SHA (без пересборки); схему НЕ трогает
deploy-auto --restore-db    # восстановление БД из последнего дампа (destructive, TTY-подтверждение)
deploy-auto --status        # read-only: релизы, образы, статус миграций, бэкапы, диск
deploy-auto --no-prune      # без чистки образов/кэша (ротация бэкапов — всегда)
deploy-auto --cutover       # необратимый выкат с остановкой записи (протокол, см. ниже)
deploy-auto --cutover-revert # откат незавершённого cutover, пока граница не записана
```

**Git-流:** деплоится только ветка **main**; перед деплоем код должен быть в `origin/main`
(скрипт откажет при ветке ≠ main или `HEAD ≠ origin/main` → `git checkout main` + push).

**Обновление самого скрипта:** `deploy-auto` стоит симлинком в рабочее дерево и пуллит сам
себя, поэтому после pull он перезапускается новой версией и продолжает деплой ею — правки в
`deploy/deploy-auto.sh` вступают в силу тем же деплоем. Без перезапуска запущенный bash дочитывал
бы старый файл через открытый дескриптор (git обновляет файл заменой inode), и деплой, привёзший
новый шаг, шёл бы по предыдущей версии — молча, без единой ошибки в выводе.

**Бэкапы (keep-2):** перед накатом миграций — `pg_dump -Fc` в
`/var/lib/technic/deploy/db-backups` (2 последних `<utc>-<sha>.dump` + `.meta`, плюс 1
аварийный `prerestore-*`); снимок `prod.env`+CA+vhost в `config-backups` (2 последних).
Ротация идёт всегда, даже при `--no-prune`. Бэкапы содержат ПДн/секреты — каталоги 700/600.

`.meta` несёт не только метки времени и коммита, но и **точный состав применённых миграций**
(`migrations_count`, `migrations_sha256` и строки `migration=`) — по нему сверяется дамп при
восстановлении (см. «Гейты отката»). Дамп с файлом `<дамп>.pin` рядом **закреплён**: его ставит
`--cutover` на предмиграционный дамп, и keep-2 такой дамп не считает и не удаляет. Снимать
закрепление руками (`rm <дамп>.pin`) можно только осознанно: это единственный дамп, к которому
откат ещё разрешён. Рядом с закреплённым дампом лежат `<дамп>.release.state` и
`<дамп>.schema-floor.state` — снимок состояния на момент записи границы.

**Откат:** `--previous` возвращает прошлый код без пересборки, но схему НЕ откатывает;
согласованный откат — `deploy-auto --previous --restore-db`. Важно: `pg_restore --clean`
не гарантирует полный откат схемы (объекты новее дампа могут остаться) — authoritative
schema-откат — **Yandex Managed PG PITR** (метку времени печатает `--restore-db`). Отсюда
правило: **миграции backwards-compatible** — после применённых миграций/`up -d` скрипт
авто-отката кода НЕ делает.

**Гейты отката (протокол выката §4–§5).** Оба разрушительных режима теперь fail-closed и молча не
проходят:

- **нет или повреждён `/var/lib/technic/deploy/schema-floor.state`** — `--previous` и `--restore-db`
  отказывают целиком. Файл заводится **однократно** обычным деплоем и дальше только дополняется,
  поэтому его отсутствие означает потерю границы, а не «границ не было». Чинится восстановлением из
  снимка конфига (`config-backups/config-*.tar.gz`, файлы лежат в корне архива), а не
  переинициализацией — её нет ни под каким флагом;
- **`--previous` ниже границы** — если целевой образ не содержит какой-то миграции из `floors`,
  откат отклоняется навсегда: этот код не умеет жить с такой схемой;
- **`--restore-db`** принимает только дамп, чей состав миграций **в точности равен** составу
  целевого образа, содержит все границы и не старше текущей схемы. Дамп без `.meta` (снят версией
  скрипта до протокола) не принимается вовсе — для него остаётся PITR.

Текущее состояние обоих файлов показывает `deploy-auto --status` (строки `cutover` и `схема`).

**Отметки перехода к заморозке склада** (план чеков на автозапчасти, Р27/Р28). Рядом с
`release.state` лежат ещё три файла состояния, и все три ведёт сам скрипт:

- `last_healthy.sha` — SHA последнего релиза, чей health был **зелёным**. Пишется в каждом месте,
  где переставляется `:latest` (обычный выкат, `--previous`, `--cutover`), и отвечает на вопрос, на
  который `release.state` не отвечает: тот записывается после `up -d`, но **до** health, то есть
  знает «что запущено», а не «что оказалось здоровым»;
- `freeze.transition` и `freeze.done` — переход к безмиграционному выпуску «Заморозка» начат и
  завершён. Обе сверяются с журналом миграций на каждом деплое, поэтому PITR их не обманывает:
  отметка, которую журнал не подтверждает, снимается сама, а законное состояние восстанавливается
  само. Создавать их руками нельзя ни при каком отказе — отметка доказывает, что переход вёл скрипт
  при выполненном предусловии, а созданная руками доказывала бы только терпение создавшего.

В рабочем дереве им отвечают два файла, и оба снимаются **коммитом**, а не руками:
`deploy/no-new-migrations.marker` (выпуск объявлен безмиграционным — деплой откажет, если появилась
хоть одна неприменённая миграция или если каталог `apps/api/drizzle/` изменился с развёрнутой
ревизии; `--cutover` такому выпуску запрещён вовсе) и `deploy/requires-frozen-release.list` (имена
миграций, которым нужна уже развёрнутая и здоровая «Заморозка»; пока переход не завершён,
`--cutover` тоже отказывает). Маркер удаляет тот же коммит, который привозит миграции, — забыть
снять его невозможно по построению.

### Необратимый выкат (`--cutover`)

Режим для миграций, которые **меняют смысл данных** и потому не переживают «старый код на новой
схеме»: обычный деплой накатывает миграции до перезапуска, и старый код какое-то время пишет по
старым правилам. Нормативное описание — [протокол выката](schema-cutover-protocol.md); здесь только
команды. Параметры своего релиза (какая миграция, какой верификатор, какой teardown) даёт план этого
релиза.

Что обязано быть сделано **до** запуска:

1. **репетиция на копии базы** по чек-листу протокола §9 — без неё выкат не начинается;
2. в релизе ровно **одна** неприменённая миграция (§6): чужая рядом — отказ ещё до остановки
   сервисов, её выкатывают обычным деплоем первой;
3. релиз привёз `apps/api/teardown/<миграция>.sql` (обратная миграция) и
   `apps/api/teardown/<миграция>.sql.verify` (строка с командой-верификатором). Нет любого из них —
   отказ до остановки сервисов: без верификатора не проверить данные, без teardown невозможен откат.

```bash
deploy-auto --cutover        # pull → build → сверка бандла → стоп api/worker → дамп (закреплённый)
                             # → миграция → верификатор → ГРАНИЦА → up -d → health → архив состояния
deploy-auto --status         # где мы сейчас: строка cutover показывает фазу
```

Идёт всё **с остановкой записи**: `technic-api` и `technic-worker` лежат от дампа до подъёма,
снаружи это 502. `technic-web` остаётся поднятым намеренно — честная ошибка лучше белого экрана.

**Повтор безопасен и является штатным способом продолжить.** После любого обрыва (упал верификатор,
умер контейнер, Ctrl-C, разорвался ssh) повторный `deploy-auto --cutover` сверяет журнал миграций,
границу и фазу и пропускает сделанное. Продолжают **тем же коммитом**: чужой SHA — отказ.

Что делать по фазе, если что-то пошло не так:

| Фаза в `--status`      | Где мы                       | Что делать                                                                         |
| ---------------------- | ---------------------------- | ---------------------------------------------------------------------------------- |
| `migrating`            | миграция накатывается        | повторить `--cutover`                                                              |
| `migrated`             | схема новая, границы ещё нет | вперёд — `--cutover`; назад — `--cutover-revert` (единственное окно для отката)    |
| `irreversible`, `done` | граница записана             | только вперёд: `--cutover` (повторит health) либо обычный `deploy-auto` нового SHA |
| нет активного выката   | всё закрыто                  | обычный `deploy-auto`                                                              |

**Health не подтвердился — выкат не заперт.** Схема уже новая, поэтому обычный `deploy-auto` с
исправленным кодом разрешён и ничего не обходит: он выкатывает следующий код на ту же схему и
закрывает состояние выката как `superseded`. Повтор `--cutover` прогоняет health заново.

**Откат — только до записи границы:**

```bash
deploy-auto --cutover-revert   # teardown релиза + возврат сервисов на прежний тег
```

Разрешён тогда и только тогда, когда фаза ровно `migrated` **и** миграции ещё нет в
`schema-floor.state`. Дополнительно проверяются: сервисы остановлены, применённый набор совпадает с
бандлом, посторонних миграций нет, закреплённый дамп на месте, образ кандидата не вычищен
ретеншном. После `irreversible` откат отклоняется навсегда — дальше PITR либо ремонт вперёд.

**Граница совместимости** живёт в `/var/lib/technic/deploy/schema-floor.state` и переживает всё:
архивирование состояния выката, следующие релизы, перенос площадки (файл едет в снимке конфига).
Она и есть «ниже этой миграции откатываться нельзя» — см. «Гейты отката» выше. Руками файл не
правят.

**Teardown руками не запускают.** `pnpm --filter @technic/api db:cutover-down <миграция.sql>` не
проверяет ни фазы, ни границы — он снимает схему и запись журнала одной транзакцией и предназначен
`deploy-auto` и репетиции на копии базы. У человека для этого есть `--cutover-revert`.

### Режим технических работ (`--maintenance`)

Окно, в котором портал **закрыт объявлением**, а не выглядит сломанным. Отвечает на вопрос «открыт
ли портал вообще» и не заменяет ни `--cutover` (тот отвечает «можно ли откатиться»), ни гейт версии
клиента, ни заморозку модуля. Нормативное описание — [план режима](maintenance-mode-plan.md).

```bash
deploy-auto --maintenance          # состояние: три канала порознь, ничего не меняет
deploy-auto --maintenance=on --reason='Миграция схемы: перенос ездок' --until='2026-09-04T03:00Z'
deploy-auto --maintenance=off      # снять режим
```

Включение делает три вещи одной командой: кладёт объявление в
`/etc/technic-portal/maintenance/maintenance.json` (веб отдаёт его как `/maintenance.json`), ставит
в `prod.env` `MAINTENANCE_MODE=on` (гейт `api` отвечает `503 maintenance_mode`) и поднимает
`AUTH_EPOCH_SINCE` — **все выданные access-токены мертвы**. Refresh-сессии при этом живут:
`/auth/refresh` и `/auth/logout` из-под гейта выведены насовсем, поэтому после снятия режима люди
продолжают работу **без пароля и без капчи**, уже с токеном новой эпохи.

**Сквозь режим не проходит никто** — ни `admin`, ни именное полномочие. Запереть себя внутри
нельзя: выключатель живёт снаружи портала. Данные в окне проверяют доступом
`DATABASE_MAINTENANCE_URL` (`docker compose … run --rm`), а не входом в интерфейс.

#### Порядок работ в окне

1. **пол клиента поднят** до контракта раздаваемой сборки: `deploy-auto --client-floor` покажет оба
   числа. Иначе `--maintenance=on` откажет — заглушку рисует только новая сборка, и вкладки старее
   увидят в окне сетевые ошибки вместо объявления. Отказ снимается либо подъёмом пола
   (`deploy-auto --client-floor=N`), либо явным `--allow-old-clients`, и тогда команда громко
   печатает, что часть вкладок останется без объявления;
2. `deploy-auto --maintenance=on --reason='<что делаем>' --until='<когда>'` — портал закрыт;
3. **при необходимости** — `docker compose -p technic stop technic-worker`. Режим воркер **не
   гасит намеренно**: фоновые задачи гасятся своим порядком, остановкой контейнера в `--cutover`.
   Следствие принято осознанно — письма рассылок, ушедшие внутри окна, позовут человека в закрытый
   портал; если это не устраивает, воркер останавливают руками (и потом руками же поднимают:
   `docker compose -p technic start technic-worker`);
4. `deploy-auto --cutover` либо иная работа со схемой и данными;
5. проверка данных доступом `DATABASE_MAINTENANCE_URL` — в портал войти нельзя;
6. после подтверждённого health — `deploy-auto --maintenance=off`;
7. вкладки снимают заглушку сами по опросу файла, чистят кэш, перезапускают bootstrap и продолжают
   работу без входа.

`--reason` — **публичный текст**: он едет в `prod.env`, поэтому обрезается до 200 символов, а
`CR`/`LF` из него вычищаются (перевод строки разорвал бы файл окружения и уронил конфигурацию всего
сервиса). `--until` принимает ISO 8601 и вообще всё, что понимает `date -d`
(`--until='2026-09-04 06:30'` — местное время сервера), и нормализуется в UTC; неразобранное
значение — отказ до всякой правки.

#### Что печатают `--maintenance` и `--status`

Три канала **порознь**, а не общий `on`/`off`:

```
prod.env  : MAINTENANCE_MODE=on   AUTH_EPOCH_SINCE=1757000000
контейнер : MAINTENANCE_MODE=on            (фактическое окружение technic-api)
файл      : есть, until=2026-09-04T03:00:00Z, с 2026-09-03T22:10:05Z
состояние : режим ВКЛЮЧЁН целиком — портал закрыт, объявление раздаётся
```

**Расхождение любых двух строк — аварийное состояние, а не «включено»**, и команда называет его
прямо:

| Что видно                        | Что это значит                                                        | Что делать                            |
| -------------------------------- | --------------------------------------------------------------------- | ------------------------------------- |
| `prod.env=on`, `контейнер=off`   | `technic-api` не пересоздавали — портал ОТКРЫТ при закрытом на бумаге | повторить `--maintenance=on`          |
| `prod.env=off`, `контейнер=on`   | гейт живёт по старому окружению — портал закрыт при открытом на бумаге | повторить `--maintenance=off`         |
| `prod.env=off`, `файл=on`        | заглушка висит на работающем портале                                  | `--maintenance=off` (снимет файл)     |
| `prod.env=on`, `файл=off`        | гейт закрыт, а объявления нет: вкладка увидит ошибку, а не текст       | `--maintenance=on` (допишет файл)     |

Повтор `on` (или `off`) после обрыва **доводит состояние**: дописывает недостающее и не ломает
сделанного. Эпоху повторный `on` второй раз не поднимает, а начало окна (`startedAt`) не двигает.

#### Чего команда не делает и почему

- **`AUTH_EPOCH_SINCE` не снимается при `off` и никогда не убывает.** Сними её вместе с режимом — и
  токены, выданные до окна, снова стали бы валидными: обнуление отменилось бы задним числом.
  Значение переживает и снятие режима, и восстановление базы;
- **`--restore-db` режим не возвращает**: он живёт в `prod.env`, а не в базе. Восстановленная база
  не притащит с собой чужое состояние портала — и это в пользу режима;
- **при активной фазе `cutover` (`migrating`, `migrated`, `irreversible`) команда отказывает**: там
  `api` остановлен протоколом намеренно, и пересоздание контейнера посадило бы код на схему,
  которой протокол его ещё не показывал. Портал в этих фазах и так закрыт — остановкой сервисов;
- обратная проверка мягче: `--cutover`, начатый при выключенном режиме, **предупреждает, но не
  отказывает** — окно бывает аварийным, и вторая дверь, которую придётся обходить, хуже, чем портал,
  закрывшийся без объявления;
- **журнала окон у режима нет** (`prod.env` хранит только текущее значение), и отчёта `deploy-auto`
  переключение не пишет. Что переход был, видно по времени пересоздания контейнера и по выводу
  самой команды.

#### Если что-то не так

| Симптом                                                          | Причина и что делать                                                                                                                     |
| ---------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `нет каталога /etc/technic-portal/maintenance`                   | каталог заводит сам `deploy-auto` при запуске (`root:docker 0751`) — значит, не отработал `sudo` или каталог снесли. Завести: `sudo install -d -o root -g docker -m 0751 /etc/technic-portal/maintenance`, проверить маунт в `technic-web` |
| `веб не отдаёт /maintenance.json` после `on`                     | нет маунта `/etc/technic-portal/maintenance:/etc/nginx/maintenance:ro` или локации в `spa.conf`; проверьте также права: каталог `0751`, файл `0644` — при `0750`/`0640` nginx внутри контейнера получает `403`, а `403` заглушку у клиента не снимает |
| `гейт не отбивает доменную ручку` после `on`                     | контейнер не пересоздан или `prod.env` правили мимо команды — повторить `--maintenance=on`, посмотреть `logs technic-api`                  |
| `обновление сессии отбивается 503`                               | из-под гейта выпал `/auth/refresh` — режим выкинет всех на форму входа; разбирать до конца окна                                            |
| `--maintenance=off` отказывает «доменная ручка отвечает 503»     | гейт не снялся; объявление намеренно **не** снято. Починить `api` и повторить; если `api` заведомо здоров, а проба не выполняется — `sudo rm -f /etc/technic-portal/maintenance/maintenance.json` |
| `AUTH_EPOCH_SINCE опережает часы сервера`                        | разошлись часы площадки. Конфиг отвергает эпоху из будущего, `api` с ней не поднимется — чинить время, а не переменную                      |
| `--maintenance` отказывает «деплой уже выполняется»              | команда берёт тот же lock, что и деплой (иначе окно и выкат пересоздавали бы контейнеры наперегонки). Состояние режима видно и в `deploy-auto --status` — он lock не берёт |

### Ездки и точки маршрута: параметры выката (ADR 0108, миграции `0136` и `0146`)

Релиз, ради которого заводился `--cutover`: миграция `0136` переносит адреса, количество и контакты
с заявки на **ездку** и удаляет колонки-источники, то есть меняет смысл данных. Параметры, которые
протокол спрашивает у релиза:

| Параметр      | Значение                                                                                                                                            |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| бандл         | одна миграция `0136`: три таблицы, `waybill_trips`, `issue_warnings`, бэкфил и запись выпуска (`seq 19`, версия `0.1.18.0108`) — всё в ней          |
| верификатор   | `apps/api/teardown/0136_route_trips.sql.verify` → `pnpm --filter @technic/api backfill:trips --check` (read-only, ненулевой код на любом нарушении) |
| teardown      | `apps/api/teardown/0136_route_trips.sql` — возвращает колонки заявки из **первой** ездки и снимает новые таблицы                                    |
| граница floor | `0136` — ниже неё откат запрещён навсегда                                                                                                           |

**Два предохранителя миграции стоят до первого изменения схемы, и разбирают их заранее** — выкат
идёт с остановкой записи, и разбираться по ходу означает держать портал лежащим:

- грузовая заявка **без строки деталей**: бэкфил ездок идёт от деталей, и такая заявка осталась бы
  без адресов вовсе;
- день линейного заказа, у объекта которого **нет ни наименования, ни адреса**: точке маршрута
  нечего записать адресом, а CHECK упал бы кодом `23514` без единого слова о том, у какого объекта
  дыра.

Оба запроса можно прогнать заранее на проде — они только читают. Остальные три предохранителя
сверяют числа после бэкфила (ездка на каждую строку деталей; две роли на грузовую строку состава и
одна на линейный день; строка `waybill_trips` на каждый талон грузовой заявки) и роняют транзакцию
целиком, ничего не оставляя.

**Миграция `0146` (порядок ролей внутри точки) в бандл выката не входит и войти не может**: протокол
§6 требует в релизе ровно одну неприменённую миграцию, а чужая рядом — отказ ещё до остановки
сервисов. Значит она выкатывается **отдельным обычным деплоем**, и у этого деплоя есть своё окно:
`ALTER TABLE … SET NOT NULL` накатывается **до** перезапуска API, а предыдущая версия кода про
колонку `position` не знает и на заведении роли получит отказ. Окно короткое (миграция → `up -d`),
но приходится оно ровно на сборку маршрутов, поэтому деплой ставят в нерабочее время и не
совмещают с чем-то ещё. Порядок обратный невозможен: `0146` правит таблицу, которую заводит `0136`.

После подъёма проверяют три вещи, и все три — на живых данных: карточка старой заявки открывается и
показывает одну ездку с прежними адресами и количеством; собранный до релиза маршрут показывает по
две точки на грузовую строку и по одной на линейный день; повторная печать ранее выданного листа
даёт **тот же** документ (он печатается из снимка и миграцией не трогается).

### Режим модуля истории назначения (заморозка записи, переключение чтения)

Два независимых переключателя в одной управляющей строке (`assignment_periods_control`, миграция
`0167`): **режим записи** — `normal` | `history_frozen` | `all_frozen` — и **режим чтения** —
`legacy` | `history`. Каждый переход пишется в `assignment_periods_mode_transitions`, журнал
физически неизменяем. Нормативное описание — [план периодов
назначения](assignment-periods-plan.md) §6 и §10; здесь только команды.

**HTTP-двери у этого пути нет и не будет.** Режим меняет отдельная команда со своим доступом:
`DATABASE_MAINTENANCE_URL`, а пока роль `technic_maintenance` не заведена — `DATABASE_MIGRATION_URL`.
Прикладной `DATABASE_URL` не используется даже как запасной: команда откажет, а не сделает молча.

```bash
# посмотреть режим (только читает; безопасно в любой момент)
docker compose -f deploy/docker-compose.yml -p technic --profile tools \
  run --rm assignment-mode status

# заморозить всю запись модуля перед необратимым выкатом
docker compose … run --rm assignment-mode set --write=all_frozen \
  --actor=<email оператора> --reason='<зачем>' --build=<sha образа>

# вернуть работу
docker compose … run --rm assignment-mode set --write=normal \
  --actor=<email> --reason='окно закрыто' --build=<sha>

# журнал переходов
docker compose … run --rm assignment-mode log --limit=20
```

`<sha образа>` — тег запущенного контейнера: `docker inspect -f '{{.Config.Image}}' technic-api`.
Умолчания у него нет намеренно: журнал читают через годы, и «переключили неизвестно чем» ничего не
доказывает. Причина обязательна, исполнитель — учётка портала, а не «system».

**За один вызов меняется что-то одно.** Дверь отвергает шаг, где двигаются оба режима сразу:
порядок выката — сначала полная заморозка, потом переключение чтения, потом разморозка. Слитые в
один шаг, они переключили бы чтение в тот же момент, когда открылись двери, то есть без drain.

**Прямой `history_frozen → normal` запрещён** (это не сбой команды): пока история была закрыта,
ручная выписка и смены двигали отменяемость бумаги. Путь один — `all_frozen`, полная revalidation,
затем `normal`.

**Что именно останавливает заморозка.** Пишущие двери портала режим читают — чтение `write_mode`
приехало предварительным релизом (подэтап 2a плана). Классов у дверей два:

- **`history_frozen`** (откат) закрывает всё, что пишет историю назначения или читает её ради
  бумаги: правку заявки и её срока, смену статуса, назначение и смену техники (в том числе
  коррекцией), запрос досрочного завершения, его визу и отзыв, применение недельной заявки,
  восстановление заявки из архива. Смены и ручная выписка ЭСМ-2 при этом **работают** — работа на
  площадке продолжается, история просто не меняется;
- **`all_frozen`** (cutover) закрывает и их: сохранение, удаление, подпись и снятие подписи смены
  плюс ручная выписка `on_demand` двигают множество листов и отменяемость бумаги уже после того, как
  прогон сверки увидел ноль расхождений.

Закрытая дверь отвечает `503` с кодом `assignment_mode_frozen` и текстом «модуль закрыт на запись».
Чтение карточек, журналов и кабинета водителя гейт не спрашивает вовсе — оно разрешено в любом
режиме. Двери самого модуля истории (команда машиниста, дверь ремонта, периодная коррекция) приедут
этапом 3 со своим гейтом класса `history`.

Заморозка — ещё и **drain**: команда меняет режим `UPDATE`'ом управляющей строки и потому дожидается
всех пишущих транзакций, начатых до неё (каждая держит эту строку `FOR SHARE` первым запросом).
Вернувшийся вызов означает, что старых писателей больше нет.

**Если режим застрял:**

| Что видно                                            | Что это и что делать                                                                                                                                 |
| ---------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Административный путь не ходит прикладными кредами` | в окружении нет ни `DATABASE_MAINTENANCE_URL`, ни `DATABASE_MIGRATION_URL` — добавить в `prod.env` (или в отдельный `MAINTENANCE_ENV_FILE`)          |
| `URL СОВПАДАЕТ С ПРИКЛАДНЫМ` в строке `доступ`       | maintenance-переменная указывает на прикладную роль: читать можно, менять режим команда откажется. Завести `technic_maintenance` и задать свой URL   |
| `Дверь переходов не загружается`                     | контейнеру не хватает переменных приложения (дверь тянет общий конфиг). Запускать сервисом `assignment-mode` профиля tools, а не голым `tsx`         |
| `Режим уже такой`                                    | переход, ничего не меняющий, в журнал не пишется. Сверить `status` — возможно, окно уже открыто кем-то                                               |
| разморозка отклонена revalidation                    | остались заявки с непересчитанной готовностью: пересчёт идёт своей командой этапа 4, режим при этом остаётся `all_frozen` — это не тупик, а ожидание |
| портал лежит, а переключить нечем                    | это и есть аварийный вход: контейнер `assignment-mode` поднимается сам по себе, `technic-api` ему не нужен                                           |

**Руками управляющую строку не правят.** `UPDATE` мимо двери не проходит проверки перехода и не
оставляет записи в журнале — а журнал и есть доказательство «чем и когда разрешён переход»; дописать
его задним числом нельзя, правку и удаление отклоняет триггер.

### Разовый шаг: перенос истории в маршруты (ADR 0050)

Маршруты — рейс машины на дату между заявкой и путевым листом (ADR 0050) — выкатываются двумя
релизами, и между ними нужен ручной прогон. Порядок обязателен: миграция `0074` начинается
предохранителем и **прервёт деплой**, если история не перенесена (схема при этом не пострадает —
падение происходит до первого изменения).

```bash
# 1. Релиз с миграцией 0072 уже выкачен (таблицы рейсов, waybills.route_id nullable).
docker compose -p technic exec api pnpm backfill:routes --check   # отчёт, база не меняется
# 2. Разобрать блокирующие пункты отчёта:
#    · заявки сразу в нескольких действующих листах — аннулировать лишний бланк в журнале;
#    · заявка и на действующем листе без рейса, и уже в рейсе — аннулировать лист либо вынуть её.
docker compose -p technic exec api pnpm backfill:routes           # перенос: рейс на пару «машина + дата»
docker compose -p technic exec api pnpm backfill:routes --check   # «Листов без рейса: 0»
docker compose -p technic exec api pnpm backfill:routes --clear-orphan-drivers
#    ↑ обнуляет водителей в назначениях, где рейса не бывает (аренда, спецтехника): без этого
#      предохранитель миграции 0074 тоже не пропустит.
# 3. Только теперь деплой релиза с миграцией 0074 (NOT NULL, «один лист на рейс», снятие
#    старого UNIQUE, удаление driver_person_id у назначений).
```

Если релиз с `0074` уже в `main`, а перенос не сделан — деплойте `deploy-auto --skip-migrate`,
прогоните шаги выше и повторите обычный `deploy-auto`. Скрипт переноса идемпотентен: повторный
запуск ничего не дублирует.

### Разовый шаг: перенос полномочий из надстроек роли (ADR 0106)

Два системных полномочия — «Оператор (оргтехника)» и «Согласование ИТ» — переезжают из
`user_role_addons` в `grants`/`user_grants` пятью шагами expand/contract (ADR 0106 §9, план
реструктуризации §13). Шаги 1a и 1e — релизы с миграцией, 1c и 1d — релизы без миграций, а между
1a и 1c обязателен ручной прогон. Скрипт `backfill:grants` **приезжает релизом 1a**: до его выката
команды в образе нет.

```bash
# 1. Релиз 1a выкачен: новые таблицы, два системных набора с нынешним составом прав, двойная
#    запись выдач и отзывов. Чтение по-прежнему из user_role_addons, user_grants пуста.
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api backfill:grants --check || true   # отчёт, база не меняется
#    ↑ до переноса расхождение ненулевое и это нормально: в новой таблице нет ничего, что выдали
#      до старта двойной записи. Цифра нужна как точка отсчёта — с ней сверяют результат.
#      Код возврата здесь ожидаемо 1 — отсюда и `|| true`: под `set -e` чек-лист оборвался бы на
#      правильном ответе скрипта. Это единственный шаг, где единица ожидается; ниже она означает
#      отказ. Ноль на этом шаге — тоже сигнал: переносить нечего, проверьте, та ли база и вправду
#      ли выкачен 1a.
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api backfill:grants           # перенос: INSERT … SELECT в одной транзакции
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api backfill:grants --check   # обе стороны по нулям, код возврата 0
# 2. Только теперь релиз 1c (переключение чтения на новые таблицы). Сверку повторить
#    непосредственно перед выкатом: между переносом и релизом могли выдать полномочие.
# 3. Релизом позже — 1d (прекращение записи в user_role_addons, таблица остаётся живой).
# 4. Ещё релизом позже — 1e (миграция удаляет user_role_addons).
```

**Признак, по которому идут дальше, — нулевой двусторонний diff**: пусто и «есть в
`user_role_addons`, нет в `user_grants`», и обратное. Перенос сериализован с выдачей и отзывом
(`LOCK TABLE user_role_addons IN SHARE MODE` на время вставки и сверки, `ON CONFLICT DO NOTHING`),
поэтому ноль означает именно совпадение назначений, а не удачный момент замера.

**Код возврата по шагам.** Первый `--check` — единственное место, где единица ожидается и ничего не
значит, кроме «переносить есть что»; в чек-листе он и запускается с `|| true`, а решение принимают
по отчёту. У переноса и у второго `--check` единица означает отказ: дальше не идти. Обратная
сторона сверки ограничена кодами двух переезжающих наборов, поэтому пользовательские наборы этапа 3
её не поднимают — расхождение здесь всегда про переезд.

**Третья строка отчёта — «права совпали, история выдачи разошлась».** Пара есть в обеих таблицах, а
`granted_by` или `granted_at` разные: так выглядит откат до версии без двойной записи, в котором
полномочие отозвали и выдали заново (`ON CONFLICT DO NOTHING` сохранил прежнюю строку назначения).
Доступ от этого не меняется, и переключение чтения такое расхождение **не** запрещает — но `--check`
из-за него возвращает 1, чтобы шаг чек-листа остановился и человек посмотрел отчёт. Перенос его не
чинит (повторять его незачем) и чинить не берётся: с шага 1d старая таблица отстаёт, и копирование
истории из неё затирало бы верную. Правится руками и только пока двойная запись работает — то есть
до 1d; после 1e восстанавливать историю будет уже не из чего:

```sql
UPDATE user_grants ug
   SET granted_by = ura.granted_by, granted_at = ura.granted_at
  FROM user_role_addons ura
  JOIN grants g ON g.code = ura.addon::text
 WHERE ug.user_id = ura.user_id AND ug.grant_id = g.id
   AND (ug.granted_by IS DISTINCT FROM ura.granted_by
     OR ug.granted_at IS DISTINCT FROM ura.granted_at);
```

**Почему перенос — ручной шаг, а не часть миграции 1a.** Миграции накатываются **до** перезапуска
приложения (`deploy-auto`: накат идёт перед `up -d`). Скопируй их миграция — между копированием и
стартом нового кода продолжает работать старая версия, пишущая только в `user_role_addons`: выдача
или отзыв полномочия в это окно не попали бы в новые таблицы и потерялись бы навсегда, потому что
второй раз копировать никто не будет. Порядок «сперва двойная запись, потом перенос» закрывает окно
целиком: всё после старта двойной записи уже в новых таблицах, всё до — доберёт перенос.

**Почему между 1d и 1e обязан пройти целый релиз.** Удали таблицу тот же релиз, что прекращает в
неё писать, — миграция снесёт `user_role_addons` до перезапуска, и работающий код предыдущей версии,
продолжающий двойную запись, начнёт падать на каждой выдаче полномочия. Релиз 1d поэтому оставляет в
базе живую, но никем не используемую таблицу, и только следующий её удаляет.

**Предохранителя в миграции здесь нет** — в отличие от маршрутов (`0074`), где непереносённая
история прерывает деплой. У 1c и 1d миграций нет вовсе, останавливать деплой нечем, и решение «идти
дальше» целиком на человеке с отчётом `--check` в руках. Если 1c выкачен раньше переноса, держатели
полномочий теряют доступ (читается пустая `user_grants`); чинится это прогоном
`backfill:grants`, а не откатом: права читаются из базы на каждый запрос, и доступ возвращается со
следующего.

**`--check` показал ненулевой diff после переноса — чтение не переключать.** Разница означает, что
двойная запись где-то не сработала, и релиз 1c в таком состоянии закрепил бы расхождение. Порядок
разбора: скрипт печатает обе стороны с примерами строк — посмотреть, в какую сторону разошлось и на
каких учётках, найти причину (выдача мимо `replaceUserAddons`, ручная правка `user_role_addons` в
базе), затем повторить перенос. Он идемпотентен: повторный запуск ничего не дублирует и совпадающие
назначения не пересоздаёт.

**Откат по шагам — неоднородный:**

| Откат                | Безопасен | Почему                                                                  |
| -------------------- | --------- | ----------------------------------------------------------------------- |
| `1c → 1b`, `1b → 1a` | да        | двойная запись работает, обе таблицы согласованы                        |
| `1d → 1c`            | да        | старая таблица уже отстала, но обе версии читают новые                  |
| **`1d → 1b`**        | **нет**   | версия читала бы `user_role_addons`, отставшую на всё выданное после 1d |
| `1e → 1d`            | да        | версия 1d старую таблицу не читает и не пишет                           |
| **`1e → 1c`**        | **нет**   | таблицы больше нет, а те версии её читают                               |

До 1d откат безопасен в любую сторону. Возврат к чтению `user_role_addons` после 1d допустим только
после **обратной сверки** — переноса из `user_grants` в старую таблицу; без неё откат молча отберёт
доступ у всех, кому его выдали после прекращения записи, и заметят это не в деплое, а по жалобе
«пропала кнопка». После 1e откатываться некуда: таблицы нет, и вернуть её может только PITR
(см. «Гейты отката»).

#### Что входит в релизы 1d и 1e (подготовлено 18.08.2026, не выкачено)

Оба шага расписаны заранее, потому что порознь они выглядят безобидно, а порядок между ними —
единственное, что отделяет их от падения на каждой правке учётки.

**Релиз 1d — только код, миграций нет.** Правки в `apps/api/src/services/user-scopes.ts`, две и
неразделимые:

1. `replaceUserAddons` перестаёт писать в `user_role_addons`: убираются `tx.delete(userRoleAddons)`
   и `tx.insert(userRoleAddons)`, вызов `mirrorAddonGrants` остаётся. Единственный писатель старой
   таблицы — эта функция, других в коде нет;
2. `addonsOfUser` начинает читать наборы из `user_grants`/`grants` (системные коды, как их отбирает
   `systemAddonsOf`) вместо `user_role_addons`. **Без этой половины первая ломает правку учётки:**
   `addonsOfUser` — это «до», от которого `replaceUserAddons` считает разницу; оставшись на
   таблице, которая перестала пополняться, оно навсегда зафиксирует прошлое состояние — каждая
   правка карточки заново выдавала бы уже выданное и никогда не снимала бы снятое.

`roleAddonsExpr` и `addonsByUserIds` не трогаются: читателей у них нет с 1c, и оставлены они ради
откатываемости — уходят на 1e.

**Условие готовности 1d:** `backfill:grants --check` возвращает 0 непосредственно перед выкатом.
Это последний момент, когда двусторонний ноль вообще достижим: с 1d старая таблица начинает
отставать, и та же сверка после выката краснеет законно.

**И после выката 1d этот критерий не переиспользовать.** Обратная сторона сверки — «есть в
`user_grants`, нет в `user_role_addons`» — растёт с каждой новой выдачей просто потому, что в старую
таблицу никто не пишет; единица от `--check` там штатна и признаком беды больше не служит. Смысл с
1d остаётся только у первой стороны («есть в `user_role_addons`, нет в `user_grants`»): непустой она
означает легаси-строки, до которых не дошёл перенос, — и вот их разбирать по-прежнему нужно.

**Побочный эффект 1d, о котором нужно знать заранее.** Реестр выдач (`routes/user-grants.ts`) пишет
только `user_grants` и в старую таблицу не зеркалит. Поэтому системный набор, выданный из реестра,
сегодня «до» не виден, и правка карточки с пустым `addons` его не снимает; с 1d — снимет. Это
выравнивание, а не регресс: карточка и список учёток показывают наборы из новой таблицы с самого
1c, то есть до сих пор снимался не тот набор, который человек видел.

**Релиз 1e — миграция плюс код, строго следующим релизом.** SQL подготовлен:
`apps/api/drizzle/pending/step1e-drop-user-role-addons.sql` (`DROP TABLE user_role_addons`, затем
`DROP TYPE role_addon`). Вместе с ним тем же коммитом:

- `apps/api/src/db/schema.ts` — `userRoleAddons`, `roleAddonEnum`, тип `UserRoleAddonRow`;
- `apps/api/src/services/user-scopes.ts` — `roleAddonsExpr`, `addonsByUserIds`;
- `apps/api/src/backfill-grants.ts` вместе со скриптом `backfill:grants` в `apps/api/package.json`
  и тестом `apps/api/test/backfill-grants.db.test.ts`: перенос читает исчезнувшую таблицу;
- db-тесты, обращающиеся к таблице напрямую: `user-grants-single-write.db.test.ts` — уходят
  проверка легаси-строки и хелпер `addonRows`, а сам файл остаётся (его предмет — единственный
  писатель назначений, а не старая таблица). В `user-grants-routes.db.test.ts` и
  `service-request-flow.db.test.ts` от таблицы остались только упоминания в комментариях;
- этот раздел runbook'а и его чек-лист: переносить будет нечего.

**Условие готовности 1e:** релиз 1d уже запущен на площадке. Проверяется не журналом `_migrations`
(у 1d миграций нет вовсе), а версией образа — `deploy-auto --status` показывает SHA релиза.

### Выкат полномочий в окне учётки (ADR 0119)

Полномочия выдаются прямо в карточке учётки — тем же решением, что рассматривает заявку на
регистрацию. Миграций фича не требует, но выкат ступенчатый, и порядок не переставляется:

| Шаг | Что везёт                                                                               | Расширяет доступ            |
| --- | --------------------------------------------------------------------------------------- | --------------------------- |
| 1d  | прекращение записи в `user_role_addons` (см. раздел выше)                               | нет                         |
| 1а  | `writeAuditTx` — журнал событий доступа пишется в транзакции и роняет операцию при сбое | нет                         |
| 1б  | сервер принимает `grants` в теле учётки, каталог отбирается ролью                       | нет: тела ещё никто не шлёт |
| 2   | портал: поле «Полномочия» вместо «Надстроек»                                            | да — это и есть фича        |

**Перед 1б обязателен preflight** — он отвечает на два вопроса по живым данным:

```bash
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api check:grants-preflight
```

- **предел назначений.** Ненулевой код возврата означает одно: у кого-то назначений больше, чем
  `MAX_ASSIGNED_GRANTS`. Выкатывать в таком состоянии нельзя — карточка этого человека откроется
  в положении, из которого нельзя сохранить даже телефон. Лечится отзывом лишнего в реестре выдач
  либо поднятием константы новым релизом;
- **список держателей.** Ошибкой не считается, но его надо отдать администраторам до выката 1б:
  между 1б и 2 старый портал не сможет сменить роль тому, у кого от этой смены меняется действие
  назначения (400 «откройте карточку заново»). Такая правка в этом окне делается отзывом набора в
  реестре выдач и повторной выдачей после смены роли. Окно закрывается выкатом шага 2.

**Проверка после выката 2:** открыть карточку любой учётки с ролью, принимающей наборы, — поле
«Полномочия» показывает наборы, совместимые с ролью, а взведённые переводом ролей отмечены и
заблокированы. Если поле пришло заблокированным с сообщением о неполном списке — сервер не отдал
каталог целиком, и высказывание портал сознательно не отправляет; смотреть надо `GET /grants`, а не
форму.

### Выкат набора позиций в фильтре техники (ADR 0124)

Фильтр «Тип ТС» принимает несколько позиций сразу. Миграций нет, но релизы разведены и порядок не
переставляется:

| Шаг | Что везёт                                                                         | Меняет поведение        |
| --- | --------------------------------------------------------------------------------- | ----------------------- |
| A   | сервер принимает `classifications` наравне со старой парой; обе формы сразу — 400 | нет: портал ещё не шлёт |
| B   | портал: множественный выбор в «Заявках», «Истории», «На объекте», «Гараже»        | да — это и есть фича    |

Календарного окна между A и B не требуется: любое сочетание контейнеров согласовано, и откат
`deploy-auto --previous` (поднимает оба контейнера прежнего тега) оставляет портал против сервера,
который понимает обе формы. Старая пара `vehicleTypeId` + `vehicleCategoryId` **не снимается** ни
этим выкатом, ни по календарю: вкладка живёт на своём билде сколько угодно — отложенный кнопкой
«Позже» баннер обновления для него больше не покажется.

**Проверка после A** (до выката портала), на dev-хосте — предельный адрес через оба nginx:

```bash
# 60 позиций в наборе: строка запроса ≈ 2,9 КБ при дефолтном лимите nginx 8 КБ
IDS=$(for i in $(seq 60); do printf 't%s,' "$(uuidgen)"; done | sed 's/,$//')
curl -s -o /dev/null -w '%{http_code}\n' -H "Authorization: Bearer $TOKEN" \
  "https://auto.su10.ru/api/vehicle-requests/feed?page=1&pageSize=50&classifications=$IDS"
```

Ответ `200` — бюджет сходится; `414`/`400` до Zod — потолок набора снижается новым релизом
(константа `CLASSIFICATION_FILTER_MAX`), буферы nginx при этом не трогаем: в `conf.d` живут чужие
vhost.

**Проверка после B:** в «Заявках» выбрать две позиции разных типов — в выдаче строки обоих, цифры
сводки над таблицей относятся к той же выборке; на телефоне тот же набор виден в шите «Фильтры» и
считается одним заданным фильтром.

### Гейт минимальной версии клиента: перевод фазы (ADR 0146, решение 7)

Портал шлёт каждому запросу к `/api/v1/**` два заголовка: `X-Client-Contract` — монотонное целое,
вшитое в бандл, и `X-Client-Build` — короткий commit SHA для диагностики. Сервер держит пол
`MIN_CLIENT_CONTRACT` (`prod.env`, умолчание `1`) и отбивает контракт **ниже** пола ответом
`426 client_upgrade_required`. Запрос **без** заголовка читается как контракт `1` — постоянно.

Гейт заведён затем, что баннер обновления отменяем кнопкой «Позже»: вкладка со старым JS живёт
сколько угодно и переживает выкат, после которого ответ ей больше не читается. Баннер просит, гейт
отказывает.

| Фаза | `MIN_CLIENT_CONTRACT` | Нет заголовка | Контракт 1 | Контракт 2 |
| ---- | --------------------- | ------------- | ---------- | ---------- |
| A    | `1`                   | пропускаем    | пропускаем | пропускаем |
| B    | `2`                   | → `426`       | → `426`    | пропускаем |

**Порядок нарушать нельзя.** Фаза A едет обычным выкатом: она никого не блокирует и только
раздаёт статику, которая заголовок шлёт. Фазу B включают **отдельным действием и вручную**, после
того как новая статика проверенно раздаётся:

Обе фазы делает `deploy-auto`, а не правка файла руками:

```bash
deploy-auto --client-floor          # что сейчас: пол, контракт раздаваемой сборки, что можно сделать
deploy-auto --client-floor=2        # фаза B: поднять пол и перезапустить api
```

**Почему командой, а не `sed` по `prod.env`.** У операции есть предусловие, которое глазами не
проверяется: пол нельзя поднимать выше контракта той сборки, которая **раздаётся**. Поднимете
выше — `426` получат все, включая только что открытую вкладку, и портал закрывается целиком.
`--client-floor=N` читает контракт из исходника запущенной ревизии (`current` в `release.state`,
а не HEAD рабочего дерева: раздаётся собранный образ, а дерево могло уехать вперёд) и отказывает
до всякой мутации. Он же правит `prod.env` атомарно, сохраняя `root:docker 0640`, пересоздаёт
`technic-api` (`env_file` читается при создании контейнера, обычный `up -d` мог бы счесть
конфигурацию неизменной) и проверяет исход.

Одним шагом с выкатом это не делается: `api` и `web` поднимаются одной командой, а `web` зависит
от `api`, — включение вместе с выкатом дало бы промежуток, в котором старый клиент уже
заблокирован, а новая статика ещё не раздаётся. Поэтому `--client-floor` и не сочетается с
выкатом и откатом: скрипт откажет.

**Проверку после B команда делает сама** и печатает три строки — старый контракт на доменной
ручке (ожидается `426`), раздаваемый контракт там же (`426` быть не должно) и обновление сессии
без заголовка (`426` быть не должно, иначе гейт разлогинивал бы живых людей). Руками то же самое:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://auto.su10.ru/api/v1/service-requests      # 426
curl -s -o /dev/null -w '%{http_code}\n' -X POST https://auto.su10.ru/api/v1/auth/refresh  # 401, не 426
```

Отказ гейта в журнале `api` виден строкой «Запрос отбит гейтом версии клиента» с полями
`clientContract`, `minContract` и `clientBuild` — по последнему видно, какая именно вкладка ещё
жива. Обратный ход — `deploy-auto --client-floor=1`: понижение разрешено и предупреждает вслух,
что старые вкладки снова получат доступ к данным, которых не умеют читать.

**Чего гейт не делает.** Он блокирует старую вкладку, но не обновляет её: обработчика `426` у
сборок до этого выпуска нет, и человек увидит обычное окно ошибки — поэтому текст в теле отказа
самодостаточен («Портал обновился, обновите страницу»). И «в логах нет старых клиентов» ничего не
доказывает: спящая вкладка запросов не шлёт вовсе.

Ручки, выведенные из-под гейта **насовсем**: `POST /auth/refresh` и `POST /auth/logout` (старый
портал читает их неуспешный ответ не как отказ), а также `/health/*`, `/metrics` и `/internal/*` —
ими ходят healthcheck контейнера и worker, а не браузер. Плата за освобождение — обязательство
держать ответы этих двух ручек обратно совместимыми.

### Первый прогон автозакрытия заявок оргтехники (ADR 0133)

Заявка, простоявшая сутки в «Решена», закрывается порталом сама: worker раз в пять минут зовёт
`POST /internal/service-requests/auto-close`, а ручка отбирает созревшие заявки и закрывает их
пачками. Миграций под этот шаг нет — правило приезжает кодом, — но **первый прогон после выката
особенный**: отбор увидит все заявки, стоявшие в «Решена» до релиза, и закроет их разом, разослав
столько же писем. Правило при этом верно, а всплеск рассылки на сотню адресатов запомнится лучше
самой работы, поэтому первый прогон идёт уменьшенной пачкой.

**Срок молчания (сутки) настройкой не вынесен и не трогается**: это правило цикла, одинаковое для
всех заявок. Настройками заданы только нагрузка и частота:

| Переменная | Где читается | Умолчание |
| --- | --- | --- |
| `SERVICE_REQUEST_AUTO_CLOSE_BATCH` | API, сколько заявок за прогон | `50` |
| `SERVICE_AUTO_CLOSE_TICK_INTERVAL_MS` | worker, как часто будить | `300000` (5 мин) |

**1. До выката** — узнать размер очереди. Запрос read-only и повторяет условие отбора: «Решена»,
сутки прошли, и закрывающий документ либо есть, либо не требуется (свой ремонт и расходники).

```bash
psql "$DATABASE_URL" -c "
select count(*) from service_requests r
 where r.status = 'done' and r.deleted_at is null and r.completed_at is not null
   and (not (r.kind = 'repair' and r.service_counterparty_id is not null)
        or exists (select 1 from service_request_files f
                    where f.request_id = r.id
                      and f.kind in ('act','invoice','warranty_card')))
   and (case when r.kind = 'repair' and r.service_counterparty_id is not null
             then greatest(r.completed_at,
                           (select min(f.attached_at) from service_request_files f
                             where f.request_id = r.id
                               and f.kind in ('act','invoice','warranty_card')))
             else r.completed_at end) <= now() - interval '24 hours';"
```

Ответ до десятка — уменьшать пачку незачем, шаг пропускается целиком. Десятки и больше — шаг 2.

**2. Перед выкатом** дописать в `/etc/technic-portal/prod.env` уменьшенное значение; деплой поднимет
контейнеры уже с ним, и отдельного перезапуска не нужно:

```bash
sudo sh -c 'echo "SERVICE_REQUEST_AUTO_CLOSE_BATCH=5" >> /etc/technic-portal/prod.env'
deploy-auto
```

**3. После подъёма** смотреть журнал worker: строка пишется только у прогонов, которые что-то
сделали, и несёт четыре числа — `taken` (взято в пачку), `closed`, `skipped` (заявку успели тронуть
между отбором и закрытием — нормально, следующий прогон посмотрит заново), `failed`.

```bash
docker compose -f deploy/docker-compose.yml -p technic logs -f technic-worker | grep -i 'Автозакрытие'
```

Очередь из шага 1 разбирается за `ceil(N / 5)` прогонов, то есть по пять заявок каждые пять минут.
`failed > 0` — смотреть журнал API по тому же событию: пачку одна негодная заявка не роняет (у
каждой своя точка сохранения), но разбирать её надо руками.

**4. Когда счётчик из шага 1 дошёл до нуля** — вернуть умолчание и перезапустить:

```bash
sudo sed -i '/^SERVICE_REQUEST_AUTO_CLOSE_BATCH=/d' /etc/technic-portal/prod.env
docker compose -f deploy/docker-compose.yml -p technic up -d --force-recreate technic-api technic-worker
```

**Заявка, которую автозакрытие не возьмёт никогда** — сервисный ремонт, ушедший в «Решена» без
закрывающего документа. Такие строки существуют: до этого выпуска планка стояла на приёмке, и без
бумаги заявка проходила дальше. Отбор отсекает их намеренно (иначе они заняли бы пачку целиком и
вытесняли законные заявки каждый прогон), а разбирает человек — подшивает документ или принимает
работу руками:

```bash
psql "$DATABASE_URL" -c "
select r.num, r.completed_at from service_requests r
 where r.status = 'done' and r.deleted_at is null
   and r.kind = 'repair' and r.service_counterparty_id is not null
   and not exists (select 1 from service_request_files f
                    where f.request_id = r.id
                      and f.kind in ('act','invoice','warranty_card'))
 order by r.completed_at;"
```

**Остановить автозакрытие по одной заявке** можно заморозкой: у отложенной статус `on_hold`, а отбор
берёт только `done`. Это штатный ход портала («ждём разбирательства»), а не аварийная мера.
Остановить его целиком — снять `INTERNAL_API_TOKEN` нельзя: тем же секретом ходит планировщик
рассылок. Нужен выключатель на время аварии — это `SERVICE_AUTO_CLOSE_TICK_INTERVAL_MS` с заведомо
большим значением и перезапуск worker.

### Разовый шаг: сверка перевода ролей (этапы 8 и 9, ADR 0113)

Упраздняемые роли переводятся тремя релизами каждая (план §13.2): **prepare** выдаёт замещающие
наборы держателям старой роли и закрывает вход в неё, **migrate** переводит учётки одним `UPDATE`,
**cleanup** убирает роль из кода. Выкачен пока prepare — миграции `0154` (снимок
`user_role_migration`), `0155` (площадка) и `0156` (отдел). Ручной шаг у него один и запускается
**дважды**:

```bash
# 1. Сразу после наката prepare: между миграцией и перезапуском работала версия, которая старую
#    роль ещё принимала, и заведённая в эти минуты учётка осталась без снимка.
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api check:role-migration
# 2. Непосредственно перед выкатом migrate — как условие выката: за релиз между шагами могли
#    отозвать взведённое назначение или сменить кому-то роль руками.
```

Скрипт считает по каждой учётке старой роли два субъекта — сегодняшний и завтрашний, — и печатает
разницу **поимённо**. Считает он рабочим кодом: права наборов берёт то же выражение, которым их
считает принципал, а складывает источники та же матрица; отличается второй субъект ровно одной
ролью. Код возврата 0 означает «перевод ничего не меняет ни у кого».

Виды отказа и решение по каждому:

- **снимка нет** — учётка заведена на старой роли после наката prepare (окно деплоя) либо роль
  правили в базе руками. Перевод идёт по снимку и такую учётку пропустит, а роль к тому времени
  уже никого не пустит. Лечится повторным накатом посевных запросов `0155`/`0156` — они
  идемпотентны (`ON CONFLICT DO NOTHING`) и добирают только недостающее;
- **права теряются** — взведённое назначение отозвали в реестре выдач. Вернуть выдачей набора не
  выйдет: старой роли набор не совместим намеренно (иначе визу объекта можно было бы выдать
  рядовому штабу), поэтому лечится тем же повторным накатом посева;
- **права появляются сверх объявленного** — расширение, которого заказчик не решал: разбирать до
  перевода. Объявленное расширение (комендант получает оргтехнику, решение №1) отказом не
  считается и печатается отдельной строкой с числом учёток;
- **снимок разошёлся с учёткой** — роль сменили руками между шагами. Перевод пропустит её по
  условию `WHERE u.role = m.role_before`; такие учётки разбираются поимённо, а не переписываются.

**Взведённые назначения выглядят в реестре выдач как «ждёт перевода роли», и это норма.** Права по
ним не идут — их даёт роль, — а гейт совместимости откроется в момент перевода. Отзыв такой строки и
есть единственный способ испортить перевод: сверка называет пострадавших поимённо.

**Откат prepare** — снятие посеянного, в порядке внешнего ключа: сначала `DELETE FROM user_grants
WHERE origin = 'migration'` по снимкам этапа, затем сами снимки. Прав это ни у кого не отнимает: до
перевода назначения не действуют. Откат кода безопасен сам по себе — снимок и назначения предыдущая
версия просто не читает.

### Шаги migrate и cleanup этапов 8 и 9: подготовлено, ждёт своих релизов

SQL обоих шагов написан заранее и лежит в `apps/api/drizzle/pending/` —
**подготовленный, но не выкатываемый**. Каталог миграций плоский, и файл с номером уехал бы
ближайшим же деплоем, то есть одним релизом с prepare; правило трёх релизов (§13.2 плана) запрещает
ровно это. Подкаталог мигратору не виден: список собирает единственная функция
`listMigrationFiles()` — `readdirSync(...).filter(f => f.endsWith('.sql'))`, обход плоский, имя
`pending` под фильтр не подходит. Через неё же ходят `db:migrate:check`, `db:migrate:files`
(состав образа для гейтов отката), `.meta` бэкапа и стартовая сверка сервера — второго обхода
каталога в проекте нет. Инвариант держит тест `apps/api/test/migration-pending-dir.test.ts`, а сам
SQL прогоняется на своей временной базе тестом `apps/api/test/role-migration-pending.db.test.ts`.

**Файл становится миграцией в релизе своего шага, и номер — единственное, что он получает:**

```bash
ls apps/api/drizzle/          # занятый номер + 1: номера идут параллельными потоками
git mv apps/api/drizzle/pending/stage8-migrate-site-role.sql \
       apps/api/drizzle/0157_stage8_migrate_site_role.sql
```

#### Релиз migrate (этапы 8 и 9)

Файлы: `pending/stage8-migrate-site-role.sql`, `pending/stage9-migrate-department-role.sql`.
Ехать могут одним релизом или разными — этапы независимы, снимок различает их номером.

Условие выката, все три пункта:

1. **этап 7 выкачен** (адресация рассылок правом, ADR 0111) — иначе перевод трёх площадочных ролей
   в одну сольёт три аудитории рассылок в одну. Для этапа 9 пункт не нужен;
2. **prepare выкачен предыдущим релизом и приложение перезапущено**: вход в упраздняемые роли
   закрыт, новых держателей без снимка не появляется;
3. **сверка возвращает 0 — прогнанная сейчас, а не после prepare:**

```bash
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api check:role-migration
```

За релиз между шагами могли отозвать взведённое назначение или сменить кому-то роль руками; разбор
каждого вида отказа — в разделе про prepare выше. Ненулевой код — не выкатывать.

Что делает миграция: `UPDATE users SET role = m.role_after` по снимку с условием
`WHERE u.role = m.role_before`, отметка `migrated_at` тем же оператором через `RETURNING`, и
`auth_version + 1` переведённым. Права не меняются ни у кого, кроме объявленного расширения
(комендант получает оргтехнику, решение №1): наборы, которые их сохраняют, выданы релизом раньше и
начинают действовать ровно в момент смены роли.

**`auth_version + 1` — не разлогин.** Сервер роль из токена не берёт вовсе (принципал читает базу на
каждом запросе); гасится клиентский снимок роли и прав из `/auth/me`. Портал получает 401 «токен
устарел», молча дёргает `/refresh` и повторяет запрос — по одному лишнему обмену на переведённую
учётку. Без этого бывший комендант не увидел бы оргтехнику до истечения токена.

**Миграция роняет деплой, если на упраздняемой роли кто-то остался** (предохранитель после
`UPDATE`, прецедент — `0074`). Пройти мимо перевода может только учётка без снимка, заведённая в
минуты между накатом prepare и перезапуском. Лечение — повторный накат посевных запросов
`0155`/`0156` (идемпотентны, `ON CONFLICT DO NOTHING`), затем повторный деплой. Миграции катятся до
перезапуска, поэтому отказ оставляет работать прежнюю версию на прежней схеме — то самое состояние,
из которого шаг повторяют.

**Проверка после выката** — та же сверка плюс витрина «Права»: у каждой переведённой учётки набор
прав тот же, что был вчера, кроме объявленного расширения.

**Откат migrate** — тем же снимком и так же условно:

```sql
UPDATE users u SET role = m.role_before, auth_version = u.auth_version + 1, updated_at = now()
  FROM user_role_migration m
 WHERE m.user_id = u.id AND m.stage = 8 AND m.migrated_at IS NOT NULL
   AND u.role = m.role_after;
UPDATE user_role_migration SET migrated_at = NULL WHERE stage = 8;
```

Условие `u.role = m.role_after` обязательно: учётка, которой роль сменили руками уже после перевода,
в откат не попадает и разбирается отдельно. Взведённые назначения откат не снимает — они
принадлежат prepare и просто снова перестают действовать.

#### Релиз cleanup (этапы 8 и 9) — последний, и после него откат перевода невозможен

Файлы: `pending/stage8-cleanup-site-role.sql`, `pending/stage9-cleanup-department-role.sql`. **Едут
одним коммитом с правками кода** — половинки одного утверждения:

| Где                                        | Что                                                                                                                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `packages/contracts/src/enums.ts`          | `ROLES` без четырёх ролей; подписи из `roleLabels` → `ARCHIVED_ROLE_LABELS`; строки уходят из `roleColors`, `OBJECT_SCOPED_ROLES`, `DEPARTMENT_SCOPED_ROLES`                               |
| `packages/contracts/src/role-addons.ts`    | `shtab` уходит из `ROLE_ADDON_BASE_ROLES` обоих оргтехнических наборов                                                                                                                     |
| `packages/contracts/src/permissions.ts`    | строки упразднённых ролей из `ROLE_PERMISSIONS`, `ROLE_VEHICLE_REQUEST_TYPES`, `ROLE_STATUS_TRANSITIONS`                                                                                   |
| `packages/contracts/src/role-migration.ts` | модуль уходит целиком вместе с пятью читателями: `retiringRoleIssue` в `routes/users.ts`, `isRetiringRole` в `UsersTab.tsx`, `roleMigrationOf` в `grantModel.ts` и `userAccountLabels.tsx` |
| `apps/api/src/check-role-migration.ts`     | сверка и её строка в `package.json`: сверять больше нечего                                                                                                                                 |

Оставлять `ROLE_MIGRATIONS` пустым нельзя: пометка «ждёт перевода роли» в реестре выдач считается по
нему, а строки `user_grants` с `origin = 'migration'` живут вечно — после перевода они означают
действующий набор, и вечно-мёртвая ветка врала бы про них при первом же взгляде.

Составлять список руками не придётся: `Role` — закрытое объединение, и компилятор назовёт каждое
место сам. Портал списков ролей не держит вовсе — он берёт их из `ROLES`.

**Одно место компилятор назовёт, но решение оставит человеку — `roleEnum` в
`apps/api/src/db/schema.ts`.** Он описывает тип в базе, а тот значения сохраняет: на них держится
`user_role_migration.role_before`. Убрать их из `roleEnum` — значит типизировать снимок ложью;
оставить — значит получить объединение шире, чем `Role`, и ошибку компилятора на
`role: u.role` в `loadPrincipal`. Предпочтительно второе: `roleEnum` остаётся полным, а сужение
делается на границе «база → код» — тем же приёмом, которым `isPermission` отсеивает право-сироту
(`grantPermissionsByUserIds`). Подпись для значения, не прошедшего сужение, уже есть — `roleTitle`
в контрактах (заведён 18.08.2026 вместе с `ARCHIVED_ROLE_LABELS`).

Условие выката:

1. **migrate выкачен предыдущим релизом** и приложение перезапущено;
2. `SELECT count(*) FROM users WHERE role IN ('shtab','rukstroy','commandant','department_head')`
   — ноль (предохранитель миграции проверяет это сам и роняет деплой, но узнать заранее дешевле);
3. `SELECT count(*) FROM user_role_migration WHERE migrated_at IS NULL` — ноль либо разобранный
   поимённо список: это учётки, которым роль меняли руками, и после cleanup возвращать их будет
   некуда.

Что делает SQL: снимает строки `grant_roles` с упразднёнными ролями — и системные (две:
`office_equipment_operator` и `office_equipment_it_approver` × `shtab`), и пользовательские, куда
prepare дописал целевую роль рядом. Значения enum в базе **не удаляются** (`ALTER TYPE ... DROP
VALUE` не существует, а пересоздание типа задевает `users.role` и `mailing_schedule_roles.role` и
требует необратимого выката): они остаются мёртвыми, и на них держится
`user_role_migration.role_before` — единственный ответ на «кем человек был».

**Почему вычитание `grant_roles` не в migrate, хотя соблазн велик.** Какие пользовательские наборы
были собраны под старую роль, нигде не записано: prepare добавлял целевую роль, а не запоминал,
кому добавил. Сними строку раньше — и откат перевода вернул бы человека на `shtab` уже без прав его
набора, молча. Между migrate и cleanup откат ещё разрешён, поэтому вычитание ждёт релиза, в котором
роль исчезает насовсем.

**Откат cleanup** — обычный откат кода: схема после него ровно та же, ни одного значения enum не
удалено. Необратимо не хранилище, а знание: строки `grant_roles` восстановить неоткуда, поэтому
откат **перевода** после cleanup означает ручной разбор пользовательских наборов.

### Реквизиты организации в шапке путевого листа

Основную организацию заводит миграция `0075` (АО «Служба механизации», по шапке бланков 4-П и
№ 3) — без неё выдача листа отвечает «Не заведена организация-владелец транспорта». Экрана у
справочника юрлиц пока нет (бэклог ADR 0037), поэтому реквизиты правятся SQL — через тот же
`db-tools`, которым ходит в базу `deploy-auto` (URL раскрывается внутри контейнера, секрета в
`argv` нет):

```bash
docker compose -f deploy/docker-compose.yml -p technic run --rm db-tools sh -c \
  'psql "${DATABASE_MIGRATION_URL:-$DATABASE_URL}"'
```

```sql
select name, address, phone, okpo, ogrn, inn from organizations where is_primary;
update organizations set inn = '<10 или 12 цифр>', updated_at = now() where is_primary;
```

Правка меняет шапку **будущих** листов: выданные печатаются из своего снимка `waybills.data` и
задним числом не переписываются (ADR 0037 п. 10).

### Реквизиты заказчика в графе «В чьё распоряжение» (ADR 0127)

Заказчик — генподрядчик, в чьё распоряжение поступает техника, — печатается графой «В чьё
распоряжение (наименование и адрес заказчика)» у 4-П и графой «Заказчик» у ЭСМ-2. Реквизит **один
на все листы** и живёт строкой-одиночкой `waybill_customer`: миграция `0164` заводит таблицу и
сразу заполняет её (наименование, адрес офиса, телефон). Экрана у настройки нет, как и у
справочника юрлиц, — правится тем же `db-tools`, которым правятся реквизиты организации выше:

```sql
select name, address, phone, updated_at from waybill_customer;
update waybill_customer set
  name = 'Генеральный подрядчик ООО «СУ-10»',
  address = 'г. Москва, ул. Полковая, д. 3, стр. 5',
  phone = '+7 (495) 616-23-22',
  updated_at = now();
```

`where` не нужен: строка в таблице ровно одна — вторую не даёт завести первичный ключ с CHECK.
Телефон хранится как записан, а печатается единым видом (ADR 0066); запись из нескольких номеров
уходит в бланк как есть.

**Выката правка не требует** — реквизит читается при каждой выписке, — и **ни одного листа не
перевыписывает**: сверка недельных листов (`esm2SyncPlan`) смотрит на набор недель, машину и
машиниста, а реквизитов бланка не знает вовсе. Меняет она шапку **будущих** листов: у листов,
выданных до выката ADR 0127, в этих графах стоит объект заявки, и повторная печать даёт именно его
(ADR 0037 п. 10).

**Предупредить бухгалтерию о двух записях даты.** Листы, выданные **до** выката `0.1.32.0127`,
печатаются с датой `2026-08-23`, выписанные **после** — `23.08.2026`. В подшивке за август это
соседние страницы с разной записью одного дня, и это ожидаемо, а не сбой печати: снимок листа
печатается как выдан, и переписывать выданное при печати портал не берётся. Тем же правилом
объясняются графа заказчика и объект в старых ЭСМ-2 — они печатаются такими, какими выданы.

## Startup checks

API при старте падает с понятной ошибкой, если: нет обязательных env/секретов, есть
placeholder (`CHANGE_ME`) в проде, некорректен `DATABASE_URL`/TLS, нет S3-креденшелов

## Загрузка файлов (S3 / CORS)

Файлы грузятся **напрямую в cloud.ru** по presigned PUT: браузер (origin `https://auto.su10.ru`)
делает PUT на `https://s3.cloud.ru/<bucket>/<key>`. **nginx и Fastify в этом запросе не участвуют** —
preflight (OPTIONS) обрабатывает cloud.ru. Поэтому CORS настраивается **на бакете**
(`docs/setup-infra.md §3`), а не в nginx/Fastify. Архитектуру на проксирование файлов через API
не менять — файлы до 50 МБ идут прямо в S3.

Симптом `No 'Access-Control-Allow-Origin' header` при загрузке — обычно одно из:

1. **`S3_FORCE_PATH_STYLE=false`** → URL вида `https://<bucket>.s3.cloud.ru/...`. cloud.ru отдаёт на такой
   host `403 AccessDenied` вообще на всё, включая preflight, и **без** `Access-Control-*` заголовков —
   браузер показывает это как ошибку CORS, хотя политика бакета корректна. Поставить `true` (см. env ниже);
2. presigned URL содержит `x-amz-checksum-crc32` / `x-amz-sdk-checksum-algorithm` (авто-checksum AWS SDK) —
   **исправлено в коде** (`apps/api/src/lib/s3-client.ts`); убедиться, что задеплоена свежая версия;
3. на бакете нет/некорректна CORS-политика — настроить (`aws s3api put-bucket-cors`, см. setup-infra §3);
4. runtime использует не тот bucket/endpoint — проверить env (ниже).

Отличить (1) от (3) можно за один запрос: preflight на path-style URL отвечает `200` + CORS-заголовками,
на virtual-hosted — `403` без них (см. «Проверка preflight» ниже).

### Проверка runtime-окружения (без секретов)

```bash
docker exec technic-api sh -lc \
  'env | grep -E "^(PUBLIC_ORIGIN|S3_ENDPOINT|S3_REGION|S3_BUCKET|S3_FORCE_PATH_STYLE)="'
```

`S3_FORCE_PATH_STYLE` должен быть `true`. Если значения не совпадают с ожидаемыми — поправить
`/etc/technic-portal/prod.env`. **Изменение `prod.env` требует пересоздания контейнеров**
(restart/reload не перечитывает `env_file`):

```bash
docker compose -f deploy/docker-compose.yml -p technic up -d --force-recreate technic-api technic-worker
```

### Проверка preflight (CORS) напрямую к бакету

`$UPLOAD_URL` — presigned PUT из ответа `POST /api/v1/files/upload-session`:

```bash
curl -i -X OPTIONS "$UPLOAD_URL" \
  -H 'Origin: https://auto.su10.ru' \
  -H 'Access-Control-Request-Method: PUT' \
  -H 'Access-Control-Request-Headers: content-type'
```

Ожидаемый ответ (`200`/`204`) содержит:

- `Access-Control-Allow-Origin: https://auto.su10.ru`
- `Access-Control-Allow-Methods: PUT` (или список с PUT)
- `Access-Control-Allow-Headers: content-type`
- `Access-Control-Max-Age: 3600`

`403 AccessDenied` без `Access-Control-*` и с host `<bucket>.s3.cloud.ru` → virtual-hosted-style,
чинится `S3_FORCE_PATH_STYLE=true`. Ответ без CORS-заголовков на **path-style** URL → проблема
в CORS-политике бакета, а не в приложении.

### Жалоба «печать не работает» (ADR 0148)

Печать — единственная долгая ручка портала, и у неё своя лестница сроков. Что искать в журнале
API, в порядке убывания частоты:

```bash
docker compose -f deploy/docker-compose.yml -p technic logs --since 6h technic-api \
  | grep -E 'печать: (не уложились|конвертация|отменена)'
```

| Строка журнала                           | Что означает                                                        | Куда смотреть                                                       |
| ---------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `печать: не уложились в срок`            | конвертер не успел за отведённое (`budgetMs`, `elapsedMs` в строке) | загрузка VPS: печать упирается в срок только на занятой машине      |
| `печать: конвертация бланков в PDF`      | LibreOffice упал; рядом `code`, `signal` и его `stderr`             | чаще всего место на диске или память в контейнере API               |
| `печать: отменена — запросивший её ушёл` | человек закрыл окно; это норма, а не отказ                          | тревожит только частота: много таких — печать долгая, смотрите срок |

Человеку при этом приходит `print_timeout` (не успели) либо совет выгрузить файлом (упал
конвертер) — разные коды означают разные причины, и путать их не надо.

Одновременных конвертаций не больше `PRINT_CONCURRENCY` (по умолчанию 2), остальные ждут в
очереди. Если печать стала вязкой у всех разом, а `elapsedMs` в норме, — упирается очередь, и
поднимать надо её, а не сроки.

### Метрики почты (`GET /metrics` на `technic-api:3000`)

Формат — текстовый Prometheus. Наружу маршрут не проксируется: снаружи проходит только `/api/`.

Почта — единственная часть портала, которая работает без человека: письмо составляется ночью,
отправляется фоном и о своей неудаче никому не рассказывает. Ошибку в интерфейсе кто-нибудь заметит
и позвонит; молчащую рассылку — нет, и узнают о ней тогда, когда водитель не приедет. Отсюда набор:

| Метрика                                     | Что показывает                                          | Когда тревожить                  |
| ------------------------------------------- | ------------------------------------------------------- | -------------------------------- |
| `technic_mail_messages{status="failed"}`    | Письма, которые уже не уйдут (без отладочных)           | любой рост                       |
| `technic_mail_messages{status="pending"}`   | Ждут очереди                                            | не убывает дольше получаса       |
| `technic_jobs{status="dead"}`               | Задачи, исчерпавшие попытки                             | любой рост                       |
| `technic_mailing_runs_24h{status="failed"}` | Упавшие запуски рассылок за сутки                       | больше нуля                      |
| `technic_mailing_schedules_overdue`         | Включённые расписания, чьё время прошло 10+ минут назад | больше нуля — планировщик молчит |

Последняя метрика — главная для рассылок: штатный запуск сдвигает время сразу, поэтому её рост
означает, что worker не тикает или не достучался до API (`INTERNAL_API_TOKEN`, `INTERNAL_API_URL`).

Отладочные письма (`is_test`) из счётчиков исключены: проверка вёрстки не должна читаться как сбой
доставки.

### Метрики капчи (там же, `GET /metrics`)

Капча внешняя — Yandex SmartCaptcha (ADR 0130), и ломается она молча в обе стороны: сервис может
перестать отвечать (тогда портал пропускает всех) или начать отвечать «всё в порядке» на что
угодно (тогда портал пропускает всех, но выглядит здоровым). Отсюда три метрики.

| Метрика                                            | Что показывает                                                             | Когда тревожить                                                                                                                                                                                                                       |
| -------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `technic_captcha_checks_total{result="fail_open"}` | Проверки, пропущенные вслепую: сервис не ответил или ответил невнятно      | любой рост за 15 минут — предупреждение; непрерывно дольше 5 минут — тревога                                                                                                                                                          |
| `technic_captcha_invalid_token_rejected`           | 1 — заведомо мусорный токен отвергнут; 0 — принят или проверить не удалось | ноль — тревога                                                                                                                                                                                                                        |
| `technic_captcha_canary_last_run_seconds`          | Время последней завершённой попытки canary                                 | возраст больше двух часов — тревога. Правило вешать только там, где `technic_captcha_enabled = 1`: при выключенной капче canary не запускается, и отметка остаётся нулём — иначе на любом стенде без ключей возраст считается от 1970 |
| `technic_captcha_enabled`                          | 1 — ключи заданы и проверка работает                                       | ноль в production — тревога: API с такими ключами не должен был подняться. Отличает «капчу выключили правкой env» от «регистраций не было»: у выключенной все счётчики нули                                                           |

Что означает `fail_open`. Серверная проверка при недоступности сервиса намеренно пропускает
запрос (ADR 0130 п. 5): отказ закрыл бы регистрацию и восстановление пароля целиком. В это время
формы держат только лимиты по адресу (5 попыток за 10 минут) и honeypot, поэтому непрерывный
`fail_open` — состояние «портал открыт», а не «немного деградировал».

Что означает ноль в `invalid_token_rejected`: ограниченный режим SmartCaptcha (платёжный аккаунт не
`ACTIVE`/`TRIAL_ACTIVE` — сервис отвечает `ok` на всё, и капча не защищает); неверный серверный ключ
(сервис отвечает `403` — в логе рядом будет «SmartCaptcha отвергла сам запрос»); или проверка не
удалась. Первым делом — лог API за последний час, затем статус платёжного аккаунта в консоли Yandex
Cloud.

Чего эти метрики НЕ показывают: что настоящий токен принимается. Самый неприятный случай — ключи
исправны, а боевой домен не внесён в список сайтов капчи: сервер видит здоровый сервис и рисует
единицу, а виджет в браузере токена не выдаёт, и три формы стоят закрытыми. Это ловится только живым
прохождением формы после релиза.

Два значения разделены намеренно: gauge — исход последней попытки, отметка времени — факт того, что
попытка была. Молчащий canary виден по возрасту отметки, плохой результат — по нулю; в одном
значении эти сигналы неразличимы.

## Почта: очередь и разбор жалоб «письмо не пришло»

Письмо составляет API и кладёт в `mail_messages` вместе с задачей `send_email` — одной транзакцией.
Отправляет `technic-worker`: он же ограничивает частоту (`MAIL_MAX_PER_MINUTE`) и проставляет
результат. Тело письма хранится готовым, поэтому повтор отправляет ровно то, что было составлено.

Состояния письма: `pending` — ждёт очереди, `sent` — принято SMTP-сервером (в `sent_at` время, в
`provider_id` идентификатор у провайдера), `failed` — не уйдёт уже никогда.

```bash
# Что не отправлено прямо сейчас и почему
psql "$DATABASE_URL" -c "select kind, status, to_email, subject, last_error, created_at
  from mail_messages where status <> 'sent' order by created_at desc limit 20;"

# Письма конкретному человеку — первый вопрос при «мне ничего не приходило»
psql "$DATABASE_URL" -c "select kind, status, sent_at, provider_id, last_error
  from mail_messages where to_email = 'ivanov@example.ru' order by created_at desc limit 20;"

# Очередь отправки: задачи, которые ещё не выполнены
psql "$DATABASE_URL" -c "select status, count(*) from jobs where type = 'send_email' group by 1;"
```

Что означают состояния и что делать:

- **`pending` дольше нескольких минут, задача `pending` с далёким `next_run_at`** — упёрлись в
  потолок отправки: рассылка растянута во времени намеренно. Проверить `MAIL_MAX_PER_MINUTE` против
  тарифа провайдера.
- **`pending`, а задач `send_email` нет вовсе** — почта выключена (`MAIL_ENABLED=false`) либо worker
  не поднялся. Письма дождутся включения: задача откладывается, а не тратит попытки.
- **`failed` с текстом ответа SMTP 5xx** — окончательный отказ: адрес не существует, домен не
  принимает почту, отправитель отвергнут. Повторять бессмысленно, надо чинить адрес: у водителя — в
  карточке справочника, у пользователя — в его учётке.
- **`failed` после исчерпания попыток** — временные отказы не кончились: смотреть `last_error` и
  доступность провайдера.
- **письмо `sent`, но человек его не видит** — искать в спаме и проверять DNS домена отправителя
  (`docs/setup-infra.md`, п. 5.1): просроченный или отсутствующий DKIM/SPF выглядит именно так.

Секретов в журнале нет: тела auth-писем содержат ссылку с одноразовым токеном, поэтому доступ к
содержимому писем даётся отдельно от обычного администрирования, а в логи тело не пишется.

**Проверить доставку руками.** Администрирование → **Рассылки** → «Отладочная отправка»: тип
письма и получатель из числа действующих администраторов (право `mailings.manage`). Письмо уходит
по-настоящему — с пометкой `[ТЕСТ]` в теме и недействительными ссылками, — но помечено `is_test` и
в статистику запусков не попадает. Каждая отправка пишется в аудит как `mailing.test_sent`. Этим и
проверяется боевая настройка после правки DNS или смены SMTP-провайдера:

```bash
# Отладочные письма за сутки: что отправляли и чем кончилось
psql "$DATABASE_URL" -c "select kind, to_email, status, last_error, created_at from mail_messages
  where is_test and created_at > now() - interval '1 day' order by created_at desc;"
```

## Рассылки по расписанию

Расписания заводит администратор: **Администрирование → Рассылки** (право `mailings.manage`).
Часы держит `technic-worker`: раз в минуту (`MAILING_TICK_INTERVAL_MS`) он спрашивает у API, чьё
время наступило, и просит выполнить запуск — сборка письма живёт в API, где есть права и область
видимости получателя (ADR 0075).

Для этого worker'у нужны две переменные в `/etc/technic-portal/prod.env`: `INTERNAL_API_TOKEN`
(общий секрет, одинаковый у API и worker) и `INTERNAL_API_URL` (по умолчанию
`http://technic-api:3000`). Без токена планировщик молчит, а `/internal/mail/*` отвечает `401`.
Наружу этот префикс не проксируется — во фронтовом nginx стоит явный `return 404`.

Что важно знать при разборе:

- **Двойной рассылки не бывает** даже при двух worker'ах: запуск уникален парой
  «расписание + назначенное время», второй экземпляр получает отказ и не делает ничего.
- **Повтор запуска безопасен**: ключ письма включает идентификатор запуска, поэтому повторное
  выполнение не создаёт новых писем. Упавшую рассылку можно просто выполнить заново.
- **Границы данных зафиксированы** в самом запуске (`period_start`/`period_end`) — повтор возьмёт те
  же дни, а не пересчитает окно от момента повтора.
- **Статистика запуска** показывает не только отправленное: `withoutEmail` — водители с рейсами, но
  без адреса (пробел справочника), `excluded` — исключённые администратором, `empty` — те, у кого
  после вычета исключённых дат рейсов не осталось.

```bash
# Что и когда сработает дальше
psql "$DATABASE_URL" -c "select name, type, is_enabled, send_at, run_weekdays,
  window_from_days, window_days, next_run_at
  from mailing_schedules order by next_run_at nulls last;"

# История запусков с итогами
psql "$DATABASE_URL" -c "select planned_at, status, is_manual, stats, error
  from mailing_runs order by created_at desc limit 20;"

# Письма конкретного запуска
psql "$DATABASE_URL" -c "select to_email, status, sent_at, last_error
  from mail_messages where mailing_run_id = '<uuid>' order by created_at;"
```

Если рассылка не ушла: сперва `mailing_runs` (создан ли запуск и в каком он статусе), затем
`mail_messages` того же запуска (составлены ли письма), затем очередь `jobs` типа `send_email`.
Пустой `next_run_at` у включённого расписания означает, что срабатывать больше нечему — например все
дни выполнения попали в исключения.

### Ролевые сводки

Сводка (`role_digest`) собирается каждому получателю своя: таблицы одни и те же, а строки в них —
только те, что человек видит в портале под собой (ADR 0078, ADR 0093). Адрес в расписании отвечает
лишь на вопрос «кому отправлять» — и с ADR 0111 адрес этот **право**, а не имя роли
(`mailing_schedule_permissions`). Право считается эффективным: дала его должность или назначенный
набор (ADR 0106), для рассылки разницы нет.

- **Получатель обязан иметь подтверждённый адрес** — иначе он в рассылку не попадает вовсе.
- **Пустая сводка не отправляется** и считается в статистике запуска как `empty`: если эта цифра
  равна числу получателей, значит рассылка настроена на тех, кому нечего показать. А если в итогах
  нули по всем счётчикам сразу — получателей не нашлось вовсе, и первым делом надо смотреть, есть ли
  у расписания хоть одно право-адресат.
- **Содержание — две таблицы по действующим путевым листам**: перевозки (4-П и форма № 3, по дате
  рейса) и техника на объектах (ЭСМ-2, по пересечению недели листа с окном). Нет листа — нет
  строки: рейсы на арендной технике в сводке не видны ни строкой, ни счётчиком, потому что лист на
  неё выписывает арендодатель. На жалобу «в письме не все рейсы» смотреть надо сюда.
- **Окно смотрит вперёд**: `window_from_days` (0 — сегодня, 1 — завтра) и `window_days`. «За вчера»
  сводка больше не рассказывает — разделов событий нет.
- **Аудитория задаётся отбором, а не исключениями**: режимы `all`/`selected` в
  `scope_mode`/`recipient_mode` и перечни в `mailing_schedule_scopes` /
  `mailing_schedule_recipients`. Режим `selected` фиксирует набор: заведённая позже площадка и
  новый сотрудник в рассылку сами не попадут, их надо отметить руками.

**После выката миграции `0124` расписания сводок перечитать глазами.** Прежний период сводки был
ретроспективным («за вчера», «за прошлую неделю»), а содержание письма переписано целиком и говорит
теперь о будущем — сохранить смысл было нечем. Перенос выбрал умолчание по времени отправки:
утренние (до 12:00) — на сегодня, вечерние — на завтра, недельные — на 7 дней вперёд. Настройка
правдоподобная, а не эквивалентная: пока каждое расписание не перечитали, что именно уходит людям,
видно только из этой таблицы.

```bash
# Окно и аудитория каждой сводки после переноса
psql "$DATABASE_URL" -c "select name, send_at, run_weekdays, window_from_days, window_days,
  request_scope, scope_mode, recipient_mode, show_trips, show_onsite
  from mailing_schedules where type = 'role_digest' order by name;"
```

```bash
# Кому ушла сводка последнего запуска и с какой темой
psql "$DATABASE_URL" -c "select to_email, status, subject from mail_messages
  where kind = 'role_digest' and mailing_run_id = '<uuid>' order by created_at;"
```

#### Разовый шаг: сверка аудитории после переезда адресации на права (ADR 0111)

Миграция `0151` не только заводит `mailing_schedule_permissions`, но и **наполняет её по факту**:
для каждого расписания ищет право, дающее на живых данных ровно ту же аудиторию, что нынешний набор
ролей. Отдельным скриптом это сделать нельзя — он приезжает тем же образом, что и новый код, то есть
запустить его можно только после перезапуска, а до тех пор все расписания адресовались бы пустой
таблицей и молчали. Поэтому перенос идёт в миграции (она накатывается **до** перезапуска), а ручной
шаг после выката один — сверка:

```bash
docker compose -f deploy/docker-compose.yml -p technic exec technic-api \
  pnpm --filter @technic/api check:mailing-audience
```

Скрипт считает «до» по прежним ролям, «после» по правам и сравнивает **поимённо**. Считает он рабочим
кодом рассылки, тогда как перенос считал то же равенство своим SQL: два независимых счёта одного
множества — в этом и смысл шага. Код возврата 0 означает «аудитория каждого расписания совпала».

Три вида отказа, и решение у каждого своё:

- **адресация не подобрана** — эквивалентного права нет, и расписание не пишет никому. Это не
  поломка переноса: аудитория роли выражается правом далеко не всегда («Штаб» как таковой не
  отделяется ни одним правом ни от «Отдела», ни от «Диспетчера»). Скрипт печатает, кому уходило до
  переезда, и ближайшие права с ценой каждого («потеряется N, добавится M»); **выбор — за
  заказчиком**, задаётся он в форме расписания. Приближение здесь означало бы менять список
  получателей молча;
- **аудитория разошлась** — право подобрано не то, письма пойдут не тем: имена обеих сторон в
  отчёте, править форму расписания надо до ближайшей вечерней рассылки;
- **право-сирота** — в таблице лежит строка вне словаря кода: адресация по ней молча не сработает.

Строку `отбор без гейта модуля изменился: −N / +M` отказом считать не надо: это люди, которым письмо
не составлялось и не составится (у них нет `vehicleRequests.read`), — счётчик кандидатов в форме
расписания из-за них станет другим, и знать об этом надо заранее.

`mailing_schedule_roles` миграция **не трогает**: пока строки на месте, откат этапа — обычный откат
кода, а сверка умеет сопоставить обе адресации. Удаляет таблицу отдельная миграция релизом позже.

## Подтверждение адреса при регистрации

Заявка на регистрацию заводится неподтверждённой, и письмо со ссылкой уходит в той же транзакции
(ADR 0072). Пока адрес не подтверждён, активация отклоняется — администратор видит это в колонке
«Адрес» списка пользователей.

- Ссылка подтверждения живёт `MAIL_VERIFY_TTL_SECONDS` (сутки), ссылка сброса пароля —
  `MAIL_RESET_TTL_SECONDS` (час). Оба значения в `/etc/technic-portal/prod.env`.
- Повторное письмо человек запрашивает сам на `/verify-email`: не чаще одного на учётку за пять
  минут и пяти запросов с адреса за десять.
- Заявка, не подтверждённая за `MAIL_REGISTRATION_EXPIRY_DAYS` (по умолчанию 7 дней), уходит в
  архив — адрес освобождается, и человек регистрируется заново. Ноль и меньше выключают закрытие.
- Ручного обхода подтверждения нет. Если письмо до человека не доходит, учётку заводит
  администратор — такая считается подтверждённой по факту создания.
- При `MAIL_ENABLED=false` саморегистрация отвечает `503`: заявку, которую невозможно подтвердить,
  портал не заводит.

```bash
# Заявки, ждущие подтверждения адреса
psql "$DATABASE_URL" -c "select email, created_at from users
  where deleted_at is null and role is null and email_verified_at is null order by created_at;"

# Ушло ли письмо конкретному человеку и что ответил SMTP
psql "$DATABASE_URL" -c "select kind, status, sent_at, last_error from mail_messages
  where to_email = 'ivanov@example.ru' order by created_at desc limit 5;"
```

## Аренда задач в очереди

`technic-worker` берёт задачу в работу под аренду: строка помечается `running`, за ней
записывается воркер (`locked_by`) и срок (`locked_until`). Пока аренда жива, задачу никто не
перехватит; когда истекает — возврат в очередь забирает её обратно, тратя попытку. Тратя, а не
обнуляя: задача, которая убивает процесс, снаружи неотличима от штатного перезапуска при выкате, и
без счётчика получился бы цикл «взял — умер — взял».

- `WORKER_LEASE_MS` в `/etc/technic-portal/prod.env` — срок аренды, по умолчанию **300000** (пять
  минут, как было до появления параметра). Минимум 30 секунд; значение ниже или мусор — берётся
  умолчание с предупреждением в лог.
- Аренда **продлевается** heartbeat'ом, пока воркер жив, поэтому длинная задача её не переживает.
  Но продление говорит «процесс жив», а не «работа идёт»: у каждого долгого вызова обязан быть
  собственный таймаут (у распознавания талонов это `TICKET_OCR_HTTP_TIMEOUT_MS`).
- Задачи, застрявшие в `running`, видно так:

```bash
docker compose -p technic exec -T technic-api node -e "…"   # либо напрямую в базе:
psql "$DATABASE_URL" -c "select id, type, attempts, locked_by, locked_until
  from jobs where status = 'running' order by locked_until limit 20;"
```

Строки с `locked_until` в прошлом означают, что воркер их не довёл: следующий такт вернёт их в
очередь. Если такие строки копятся, смотрите не на них, а на воркер — перезапускается ли он.

## Распознавание талонов вывоза (ADR 0114)

Модуль читает сканы контрольных талонов моделью через LLM-прокси заказчика и сверяет прочитанное с
заявкой: уникальность номера, объём, дата, адрес. Выключен по умолчанию.

Читаются талоны заявок **всех типов** (ADR 0150). Сверка объёма при этом считается только там, где
объём есть: у металлолома вывезенное лежит в весе (ADR 0067), у контейнерных операций его нет
вовсе — для них работают уникальность номера, дата вывоза и адрес площадки.

### Включение

Всё в `/etc/technic-portal/prod.env`, обе службы читают одни и те же переменные и обязаны
перезапускаться **парой** — API ставит задачи, воркер их выполняет:

```
AI_PROVIDER_MODE=proxy            # stub — заглушка без сети и без расхода
PROXY_LLM_BASE_URL=https://proxyllm.fvds.ru
PROXY_LLM_TOKEN=…                 # токен оператора прокси, в репозитории его нет
PROXY_LLM_ACK_NO_PROVIDER_POLICY=1
TICKET_OCR_ENABLED=true
TICKET_OCR_MODEL=…                # слаг каталога либо `proxy` — «выбирает прокси»
TICKET_OCR_ESCALATION_MODEL=…     # пусто — каскада нет, читает одна модель
```

`TICKET_OCR_ENABLED=false` при живом транспорте — законное состояние: задачи не ставятся вовсе, а
не копятся в очереди. Обратное сочетание (`enabled` без транспорта) API отбивает на старте.

**Выключенный модуль ничего не откладывает на потом.** Задача не заводится в момент закрытия
заявки, и после включения прошлые талоны сами не прочитаются — их поднимает кнопка
«Перераспознать» в карточке, по одному файлу.

### Пусковой чек-лист (этап 0)

Пока не пройден, `TICKET_OCR_ENABLED` остаётся `false`. Порядок именно такой: каждый следующий
пункт бессмысленно проверять, пока не закрыт предыдущий.

**1. Адрес портала в списке разрешённых у оператора прокси.** Проверяется одной командой с той
машины, откуда ходит воркер:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' -X POST "$PROXY_LLM_BASE_URL/api/v1/chat/completions" \
  -H "Authorization: Bearer $PROXY_LLM_TOKEN" -H 'Content-Type: application/json' \
  --data '{"model":"proxy","messages":[{"role":"user","content":"ping"}],"max_tokens":1}'
```

`403` от nginx — адреса нет в списке: **токен при этом не проверялся и вызов не оплачен**. Дать
оператору egress-адреса обеих машин (API и воркера — они могут отличаться). `401` — адрес прошёл,
не принят токен. `200` — идём дальше.

**2. Картинка проходит и модель её видит.** Это главный вопрос этапа, и ответить на него чтением
документации нельзя: `chat/completions` описан без единого слова о вложениях, а модель, до которой
изображение не дошло, честно вернёт `null` по всем полям — то есть будет выглядеть как плохо снятый
талон, а не как неверный транспорт. Поэтому — проба тем же кодом, что пойдёт в бой:

```bash
set -a; . /etc/technic-portal/prod.env; set +a
pnpm --filter @technic/worker exec tsx src/ticket-ocr/probe.ts /path/to/talon.jpg
```

Печатает `x-proxy-request-id`, фактическую модель, токены и разобранные поля. Проба ничего не
пишет в базу и стоит один вызов. Исходы различаются кодом возврата — по нему её можно поставить в
скрипт:

| Код | Что на экране | Что делать |
| --- | --- | --- |
| `0` | `ГОТОВО. Прокси пропускает изображение, модель его видит…` | можно включать модуль |
| `1` | `ОТКАЗ <код> (<класс>, <область>)` и человеческая причина | смотреть таблицу причин ниже |
| `3` | `ПУСТО. Транспорт работает, но полей нет ни одного…` | повторить на заведомо читаемом скане; если и он пуст — вопрос к оператору о мультимодальности |
| `2` | отказ до вызова: файла нет, `AI_PROVIDER_MODE=stub`, файл не изображение и не PDF | поправить команду; вызов не делался и не оплачен |

Вот как выглядит закрытый allowlist — это ровно то, что портал видит сегодня:

```
Прокси:  https://proxyllm.fvds.ru
Модель:  proxy (вариант A — выбирает прокси)
Файл:    talon.jpg, 11 КБ
Страниц: 1, пробуем первую: image/jpeg, 11 КБ, sha256 0b0ce6ad53d5…

Заняло:  1103 мс
Запрос:  x-request-id fee51e42-1456-4b47-9604-3ed62870b4ad
Прокси:  x-proxy-request-id (не назван)
Биллинг: upstream (не назван)
Модель:  отработала (не названа)
Токены:  вход ?, выход ?

ОТКАЗ http_403 (terminal, subsystem)
Прокси ответил отказом доступа (403) страницей nginx: адрес воркера не в allowlist либо
неверен токен. Нужен администратор.
```

`(не назван)` в трёх строках подряд — признак того, что до прокси запрос не дошёл вовсе: свои
идентификаторы он проставляет всегда, даже отказывая.

**3. Что спросить у оператора письменно** (это не развилки, а данные, без которых нельзя считать
ни расход, ни нагрузку):

| Вопрос | Зачем |
| --- | --- |
| `clientId` портала | по нему оператор находит наш трафик, когда разбираются |
| вариант политики модели: **A** — слаг выбирает оператор, **B** — выбираем мы, **C** — фиксирован | от этого зависит `TICKET_OCR_MODEL`. При варианте A портал **выключает кэш попыток**: за одним слагом в разное время стоит разная модель, и склеенные ответы сделали бы метрики выдумкой. Значит вариант A дороже — каждая страница читается заново |
| лимиты `maxConcurrency` / `maxPending` | `TICKET_OCR_MAX_PER_MINUTE` не должен их превышать: очередь у прокси общая с чужими сервисами |
| чей ключ OpenRouter и виден ли ему наш расход | при общем ключе расход портала виден оператору, а не порталу, — сверять счёт нечем, кроме `x-openrouter-request-id` |
| что попадает в журнал прокси и надолго ли; политика хранения у OpenRouter и провайдера | талон — документ заказчика; ответ нужен письменный |
| смысл `PROXY_LLM_ACK_NO_PROVIDER_POLICY` | переменной нет в документации ни строкой, её выдали отдельно. Пока смысл не подтверждён, портал её **хранит, но не отправляет** — толковать флаг по названию нельзя |

**4. Замер на реальных сканах** — 50–100 талонов через пробу с разными моделями и разрешением;
из них откладывается неизменяемый holdout, по которому потом сверяют смену версии промпта. Только
после этого выбирается `TICKET_OCR_MODEL` и включается модуль.

### Когда «не читается»

Первое, что нужно знать: **молчание — не признак порядка**. Поэтому у подсистемы есть своё
состояние, и портал показывает его баннером над карточкой:

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  https://<host>/api/v1/waste-requests/ticket-recognition/health
```

- `ok` — работает;
- `degraded` — временный сбой (сеть, 503 прокси, лимит): портал повторит сам, в карточке видно
  «попытка N из M»;
- `unconfigured` — нужен администратор: 401/403 от прокси, не настроенный транспорт. Само не
  восстановится.

Разбирать начинают с журнала попыток в карточке заявки (сворачиваемый блок «Файлы и попытки»):
в нём стоит `x-proxy-request-id` — **именно его называют оператору прокси**. Без него разговор
сводится к «у нас что-то не читается».

Частые причины отказа:

| Что видно | Что это | Что делать |
| --- | --- | --- |
| `403` на все попытки, `unconfigured` | адрес портала не в allowlist прокси | дать оператору egress-адреса обеих машин |
| `401` | токен не принят | сверить `PROXY_LLM_TOKEN` |
| `413`, файл `unsupported` | скан больше допустимого либо не картинка и не PDF | перезалить скан; талон можно завести руками |
| `503` с `Retry-After` | очередь у прокси занята | ничего: задача переносится ровно на названный срок |

### Что видно в журнале воркера

```bash
docker compose -p technic logs -f technic-worker | grep -i "Распознавание талона"
```

Строки жизненного цикла — по одной на событие, все с `requestId` и `fileId`:

| Строка | Когда |
| --- | --- |
| `Распознавание талона: начало` | задача взята, файл ещё не скачан |
| `Распознавание талона: страница взята из кэша попыток` | вызова не было, ответ переиспользован |
| `Распознавание талона: файл разобран` | итог: `pages`, `tickets`, `skippedPages` |
| `Распознавание талона: файл отвергнут — …` | подготовка не пропустила файл: не картинка, больше лимита |
| `Распознавание талона: страница не прочитана` | отказ модели с кодом, классом и областью |
| `Распознавание завершилось в пустоту…` | заявку откатили, пока шло чтение: результат не пишется |
| `Распознавание талонов выключено: задача пропущена` | `TICKET_OCR_ENABLED=false`, а задача в очереди осталась с прежних времён |
| `Потолок обращений к прокси на минуту исчерпан: задача отложена` | сработал `TICKET_OCR_MAX_PER_MINUTE` |

Тишина в этом гребне при закрытой заявке с талоном означает, что **задача не заводилась**: либо
модуль выключен в том процессе, что её ставит, либо файл приложен не как талон. Тип заявки задачу
больше не отбирает — с ADR 0150 читаются талоны всех типов, включая металлолом и операции с
контейнерами.

Отдельный случай той же тишины: задача заведена, а **воркер её пропускает**. Так выглядит
`prod.env`, поправленный без пересоздания контейнеров: у API `TICKET_OCR_ENABLED=true` — кнопка
«Перераспознать» отвечает успехом и задачу ставит, — а воркер живёт со старым окружением и каждую
задачу закрывает строкой `Распознавание талонов выключено: задача пропущена`. Ни попытки, ни
отказа, ни следа в аудите. Проверяется одной командой:

```bash
docker exec technic-worker printenv | grep TICKET_OCR
```

### Что видно в мониторинге

`GET /metrics` на `technic-api:3000` отдаёт четыре ряда про распознавание:

- `technic_ticket_attempts_24h{engine,status,scope}` — попытки за сутки. **Алерт ставится на
  `scope="subsystem"`**: он означает «сервис не работает». `scope="item"` — «эта бумага не
  читается», человеку работа, тревоге повода нет;
- `technic_ticket_tokens_24h{direction}` — расход боевых вызовов, пока счёт оператора не пришёл;
- `technic_ticket_blind_checks{status}` — перепроверки; растущий `mismatch` означает не плохую
  модель, а неразобранную очередь арбитража;
- `technic_ticket_review_pending` — заявки в реестре «Требуют разбора», тем же предикатом, что и
  список в портале.

### Что живёт по сроку

- `TICKET_OCR_ATTEMPT_TTL_DAYS` (по умолчанию **180**) — через столько дней воркер удаляет попытку
  распознавания целиком, в той же часовой уборке, что и файлы. Попытки, на которые ссылается живой
  талон, не убираются никогда: их ответ объясняет цифру, стоящую в талоне.
- Талоны, страницы и файловые строки уходят вместе с откатом заявки из «Выполнена» — распознанное
  не переживает отката. Попытки, наоборот, остаются: они принадлежат содержимому страницы и служат
  кэшем, поэтому повторное закрытие той же бумагой не стоит ни копейки.
- `TICKET_OCR_BLIND_CHECK_RATE` (по умолчанию **0.05**) — доля подтверждённых машинных талонов,
  уходящих в слепую перепроверку. Ноль выключает её целиком: заданий не заводится.

## Срок хранения отклонённых заявок на регистрацию

`technic-worker` раз в час (`WORKER_CLEANUP_INTERVAL_MS`) сносит из архива учётки, которым отказали
в регистрации: те, что лежат в архиве дольше срока, без роли и неактивны (ADR 0063). Учётки
работавших сотрудников уборка не трогает — их держат внешние ключи, и срока хранения у них нет.

- `USER_REJECTED_REGISTRATION_TTL_DAYS` в `/etc/technic-portal/prod.env` — срок в днях, по
  умолчанию **7**. Ноль и меньше выключают уборку.
- Пока отказ в архиве, его можно вернуть в очередь: карточка учётки → **Восстановить** (право
  `archive.restore`). После уборки восстанавливать нечего.
- След остаётся в журнале: `user.purge_expired` с адресом и сроком, без актора — удалил срок, а не
  человек. Ручное удаление администратором пишется как `user.purge`.

```bash
# Сколько заявок ждёт уборки прямо сейчас
psql "$DATABASE_URL" -c "select count(*) from users where deleted_at < now() - interval '7 days' and role is null and is_active = false;"
```

## Наполнение справочника водителей

Кадровая выгрузка приезжает JSON-файлом и в git не попадает: ФИО, дата рождения и СНИЛС живых
людей в репозитории не хранятся (ADR 0037 п. 12–13).

**Наполняют только из портала, доступ к серверу не нужен** (ADR 0047). Справочники → Водители →
**Загрузить выгрузку**: портал разбирает файл и показывает, кого заведёт (база при этом не
меняется), заведение — вторым шагом. Право то же, что у заведения водителя руками
(`drivers.write`). Ошибка в файле объясняется дословно — «Петров Пётр: СНИЛС … не проходит
проверку контрольной суммы», — и чинится в самом файле. Формат файла, разбор отчёта и частые
отказы — в [инструкции](guide-staff-import.md).

Пути через сервер нет: файл на VPS не кладут, деплой справочник не наполняет и `seed:drivers`
больше не существует. Повторная загрузка того же файла ничего не дублирует — ключ человека
СНИЛС, заведённые пропускаются.

Загрузка заводит физлицо, специализацию «Водитель», трудовое отношение и удостоверение с
категориями. Серия, номер и сроки удостоверения в кадровой выгрузке отсутствуют — они остаются
пустыми, документ помечен `unverified`. Такой водитель в отбор под машину попадает (пустой срок
отбор читает как бессрочный), но графа «номер удостоверения» в путевом листе печатается пустой.
Реквизиты вносит администратор в карточке водителя: **Добавить удостоверение** с настоящими
данными, затем **Аннулировать** временное — иначе человек покажется в списке выбора дважды.

## История назначения заказа техники

Модуль ведёт «кто и на какой машине работал по дням» отдельной таблицей
`vehicle_request_assignment_changes` — вместо одного назначения на весь срок (ADR 0126, план
`docs/assignment-periods-plan.md`). Код выкачен весь: схема, автомат режимов, двери, окна портала и
исполнитель отрезкового плана бумаги. **Не сделано одно — переключение чтения** (`read_mode`), и
это отдельная операция сопровождения, описанная ниже.

| Ручка | Что делает |
| --- | --- |
| `GET /api/v1/vehicle-requests/:id/assignment-changes` | история заявки и её состояние готовности |
| `POST …/assignment-changes` (+ `/preview`) | команда машиниста: `set` и `cancel` |
| `POST …/assignment-changes/repair` (+ `/preview`) | ремонт истории: якоря, заполнение `unknown`, машина после конца срока, режим `restore` |
| `GET …/assignment-changes/repair/state` | осмотр: что в истории чинить. Ничего не пишет |
| `POST …/assignment-changes/correction` (+ `/preview`) | правка прошлого решения о машине |
| `PATCH …/period` (+ `POST …/period/preview`) | правка срока работ: продление, сокращение, гашение решений |

В портале это окна «Сменить машиниста», «Починка истории» и правка срока в карточке заказа; «Состав
по датам» — панель истории внутри первых двух.

Каждая боевая ручка двухфазна: `/preview` считает и **не пишет ничего**, боевая принимает отпечаток
предпросмотра. Протухший отпечаток — 409 `assignment_preview_stale`: «Последствия изменились с
момента предпросмотра — посмотрите их заново и подтвердите». Это норма, а не поломка: между двумя
нажатиями заявку успели тронуть.

**Чтение сегодня идёт по-старому.** `read_mode = legacy`: «кто работал» портал по-прежнему берёт из
назначения и недельных листов, а история пишется рядом. Отсюда половина здешних оговорок — часть
проверок пока считает, но никого не останавливает.

```bash
# Режим модуля: запись, чтение, поколение сверки
psql "$DATABASE_URL" -c "select write_mode, read_mode, cutover_run_id, updated_at
  from assignment_periods_control;"

# То же с площадки, когда портал недоступен или заморожен (ходит своей ролью, не прикладной)
docker compose -f deploy/docker-compose.yml -p technic --profile tools \
  run --rm assignment-mode status
```

### Режим модуля истории назначения (заморозка записи, переключение чтения)

Два независимых переключателя в одной управляющей строке (`assignment_periods_control`, миграция
`0167`): **режим записи** — `normal` | `history_frozen` | `all_frozen` — и **режим чтения** —
`legacy` | `history`. Каждый переход пишется в `assignment_periods_mode_transitions`; журнал
физически неизменяем — правку и удаление отклоняет триггер. Нормативное описание — план периодов
назначения (§6 и §10), место заморозки в окне необратимого выката —
[протокол выката](schema-cutover-protocol.md) §10; здесь только команды.

Режим меняет отдельная команда со своим доступом: `DATABASE_MAINTENANCE_URL`, а пока роль
`technic_maintenance` не заведена — `DATABASE_MIGRATION_URL`. Прикладной `DATABASE_URL` не берётся
даже как запасной: команда откажет, а не сделает молча. Прикладного окружения (JWT, S3, почта) ей не
нужно — дверь исполняет транзакцию тем соединением, которое команда ей дала.

```bash
# заморозить всю запись модуля (перед необратимым выкатом или на время разбора аварии)
docker compose -f deploy/docker-compose.yml -p technic --profile tools \
  run --rm assignment-mode set --write=all_frozen \
  --actor=<email оператора> --reason='<зачем>' --build=<sha образа>

# заморозить только двери истории, оставив работу портала
docker compose … run --rm assignment-mode set --write=history_frozen \
  --actor=<email> --reason='<зачем>' --build=<sha>

# вернуть работу
docker compose … run --rm assignment-mode set --write=normal \
  --actor=<email> --reason='окно закрыто' --build=<sha>

# журнал переходов: чем и когда переключали
docker compose … run --rm assignment-mode log --limit=20
```

`<sha образа>` — тег запущенного контейнера: `docker inspect -f '{{.Config.Image}}' technic-api`.
Умолчания у него нет намеренно: журнал читают через годы, и «переключили неизвестно чем» ничего не
доказывает. Причина обязательна, исполнитель — учётка портала, а не «system».

**Заморозка действительно останавливает запись.** `history_frozen` закрывает двери, пишущие
историю; `all_frozen` — ещё и ручную выписку ЭСМ-2 со всеми ручками смен. Отказ приходит кодом 503
(`assignment_mode_frozen`), разбор его текста — ниже, в «Заявка не даёт сменить машиниста или
технику». Заморозка ждёт активных писателей: команда возвращается, когда пишущих транзакций больше
нет, — это и есть drain, и именно поэтому она ставится **до** остановки контейнеров, а не после.

**За один вызов меняется что-то одно.** Дверь отвергает шаг, где двигаются оба режима сразу:
порядок — сначала полная заморозка, потом переключение чтения, потом разморозка. Слитые в один шаг,
они переключили бы чтение в тот момент, когда двери уже открылись, то есть без drain.

**Прямой `history_frozen → normal` запрещён** (это не сбой команды): пока история была закрыта,
ручная выписка и смены двигали отменяемость бумаги. Путь один — `all_frozen`, полная revalidation,
затем `normal`.

**Переключение чтения — операция этапа 5, а не дежурное действие.** Сегодня `read_mode = legacy`, и
`--read=history` дверь без поколения сверки (`--run=`) и аттестации деплоя (`--attestation=`) не
пропустит. Аттестация живёт полчаса и потребляется **однажды**: повторное включение той же
аттестацией отклоняет уникальный индекс журнала, а не только проверка в коде. Возврат
`--read=legacy` ни поколения, ни аттестации не требует — он бывает аварийным.

**После восстановления базы режим сверяют отдельно.** Управляющая строка лежит в той же базе и
едет в дампе, поэтому `deploy-auto --restore-db` возвращает и режим — тот, что был на момент дампа.
Предмиграционный дамп необратимого выката снимается уже под заморозкой: после восстановления модуль
останется замороженным, и разморозка — отдельный шаг.

**Если режим застрял:**

| Что видно                                                                            | Что это и что делать                                                                                                                                             |
| ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Административный путь не ходит прикладными кредами`                                 | в окружении нет ни `DATABASE_MAINTENANCE_URL`, ни `DATABASE_MIGRATION_URL` — добавить в `prod.env` (или в отдельный `MAINTENANCE_ENV_FILE`)                      |
| `URL СОВПАДАЕТ С ПРИКЛАДНЫМ` в строке `доступ`, а `set` отказан                      | maintenance-переменная указывает на прикладную роль: читать можно, менять режим — нет. Завести `technic_maintenance` и задать свой URL                           |
| `Не названа сборка`                                                                  | не передан `--build=<sha>`; взять тег у запущенного `technic-api`                                                                                                |
| `Режим уже такой`                                                                    | переход, ничего не меняющий, в журнал не пишется. Сверить `status` — возможно, окно уже открыл кто-то другой                                                     |
| `Разморозка запрещена: у N заявок поднята метка загрязнения истории`                 | revalidation не закончена, режим остаётся `all_frozen` — это ожидание, а не тупик. Кто именно: `select num from vehicle_requests where assignment_history_dirty` |
| `Аттестация уже потреблена другим переходом` / `описывает уже не сегодняшний раскат` | аттестация одноразовая и живёт полчаса — снять новую и повторить переключение                                                                                    |
| портал лежит, а переключить нечем                                                    | это и есть аварийный вход: контейнер `assignment-mode` поднимается сам по себе, `technic-api` ему не нужен                                                       |

**Руками управляющую строку не правят.** `UPDATE` мимо двери не проходит проверки перехода и не
оставляет записи в журнале — а журнал и есть доказательство «чем и когда разрешён переход»; дописать
его задним числом нельзя.

### Заявка не даёт сменить машиниста или технику

Отказ приходит от той двери, в которую постучали, и разбирать надо **текст**, а не код: 422 общий
почти у всех.

- **«История назначения этой заявки не восстановлена: …»** (422; команда машиниста и периодная
  коррекция) и **«История этой заявки ещё не построена и не восстанавливается: …»** (422; дверь
  ремонта) — отказ не про «истории ещё нет»: строк действительно нет, но двери достраивают её сами
  при первом же обращении, и отказывают только тогда, когда достроить её **не из чего**. Причина
  дописана в тот же текст, и путь у каждой свой:
  - «заявке не назначена техника — восстанавливать историю не от чего» — назначить технику, и
    история построится при следующем обращении;
  - «на 2026-03-02 действуют два путевых листа разных машин (2 шт.) — какая из них работала, из
    бумаги не следует» — разобрать бумагу и аннулировать лишний номер;
  - «периоды действующих путевых листов пересекаются — одной шкалы из них не построить» — то же:
    оставить на каждый период один действующий лист.
- **«История заявки полна: ремонтировать в ней нечего, кроме решения о машине после конца срока и
  отмены заполнения»** (422, код `assignment_history_ready`) — заявка `ready`, блокеров нет. В этом
  состоянии ремонт принимает только `tailResolution` и отмену заполнения.
- **«Чинить нечего: машинист с 2026-03-02 — в истории заявки это уже стоит. Откройте карточку
  заявки заново: пробелы и границы там посчитаются по свежей истории»** (422; дверь ремонта) —
  названное телом уже сделано (в перечне бывают «машинист с …», «заполнение … — …», «решение о
  машине после конца срока»). Обычно это второе нажатие по устаревшему окну.
- **«Назовите машиниста на отрезках без человека: 2026-03-02 (2026-03-02 — 2026-03-08)»** (422) —
  команда двухфазна: первый `/preview` без якорей называет границы (`requiredAnchors`), второй, с
  именами, отдаёт план и отпечаток. Якорь ставится на **начало отрезка**, а не на любую дату внутри
  него: строка посреди отрезка разрезала бы его надвое и оставила первую половину без человека.
  Фамилию портал не подставляет никогда — она уезжает в бланк строгой отчётности настоящей.
- **«Якорь на 2026-03-02 не нужен: предпросмотр этой границы не называл»** и **«Якорь на дату … не
  требуется: назначить машиниста на эту дату можно отдельной командой»** (422) — прислан якорь на
  дату, которой в списке предпросмотра нет. Взять список заново.
- **«Смена статуса заказа машиниста не назначает — в истории не назван машинист: заказ ТС-123 —
  01.03.2026. Назначьте его действием „Сменить машиниста“ в карточке заказа, и повторите
  операцию»** (422, код `assignment_history_incomplete`) — это бэкстоп: чужая дверь задела дни, о
  машинисте которых история молчит, а называть людей она не вправе. Дверей шесть: смена статуса,
  смена техники заказа, запрос и виза досрочного завершения, правка срока работ, применение
  недельной заявки. **Сегодня такого отказа не бывает**: при `read_mode = legacy` вердикт уходит в
  диагностику, а операция проходит (см. «Чего сегодня нельзя»).
- **«…история и назначение расходятся по технике: заказ ТС-123 — история ведёт „ЭО-3323“,
  назначено „ЭО-4321“. Выберите, какая машина работает дальше, в окне ремонта истории»**
  (тот же код) — расходится машина, которая числится за заявкой после конца срока. Спрашивается
  только у дверей, **открывающих новые дни**: правка срока вперёд и применение недельной заявки;
  статусу и сокращению срока это расхождение не мешает. Лечится дверью ремонта, поле
  `tailResolution`:
  - `assignment_wins` — история догоняет назначение: на `dateTo + 1` пишется граница с машиной
    назначения, само назначение и ставки не трогаются;
  - `history_wins` — назначение переводится на машину истории вместе со ставками (арендной нужна
    цена за час или за смену). Это **переключение уже принятого** `assignment_wins`; первый выбор
    «работает машина истории» делается обычной сменой техники.

  Отсюда четыре отказа-подсказки двери ремонта: «Портал уже записал, что после конца срока за
  заявкой числится машина назначения. Переигрывают это решение выбором «работает машина истории»…»;
  «История и назначение сходятся на конце срока — за заявкой числится одна и та же машина, и
  выбирать не из чего. Обновите карточку заявки…»; «Портал ещё не записывал, какая машина числится
  за заявкой после конца срока, — переигрывать нечего. Первый раз машину истории выбирают обычной
  сменой техники заказа…»; «Срок работ продлили, и запись о машине после конца срока попала внутрь
  срока — она описывает рабочие дни, и этой дверью уже не снимается. Снимайте её обычной отменой
  изменения в истории заявки».

- **«Коррекция задевает действующие листы ЭСМ-2 (№ …): переоформить их по отрезкам портал пока не
  умеет — недельная сверка знает одну машину на заявку и переписала бы эти недели машиной
  назначения, то есть ровно вопреки правке. Переоформление по отрезкам включится вместе с
  переключением чтения истории; до него правьте историю на днях, которых действующие листы не
  касаются»** (422) — задет действующий лист. Номера предпросмотр называет заранее и отказом не
  отвечает: посмотреть, какие недели заняты бумагой, и брать дату вне их. Если правка нужна именно
  на этих днях — она откладывается до этапа 5 либо идёт обычной сменой техники с переоформлением
  всей бумаги заявки.
- **«Исполнить эту команду нечем: до переключения чтения истории портал печатает во всех листах,
  которые выписывает, одного машиниста — того, кто работает на день расчёта, — а листам с
  2026-03-09 нужен другой. Смена машиниста отрезком включится вместе с переключением чтения;
  сейчас машиниста меняют датой не позже сегодняшней, и работает он до конца срока»** (422) —
  плановая смена машиниста будущей датой на заявке, по которой идёт бумага. Недельная сверка,
  которая эти листы выписывает, знает **одного** машиниста заявки и напечатает его во всех
  выписанных бланках; команда, после которой бумаге нужен другой человек, ей неисполнима. Выход
  один и назван в тексте: назначать датой не позже сегодняшней. Отвечают одинаково предпросмотр и
  боевая ручка — по кругу «предпросмотр обещал, команда отказала» человек больше не ходит.
- **«Такая дата режет уже выписанную неделю надвое, а до переключения чтения истории портал ведёт
  бумагу неделями: выберите границу недели или границу существующего листа»** (422) — гейт
  совместимости у команды машиниста: пока бумага ведётся неделями, дверь пропускает только те
  команды, у которых отрезковый и недельный планы совпадают. Этот отказ теперь означает именно
  разрез недели: дата, совпадающая с границей недели или существующего листа, его не получает.
- **«Дата за пределами срока работ: запись, которая ждёт продления срока, включается вместе с
  переключением чтения истории»** (422) — дремлющая запись за концом срока пока не заводится: при
  продлении она ожила бы, и старый расчёт разошёлся бы с новым. Отмена такой записи при этом
  разрешена.
- **«Список отработанных листов, которые переоформит операция, изменился»**, **«Список
  переоформляемых бланков изменился»** (422) и **«Бумага заявки не сошлась с составом по датам —
  операция отменена»** (409, код `assignment_paper_diverged`) — между предпросмотром и командой
  бумагу заявки тронули. Повторить с нуля: предпросмотр, затем команда. Прежняя вторая дорога к
  этому 409 — смена машиниста будущей датой — закрыта отказом выше, и теперь сюжет у него один.
- **«Ремонт занёс бы в историю новые пробелы: 2026-03-02 (нет данных), …»** (422, код
  `assignment_blockers_introduced`) — команда сняла бы одну дыру и открыла другую; не записано
  ничего. Частичный ремонт разрешён, ухудшение — нет.
- **Нет права** (403). Права спрашиваются по **посчитанному исходу**, а не по составу тела: смена
  машиниста сегодняшней датой коррекционных прав не требует, та же команда мартовской датой —
  требует.
  - «Изменение задевает прошедшие дни — правит их тот, у кого есть право коррекции задним числом» и
    «Ремонт трогает прошедшие дни: нужно право на коррекцию задним числом» — нужен
    `waybills.correct` (администратор и диспетчер);
  - «Изменение глубже тридцати дней — такую коррекцию проводит администратор» и «Такую давность
    правит администратор: попросите его выполнить коррекцию истории» — нужен
    `waybills.correctBeyondLimit` (неотчуждаемое, только администратор);
  - «Вывод заявки из архива — администраторское действие» — нужен `archive.restore`.
- **Заявка в архиве**:
  - команда машиниста и периодная коррекция отвечают **404 «Заявка не найдена»**: архив они не
    открывают вовсе;
  - дверь ремонта открывает архивную заявку **по идентификатору** и без `archive.read` — но
    отвечает «Ремонт разошёлся бы с действующими бланками архивной заявки — включите режим
    восстановления» либо «Решение о машине после конца срока у архивной заявки принимается только
    вместе с восстановлением — включите режим восстановления».
    Мягкое удаление сверку не зовёт, поэтому листы, выписанные до архивирования, остаются
    действующими, и «бесплатного» ремонта архивной заявки с непустым бумажным планом не бывает.
    Режим `restore` снимает архив **той же транзакцией**, требует `archive.restore`, и половинчатого
    исхода «историю починили, а архив не сняли» не бывает;
  - «Заявка не в архиве — восстанавливать нечего» — `restore` прислан живой заявке.
- **«Модуль периодов назначения закрыт на запись (заморожена история) — операция недоступна»**
  (503, код `assignment_mode_frozen`) — идёт откат или cutover. `history_frozen` закрывает двери,
  пишущие историю; `all_frozen` — ещё и ручную выписку ЭСМ-2 со всеми ручками смен. Вины запроса
  здесь нет: посмотреть режим (`assignment-mode status`) и дождаться разморозки.
- **«Управляющая строка модуля периодов назначения не найдена — запись остановлена»** (503, код
  `assignment_mode_unavailable`) — строки в `assignment_periods_control` нет, и модуль fail-closed
  остановил запись целиком. Строку заводит миграция `0167`, а удалить её триггером нельзя — значит
  был `TRUNCATE` или ручное вмешательство. Не вставлять новую наугад: она несёт режим, и «нормальный
  по умолчанию» откроет запись там, где всё было заморожено. Сначала журнал переходов
  (`assignment_periods_mode_transitions`) и последний дамп.

### Переключение чтения на историю (cutover)

Операция необратимая по последствиям и делается один раз. Порядок ниже — не рекомендация, а условие:
дверь перехода проверяет каждый его шаг и без доказательств не пропустит.

**Что должно сойтись до окна.**

1. **Данные готовы.** У всех заявок предиката (заказ спецтехники «В работе»/«Выполнена» со сроком,
   включая архивные) `assignment_history_state = 'ready'`. Доводит массовый прогон:

   ```bash
   # сначала dry-run — он ничего не пишет и печатает те же числа
 docker compose -f deploy/docker-compose.yml -p technic --profile tools run --rm assignment-backfill --state=/var/lib/technic/backfill.json
   # затем запись
   docker compose … run --rm assignment-backfill --apply --state=/var/lib/technic/backfill.json
   ```

   Тот же прогон с флагом `--revalidate` делает **другую** работу: не достраивает пустую историю, а
   пересчитывает валидность непустой под заданным днём. Он нужен в самом окне (шаг 1a ниже), а до
   окна им проверяют, что пересчёт проходит без отказов.

   Заявки, которым историю строить не из чего (в работе, но без назначенной машины), прогон
   пропустит: это работа диспетчера, а не оператора. Их список — в отчёте и в сводке.

2. **Клиентский гейт пройден** (И5): срок работ никто не правит старым широким маршрутом. Метрика
   `technic_assignment_legacy_period_calls` показывает число за неделю; ноль — условие перехода.
   Кто ходил:

   ```bash
   psql "$DATABASE_URL" -c "select created_at, entity_id, metadata
     from audit_log where action = 'assignment.legacy_period_call'
     order by created_at desc limit 20;"
   ```

3. **Сводка готовности зелёная.** Она и есть машинный вердикт: два яруса — `data` (готовность
   заявок, снимается прогоном) и `window` (заморозка, поколение, аттестация, гейт — снимается в
   самом окне).

   ```bash
 docker compose … run --rm assignment-report # человеку
 docker compose … run --rm assignment-report --json # машине
 docker compose … run --rm assignment-report --data # только ярус данных
   ```

**Окно выката.** Здесь считаются минуты: заморозка останавливает запись всему модулю, и портал в это
время «не сохраняет заявки».

```bash
# 1. Заморозить запись целиком и дождаться завершения активных писателей
docker compose … run --rm assignment-mode set --write=all_frozen --actor=<email> --reason='cutover истории назначения' --build=<sha>

# 1a. Ревалидация: пересчёт состояния всей непустой истории под единым днём. Обязательна и
#     обязательно здесь — календарь двигает границу изменяемого сам, каждую полночь, а дверь
#     активации требует `validated_on = день поколения` у всех заявок. 3 тыс. заявок — 7 секунд.
docker compose … run --rm assignment-backfill --revalidate --apply

# 2. Поколение теневого сравнения — на сегодняшний день и на раскатанной сборке
docker compose … run --rm assignment-shadow start --build=<sha> # печатает run-id
docker compose … run --rm assignment-shadow run --run=<run-id> # считает цели манифеста
docker compose … run --rm assignment-shadow finalize --run=<run-id> # исход: completed или mismatch

# 3. Аттестация раската — её пишет тот, кто раскатывал (годна 30 минут, на одно переключение)
docker compose … run --rm assignment-attest --build=<sha> # печатает attestation-id

# 4. Сводка обязана быть зелёной именно с этим поколением
docker compose … run --rm assignment-report --build=<sha> --run=<run-id>

# 5. Переключение чтения. Дверь проверит всё заново под блокировкой и запишет cutover_run_id
docker compose … run --rm assignment-mode set --read=history --actor=<email> --reason='cutover истории назначения' --build=<sha> --run=<run-id> --attestation=<attestation-id>

# 6. Разморозить запись
docker compose … run --rm assignment-mode set --write=normal --actor=<email> --reason='cutover завершён' --build=<sha>
```

**Почему шаги нельзя переставить.** Поколение, снятое до заморозки, доказывает состояние, которое
успело измениться: legacy-транзакция, начатая до проверки, закоммитит старый план уже после того,
как прогон увидел ноль. Поколение, пережившее полночь, дверь не примет вовсе — календарь двигает
валидность истории сам. Аттестация живёт 30 минут и потребляется один раз: снятая заранее «чтобы
была» протухнет к шагу 5.

**Что делать с отказом двери.** Каждый её отказ называет предмет: незавершённое поколение,
расхождения в манифесте, неготовые заявки, поднятый `dirty`, чужая сборка, ненулевой гейт. Ни один
не обходится — все они и есть смысл операции. Разбирать по сводке: она печатает то же самое числами
и номерами заявок.

### Откат

**Точка невозврата — не переключение чтения, а появление пользовательских команд** (они выкачены).
До них история была производной и пересобиралась из бумаги и назначения; после — в ней есть то,
чего в бумаге нет вовсе: отмены решений, автор и время решения, операции коррекций и якоря.
Пересборка потеряет их молча.

Поэтому откат — это не «вернуть старую сборку», а **остановить двери и вернуть старую сборку**.
Останавливать нужно не те, что историю меняют, а все, что читают её ради бумаги: старая сборка
испортит документы, не тронув ни одной строки истории.

| Дверь                                                            | При откате                                                                    |
| ---------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| команда машиниста, ремонт, коррекция назначения, смена техники   | остановлены                                                                   |
| статус, правка срока, досрочное завершение, недельное применение | остановлены — читают историю ради бумаги                                      |
| восстановление из архива                                         | остановлено                                                                   |
| ручная выписка `on_demand`, сохранение и подпись смен            | разрешены в `history_frozen` (откат) и **запрещены** в `all_frozen` (cutover) |
| чтение карточек, журналов, кабинет водителя                      | разрешено                                                                     |

Порядок:

```bash
# 1. Режим: history_frozen при откате, all_frozen при незавершённом cutover
docker compose … run --rm assignment-mode set --write=history_frozen --actor=<email> --reason='откат релиза истории' --build=<sha>

# 2. Дождаться завершения активных писателей и убедиться, что новых записей нет
psql "$DATABASE_URL" -c "select max(created_at) from vehicle_request_assignment_changes;"

# 3. Откатить API на нужный образ (digest — в журнале выката)

# 4. Обязательный путь возврата к работе: history_frozen → all_frozen + полная revalidation → normal
docker compose … run --rm assignment-mode set --write=all_frozen --actor=<email> --reason='возврат после отката' --build=<sha>
docker compose … run --rm assignment-backfill --revalidate --apply
docker compose … run --rm assignment-report # dirty и stale должны быть нулями
docker compose … run --rm assignment-mode set --write=normal --actor=<email> --reason='после отката: история пересчитана' --build=<sha>
```

Шаг 4 не формальность: в `history_frozen` разрешены `on_demand`, сохранение и подпись смен — они
двигают отменяемость бумаги, а откатившаяся сборка пересчёта не делает. Флаг `dirty` для этого и
заведён; его ненулевое значение запирает и разморозку, и cutover.

**Возврат чтения** (`history → legacy`) дверь разрешает всегда и доказательств не требует: запрет
стоит на включении, а не на выключении. Но это деградированный режим, а не восстановление обычной
работы: бумага снова ведётся неделями, а разрезы, сделанные после переключения, из неё не выводятся.

**Обратный прогон** (удалить историю и вернуть заявкам `empty`) — крайняя мера, и он проверяет
предикат обратимости заново под блокировкой каждой заявки: строку, которую человек отменил вручную,
прогон не тронет и вынесет заявку в отчёт.

```bash
docker compose … run --rm assignment-rollback --dry-run
docker compose … run --rm assignment-rollback --apply
```

### Как довести историю заявки до полной

Состояний три, и хранятся они прямо в заявке. `empty` — строк нет; `materialized` — строки есть, но
на изменяемой части остались дни без машиниста (`unknown`) или со снятым машинистом у собственной
машины (`cleared`); `ready` — история полна. Изменяемая часть — это дни, чей лист ещё можно
аннулировать (`period_to >= сегодня`), плюс будущее, обрезанные сроком заявки: за отработанное
прошлое портал человека не требует, иначе ни одна старая заявка не стала бы `ready` никогда.

```bash
# Состояние конкретного заказа
psql "$DATABASE_URL" -c "select r.num, r.status, r.deleted_at is not null as archived,
  r.assignment_history_state, r.assignment_history_validated_on, r.assignment_history_dirty,
  d.date_from, d.date_to
  from vehicle_requests r
  join special_equipment_request_details d on d.request_id = r.id
  where r.num = 123;"

# Срез по всем заказам спецтехники
psql "$DATABASE_URL" -c "select assignment_history_state, count(*) from vehicle_requests
  where request_type = 'special_equipment' and deleted_at is null group by 1 order by 1;"

# Сама история заказа: что и когда решали, что погашено
psql "$DATABASE_URL" -c "select c.effective_date, c.dimension, c.vehicle_id, c.driver_state,
  c.origin, c.change_group_id, c.superseded_kind
  from vehicle_request_assignment_changes c
  join vehicle_requests r on r.id = c.request_id
  where r.num = 123 order by c.effective_date, c.dimension;"
```

Что делать по состоянию:

- **`ready`** — делать нечего. Расхождение «машина назначения против машины на конце срока»
  готовности не отменяет: это предупреждение, а не блокер, и мешает оно только продлению срока.
- **`materialized`** — лечится дверью ремонта: якорями на границах, которые назвал предпросмотр, и
  решением о машине после конца срока. Ремонт по частям разрешён: снять июньскую дыру, оставив
  сентябрьскую, — законный исход, состояние останется `materialized` и поднимется до `ready`, когда
  снимут последнюю. Дни блокеров предпросмотр отдаёт интервалами (`blockedDays`) — их у многолетней
  заявки бывают тысячи, и списком они не ходят.
- **`empty`** — «строк ещё нет», а не «работать нельзя». Историю строит автомат готовности, и зовут
  его три двери истории (расчётом — на входе, записью — шагом 11) и восстановление из архива:
  первое же обращение к такой заявке достраивает её по назначению и выписанным листам и записывает
  состояние. Машина начала срока берётся из назначения, смены шкалы — по границам листов, а человек
  **назад не тянется**: дни до первого листа получают `unknown`, потому что бумага о них молчит.
  Заявка остаётся `empty` только тогда, когда достроить историю не из чего, — и тогда дверь
  называет причину (см. отказы выше и запросы ниже). Массовый прогон по всей базе — этап 4; до него
  заявки, к которым никто не подошёл, так и стоят `empty`, и это нормально.
- **`assignment_history_dirty = true`** — внутри дня заявку тронули ручки, двигающие бумагу или её
  отменяемость (сохранение, удаление, подпись и снятие подписи смены, ручная выписка ЭСМ-2). Метка
  говорит «пересчитать состояние, не дожидаясь смены суток», и снимает её один-единственный путь —
  тот же автомат готовности, то есть команда истории или восстановление из архива. Сама по себе она
  не авария: заявки, к которым за день не подошла ни одна дверь, разбирает массовый пересчёт перед
  cutover. Значение метка получает к разморозке модуля: пока хоть одна поднята, переход в «обычный
  режим» отвечает «Разморозка запрещена: у N заявок поднята метка загрязнения истории».

**Чего бэкфилл честно не восстановит.** Заявка, историю которой из бумаги однозначно не построить,
остаётся `empty` без единой строки, и это лучше выдуманной истории: заявку без истории видно, а с
выдуманной — нет. Причин три, и все три ищутся заранее:

```bash
# 1. no_assignment — нет назначения, а из него берётся машина начала срока и после его конца
psql "$DATABASE_URL" -c "select r.num, d.date_from, d.date_to
  from vehicle_requests r
  join special_equipment_request_details d on d.request_id = r.id
  left join vehicle_request_assignments a on a.request_id = r.id
  where r.request_type = 'special_equipment' and r.assignment_history_state = 'empty'
    and a.request_id is null order by r.num;"

# 2. ambiguous_sheets — два действующих листа с одной датой начала (машины разные: тройка
#    «заказ + начало + машина» уникальна)
psql "$DATABASE_URL" -c "select r.num, w.period_from, count(*) as sheets
  from waybills w
  join vehicle_requests r on r.id = w.source_request_id
  join vehicle_types t on t.id = r.vehicle_type_id
  where w.status <> 'cancelled' and w.period_from is not null
    and coalesce(r.is_linear_frozen, t.is_linear) = false
  group by r.num, w.period_from having count(*) > 1 order by r.num;"

# 3. overlapping_sheets — периоды действующих листов пересекаются
psql "$DATABASE_URL" -c "select r.num, a.id as sheet_a, b.id as sheet_b,
  a.period_from, a.period_to, b.period_from
  from waybills a
  join waybills b on b.source_request_id = a.source_request_id and b.id <> a.id
  join vehicle_requests r on r.id = a.source_request_id
  join vehicle_types t on t.id = r.vehicle_type_id
  where a.status <> 'cancelled' and b.status <> 'cancelled'
    and coalesce(r.is_linear_frozen, t.is_linear) = false
    and a.period_from < b.period_from and b.period_from <= a.period_to order by r.num;"
```

Линейные заказы в двух последних запросах исключены намеренно: у них неделю законно закрывают два
листа разных машин, и история им строится не из бумаги, а одной строкой из назначения.

Что делать с находками: у первой — назначить технику (без неё восстанавливать не от чего); у второй
и третьей — разобрать бумагу и **аннулировать лишний лист**, оставив по неделе один действующий.
Пока неоднозначность в листах живёт, заявка останется `empty`, и двери истории будут на ней закрыты.

Заявка «Выполненная» ремонтируется тем же порядком, что и всякая правка выполненного заказа
(ADR 0101): администратор возвращает её в работу (`requests.rollbackStatus`), диспетчер исправляет,
заявку закрывают заново. Причину вписывают в **оба** статусных события — иначе в журнале останется
необъяснимый откат.

### Чего сегодня нельзя — и почему это нормально

- **Разрезать неделю пока нельзя — исполняет её недельная сверка.** Отрезковый план считается и
  показывается предпросмотром, но пока `read_mode = legacy`, бумагу пишет прежний путь: он знает
  одну машину и одного машиниста на заявку. Отсюда три отказа, и все три — про одно: команда
  машиниста проходит, только если отрезковый и недельный планы совпадают по документам (границы
  недели) **и** по человеку (дата не позже сегодняшней), а периодная коррекция, задевающая
  действующий лист, отвергается до единой записи. Снимаются они переключением чтения — все три
  разом, отдельной ветки в коде для этого нет.
- **Часть отказов работает диагностикой, а не запретом.** Пока `read_mode = legacy`, бэкстоп чужих
  дверей считает вердикт, пишет его в журнал и **пропускает операцию**. Это сделано нарочно:
  включи отказы сейчас — продление заявки с неизвестным машинистом стало бы тупиком, потому что
  чинить историю нечем (дата ремонта обязана лежать внутри срока, которого ещё нет).

  ```bash
  # Что задели чужие двери и чем именно
  psql "$DATABASE_URL" -c "select a.created_at, r.num, a.metadata->>'door' as door,
    a.metadata->>'readMode' as read_mode,
    jsonb_array_length(coalesce(a.metadata->'requiredAnchors','[]'::jsonb)) as anchors,
    a.metadata->'requiredVehicleResolution' as tail
    from audit_log a
    left join vehicle_requests r on r.id::text = a.entity_id
    where a.action = 'assignment.backstop_shadow'
    order by a.created_at desc limit 50;"
  ```

  Не заглядывая в базу, то же видно метрикой `technic_assignment_backstop_shadow{door}` в
  `GET /metrics` на `technic-api:3000`. Она процессная и растёт с запуска: перезапуск обнуляет, и
  это нормально — счётчик отвечает на вопрос «идти ли смотреть», а «что именно» отвечает журнал.

- **История ничего не решает в бумаге и в кабинете.** До переключения чтения задание водителя,
  занятость гаража, отбор заявок по машине и срез «Техника на площадке» идут от назначения. Заявка
  с неполной историей работает как прежде — модуль на неё пока только смотрит.

**Заполнение неизвестных дней (`knownFills`) открыто** с 24.08.2026: бухгалтерия согласовала выписку
бланков задним числом. Там, где листа за эти дни не было вовсе (а `unknown` восстановление ставит
именно туда), сверка **выпишет недостающие бланки** на прошедшие даты — номера показываются
предпросмотром до нажатия. Свернуть фичу обратно — одно значение `KNOWN_FILLS_ENABLED` в
`services/assignment-repair.ts`; сервер тогда отвечает `409 backdated_issue_not_authorized`, а
остальной ремонт (якоря и решение о машине после конца срока) от него не зависит.

### Кто что может

| Действие                                                   | Право                                      | Кто держит                                         |
| ---------------------------------------------------------- | ------------------------------------------ | -------------------------------------------------- |
| Смотреть историю; предпросмотр смены машиниста и коррекции | `vehicleRequests.read` + `waybills.read`   | администратор, менеджер, диспетчер                 |
| Предпросмотр ремонта и любая боевая команда истории        | `vehicleRequests.status` + `waybills.read` | администратор, менеджер, диспетчер                 |
| Правка, задевающая прошедшие дни                           | + `waybills.correct`                       | администратор, диспетчер                           |
| То же глубже тридцати дней                                 | + `waybills.correctBeyondLimit`            | только администратор (право неотчуждаемое)         |
| Ремонт архивной заявки с `restore`                         | + `archive.restore`                        | только администратор                               |
| Вернуть «Выполненную» в работу                             | `requests.rollbackStatus`                  | администратор, диспетчер                           |
| Смена режима модуля (заморозка, чтение)                    | HTTP-двери нет вовсе                       | maintenance-доступ к БД, команда `assignment-mode` |

Три уточнения, которые в таблицу не помещаются:

- **Менеджер** входит в двери, но правку прошлого не проводит: `waybills.correct` у него нет, и
  историческая команда упрётся в 403. Смена машиниста сегодняшней датой ему доступна — а будущей
  датой её сегодня не проводит никто, независимо от прав (см. «Исполнить эту команду нечем»).
- **Площадка** (роль «Площадка», а также штаб и руководитель строительства) машиниста не называет
  никогда и `anchors` не присылает: её правка срока работ — чужая дверь, и максимум, что она
  получит, — отказ бэкстопа с указанием, к кому идти. Право на её стороне одно —
  `vehicleRequests.update` (полномочие «Заказ техники»), и открывать ей двери истории не нужно.
- **Архивную заявку** дверь ремонта открывает по идентификатору и `archive.read` не требует — это
  намеренное отступление, сделанное ради диспетчера: `archive.read` означает «видит удалённые
  записи» во всём модуле записей, то есть открыло бы ему весь архив портала. Дверь архив не
  показывает ни в списках, ни в поиске, а запрошенный идентификатор и результат идут в аудит.
