# План: смена адреса электронной почты учётной записи администратором

Сегодня адрес учётки задаётся один раз — при саморегистрации или при заведении администратором — и
дальше не правится: в форме карточки поле `email` выключено (`UsersTab.tsx:1096`), а портал вырезает
его из тела `PATCH` (`UsersTab.tsx:378`). Человеку, у которого сменился рабочий ящик, портал
предлагает только одно — завести вторую учётку, а первую отправить в архив. Это теряет привязку
заявок, путевых листов и журнала к тому же человеку.

Задача: дать администратору сменить адрес живой учётки — с предупреждающим окном, письмами на оба
адреса и без потерь на связях, которые за адрес держатся.

Документ — вход для ADR и для работ; сам по себе он ничего не меняет.

---

## 1. Где адрес учётки работает сегодня

Адрес — не просто поле карточки: это **логин**, **ключ занятости**, **адресат писем** и **признак
подтверждённости**. Ниже — все места, где он что-то решает, и что с ними станет при смене.

| Место                                                                                   | Что решает адрес                                                                              | Что будет при смене                                                                                                      |
| --------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `POST /auth/login` (`auth.ts:501`)                                                      | вход по паре «адрес + пароль» среди живых учёток                                              | старым адресом войти нельзя — человек **обязан** узнать новый, иначе смена читается им как поломка портала               |
| `users_email_unique` — частичный UNIQUE `WHERE deleted_at IS NULL` (ADR 0063)           | занятость: адрес занимает действующая учётка, архивная его освобождает                        | новый адрес обязан быть свободен; гонка двух запросов доходит до индекса — нужен разбор `23505`                          |
| `assertEmailFree` (`services/user-email.ts`)                                            | одна проверка занятости на три входа: регистрация, создание, восстановление                   | появляется **четвёртый** вход — он обязан звать её же, иначе ответы разойдутся                                           |
| `POST /users/:id/restore` (`users.ts:841`)                                              | восстановление требует свободного адреса                                                      | заняв адрес архивной учётки, смена делает её невосстановимой — это допустимо, но администратор должен это увидеть        |
| `users.email_verified_at` (ADR 0072)                                                    | активацию заявки, отбор в дайджест (`role-digest.ts:74`), образцы писем (`admin-mail.ts:210`) | сброс в `null` **молча** выключает человеку ролевые дайджесты                                                            |
| `user_email_tokens` — `verify_email`, `password_reset` (миграция 0098)                  | живые ссылки из уже отправленных писем                                                        | ссылка, ушедшая на **старый** ящик, останется рабочей: его владелец сбросит пароль и войдёт уже по новому адресу         |
| refresh-сессии + `users.auth_version`                                                   | живой доступ выданных токенов                                                                 | без повышения версии сессии продолжают работать — вопрос политики, см. §3 Р3                                             |
| `mail_messages.to_email` + UNIQUE `(kind, dedupe_key)` (миграция 0097)                  | снимок адресата и дедупликацию писем                                                          | журнал переписывать не нужно — он снимок; но **ключ нового письма обязан содержать время**, иначе вторая смена промолчит |
| `persons.email` (ADR 0008) и рассылка `driver_routes` (`mailings/driver-routes.ts:288`) | адрес водителя в справочнике — отдельная сущность                                             | **не меняется** вместе с учёткой: задания на рейс продолжат уходить на прежний ящик                                      |
| `audit_log` (ADR 0088)                                                                  | разбор «кто и когда»                                                                          | нужны своё действие и подпись: `user.update` про смену логина ничего не скажет                                           |
| `seed-admin.ts:41` (`ADMIN_EMAIL`)                                                      | идемпотентность сида: «такой уже есть — пропуск»                                              | сменив адрес администратора, следующий прогон сида заведёт **вторую** учётку со старым адресом                           |
| `isInternalEmail` (ADR 0090)                                                            | пометку «внешняя почта»                                                                       | новый адрес может оказаться внешним — предупреждение в окне                                                              |
| `/auth/me`, `AuthContext`                                                               | показ адреса в шапке портала                                                                  | сменив адрес себе, администратор должен увидеть новый, а не прежний из кеша                                              |

Чего в этом списке **нет** — и это важно: адрес не хранится снимком ни в одной бизнес-сущности.
Заявки, путевые листы, рейсы, назначения ссылаются на `users.id`; контактного email у заявок нет
вовсе (проверено поиском `contact_email` — пусто). Учётки создаются ровно в трёх местах
(`routes/users.ts`, `routes/auth.ts`, `seed-admin.ts`), адрес правится нигде. Значит смена адреса
не рвёт историю: рвутся только вход, письма и подтверждённость — то есть ровно то, что перечислено
выше.

## 2. Решения

**1. Отдельная ручка `POST /users/:id/email`, а не поле в `PATCH /users/:id`.**
У правки карточки другой смысл: она меняет права и область, а сохраняется целиком и мимоходом.
Смена логина — событие с побочными действиями (гашение ссылок, отзыв сессий, два письма) и со своей
записью в журнале; получи она вид «ещё одного поля формы», её нельзя было бы ни подтвердить окном,
ни отличить в аудите от смены телефона. Тот же довод, по которому отдельными ручками сделаны сброс
пароля (`/:id/password`) и отказ по заявке (`/:id/reject`).

**2. Право — `users.manage`**, как у остальных операций с учётками. Новое право не заводится: тот,
кто выдаёт роли и сбрасывает пароли, уже распоряжается доступом целиком, и отдельное право на смену
адреса разделило бы то, что в жизни делает один человек.

**3. Смена одношаговая: адрес, который ввёл администратор, считается проверенным им же.**
`email_verified_at` ставится в `now()` — ровно так же, как при заведении учётки администратором
(`users.ts:439`, ADR 0072). Причина не в удобстве: сброс в `null` тихо выключает человеку ролевые
дайджесты (`role-digest.ts:74` отбирает только подтверждённых), а при включённом
`EMAIL_VERIFICATION_ENABLED` ещё и запирает активацию — то есть административная правка контакта
превращалась бы в скрытое поражение в правах. Двухшаговая схема разобрана как альтернатива в §7.

**4. Заявке на регистрацию адрес не меняют.** Нерассмотренная заявка (`role IS NULL AND NOT
is_active`) — это утверждение заявителя о себе, включая ящик; переписав адрес и одобрив заявку,
администратор выдал бы доступ ящику, который заявку не подавал, и подтверждение адреса (ADR 0072)
перестало бы что-либо значить. Такую заявку отклоняют, а человек подаёт новую — 400 с этим текстом.

**5. Оба письма — правило, а не галочка.** Смысл письма на **старый** адрес — сигнал владельцу
ящика: «твой доступ переписали, и если это не ты — скажи администратору». Галочка «уведомить»
превращает сигнал в необязательный, а именно в случае злоупотребления её и снимут. Письмо на
**новый** адрес — то, без чего человек не узнает, чем теперь входить. Отдельного вопроса
администратору здесь нет; на выключенной почте операция не отменяется, но исход отправки
возвращается (`MailOutcome`, как у писем о доступе) и показывается сообщением.

**6. Живые ссылки гасятся, сессии отзываются.** `revokeEmailTokens` по обоим назначениям в той же
транзакции: письмо со ссылкой сброса, ушедшее на прежний ящик, иначе остаётся действующим ключом от
учётки с новым адресом. `auth_version + 1` и `revokeAllForUser` после фиксации — по правилу смены
пароля (`auth.ts:451`): адрес меняют в том числе тогда, когда прежний ящик потерян или
скомпрометирован, и оставлять на устройствах живые токены в этот момент нельзя.

**7. Новый адрес вводится дважды.** Опечатка в адресе — это одновременно потеря входа и уход писем
неизвестно кому, причём портал её не заметит: адрес синтаксически верен. Повторный ввод в окне
(поля не совпали — форма не отправляется) стоит одной строки и ловит ровно этот случай.

**8. Свой адрес администратор меняет с вводом текущего пароля.** Запрет «себе — нельзя», как у
деактивации и смены роли (`users.ts:507`), здесь не годится: у единственного администратора не
осталось бы пути вовсе. Пароль подтверждает, что за клавиатурой владелец учётки, — и это же
защищает от смены логина через оставленную открытой сессию.

**9. Чужую администраторскую учётку не трогают: адрес учётки с ролью `admin` меняет только её
владелец.** Смена логина — это передача входа в учётку, у которой права портала полные; будь она
доступна другому администратору, любой из них мог бы увести чужой полный доступ на свой ящик за два
действия и без ведома владельца. Отказ — 403 с прямым текстом: «Адрес учётной записи администратора
меняет только её владелец».

Путь на случай, когда владелец потерял доступ к ящику, при этом остаётся и проходит через уже
существующие ручки: второй администратор сбрасывает ему пароль (`POST /users/:id/password`, пароль
передаётся лично), тот входит и меняет адрес себе — с вводом этого пароля по решению 8. То есть
доступ восстанавливается, но каждый шаг остаётся в журнале отдельной записью, а смена логина
по-прежнему требует знания пароля.

Это правило новее остальных операций с учётками и **шире их не распространяется**: сброс пароля и
смена роли чужому администратору сегодня разрешены. Расхождение осознанное — смена адреса уводит
учётку целиком и тихо (владелец узнаёт о ней только письмом), а сброс пароля владелец обнаруживает
первым же входом. Если правило решат распространить на остальные операции, это отдельная работа по
плану реструктуризации прав.

**9. В аудит — своё действие `user.change_email` с адресами «было → стало»** и исходом писем.
Адреса в метаданных — не избыточность: после смены по `entityId` виден только текущий адрес, а
вопрос разбора звучит «на что и с чего его переписали». Тот же приём уже применён в `user.purge`
(`users.ts:891`).

## 4. Поведение ручки

`POST /users/:id/email`, право `users.manage`.

Тело: `{ newEmail: string, currentPassword?: string }` — пароль обязателен и проверяется только
когда `id === actor.id` (решение 8).

Порядок внутри транзакции — он же порядок отказов:

1. `SELECT … FOR UPDATE` по строке учётки; нет строки или `deleted_at` — 404 (Р11).
2. Чужая учётка с ролью `admin` — 403 (решение 9, Р15). Роль читается из **заблокированной строки**,
   а не из списка, показанного порталу: иначе роль, выданную секундой раньше параллельной правкой,
   проверка не увидела бы.
3. Нерассмотренная заявка — 400 с текстом решения 4 (Р8).
4. Адрес совпадает с текущим (сравнение `citext`, регистронезависимое) — 400 «Адрес совпадает с
   текущим»: письмо о несостоявшейся смене и запись в журнале о ней одинаково вводят в заблуждение.
5. Своя учётка — проверка `currentPassword` (`verifyPassword`); неверный — 400 с указанием поля.
6. `assertEmailFree(tx, newEmail)` — 409 «Пользователь с таким email уже существует» (Р6).
7. `UPDATE users`: `email`, `email_verified_at = now()`, `auth_version + 1`, `updated_at`.
8. `revokeEmailTokens` по `password_reset` и `verify_email` (Р1).
9. Два письма в очередь через существующий `queueAccessMail` — на новый адрес и на старый, разными
   ключами со временем (Р9).

Вокруг транзакции — `asEmailConflict` (гонка доходит до индекса). После фиксации:
`revokeAllForUser(id)` (Р3) и `writeAudit({ action: 'user.change_email', metadata: { oldEmail,
newEmail, notifiedNew, notifiedOld, shadowsArchived, self } })`.

Ответ: `{ user: UserDto, notifiedNew: MailOutcome, notifiedOld: MailOutcome, shadowsArchived:
boolean }` — где `shadowsArchived` считается тем же запросом, что и проверка занятости (Р5).

## 5. Письма

Оба — новым видом `email_changed` (`mail_kind`), тексты в `services/mail-auth.ts` рядом с
остальными письмами о доступе.

**На новый адрес** — «Адрес учётной записи изменён»: вход теперь по этому адресу, пароль прежний,
все сессии завершены; ссылка на страницу входа (`portalLink()`, проверка `assertOwnOrigin`).
Пароля в письме нет — правило файла.

**На старый адрес** — то же событие с другой стороны: «адрес учётной записи в портале изменён на
другой; если этого не делали вы — свяжитесь с администратором портала». Ссылки нет намеренно, по
доводу письма о смене пароля: доступа по этому адресу больше нет, вести человека в портал некуда.
Новый адрес в этом письме показывается **в маскированном виде** (`i***@su10.ru`): письмо уходит на
ящик, который с этого момента к учётке отношения не имеет, и полный новый адрес — лишнее раскрытие,
а узнаваемости хвоста домена для «это не я» достаточно.

## 6. Изменения по файлам

**Миграция `0122_email_changed_mail_kind.sql`** (`0117`–`0121` застолблены
`docs/office-equipment-upgrade-plan.md`, включая релизную `0121`):

```sql
ALTER TYPE mail_kind ADD VALUE IF NOT EXISTS 'email_changed';
```

Отдельным файлом и без использования значения в той же миграции — PostgreSQL не разрешает
пользоваться новым значением enum до фиксации транзакции (приём миграций 0114, 0103, 0065, 0054).
Миграция аддитивная: смысл существующих данных не меняется, протокол выката необратимых миграций
(`docs/schema-cutover-protocol.md`) не применяется. **Других изменений схемы фича не требует** —
адрес, подтверждённость, токены, журнал писем и аудит уже есть.

**Контракты** (`packages/contracts/src`):

- `users.ts` — `changeUserEmailSchema` (`emailSchema` + необязательный `currentPassword`),
  `ChangeUserEmailInput`, `ChangeEmailResult`.
- `audit.ts` — `'user.change_email'` в `USER_AUDIT_ACTIONS`, подпись «Адрес электронной почты
  изменён администратором» в `userAuditActionLabels`, ветка в `describeAuditEntry`: «было → стало».

**Сервер** (`apps/api/src`):

  `emailChangedNoticeContent` + маскирование адреса.
- `db/schema.ts` — `'email_changed'` в `mailKindEnum` (вслед за миграцией).

**Портал** (`apps/web/src`):

- `api/resources.ts` — `usersApi.changeEmail`.
- `pages/admin/ChangeEmailModal.tsx` — предупреждающее окно (по образцу `RejectRegistrationModal`):
  «было → станет», два поля нового адреса, поле текущего пароля при смене себе, список последствий
  (вход только по новому адресу; все сессии завершены; ссылки восстановления погашены; письма уйдут
  на оба адреса), предупреждение о внешнем домене (`isInternalEmail`, ADR 0090) и строка про адрес
  водителя в справочнике (Р10). Кнопка подтверждения — `danger`.
- `pages/admin/UsersTab.tsx` — пункт «Сменить email» в меню строки рядом со «Сменить пароль»,
  только для живых учёток и не для нерассмотренных заявок; у чужой учётки с ролью `admin` пункта
  нет вовсе (решение 9) — недоступного портал не показывает даже выключенным (ADR 0033 §6), иначе
  выключенный пункт обещал бы действие, которого не бывает. После успеха — инвалидация `['users']`,
  а при смене себе ещё и сессии (Р13); сообщение с исходом писем (`withMailOutcome`) и
  предупреждением про архивную тень (Р5).

**Документы**: ADR `0092-user-email-change.md` (номер перепроверить — `0091` занят
retype-заявкой), строка в `docs/runbook.md` про `ADMIN_EMAIL` (Р12).

## 7. Альтернатива: двухшаговая смена с подтверждением по новому ящику

Смена не применяется сразу: адрес кладётся в `users.pending_email`, на него уходит ссылка
`verify_new_email`, и `users.email` переписывается только переходом по ней.

- Что даёт: опечатка (Р2) не приводит ни к чему — учётка продолжает работать на прежнем адресе.
- Чего стоит: миграция с колонками `pending_email`/`pending_email_at`, новое значение
  `email_token_purpose`, ветка потребления токена в `auth.ts`, состояние «смена в процессе» в
  карточке и в списке, отдельная отмена — плюс ответ на вопрос, что делать, если за время ожидания
  адрес занял кто-то другой.
- Почему не сейчас: при `EMAIL_VERIFICATION_ENABLED = false` (`contracts/src/auth.ts:102`) портал
  вообще не требует подтверждения адресов, и вводить его частным случаем — значит завести второе
  правило на тот же вопрос. Как только подтверждение включат целиком, эта схема станет
  продолжением: `pending_email` ложится поверх готовой ручки, а одношаговая смена остаётся
  административной.

Оценка, если делать сразу: +1,5 дня и одна миграция сверх плана.

## 8. Осознанно вне области

- **Самостоятельная смена адреса пользователем** (страница профиля). Отдельная задача: там
  подтверждение по новому ящику обязательно — за клавиатурой может быть не владелец учётки.
- **Синхронизация `persons.email`.** Адрес водителя в справочнике и адрес учётки — разные вещи:
  задания на рейс получает физлицо, у которого учётки может не быть вовсе (`mail_messages.person_id`
  заведён ровно под это). Переписывать один по другому значило бы решать за администратора; окно
  вместо этого напоминает, где правится второй.
- **Смена адреса архивной учётки** — архив не редактируется нигде в портале; конфликт адресов
  решается в момент восстановления (ADR 0063).
- **Массовая смена домена** (переезд компании на новый домен). Если понадобится — это задача
  миграции данных с отдельным разбором, а не кнопка в карточке.

## 10. Закрытые развилки

Решены 11.08.2026, до начала работ:

1. **Модель смены — одношаговая** (решение 3): адрес применяется сразу, `email_verified_at = now()`,
   подтверждение по новому ящику не запрашивается. Двухшаговая схема остаётся заготовкой на случай,
   когда включат `EMAIL_VERIFICATION_ENABLED` целиком (§7).
2. **Свой адрес — с вводом текущего пароля** (решение 8). **Чужой администраторский — нельзя**
   (решение 9): учётку с полными правами уводит только её владелец, а восстановление после потери
   ящика идёт через сброс пароля вторым администратором.
3. **Сессии отзываются все** (решение 6): `auth_version + 1` и `revokeAllForUser`, как при смене
   пароля.
