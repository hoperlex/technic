## 1. Что просят

В модуле «Заказ автотехники», вкладка **«Заявки»**, фильтр **«Тип ТС»** сегодня принимает одну
позицию классификатора. Просят выбирать **несколько** — и получать одну выдачу по всем выбранным
сразу: «покажи автокраны и самосвалы» одним списком, а не двумя заходами.

Смысл фильтра не меняется: выбирают позиции классификатора (ADR 0028) — тип целиком («Автокраны —
все категории») либо одну его категорию («Автокраны, г/п 130 т»). Множественный выбор — набор таких
позиций, объединяемый по ИЛИ.

## 5. Формат провода и бюджет строки запроса

Портал собирает query через `URLSearchParams` ([http.ts:55](../apps/web/src/shared/api/http.ts#L55)),
то есть `:` кодируется как `%3A`, `,` — как `%2C`. Отсюда счёт:

| Форма                                   | Байт на позицию | 60 позиций | 130 позиций (весь классификатор) |
| --------------------------------------- | --------------- | ---------- | -------------------------------- |
| пара `<uuid>:<uuid>` (редакция 1)       | 75 + 3 = 78     | 4,7 КБ     | 10,1 КБ                          |
| ключ `c<uuid>` / `t<uuid>` (редакция 2) | 37 + 3 = 40     | 2,4 КБ     | 5,2 КБ                           |

Лимит: `large_client_header_buffers` не переопределён ни на edge-nginx, ни на nginx web-контейнера,
значит на обоих прыжках действует дефолт 8 КБ на строку запроса. Полный адрес ленты с предельным
набором — 2,4 КБ фильтра + `classifications=` + остальные параметры (страница, размер, сортировка,
объект, тип заявки, статус, виза, поиск) ≈ **2,9 КБ**, запас ≈ 2,7×. У всего классификатора целиком
(5,2 КБ) место до предела формально ещё остаётся, но запас существенно меньше — это второй довод за
потолок 60 (Р7), помимо того, что «выбрано всё» и «фильтр не задан» — один и тот же вопрос к списку.

Проверка бюджета руками — не «на глаз»: замер П1 в §9 бьёт предельным адресом через оба nginx.

## 6. Переход со старой пары (expand/migrate)

| Релиз | API                                                                                                   | Портал                                                                     | Что видит человек                          |
| ----- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------ |
| **A** | принимает `classifications` **и** старую пару; обе формы сразу — 400 «Фильтр по технике задан дважды» | не меняется, шлёт старую пару                                              | ничего: сервер расширен, поведение прежнее |
| **B** | тот же                                                                                                | множественный выбор во всех четырёх списках, шлёт только `classifications` | сама фича                                  |

Почему граница именно здесь:

1. **Старые вкладки живут неопределённо долго.** «Позже» кладёт `dismissedBuildId` в `useState`
   вкладки, и для этого build баннер больше не покажется — то есть вкладка может остаться на старом
   JS до самого закрытия. Календарного окна, после которого «старых вкладок не осталось», не
   существует.
2. **Откат должен оставаться безопасным.** `deploy-auto --previous` поднимает оба контейнера
   прежнего тега. При разведённых релизах любое сочетание согласовано: откат B возвращает портал
   релиза A против API, принимающего обе формы; откат A (пока B не выкачен) возвращает пару
   «старый портал + старый API».

**Когда-нибудь потом** старую пару можно снять — отдельной работой и только когда появится
принудительный гейт (минимальная версия сборки или версия API), а не по календарю. Снятие означает
**400** на старые поля: молчаливое игнорирование — это ровно тот дефект, ради которого затевался
переход, только отложенный во времени. Тест на 400 пишется вместе с той работой; в этой его нет,
потому что нет и снятия.

## 7. Что меняется по слоям

### 7.1 Контракты (`packages/contracts`)

1. `vehicle-classifications.ts` — рядом с `vehicleClassificationKey` / `parseVehicleClassificationKey`:
   - `classificationFilterKey(typeId, categoryId | null)` → `c<uuid>` либо `t<uuid>` и обратный
     `parseClassificationFilterKey` — ключ фильтра, в отличие от ключа позиции формы;
   - `classificationFilterSchema` — CSV → `{ typeIds: string[]; categoryIds: string[] }`: разбор
     префикса, проверка UUID, `.max(60)` и предел длины строки; пустая строка = «фильтра нет»,
     мусорный ключ = 400 (опечатка должна быть видна);
   - `serializeClassificationFilter(keys: string[])` — дедуп + сортировка по ключу + `join(',')`;
   - `CLASSIFICATION_FILTER_MAX = 60` — одна константа на схему, портал и подпись.
2. `vehicle-requests.ts` — в списочную, «На объекте» и сводочную схемы добавляется
   `classifications`; старая пара остаётся, плюс общая проверка «обе формы сразу — 400»
   (`superRefine`). Журнал получает поле наследованием.
3. `vehicle-request-feed.ts` — `weeklyRowsExcludedBy`: непустой набор **или** старая пара.
4. `garage.ts` — то же в схеме списка машин гаража.

### 7.2 API (`apps/api`)

1. Новый `apps/api/src/lib/classification-filter.ts` с двумя входами и одним выходом:
   - `classificationWhere(typeCol, categoryCol, filter)` — набор: `undefined` при пустом,
     иначе `or(inArray(type, typeIds), inArray(category, categoryIds))` с пропуском пустой ветки;
   - `legacyClassificationWhere(typeCol, categoryCol, { vehicleTypeId, vehicleCategoryId })` —
     **прежнее «И» без изменений**: только тип → `type = t`; только категория → `category = c`;
     оба → `type = t AND category = c`. Приведение старой пары к набору здесь запрещено: пара
     `типA + категорияB` сегодня отвечает пусто, и обязана отвечать пусто и завтра.
2. `routes/vehicle-requests.ts` — четыре точки (`listWhere`, `historyWhere`, `onSiteWhere`,
   `/summary`) вызывают хелпер: набор задан — первая ветка, иначе — legacy-путь.
3. `routes/garage.ts` — то же в `vehiclesWhere`.
4. Комментарии в этих местах переписываются: сегодня они обещают «один тип целиком либо одну его
   категорию».

Когда старая пара будет снята (§6), из этого модуля уходит одна функция и по одной строке в пяти
местах — вся совместимость собрана здесь намеренно.

### 7.3 Портал (`apps/web`)

1. `useVehicleClassifications.ts` — значения `classificationFilterGroups` переводятся на ключи
   фильтра (`classificationFilterKey`). Это единственный потребитель — фильтр; `groups` формы
   заявки остаются на ключе позиции `тип:категория` и не трогаются. После правки `Select`,
   черновик шита и CSV говорят одним ключом, и восстанавливать выбор из справочника не требуется.
2. `shared/ui/listControls.ts` — вид `multiSelect` (значение `string[]`, `maxTagCount`, `maxCount`),
   `FilterDraftValue` расширяется массивом, `isFilterActive` считает пустой массив незаданным.
3. `shared/ui/FilterSheet.tsx` — отрисовка `multiSelect`; `emptyValue` → `[]`; сравнение
   «изменилось ли» по составу набора, а не по ссылке, иначе «Применить» дёргал бы список после
   каждого открытия шита.
4. `hooks/useVehicleClassificationFilter.tsx` — вход `classifications?: string`, наружу
   `onChange({ classifications })` уже канонической строкой; пустой набор → `undefined`, чтобы
   параметр не уезжал вовсе.
5. Четыре страницы (`VehicleRequestsTab`, `VehicleRequestsHistoryTab`, `VehicleRequestsOnSiteTab`,
   `GarageVehiclesTab`): пара полей → `classifications?: string`; на «Заявках» — и в `summaryQuery`.

## 9. Тесты и замеры

**Контракты** (`vehicle-requests-contracts.test.ts`, `vehicle-feed-contracts.test.ts`,
`garage-contracts.test.ts`)

- один ключ — тоже набор; пустая строка = «фильтра нет»; неизвестный префикс, не-UUID и пара
  `uuid:uuid` отвергаются;
- 61 ключ — 400; 60 — проходит;
- канонизация: `A,B` и `B,A` дают одну строку; дубликат схлопывается;
- `classifications` вместе со старой парой — 400; старая пара сама по себе принимается;
- непустой набор исключает недельные строки; старая пара — по-прежнему тоже.

**База** — новый `apps/api/test/classification-filter.db.test.ts`, одна фикстура на все выдачи
(`/`, `/feed`, `/history` + `/history/summary`, `/on-site` + `/on-site/summary`, `/summary`,
`/garage/vehicles` + его сводка — шестая выдача покрыта здесь же, а не в `garage.db.test.ts`:
дублировать случаи в соседнем файле незачем). Отдельной сводки у ленты нет — цифры над ней
считает тот же `GET /vehicle-requests/summary`, что и над списком:

- два типа отдают строки обоих и не отдают третий;
- «весь тип» + категория чужого типа — обе ветки в одной выдаче;
- **категория не тянет соседние категории того же типа** — главный риск раскладки на две ветки;
- набор из одного элемента совпадает со старым поведением пары;
- **несовпадающая старая пара (`типA` + `категорияB`) отвечает пусто** — legacy-«И» сохранено;
- сводки считают по тому же набору, что и их списки.

**Портал**

- `vehicle-feed-tab.test.tsx` — выбор двух позиций уезжает одним `classifications`; снятие одной
  оставляет вторую; полная очистка убирает параметр; сводка запрашивается тем же набором; порядок
  кликов не меняет строку запроса;
- `vehicle-history-filters.test.tsx`, `vehicle-on-site.test.tsx`, `garage-journal.test.tsx` — тот же
  контрол в трёх соседних списках;
- `list-mobile.test.tsx` — `multiSelect` в шите: черновик копит выбор, «Применить» отдаёт набор один
  раз, «Сбросить» чистит, счётчик на кнопке «Фильтры» считает набор одним заданным фильтром.

**Замеры руками**

- **П1 — бюджет адреса.** Предельный запрос (60 позиций + остальные фильтры) через оба nginx на
  dev-хосте: ответ 200, а не 414/400. Не сошлось — снижаем потолок (Р7), а не поднимаем буферы:
  в `conf.d` соседние vhost.
- **П2 — план запроса.** `EXPLAIN (ANALYZE, BUFFERS)` для наборов в 1, 10 и 60 позиций на
  `vehicle_requests` и `vehicles`. Критерий — **время и прочитанные буферы на репрезентативном
  объёме и отсутствие деградации при росте набора**, а не конкретный узел плана: на маленькой
  dev-базе seq scan законен и сам по себе ни о чём не говорит. Замер расходится с ожиданием —
  возвращаемся к вопросу об индексе (и тогда номер миграции берётся заново: потоки нумерации идут
  параллельно).

### Результат П2 (19.08.2026, dev-база)

Объём, без которого цифры нечитаемы: `vehicle_requests` — 577 строк (5,2 МБ с индексами, куча 204
буфера), `vehicles` — 216 строк (480 КБ, 12 буферов), классификатор — 27 типов и 46 категорий, то
есть набор в 60 позиций покрывает почти весь справочник. PostgreSQL 16.14, кэш тёплый.

| Выборка                                        | Набор       | Execution             | Buffers             | План                                   |
| ---------------------------------------------- | ----------- | --------------------- | ------------------- | -------------------------------------- |
| `vehicle_requests`, только условие             | 1 / 10 / 60 | 0,73 / 0,72 / 0,70 мс | 204 / 204 / 204 hit | Seq Scan                               |
| `vehicles`, только условие                     | 1 / 10 / 60 | 0,13 / 0,16 / 0,14 мс | 12 / 12 / 12 hit    | Seq Scan                               |
| страница 50 строк с `ORDER BY created_at DESC` | 1 / 60      | 0,37 / 0,33 мс        | 141 / 76 hit        | Incremental Sort ← Index Scan Backward |

Прочитанные буферы от размера набора не зависят вовсе, время плоское, а на реальном запросе
страницы больший набор оказался **дешевле**: он менее избирателен, и обратный проход по индексу
срока обрывается раньше. Вся плата за длинный набор — константные ~0,1–0,2 мс планирования (на 200
последовательных запросах: 0,31 мс/запрос против 0,39 мс). При `enable_seqscan=off` планировщик
собирает по обеим веткам `BitmapOr` — `vehicle_requests_vehicle_type_idx` с частичным
`vehicle_requests_vehicle_category_idx`, у машин `vehicles_type_status_idx` с частичным
`vehicles_category_idx`; частичность (`IS NOT NULL`) веткам не мешает, `IN (…)` NULL и не ищет.

**Вывод: миграция не требуется.** Оговорка, которую замер не снимает: база dev крошечная (576
заявок), seq scan на ней законен, и о продовых временах он не говорит — доказано отсутствие
деградации от роста набора, а не абсолютные величины. Там же видно, почему «60 позиций против
малой доли таблицы» на этой базе не поставить: 60 ключей — это почти весь классификатор, и отбор
возвращает все 576 строк.

## 10. Оценка

Релиз A — ≈ 1,25 дня, релиз B — ≈ 1,25 дня. Календарного окна между ними не требуется: любое
сочетание контейнеров согласовано (§6), и B можно выкатывать сразу после подтверждённого health A.

## 11. Риски

1. **Бюджет адреса** — П1; при отрицательном результате снижается потолок, nginx не трогаем.
2. **План запроса** — П2 по времени и буферам; при деградации возможна миграция с составным
   индексом.
3. **Старая пара живёт неопределённо долго** — сознательная плата за безопасный откат (§6). Цена:
   одна функция в `classification-filter.ts` и пять строк ветвления, пока не появится гейт версии.
4. **Сводка расходится со списком** — закрыто Р4 и db-тестами сводок.
5. **Телефон** — без вида `multiSelect` шит показывал бы одну позицию там, где список отобран по
   нескольким; поэтому Р9 входит в релиз B вместе с самой фичей, а не «потом».
