## 1. Что чинится

Тестовая учётка «Оператор (внешний исполнитель) — Сервисная компания» после входа попадает на
**смену пароля**, хотя пароль менять не требуется: `mustChangePassword` у неё `false`, и даже
предупреждения на экране нет — просто форма, приехавшая ниоткуда.

Цепочка целиком:

1. [LoginPage.tsx:19](../apps/web/src/pages/LoginPage.tsx#L19) — после входа портал идёт на
   жёстко зашитый `/waste`.
2. `/waste` закрыт гейтом `RequirePermission('wasteRequests.read')`
   ([App.tsx:88](../apps/web/src/App.tsx#L88)) — гейт уводит в `homePath`.
3. [ProtectedRoute.tsx:67-89](../apps/web/src/auth/ProtectedRoute.tsx#L67-L89) — `homePath`
   перебирает разделы: кабинет, вывоз, заказ ТС, гараж, листы, справочники, администрирование.
   **Раздела «Орг.техника» в переборе нет**, хотя маршрут ([App.tsx:107](../apps/web/src/App.tsx#L107))
   и пункт меню ([AppLayout.tsx:139](../apps/web/src/components/AppLayout.tsx#L139)) у него есть с
   ADR 0085. Ни одна строка не сработала → `return '/change-password'`.
4. Экран смены пароля лежит вне каркаса: ни меню, ни разделов, ни кнопки «назад» — из него
   выходят только сменой пароля или выходом из портала
   ([ChangePasswordPage.tsx:86-90](../apps/web/src/pages/ChangePasswordPage.tsx#L86-L90)).
5. Сменить пароль не помогает: [ChangePasswordPage.tsx:21](../apps/web/src/pages/ChangePasswordPage.tsx#L21)
   после успеха идёт на тот же `/waste` → тот же гейт → тот же экран. Круг замкнут.

Перебор `ACCESS_PROFILES` в двух состояниях области даёт пять профилей, приземляющихся на смену
пароля. Но живой из них сегодня **один**:

| Профиль                                      | Приземляется на    | Бывает ли в проде                                                                            |
| -------------------------------------------- | ------------------ | -------------------------------------------------------------------------------------------- |
| Оператор — Сервисная компания                | `/change-password` | **да, это и есть заявленный случай**                                                         |
| Площадка без объекта                         | `/change-password` | нет: объектной роли объект обязателен ([users.ts:534](../apps/api/src/routes/users.ts#L534)) |
| Площадка + Оператор (оргтехника) без объекта | `/change-password` | нет, по той же причине                                                                       |
| Площадка + Согласование ИТ без объекта       | `/change-password` | нет, по той же причине                                                                       |
| Комендант без объекта                        | `/change-password` | нет, по той же причине                                                                       |

Три вывода из этой таблицы, и все три идут в решение:

- чинить нужно **раздел «Орг.техника» в стартовой странице** — это единственная живая дыра;
- «объекта нет» защищено инвариантом API, но не навсегда: объекты учётки могут исчезнуть позже,
  а со свободной сборкой полномочий (ADR 0106) набор прав учётки вообще перестал выводиться из
  роли — «профилей матрицы» для проверки больше не достаточно;
- состояние «разделов нет ни одного» портал обязан уметь показывать **экраном**, а не служебной
  формой: сегодня оно неотличимо от «пароль просрочен».

## 2. Почему это повторяется

Состав разделов портала описан **трижды**, независимыми списками:

| Копия                   | Файл                                                                        | Знает про «Орг.техника» |
| ----------------------- | --------------------------------------------------------------------------- | ----------------------- |
| Маршруты и их гейты     | [App.tsx:88-145](../apps/web/src/App.tsx#L88-L145)                          | да                      |
| Меню и нижняя навигация | [AppLayout.tsx:91-176](../apps/web/src/components/AppLayout.tsx#L91-L176)   | да                      |
| Стартовая страница      | [ProtectedRoute.tsx:67-89](../apps/web/src/auth/ProtectedRoute.tsx#L67-L89) | **нет**                 |

Новый раздел заводят в двух копиях из трёх, и промах виден только той роли, для которой
пропущенный раздел — единственный. Комментарии в самом `homePath` это и протоколируют: так уже
ловили водителя (ADR 0102), службу главного механика, держателя одних «Руководств» и одних
«Рассылок» (`docs/manuals-plan.md` §3.6 — там список прав администрирования как раз и свели в
`ADMIN_PAGE_PERMISSIONS`, потому что «поимённые копии в трёх местах разъехались»). Сервисная
компания — четвёртый случай ровно того же промаха; список правили строкой, а не устройством.

Второе — **fallback ведёт на служебный маршрут**. «У учётки нет ни одного раздела» отображается
формой смены пароля: баг доступа маскируется под истёкший пароль, и человек ищет не там. Тот же
приём в двух точках входа — вход и смена пароля идут на `/waste`, то есть на **чужой раздел**,
а не на «свою» страницу.

Третье — этого никто не проверял. Ни один тест не спрашивал «куда приземляется каждый субъект».
Хуже: [admin-page-gates.test.tsx:105](../apps/web/test/admin-page-gates.test.tsx#L105) закрепил
промах как норму — ожидает, что учётка без разделов увидит «Смену пароля».

## 3. Решённые развилки

| Развилка                                             | Решение                                                                                                                                                                                                                                                                     |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Где живёт состав разделов                            | `packages/contracts/src/portal-sections.ts` — данные без React, рядом с матрицей прав и `links.ts`                                                                                                                                                                          |
| Что описывает реестр                                 | **разделы**: то, что бывает пунктом меню и стартовой страницей. Подстраницы (недельная заявка) — нет                                                                                                                                                                        |
| Порядок меню и порядок стартовой                     | разные вещи: порядок массива — меню, отдельное поле `startOrder` — стартовая                                                                                                                                                                                                |
| Каким числом входит «Орг.техника»                    | **последним** (§4.1): стартовый порядок остаётся точной копией сегодняшнего `homePath`, новый раздел дописывается в хвост. Иначе механик с назначенным `officeEquipment.read` (ADR 0106) уехал бы из «Гаража» в «Орг.технику» — рефакторинг менял бы поведение живых учёток |
| Кабинет водителя                                     | тот же реестр и **тот же гейт**: `RequireDriverCabinet` упраздняется, ветка `/driver` оборачивается в `RequireSection id="driver-cabinet"`. Условие остаётся ролью вместе с правом (ADR 0102), но живёт в одном месте                                                       |
| Страницы разделов                                    | `Record<PortalShellSectionId, ReactNode>` — по разделам **каркаса**: у кабинета своя ветка с `DriverLayout` и index-страницей, и в `Record` ему места нет                                                                                                                   |
| `can` или `canUse`                                   | всегда `canUse`, один предикат `isSectionOpen` на меню, гейты и стартовую. Область сужает только вывоз мусора (`MODULE_SCOPE`), для остальных прав `canUse ≡ can` — три разных ответа в трёх копиях были следствием копий, а не смысла                                      |
| Нет ни одного раздела                                | **пустой главный экран внутри каркаса**, без редиректа куда бы то ни было (§4.5)                                                                                                                                                                                            |
| Куда ведут вход и смена пароля                       | на `/`, то есть к стартовой странице роли; жёстких `/waste` в коде не остаётся                                                                                                                                                                                              |
| Возврат с формы смены пароля                         | кнопка «Вернуться в портал» при `mustChangePassword === false`; при обязательной смене её нет — только «Выйти» (§4.6)                                                                                                                                                       |
| Единственный законный редирект на `/change-password` | `mustChangePassword` в `ProtectedRoute` — он и остаётся                                                                                                                                                                                                                     |

## 4. Устройство

### 4.1 Реестр разделов

```ts
// packages/contracts/src/portal-sections.ts
export type PortalShellSectionId =
  | 'waste'
  | 'vehicle-requests'
  | 'waybills'
  | 'garage'
  | 'office-equipment'
  | 'directories'
  | 'admin';
export type PortalSectionId = PortalShellSectionId | 'driver-cabinet';

interface SectionBase {
  /** Адрес раздела — он же ключ пункта меню и подсветки. */
  path: string;
  label: string;
  /** Подпись нижней навигации: на 360 px пункту достаётся четверть экрана (ADR 0030). */
  short: string;
  /** Раздел открывает ЛЮБОЕ из этих прав. */
  permissions: readonly Permission[];
  /** Дополнительное условие роли; сегодня только у кабинета водителя (ADR 0102). */
  roles?: readonly Role[];
  /** Каким по счёту раздел становится стартовым, если открыт учётке. */
  startOrder: number;
}

/** Раздел каркаса: пункт меню, маршрут в общей ветке, страница в `SECTION_PAGES`. */
export interface PortalShellSection extends SectionBase {
  id: PortalShellSectionId;
  shell: 'portal';
}

/** Второй контур (ADR 0102): свой каркас, своя ветка маршрутов, в меню не показывается. */
export interface DriverCabinetSection extends SectionBase {
  id: 'driver-cabinet';
  shell: 'own';
}

export type PortalSection = PortalShellSection | DriverCabinetSection;
```

Разделены **типами, а не фильтром**: `SHELL_SECTIONS.filter((s) => s.shell === 'portal')` вернул бы
`PortalSection[]`, и `SECTION_PAGES[s.id]` перестал бы типизироваться — сужение пришлось бы
дописывать предикатом, то есть держать руками. Поэтому массивы объявляются порознь, а общий
собирается из них:

```ts
export const SHELL_SECTIONS: readonly PortalShellSection[] = [/* порядок меню */];
export const DRIVER_CABINET_SECTION: DriverCabinetSection = {/* … */};
export const PORTAL_SECTIONS: readonly PortalSection[] = [
  DRIVER_CABINET_SECTION,
  ...SHELL_SECTIONS,
];
```

| id                 | Адрес               | Права                                                | Меню            | `startOrder` |
| ------------------ | ------------------- | ---------------------------------------------------- | --------------- | ------------ |
| `driver-cabinet`   | `/driver`           | `driverCabinet.read` + роль из `PERSON_SCOPED_ROLES` | — (свой контур) | 1            |
| `waste`            | `/waste`            | `wasteRequests.read`                                 | 1               | 2            |
| `vehicle-requests` | `/vehicle-requests` | `vehicleRequests.read`                               | 2               | 3            |
| `garage`           | `/garage`           | `garage.read`                                        | 4               | 4            |
| `waybills`         | `/waybills`         | `waybills.read`                                      | 3               | 5            |
| `directories`      | `/directories`      | `directories.write`, `officeEquipment.write`         | 6               | 6            |
| `admin`            | `/admin`            | `ADMIN_PAGE_PERMISSIONS`                             | 7               | 7            |
| `office-equipment` | `/office-equipment` | `serviceRequests.read`, `officeEquipment.read`       | 5               | **8**        |

Столбец `startOrder` — **посимвольная копия сегодняшнего `homePath`**, к которой в хвост дописан
пропущенный раздел. Отсюда и точная формулировка совместимости: учётка, которой `homePath` сегодня
отвечает **рабочим разделом**, оставляет его за собой; меняются только ошибочные состояния — те,
где сегодняшний перебор доходил до `return '/change-password'`. Сервисная компания меняет стартовую
страницу намеренно, и это ровно то, ради чего волна затевается. Перебор профилей матрицы такой
гарантии не даёт — со свободной сборкой полномочий (ADR 0106) набор прав учётки не выводится
из роли, и, поставь мы «Орг.технику» четвёртой, механик с назначенным `officeEquipment.read`
стартовал бы не в «Гараже», как сегодня, а в оргтехнике. Приоритет раздела — продуктовое решение;
менять его побочным эффектом рефакторинга нельзя. Порядок меню при этом остаётся прежним
(«Орг.техника» пятой) — это разные вопросы, и потому это разные поля.

Перебор прав, написанный ради этой самой гарантии, нашёл по дороге **третий экземпляр той же
болезни** — уже в «Справочниках»: `homePath` знал у раздела одно право (`directories.write`), а меню
и маршрут — два (`directories.write` и `officeEquipment.write`, ADR 0085 Р7). Реестр отвечает
одинаково всем троим, и потому в четырёх наборах из 1711 стартовый раздел меняется:
`officeEquipment.write` вместе с одним из прав администрирования (`directories.export`,
`users.manage`, `mailings.read`, `manuals.manage`) ведёт теперь в «Справочники», а не в
«Администрирование» — то есть в раздел, который такому держателю открыт и стоит выше. Живых учёток
это не двигает: оба права вместе есть сегодня только у администратора и диспетчера, а им обоим
стартовым остаётся «Вывоз мусора». Все четыре расхождения перечислены **снимком** в
`apps/api/test/portal-sections.test.ts` рядом со сличением с переписанным туда прежним `homePath`, а
не допущены молча: обещание «меняется только то, где сегодня ошибка» стоит ровно столько, сколько
стоит список исключений к нему.

Один предикат и две функции над ним, все чистые:

```ts
export function isSectionOpen(section: PortalSection, access: SectionAccess): boolean;
/** Пункты меню: только каркас, в порядке `SHELL_SECTIONS`. */
export function openShellSections(access: SectionAccess): readonly PortalShellSection[];
/** Стартовый раздел: по `startOrder`, среди всех — кабинет тоже бывает стартовым. */
export function startSection(access: SectionAccess): PortalSection | null;

interface SectionAccess {
  role: Role | null;
  canUse: (permission: Permission) => boolean;
}
```

`canUse` передаётся предикатом, а не пересчитывается внутри: права считает сервер (ADR 0106),
контрактам их выводить нельзя, а область они и так знают. `startSection` возвращает `null` —
«разделов нет», и это **значение, а не адрес**: подставить сюда служебный маршрут больше негде.

Почему в контрактах, а не в `widgets`: адреса портала там уже живут (`links.ts`) и по той же
причине — их спрашивают двое, ответ обязан быть один. Плюс тест полноты оказывается рядом с
`ACCESS_PROFILES`, а таблица «Разделы портала» в [access-model.md](access-model.md) §3 получает
источник в коде вместо третьей копии словами.

### 4.2 Меню и нижняя навигация

`AppLayout` перестаёт перечислять разделы и собирает пункты из `openShellSections`. Иконки —
`Record<PortalShellSectionId, ReactNode>` в самом каркасе: контракты про React не знают, а `Record`
по всем восьми id требовал бы иконку кабинету — разделу, которого в меню нет и быть не должно. Бейджи (заявки на регистрацию,
«ждут меня» на оргтехнике) остаются украшением иконки в каркасе — реестр отдаёт базовую.

### 4.3 Маршруты

Ветка разделов каркаса строится циклом по `SHELL_SECTIONS` — по массиву, уже суженному типом, а не
по общему реестру с фильтром: страницы лежат в `Record<PortalShellSectionId, ReactNode>`, и
`SECTION_PAGES[s.id]` типизируется только потому, что `s` здесь `PortalShellSection`. Новый раздел
каркаса без страницы не собирается. Гейт один — `RequireSection`, и он же
закрывает кабинет:

```tsx
{
  /* Кабинет — своя ветка (свой каркас и index-страница), но гейт общий. */
}
<Route element={<RequireSection id="driver-cabinet" />}>
  <Route path="/driver" element={<DriverLayout />}>
    <Route index element={<DriverPage />} />
  </Route>
</Route>;

{
  SHELL_SECTIONS.map((s) => (
    <Route key={s.id} element={<RequireSection id={s.id} />}>
      <Route path={s.path} element={SECTION_PAGES[s.id]} />
    </Route>
  ));
}
```

`RequireDriverCabinet` удаляется: его условие («роль вместе с правом») переезжает в строку реестра
и проверяется тем же `isSectionOpen`, что меню и стартовая. Именно это и было причиной живучести
бага — три места спрашивали доступ тремя способами.

`RequirePermission` остаётся — для **подстраниц** со своим правом (`/vehicle-requests/weekly/:id`).
Разделом они не являются и стартовыми быть не должны.

### 4.4 Стартовая страница

```tsx
export function HomeRedirect() {
  const { user, canUse } = useAuth();
  const section = startSection({ role: user?.role ?? null, canUse });
  return section ? <Navigate to={section.path} replace /> : <NoSectionsPage />;
}
```

Гейт при отказе ведёт на `/`, а не считает стартовую сам: адрес отказа — один, и решает по нему
стартовая страница. Зацикливания это не даёт по построению: гейт раздела и стартовая спрашивают
**один и тот же предикат** `isSectionOpen`, поэтому `startSection` не может вернуть раздел, из
которого выкидывает.

### 4.5 Пустой главный экран (отдельно)

Учётке без разделов портал показывает **экран, а не редирект**. Он живёт index-маршрутом внутри
`AppLayout`, поэтому вокруг остаётся каркас: шапка с именем и ролью, меню учётной записи со
«Сменить пароль» и «Выйти», служебное меню с поддержкой и руководствами. Меню разделов пустое —
`MobileNav` при пустом списке не рисуется вовсе, и на телефоне экран остаётся чистым.

Содержание — `Empty` и три строки без жаргона:

- «Разделы портала вам пока не назначены»;
- «Учётная запись активна, но ни один раздел ей не открыт. Доступ выдаёт администратор портала»;
- кнопки: «Написать в поддержку» и «Выйти».

Кнопка поддержки открывает **своё** окно, а не служебное меню каркаса: состояние `useUtilityMenu`
принадлежит `AppLayout` и через `<Outlet />` наружу не отдаётся. Страница держит собственный
`useState` и рендерит `SupportContactsModal` — ровно тем же приёмом, что уже применён в
[EquipmentNotFoundLink.tsx:109](../apps/web/src/features/quick-create-equipment/ui/EquipmentNotFoundLink.tsx#L109).
Окно самодостаточно (контакты берёт из `@shared/config`), второго состояния портала это не заводит.

Что этот экран **не** делает: не редиректит, не предлагает сменить пароль, не притворяется
разделом. Он честно сообщает состояние учётки — и ровно этим отличает «доступ не настроен» от
«пароль просрочен». Побочная польза: следующий промах реестра (а он рано или поздно будет) выйдет
наружу как «разделов нет», а не как «портал требует новый пароль», и вопрос заказчика придёт в
правильную сторону.

Файл — `apps/web/src/pages/NoSectionsPage.tsx`. Не `components/`: бюджет качества считает файлы в
легаси-каталогах (`quality-budget.json`, `legacyFiles.components`), и новый файл там — рост долга.

| Место                                                                         | Было                           | Стало                                                                             |

Последние две строки — про **ловушку**, и она шире исходного бага. Форму открывают добровольно,
пунктом меню учётной записи ([AppLayout.tsx:189](../apps/web/src/components/AppLayout.tsx#L189)) и

а обратной дороги с неё нет ни у кого: передумал — либо меняй пароль, либо выходи из портала.
Правка адреса после сохранения этого не лечит. Поэтому кнопка возврата ставится по условию: при
обязательной смене (`mustChangePassword === true`) её нет — иначе она обходила бы требование,
против которого `ProtectedRoute` и стоит.

### 4.7 Что вне реестра

Вкладки внутри разделов (архив, показания, «Пользователи/Аудит»), подстраницы со своим правом,
публичные маршруты (`/login`, `/register`, `/forgot-password`, `/reset-password`) и служебный
`/change-password`. Реестр отвечает на один вопрос — «какие у портала разделы и кому они открыты».

## 6. Тесты

**Новые, на модели** (`apps/api/test/portal-sections.test.ts` — там же, где перебирают `ACCESS_PROFILES`):

- **снимок стартового порядка**: массив id по `startOrder` сравнивается с эталоном
  `['driver-cabinet', 'waste', 'vehicle-requests', 'garage', 'waybills', 'directories', 'admin', 'office-equipment']`.
  Это и есть настоящая защита совместимости: перебор профилей её не даёт (наборы прав живут в базе),
  а порядок — даёт, потому что `startSection` — тот же линейный перебор, что и `homePath`;
- **снимок порядка меню** — отдельным списком: два порядка обязаны расходиться осознанно;
- уникальность `id`, `path` и `startOrder`; `startOrder` — перестановка без дыр;
- каждый профиль `ACCESS_PROFILES` в двух состояниях области: `startSection` возвращает раздел
  либо `null`; профили с `null` перечислены снимком;
- перебор **одиночных прав и пар прав** (≈2 тыс. комбинаций): субъект, которому раздел открыт,
  получает стартовым раздел с наименьшим `startOrder` из открытых. Роль в переборе значима только
  для кабинета: комбинации с `driverCabinet.read` гоняются под ролью `driver`, а отказ кабинета
  неводителю с тем же правом проверяется отдельным случаем — это и есть условие ADR 0102, ради
  которого у раздела вообще есть поле `roles`. Ловит ошибку в предикате и
  расхождение прав раздела с правами гейта — но **не** отсутствие строки в реестре: тест построен
  из реестра и о разделе, которого в нём нет, не знает. Эту дыру закрывает не тест, а §6 ниже.

**Новые, на портале** (`apps/web/test/`):

- сервисная компания входит и попадает в «Орг.техника», а не на смену пароля;
- механик по-прежнему приземляется в «Гараж» (порядок стартовой ≠ порядок меню);
- учётка без разделов видит пустой главный экран: каркас, «Выйти», ни слова о пароле;
- с формы смены пароля есть возврат в портал, когда смена добровольная, и нет — когда обязательная;
- смена пароля возвращает в раздел роли, а водителя — в кабинет;
- неизвестный адрес ведёт на `/`, и заглушка не рендерится вне каркаса;
- `mustChangePassword` уводит на смену пароля с любого **защищённого** адреса.

**Чем закрывается «маршрут мимо реестра».** Типом — никак: ручной `<Route path="/new">` в `App.tsx`
скомпилируется и заработает. Тип даёт ровно одну гарантию — **полноту `SECTION_PAGES`**: раздел
каркаса, заведённый в реестре, обязан получить страницу. Обратную сторону закрывает скрипт
`apps/web/scripts/check-portal-routes.mjs` в `pretest`.

Собирать `<Route path=…>` строками он не может: после рефакторинга в JSX стоит `path={s.path}`, а
не литералы, и литеральных путей разделов там не остаётся вовсе. Поэтому скрипт разбирает **AST**
(`ts.createSourceFile`, тот же приём, что в
[check-form-blockers.mjs:18](../apps/web/scripts/check-form-blockers.mjs#L18)) и проверяет четыре
вещи:

1. пути разделов читаются из `portal-sections.ts` — тоже разбором AST, а не `import`: модули
   контрактов пишутся без расширений, и обычным Node такой файл не грузится;
2. генератор ветки каркаса на месте и не переписан руками — `SHELL_SECTIONS.map(…)` с
   `path={s.path}` внутри и `RequireSection` над ним;
3. ручная ветка `/driver` — единственный литеральный путь раздела, и она обёрнута в
   `RequireSection id="driver-cabinet"`;
4. других литеральных `path` в ветке каркаса нет, кроме перечисленных подстраниц
   (`/vehicle-requests/weekly/:id`) — список с причинами лежит в самом скрипте, как `ALLOWED` в
   `check-form-blockers.mjs`, и редактируется осознанно.

Проверка грубая намеренно: она сторожит не «правильность маршрутов», а то, что состав разделов
по-прежнему приходит из одного места.

**Правятся** (по этапам — см. §5): `admin-page-gates.test.tsx:105` (закреплял промах как норму),
`driver-cabinet-routing.test.tsx:29`, `manuals-admin.test.tsx:254`, `permissions-ui.test.tsx`.

**Бюджеты.** `quality:update` после этапа 2 (`AppLayout` худеет). Новые файлы — в `pages`,
`contracts` и `scripts`; легаси-каталоги не растут.

## 7. Приёмка

1. Оператор сервисной компании входит и попадает в «Орг.техника»; смена пароля возвращает туда же.
2. Учётка без единого раздела видит пустой главный экран с каркасом, поддержкой и «Выйти» — и
   не попадает на смену пароля ни со входа, ни с неизвестного адреса.
3. С добровольно открытой формы смены пароля есть дорога назад; при `mustChangePassword` её нет.
4. Стартовая страница сменилась **только там, где сегодня ошибка**: учётка, которой `homePath`
   отвечал рабочим разделом, получает тот же раздел; меняются те, кого перебор доводил до
   `/change-password`. Проверяется снимком стартового порядка — сегодняшний перебор `homePath`
   плюс «Орг.техника» в хвосте.
5. Водитель по-прежнему попадает в кабинет, администратор в кабинет не попадает — уже общим гейтом.
6. `mustChangePassword` работает как раньше: с любого защищённого и с неизвестного адреса уводит на
   смену пароля; публичные страницы (`/login`, `/register`, `/reset-password`) он не трогает, как и
   сегодня.
7. Раздел каркаса в реестре без страницы не собирается; маршрут мимо реестра валит
   `check-portal-routes`. `pretest && test`, `typecheck`, `lint` — чисто.

## 8. Границы

- Модель доступа не меняется: ни одного нового права, ни одной новой роли, миграций нет.
- Сервер не трогается: `access-manifest` и проверки API остаются как есть.
- Приоритет «Орг.техники» как стартовой не обсуждается этой волной — она встаёт в хвост ради
  сохранения поведения; захотят выше — отдельным решением и отдельным снимком.
- Вкладки внутри разделов и подстраницы со своим правом остаются на `RequirePermission`.
- Кабинет водителя остаётся вторым контуром вне `AppLayout`: общим становится гейт, не каркас.
- FSD-рефакторинг (`frontend-fsd-stage-2.md`) этой волной не двигается: `AppLayout` остаётся в
  легаси-`components`, реестр в контрактах доступен ему без нарушения границ.
