# Этап 1 — слой `shared`: подробный план

Часть [плана рефакторинга фронтенда](frontend-fsd-plan.md) (§7.3, этап 1). Редакция 3.1 — по третьему ревью 31.07.2026
(что изменилось — «Журнал правок» в конце). Опирается на
[этап 0](frontend-fsd-stage-0.md): алиасы, линт границ с фикстурами, 27 тестов сети безопасности.

**Смысл этапа — перенос, а не переделка.** В `shared` едет только то, что уже generic. Всё, что
требует расщепления на общее ядро и доменную оболочку, ждёт этапа 2: там появится `entities`, куда
доменную половину можно положить. Иначе этап 1 создаст промежуточное состояние, где половина
правила уже в `shared`, а вторая половина ещё в `utils`, — и разбираться в нём придётся дважды.

**Исходное состояние:** 35 тестовых файлов, 251 тест, `typecheck` и `lint` зелёные;
`src/shared/config` существует (`files.ts` + `index.ts`).

## 2. Места, где перенос не механический

### 2.1 Линт сейчас НЕ обеспечивает границу — это надо исправить до переезда

Проверено экспериментом: файл `src/shared/__probe/probe.ts` с импортом `../../api/resources`
проходит линт **без единого сообщения**. Причина — `boundaries/no-unknown-dependencies` выключен
до этапа 7, а `api/resources` не отнесён ни к одному слою: политики для «неизвестного» нет, и
запрет не срабатывает.

Значит заявление «после переезда `shared` не сможет импортировать домен» сегодня ничем не
обеспечено, а «пробная заглушка» была бы зелёной в любом случае и ничего бы не доказала.

Что делаем в первом же коммите:

1. **`boundaries/no-unknown-dependencies: error` для `src/shared/**`** — нижний слой обязан
   зависеть только от размеченного. Остальной код продолжает жить без этой проверки до этапа 7.
2. **Фикстуры на новый случай**: `shared` → неразмеченный legacy-модуль — ошибка; разрешённые
   направления между сегментами — по матрице §2.2, каждое своей фикстурой.
3. **Заглушки — явные реэкспорты из публичного входа**: `export { DataTable } from '@shared/ui'`,
   а не `export * from '@shared/ui/DataTable'`. Второе само по себе deep import — то, что мы
   запрещаем.
4. В `ignores` заглушки **не добавляются**: правило, отключённое ради собственного удобства,
   перестаёт быть правилом.
5. **Запрет deep import — отдельным правилом.** `boundaries` не поймает
   `import { DataTable } from '@shared/ui/DataTable'` в legacy-файле: тот не классифицирован, и
   политики для него нет. Поэтому `no-restricted-imports` — он действует независимо от разметки:
   - шаблон `@shared/*/*` запрещён **везде**;
   - относительные пути внутрь `shared` запрещены только **вне** `src/shared/**`: внутри слоя
     `export * from './DataTable'` и `import { ActionSheet } from './ActionSheet'` — обычная
     внутренняя жизнь сегмента, и запрещать её нечем и незачем.

   Фикстуры: legacy → `@shared/ui/DataTable` падает; `shared/ui/index.ts` → `./DataTable` проходит.

### 2.2 Направление внутри `shared`: матрица сегментов, а не «shared → shared»

Хук `useListParams` берёт тип `TableChange` из `DataTable`, то есть `lib` смотрит в `ui`. Соблазн —
разрешить `shared → shared`, но такая политика открывает и циклы `ui ↔ lib ↔ api`, которые потом не
выловить. В прошлой редакции я сам же и написал разрешение задом наперёд в трёх местах — это лучшее
доказательство, что абстрактной формулировки мало.

Поэтому протокол изменения списка (`TableChange`, порядок сортировки) переезжает в
`shared/lib/table`, а `DataTable` его импортирует. Разрешения задаются **явной матрицей**, и ни
одно направление не подразумевается:

| Откуда   | Куда разрешено  | Почему                                                       |
| -------- | --------------- | ------------------------------------------------------------ |
| `ui`     | `lib`, `config` | компоненту нужны хуки, форматирование и константы            |
| `lib`    | `config`        | `useListParams` берёт размеры страниц из `config/pagination` |
| `config` | ничего          | нижняя точка: константы ни от чего не зависят                |

`api → config` не разрешается: сегодня у транспорта нет ни одного потребителя констант (базовый
адрес приходит из `import.meta.env`), а полномочие «на будущее» — это разрешение, которое никто не
проверяет. Понадобится — заводится вместе с `config/api.ts` и своей фикстурой.

Запрещено всё остальное, и прежде всего `lib → ui`: именно оно и было исходной проблемой.

**Механизм.** Сегменты должны различаться линтом, а сейчас все они — один тип `shared`. Заводим
отдельные типы элементов по путям: `shared-ui` (`src/shared/ui/*`), `shared-lib`, `shared-api`,
`shared-config`.

Здесь есть ловушка, из-за которой переезд мог бы отрезать `shared` от всего приложения: политики
верхних слоёв строятся перечислением «что ниже», и тип `shared` в этом перечислении просто
исчезнет — `pages → @shared/ui` станет ошибкой. Поэтому слои описываются **группами**, а не
плоским списком:

```js
const SHARED_TYPES = ['shared-config', 'shared-api', 'shared-lib', 'shared-ui'];
const LAYER_GROUPS = [SHARED_TYPES, ['entities'], ['features'], ['widgets'], ['pages'], ['app']];
// ниже данного слоя = LAYER_GROUPS.slice(0, index).flat()
```

Внутренняя матрица `shared` добавляется отдельными политиками поверх этого.

**Фикстуры.** Каждое разрешение и каждый запрет проверяются своим случаем; числа сценариев в
критериях намеренно нет — считать их можно по-разному, а пропущенным окажется тот, о ком забыли,
а не «восьмой».

| Сценарий                                     | Ожидание                                      |
| -------------------------------------------- | --------------------------------------------- |
| `features`/`pages` → `shared-ui` через index | проходит (ни `dependencies`, ни `no-unknown`) |
| `ui` → `lib` через `index.ts`                | проходит                                      |
| `lib` → `config`                             | проходит                                      |
| `shared/ui/index.ts` → `./DataTable`         | проходит (внутренняя жизнь сегмента)          |
| `lib` → `ui`                                 | `boundaries/dependencies`                     |
| `config` → `lib`                             | `boundaries/dependencies`                     |
| `shared` → неразмеченный legacy              | `boundaries/no-unknown-dependencies`          |
| legacy → `@shared/ui/DataTable`              | `no-restricted-imports`                       |
| `src/shared` → `@technic/contracts`          | `no-restricted-imports`                       |

Первый сценарий — тот, без которого можно безупречно проверить внутреннюю матрицу и одновременно
отрезать `shared` от всего портала. Отрицательные проверяются по конкретному `ruleId`,
положительные — по отсутствию сообщений обоих правил границ.

### 2.3 `shared` не знает правил портала

`no-unknown-dependencies` не спасёт от доменного кода, приехавшего из `@technic/contracts`: это
внешний workspace-пакет, для линта такой же, как antd. А между тем `PasswordField` тянет оттуда
парольную политику, `PersonNameFields` — правила ФИО, `PhoneField` — проверку контакта.

Поэтому вводится простое проверяемое правило: **`src/shared/**` не импортирует
`@technic/contracts`** (`no-restricted-imports`). Оно выполнимо ровно потому, что список §1.4
сузился — ни один из четырнадцати оставшихся компонентов и ни один хук контрактов не импортируют
(проверено). Когда в `shared` действительно понадобится общий тип из контрактов, исключение
заводится точечно и с обоснованием, а не молчаливым импортом.

**Пагинация — первый случай, где это правило встречается с реальностью.** Сервер принимает только
`PAGE_SIZES` (`[50, 100, 200, 500]`) и `DEFAULT_PAGE_SIZE` из контрактов, а `shared/config/pagination`
должен с ними совпадать. Из двух выходов — исключение в правиле или локальные константы —
выбираются локальные константы **плюс тест сверки**: `test/pagination.test.ts` сравнивает
их с `PAGE_SIZES`. Тест лежит в `test/`, ему контракты импортировать можно, и расхождение
становится красным прогоном, а не сюрпризом при первом же запросе с неподдерживаемым размером.
Дублирование чисел без такой сверки было бы хуже исключения.

### 2.4 Заглушки не спасают от правок в самом перемещаемом файле

Заглушка сохраняет старый путь импорта, но не сохраняет изменение, сделанное в старом
`DataTable.tsx` после переноса: такая правка в параллельной ветке либо воскресит старую
реализацию при мерже, либо встретится конфликтом.

Поэтому окно нужно не одно (на `api/client.ts`), а короткое — на каждую группу переезда:

| Группа                                           | Файлов | Окно                          |
| ------------------------------------------------ | ------ | ----------------------------- |
| `config` (`time`, `pagination`)                  | 2      | не нужно — только новые файлы |
| `api` (`http`, `session`, `dadata`)              | 3      | **A**, ~20 мин                |
| `lib` (8 модулей, включая `table`) + `DataTable` | 9      | **B**, ~20 мин                |
| `ui` (14 компонентов)                            | 14     | **C**, ~20 мин                |

`table.ts` — не новый файл, а переезжающий, и вместе с ним меняется тип-импорт в `DataTable.tsx`:
протокол `TableChange` переходит из компонента в `lib`. Поэтому окно B блокирует и `DataTable.tsx`,
хотя сам компонент переезжает только в окне C. Собственное правило «каждый изменяемый старый файл
защищён окном» иначе нарушалось бы на первом же коммите.

Перед каждым окном — `git status` и проверка незамерженных веток: если группа сейчас правится,
она переносится следующей.

### 2.5 Побочный эффект в `dadata.ts`

Модуль печатает предупреждение об отсутствующем токене прямо при импорте. После переезда в
`shared/api` с barrel-входом оно начнёт выполняться у всех, кто импортирует хоть что-то из
`@shared/api`, — и заодно помешает tree-shaking.

Предупреждение переезжает в `dadataEnabled()` — и именно туда, а не в `suggestAddress()`: поле
адреса сначала спрашивает `dadataEnabled()` и при отсутствии токена запрос вовсе не делает, так что
из `suggestAddress()` предупреждение не прозвучало бы никогда. Печатается один раз за сессию.

### 2.6 Barrel-файлы и размер бандла

Публичные входы (`index.ts`) — это barrel, и при неудачном раскладе они тянут в сборку больше, чем
нужно.

Замер оформляется скриптом пакета — сейчас он ищет `dist` от текущего каталога и работает только
из `apps/web`:

```json
"bundle:size": "node scripts/bundle-size.mjs"
```

```bash
pnpm --filter @technic/web build && pnpm --filter @technic/web bundle:size waste
```

Сравнение — с замером **непосредственно перед этапом**, а не с историческими 526,2 КБ: за время
этапа 0 код успел вырасти, и разница «этап 1 против прошлой недели» ничего не покажет. Build и
замер делаются уже после коммита 3 (там появляется первый barrel — `shared/api`), а затем после
каждого переезда. Рост gzip первого экрана более чем на 2 % — повод разбираться.

## 4. Контракт сессии (коммит 3)

Этап 0 закрыл утечку кэша между учётками, но оставил гонку, которую нашло ревью: при 401 клиент
зовёт `sessionExpired()` **без проверки поколения** ([client.ts](../apps/web/src/api/client.ts)).
Сценарий: запрос пользователя A ждёт refresh; A выходит, входит B; refresh A возвращает «не
удалось» — и обработчик выкидывает уже сессию B.

Инвариант должен быть выражен типами, а не договорённостью «не забыть сверить поколение»:

```ts
// shared/api/session.ts
export type RefreshOutcome =
  | { status: 'refreshed' }
  /** Сессия кончилась. `generation` — та, в которой это выяснилось. */
  | { status: 'expired'; generation: number }
  /** Ответ пришёл к другой сессии: применять его нельзя, и говорить о нём — тоже. */
  | { status: 'stale' };

export interface Session {
  getToken(): string | null;
  /** Вход: новая сессия, новое поколение. Отдельно от продления — их путать нельзя. */
  startSession(token: string): void;
  /** Продление текущей сессии своим же refresh: поколение не меняется. */
  refresh(): Promise<RefreshOutcome>;
  /** Объявить сессию законченной, только если поколение всё ещё текущее. Возвращает, сработало ли. */
  expireIfCurrent(generation: number): boolean;
  /** Обрыв: забыть токен, обесценить висящее обновление, поднять поколение. Не уведомляет. */
  clear(): void;
  onExpired(handler: () => void): () => void;
}
```

Три решения, каждое отвечает на конкретную неоднозначность прошлой редакции:

1. **`startSession` вместо общего `setToken`.** Прежний `setToken` не различал «продлили свою
   сессию» и «вошёл другой человек», хотя поколение должно расти только во втором случае.
2. **`expireIfCurrent(generation)` вместо `notifyExpired()`.** Поколение передаётся тем, кто
   получил его при отправке запроса; сверка происходит внутри сессии, атомарно. Снаружи «забыть
   сверить» уже нельзя — параметр обязателен.
3. **`clear()` не уведомляет.** Подписчик (`AuthContext`) в обработчике сам зовёт `clear()`, и
   уведомляющий `clear()` замкнул бы вызов в кольцо.

**`bootstrapPromise` остаётся в `AuthContext`**: bootstrap зовёт `authApi.me()`, то есть знает о
пользователе, а `shared/api/session` о доменных ручках знать не должен. Общий план приведён к
этому решению (§4.1 и карта переездов).

**Тест, которого нет** (пишется здесь же): refresh пользователя A подвешивается, за это время идут
выход и вход B, затем отпускается ответ A — B остаётся авторизованным, кэш не очищен, токен не
подменён. Существующие `flow-session-*` последовательны и такую гонку не ловят.

## 5. Флак, который чинится до переезда (коммит 0)

`driver-category-advisory.test.tsx` падает через раз в общем прогоне, в одиночку проходит. Причин
две, и первая — не та, что я назвал в прошлой редакции:

1. **Обращение к полю до его появления.** `document.querySelector('#driverPersonId')!.closest(...)`
   выполняется синхронно, без ожидания: под нагрузкой поле ещё не отрисовано, и `!` превращает
   отсутствие узла в падение на `.closest()`. Это и есть само падение.
2. **Поиск вариантов по всему документу** (`.ant-select-item-option`) — тот же приём, что уже дал
   нестабильность в форме перевода в работу: закрытые выпадашки других полей из разметки не
   исчезают.

Существующий `selectOption` здесь не подходит: он выбирает вариант, а тесту нужен весь список —
он проверяет и порядок, и пометки. Поэтому в `test/antd.ts` добавляется соседний helper:

```ts
/** Открыть список поля и вернуть его варианты — только из выпадашки этого поля. */
export async function openSelectOptions(labelText: string): Promise<HTMLElement[]>;
```

Он ждёт подпись и связанное с ней поле, открывает список, дожидается `${fieldId}_list` и
возвращает варианты только из него. Сеть безопасности с неоднозначным сигналом хуже отсутствующей,
поэтому это делается до массового переезда.

1. `pnpm typecheck`, `pnpm --filter @technic/web test`, `pnpm lint` — зелёные; тестов не меньше
   251 + новый тест гонки; **три полных прогона подряд без флака**.

   относительно исторических 526,2 КБ — код с тех пор вырос). Замер повторяется после коммита 3
   (первый barrel) и после каждого переезда.

   (`scripts/check-stage1-layout.mjs`, скрипт пакета — как `bundle:size`, чтобы не зависеть от
   каталога запуска), а не грепом: простой поиск
   `from '@shared` по legacy-каталогам всегда будет непустым — оставшиеся файлы обязаны
   импортировать переехавшее (`AppLayout` → `useIsMobile`, `CancelReasonModal` → `FormModal`,
   `api/resources` → новый транспорт). Скрипт держит manifest и проверяет три вещи:
   - ни одного из переехавших путей больше не существует (включая `api/client.ts`, `api/dadata.ts`);
   - в `src/components`, `src/hooks`, `src/utils`, `src/api` лежат **ровно** файлы из allowlist §1.5;
   - ни один файл не является заглушкой-реэкспортом (единственный `export ... from '@shared/...'`
     без собственного кода).
4. `src/shared/{ui,lib,api,config}` — каждый сегмент с `index.ts`; снаружи импорт только через них.
5. Линт **доказано** ловит нарушения: все сценарии §2.2 проверены фикстурами — отрицательные по
   конкретному `ruleId`, положительные по отсутствию сообщений `boundaries/dependencies` и
   `boundaries/no-unknown-dependencies`.
6. `theme.ts` без `MOSCOW_TZ`; `src/api/client.ts` и `src/api/dadata.ts` не существуют;
   `shared/api/http.ts` не содержит состояния сессии; `shared/api/dadata.ts` не выполняет ничего
   при импорте.
7. `first-screen-requests.test.tsx` даёт те же числа (6 и 5): этап ничего не оптимизирует.

## 7. Риски

1. **Правки в перемещаемых файлах из параллельных веток** — §2.3: окна по группам и сверка перед
   каждым переездом. Незамерженная ветка, трогающая группу, откладывает её.
2. **Кодмод переписывает лишнее** — прогоняется на чистом дереве, проверка `git diff --stat` и
   полный прогон.
3. **Barrel раздувает бандл** — §2.5, замер в критериях.
4. **Растущий код**: пока идёт этап, соседняя сессия добавляет файлы в `components/`; перед
   коммитом 5 список сверяется свежим `ls`, добавленное довозится или откладывается явным списком.
5. **Слишком широкая политика границ** — §2.2: разрешения заданы матрицей сегментов; `lib → ui` запрещено и проверено фикстурой.
