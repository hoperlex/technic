# Оргтехника: backlog правок по итогам обсуждения 02.09.2026

Документ переводит обсуждение правок в последовательность самостоятельных задач. Порядок учитывает
риски и зависимости: сначала безопасность и контролируемый запуск, затем права и обязательные
рабочие сценарии, после них ускорение операций, история и аналитика.

Для каждого пункта приведены:

- краткая суть изменения;
- готовый заголовок для таск-трекера;
- подробный промт для подготовки отдельного поэтапного плана реализации.

Пароли и другие секреты из исходной переписки намеренно не перенесены в документ.

## До запуска

## 1. Ротация раскрытых учётных данных

### 1.1. Краткая суть фичи / фикса

Сменить раскрытые в переписке учётные данные служебной почты и тестового пользователя, завершить
активные сессии и проверить, что старые секреты не сохранились в репозитории, документации, логах и
артефактах обмена.

### 1.2. Задача для таск-трекера

**SECURITY: ротировать раскрытые SMTP- и тестовые учётные данные модуля «Оргтехника»**

### 1.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план устранения инцидента с раскрытием учётных данных в переписке по модулю
«Оргтехника». Не воспроизводи значения паролей ни в плане, ни в командах, ни в логах. План должен
включать инвентаризацию затронутых учётных записей, смену пароля служебного SMTP-ящика, смену или
отключение тестовой учётной записи, завершение её активных сессий, проверку секретов в Git,
документации, CI/CD, логах, резервных копиях и переданных архивах. Опиши безопасный способ передачи
новых значений в production через секреты окружения, проверку живой отправки после ротации и
подтверждение того, что старые данные больше не работают. Добавь владельцев действий, порядок
выполнения без простоя заявок, процедуру отката конфигурации без возврата старого секрета и критерии
закрытия инцидента.

## 2. Контролируемое открытие модуля и тестовый контур

### 2.1. Краткая суть фичи / фикса

Исключить повторное появление незавершённого модуля у реальных пользователей: закрыть доступ
серверными проверками и feature flag, подготовить тестовый контур и smoke-проверки по ролям.

### 2.2. Задача для таск-трекера

**Оргтехника: внедрить безопасный контур пилота и управляемое включение модуля**

### 2.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план безопасного запуска модуля «Оргтехника». Сначала исследуй текущие маршруты,
пункты меню, серверные access guards, механизм технических работ и существующие feature flags.
Предложи единый серверный и клиентский переключатель доступности модуля, который закрывает не только
меню, но и прямые URL и API. Опиши отдельный тестовый или пилотный контур, тестовые учётки для
оператора, системного администратора, сервисного центра и заявителя, минимальный набор данных и
smoke-сценарии после выката. Включи журналирование изменения флага, безопасное включение по группам,
быстрое аварийное отключение без отката релиза и проверку отсутствия фоновых писем при закрытом
модуле. План должен назвать затронутые контракты, API, UI, конфигурацию, миграции при необходимости,
автотесты, порядок выката и критерии допуска к пилоту.

## 3. Матрица ролей и наборов полномочий

### 3.1. Краткая суть фичи / фикса

Описать четыре понятных бизнес-профиля — оператор, системный администратор, сервисный центр и
заявитель — как управляемые пресеты над существующими ролями, областями и наборами полномочий.

### 3.2. Задача для таск-трекера

**Оргтехника: зафиксировать матрицу доступа для четырёх бизнес-профилей**

### 3.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план формирования и внедрения матрицы доступа модуля «Оргтехника» для четырёх
бизнес-профилей: оператор, системный администратор, представитель сервисного центра и заявитель.
Сначала сопоставь их с текущей моделью базовых ролей, областей видимости, role addons, разрешений и
связи пользователя с контрагентом. Не создавай жёсткое правило «один модуль — одна глобальная роль»:
профили должны быть пресетами полномочий, не ломая пользователей, работающих в нескольких модулях.
Для каждого профиля перечисли права на просмотр, создание, изменение, назначение исполнителей,
статусы, срочность, смету, документы, обсуждение, перемещение, активацию техники, удаление, архив,
историю и массовые операции. Отдельно опиши область данных по объектам, отделам и контрагентам.
Выбор «Что вы будете делать на платформе» при регистрации трактуй как пожелание и предзаполнение
формы активации; повышенные права должны появляться только после решения администратора. В план
включи миграцию текущих назначений, обратную совместимость, отрицательные access-тесты и критерии
приёмки каждой строки матрицы.

## 4. Строгие границы прав исполнителей

### 4.1. Краткая суть фичи / фикса

Проверить и усилить ограничения для внутренних исполнителей и сервисных компаний, чтобы право роли
без назначения на конкретную заявку не давало возможности читать или изменять чужую работу.

### 4.2. Задача для таск-трекера

**Оргтехника: усилить серверные проверки назначения и области исполнителей**

### 4.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план аудита и усиления модели исполнителей заявок на обслуживание оргтехники.
Раздели право выполнять работу, факт поимённого назначения, назначение сервисной компании и область
видимости. Проверь все API чтения и мутаций: список, карточку, историю, чат, файлы, смету, смену
статуса, отказ, закрытие работ и массовые операции. Внутренний сотрудник должен действовать только
при поимённом назначении и нужном разрешении; представитель сервиса — только по заявкам своего
контрагента; отзыв права или переназначение должны прекращать доступ немедленно. UI обязан скрывать
недоступные действия, но источником истины остаётся сервер. Опиши общие предикаты контрактов вместо
дублирования правил, проверку прямых запросов, гонки переназначения, аудит отказов, миграционные
последствия, отрицательные тесты и доказуемые критерии отсутствия доступа к чужим заявкам.

## 5. Ограниченная карточка заявки для заявителя

### 5.1. Краткая суть фичи / фикса

Оставить заявителю только вкладки «Заявка», «История» и «Документы», скрыть объём работ, финансовые
данные и закрытые типы документов одновременно в UI и API.

### 5.2. Задача для таск-трекера

**Оргтехника: ограничить данные и вкладки карточки для заявителя**

### 5.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план разграничения карточки заявки по аудиториям. Для заявителя должны остаться
«Заявка», «История» и «Документы»; вкладка «Объём работ» и связанные финансовые поля должны быть
недоступны. Сначала составь и согласуй матрицу видимости типов файлов: исходные вложения, смета или
объём работ, счёт, акт и гарантийный талон. Учти исходное требование, что счёт не должен попадать в
доступные заявителю документы, но пометь эту границу как требующую окончательного продуктового
подтверждения. Не ограничивайся условным рендером вкладок: предложи серверную фильтрацию DTO,
списков файлов, скачивания по прямой ссылке и истории изменений, чтобы скрытые значения нельзя было
получить через API. Учти архивные заявки, изменение роли после создания заявки, кэширование и
экспорт. Включи контрактные, API- и UI-тесты для каждой аудитории, проверку прямого доступа к файлу,
порядок совместимого выката и критерии приёмки.

## 6. Полный контур уведомлений Копи-Лайт

### 6.1. Краткая суть фичи / фикса

Расширить существующую событийную почту: Копи-Лайт получает самодостаточные уведомления по
назначенной заявке, её значимым изменениям и комментариям, отправленные через служебный почтовый
канал.

### 6.2. Задача для таск-трекера

**Оргтехника: добавить Копи-Лайт уведомления об изменениях и комментариях заявки**

### 6.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план расширения почтовых уведомлений модуля «Оргтехника». Используй существующие
очередь писем, именованный почтовый канал, дедупликацию, адресатов назначения и шаблоны, не создавая
параллельный SMTP-контур. Сначала зафиксируй матрицу событий: назначение и переназначение,
отзыв назначения, отмена, переходы статуса, изменение объёма работ, добавление документа и новый
комментарий. Отдельно вынеси решение, должны ли сервису отправляться все комментарии видимой ему
заявки или только адресованные сервисной стороне. Опиши прекращение уведомлений прежнему подрядчику
сразу после переназначения, исключение собственного письма автору события, снимок адресатов на
момент события и защиту от повторов. Письмо должно содержать номер заявки, статус, технику,
инвентарный и серийный номера, место, отдел, описание, срочность, контакт, исполнителей и допустимую
для аудитории ссылку. Ошибка SMTP не должна откатывать заявку; исход постановки в очередь должен
быть виден пользователю и в аудите. Включи retry/dead-letter, ограничение частоты, Reply-To,
наблюдаемость, тест живой отправки, db- и worker-тесты, порядок выката и критерии приёмки.

## 7. Безопасное заведение отсутствующей техники

### 7.1. Краткая суть фичи / фикса

Разрешить сообщить об отсутствующем в справочнике аппарате без права создавать активную мастер-запись:
формировать кандидата, который проходит проверку и только затем появляется в рабочих списках.

### 7.2. Задача для таск-трекера

**Оргтехника: внедрить проверяемые карточки отсутствующей техники из заявки**

### 7.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план сценария «техника не найдена» при создании заявки. Заявитель не должен
получать право на обычное создание или редактирование справочника. Предложи модель кандидата на
добавление либо неактивной карточки со статусом проверки, связью с исходной заявкой, автором и
минимальным набором реквизитов. До подтверждения запись не должна попадать в активные селекторы,
статистику, интеграции и чужие области видимости; её видят автор и ответственные за проверку.
Проверь дубли по инвентарному и серийному номеру, а также гонку двух одновременных заявителей.
Опиши отдельное явное действие «Подтвердить технику» или безопасное транзакционное объединение с
переходом заявки, обязательный аудит подтверждения и отклонения, исправление реквизитов оператором,
поведение связанной заявки после отказа и уведомления сторон. Сопоставь решение с текущим быстрым
созданием, которое доступно держателю права записи и создаёт активную карточку. Включи схему данных,
контракты, API, UI, миграции, access-тесты и критерии приёмки.

Убрать дублирующиеся и отменённые действия, сохранив один очевидный вход в каждую операцию.

### 8.2. Задача для таск-трекера

**Оргтехника: привести меню действий заявки к согласованному составу**

### 8.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план очистки меню действий заявки. Удали «Отправить службе ещё раз». Убери
«Изменить исполнителей» из контекстного меню там, где назначение уже доступно отдельным быстрым

в Новую», но только если новый вход вызывает те же доменные команды и сохраняет причины, документы,
аудит, уведомления и правила исполнителей. Оставь доступные по правам действия «Объём работ»,
«Отложить», «Отметить срочной», «Обсуждение», «Отменить» и «Удалить». Перемещение вынеси в карточку
заявки и показывай по отдельному полномочию. Составь таблицу «действие × статус × профиль × место в
интерфейсе», проверь десктоп и мобильную карточку, прямые серверные ручки и отсутствие мёртвого кода.
Включи UI-тесты, тесты доступности и критерий «одно действие — один основной вход».

## 10. Быстрая смена статуса на десктопе и мобильном

### 10.1. Краткая суть фичи / фикса

Добавить смену допустимого статуса непосредственно из строки: выпадающий список на десктопе и
нижнюю панель на мобильном, без обхода бизнес-правил перехода.

### 10.2. Задача для таск-трекера

**Оргтехника: реализовать быструю смену статуса заявки в списке**

### 10.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план быстрой смены статуса заявки. На десктопе текущий статус должен открывать
список разрешённых переходов, на мобильном — action sheet или bottom sheet. Функция доступна
оператору, системному администратору и назначенному сервисному исполнителю в пределах их полномочий;
заявителю недоступна. Не проектируй универсальную запись значения статуса: список должен строиться
из общих серверных и контрактных предикатов, а выбор вызывать существующую доменную команду.
Переходы с причиной, подтверждением, документом, сметой или особыми побочными эффектами должны
открывать соответствующее окно. Учти оптимистическую версию, устаревшую строку, отложенные и
терминальные состояния, сохранение или снятие исполнителей, почту, историю и инвалидацию кэшей.
Опиши доступность с клавиатуры, мобильную эргономику, loading/error-состояния, API- и UI-тесты,
поэтапный выкат и критерии приёмки каждого перехода.

## 11. Массовые действия над заявками

### 11.1. Краткая суть фичи / фикса

Дать оператору, системному администратору и сервисному центру безопасно выполнять разрешённые
операции над несколькими заявками; заявителю массовые действия не показывать.

### 11.2. Задача для таск-трекера

**Оргтехника: добавить массовые действия в реестр заявок**

### 11.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план массовых действий в реестре заявок оргтехники. Начни с продуктовой матрицы
операций: смена статуса, назначение или переназначение, срочность, отложить, возобновить, отменить и
архивировать; не включай действие, пока для него не определены общая причина, документы и
побочные эффекты. Выбор строк и доступные команды должны зависеть от профиля, области и текущих
состояний. Предложи отдельный пакетный API, который проверяет каждую заявку теми же доменными
предикатами, что одиночная ручка, принимает версии строк и идемпотентный ключ, не обходит аудит и
уведомления. Определи транзакционную модель: полный откат либо частичный результат с явным отчётом
по каждой строке; обоснуй выбор. Учти большие выборки, пагинацию, выбор только видимых строк,
повторный клик, гонки и ограничение размера пачки. Включи UX подтверждения, прогресс, отчёт об
ошибках, серверные и UI-тесты, наблюдаемость, порядок выката и критерии приёмки.

## 12. Перемещение техники из карточки заявки

### 12.1. Краткая суть фичи / фикса

Развести сообщение заявителя о фактическом месте и подтверждённое перемещение справочной карточки;
операцию перемещения перенести в карточку заявки и ограничить отдельным правом.

### 12.2. Задача для таск-трекера

**Оргтехника: перенести запись перемещения в карточку заявки и разделить фактическое место с учётом**

> **Часть работы уже сделана (04.09.2026, [ADR 0162](adr/0162-service-request-actions-single-entry.md)).**
> Действие убрано из общего контекстного меню — и из строки списка, и из мобильной карточки, и из
> меню карточки заявки, — а вход у него теперь один: кнопка «Записать перемещение» рядом с полем
> «Какой аппарат». Право осталось прежним (`officeEquipment.write`) намеренно: отдельное
> полномочие заводит этот пункт, вместе с моделью снимка места и признаком расхождения, ради
> которых круг и сужают. Кнопка берёт готовый пункт набора действий, поэтому сузить круг — значит
> поправить один предикат, а не искать места показа.

### 12.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план корректировки сценария перемещения оргтехники. Заявитель может указать,
что аппарат фактически находится не там, где записано, но это не должно автоматически менять
мастер-данные. Ответственный с отдельным полномочием подтверждает реальное перемещение из карточки
заявки. Убери действие из общего контекстного меню, размести его рядом с реквизитами техники и
показывай только пользователям с правом ведения парка; не привязывай исключение к конкретному ФИО.
Опиши модель снимка места в заявке, признак расхождения с карточкой, выбор исходной и целевой стороны,
место, отдел, дату, причину и ссылку на заявку. Проверь область по исходной стороне, конкурирующие
перемещения, изменение отдела без смены объекта, отсутствие аппарата и погашение признака
расхождения после подтверждения. Включи аудит, историю, API- и UI-тесты, миграции при необходимости
и критерии приёмки.

## 13. История аппарата тремя бизнес-блоками

### 13.1. Краткая суть фичи / фикса

Представить историю аппарата в виде связанных заявок, ручных правок и перемещений, сохранив полную
событийную ленту как источник аудита.

### 13.2. Задача для таск-трекера

**Оргтехника: перестроить историю единицы в связанные заявки, правки и перемещения**

### 13.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план нового представления истории единицы оргтехники. Не удаляй существующую
событийную модель из шести источников: используй её как канонический аудит и построй над ней
бизнес-проекции. Экран должен содержать три блока или вкладки: «Связанные заявки», «Ручные правки»
и «Перемещения». Одна заявка должна занимать одну строку с номером, кратким содержанием,
исполнителями, датой создания, датой последнего изменения, итоговым статусом или результатом и
ссылкой в карточку. В ручных правках покажи значимые изменения реквизитов с автором и датой. В
перемещениях — откуда, куда, место, отдел, дату, причину и связанную заявку. Отдельно реши, куда
попадают гарантийные события и жизненный цикл карточки: в дополнительный режим «Полная история»
либо в явно выбранный блок. Сохрани серверную пагинацию, детерминированный порядок, экспорт и ту же
область видимости, что у заявок. Включи контракты read model, запросы без N+1, индексы, API/UI,
регрессионные access-тесты и критерии приёмки.

## 14. Завершение гарантийных сценариев

### 14.1. Краткая суть фичи / фикса

Провести отдельную приёмку гарантий поставщика и гарантий по ремонту, закрыть неописанные переходы,
отображение, историю и граничные даты.

### 14.2. Задача для таск-трекера

**Оргтехника: завершить и принять учёт гарантийных сроков**

### 14.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план завершения гарантийных сроков в модуле «Оргтехника». Сначала проведи
инвентаризацию уже реализованных сущностей и экранов: гарантия самой единицы, гарантия результата
ремонта или позиции работ, гарантийный талон, реестр действующих гарантий и события истории.
Зафиксируй бизнес-источник каждой даты, обязательность, ручной и вычисляемый режим, границы «истекает
сегодня», часовой пояс и поведение при возврате заявки на доработку, повторном закрытии,
переназначении сервиса, архивировании и исправлении ошибочной даты. Определи, кто видит и меняет
каждый срок, какие документы подтверждают гарантию, как срок появляется в карточке аппарата и
агрегированной истории. План должен выявить расхождения между кодом и ожиданиями заказчика, не
объявлять готовым то, что не имеет критериев приёмки, включить миграции данных, db/API/UI-тесты,
выгрузку и чек-лист продуктовой приёмки.

## После накопления данных пилота

## 15. Признак повторного обращения

### 15.1. Краткая суть фичи / фикса

Помечать повторные обращения по одному аппарату по прозрачному правилу и давать быстрый переход к
предыдущим заявкам, не используя на первом этапе нечёткое сравнение текста.

### 15.2. Задача для таск-трекера

**Оргтехника: добавить признак повторной заявки по аппарату**

### 15.3. Подробное описание задачи — промт для создания поэтапного плана реализации

Подготовь поэтапный план выявления повторных обращений по оргтехнике после накопления достаточной
истории пилота. Сначала отдели существующий запрет второй одновременно открытой заявки того же вида
по аппарату от нового признака повторной поломки после закрытия. Предложи детерминированную первую
версию: тот же аппарат, совместимая категория обращения и предыдущая закрытая или отменённая заявка
в настраиваемом временном окне. Не применяй NLP и нечёткое сравнение описаний без отдельного
обоснования и измеряемой точности. Зафиксируй решения заказчика: период, категории, учитываемые
статусы, место показа и аудитории. В строке и карточке покажи понятную метку, количество совпадений
и ссылку на отфильтрованный список предыдущих заявок. Опиши вычисление без хранения либо
материализованный признак, индексы, обновление при смене статуса, влияние архивов и объединения
дубликатов, права доступа, тесты на границах периода и критерии полезности по данным пилота.
