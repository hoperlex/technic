# Целевой этап: заморозка legacy — инвентари API и ключей

Часть [плана доработок](frontend-followup-plan.md) (§4), работы Б3 и Б4. Опирается на бюджеты
качества (`apps/web/scripts/quality.mjs`, коммит `0f41687`) и продолжает их вторым механизмом.

**Смысл этапа.** Числовые бюджеты умеют одно: не давать долгу вырасти молча. Они не умеют
запрещать **новые исключения** — метод, добавленный в существующий объект API, не поднимает
счётчика объектов; ключ, заведённый в уже «грязном» файле, не поднимает счётчика файлов. Ровно это
и произошло за девять дней: `src/api/` вырос на 70 %, потребителей стало 86 вместо 49, а все
проверки оставались зелёными.

**Чего этап НЕ делает.** Он ничего не переносит и не разрезает. Он не чинит инвалидацию (это Р3),
не включает границы `features` (Б5), не трогает бандл (Р5). Его единственная задача — сделать так,
чтобы завтрашнее «допишу пока сюда» упиралось в красную проверку с внятной подсказкой.

## 2. Решения, принятые до начала

### 2.1 Сигнатура API — `объект.метод`, без имени файла

`vehiclesApi.list`, а не `resources.vehiclesApi.list`. Причина: разрезание legacy вбок (как
`1d60892`, вынесший 302 строки в `users.ts` и `grants.ts`) не должно выглядеть как появление нового
API — иначе проверка запретит ровно то улучшение, которого мы хотим. Инвентарь следит за
**появлением ручек**, а не за их расположением.

Побочный эффект: переименование объекта читается как «удалили одно, завели другое» и требует
осознанного `quality:update`. Это приемлемо — переименование API и есть событие, которое стоит
заметить.

### 2.2 Файлы `src/api` — отдельным списком

Инвентарь методов не заметит нового файла, если тот пока пуст или устроен непонятно. Поэтому
рядом — список файлов `src/api/**`. Новый файл требует осознанной строки в диффе.

Это же закрывает дыру, найденную 19.08: `check-stage2-layout` следит за фиксированным
`['api/resources.ts', 'api/auth.ts']` и трёх новых файлов не видит вовсе.

### 2.3 Ключ — пара «файл → корень», а не весь ключ целиком

`pages/admin/MailingSchedulesBlock.tsx → mailing-schedules`. Параметры меняются каждый день, корень
же отвечает на единственный важный вопрос: к какой чужой сущности лезет этот файл. Новая пара —
ошибка; изменившиеся параметры проверку не тревожат.

### 2.4 Переменная считается ключом только по употреблению

`const SCHEDULES_KEY = ['mailing-schedules']` — ключ, `const STATUSES = ['new', 'done']` — нет, и по
самому объявлению они неотличимы. Поэтому обход двухпроходный: сначала собираются имена, реально
подставленные в `queryKey` или в методы кэша, затем ищутся их объявления. Списывать в ключи всякий
массив строк — значит завести проверку, которая кричит на пустом месте; такую отключат первой.

### 2.5 Непонятное не пропускается, но и не блокирует работу сразу

Скрипт, молча пропускающий то, чего не понял, — это ровно тот дефект, из-за которого нынешняя
проверка раскладки даёт ложное спокойствие. Но и падать на первом же прогоне из-за десятка
конструкций, которых никто не ждал, — способ добиться, чтобы проверку выключили.

Поэтому третий список — `unresolved`: место, где скрипт не смог определить владельца ключа. Он
фиксируется на первом прогоне и **дальше только уменьшается**, как и остальные бюджеты. Рост
`unresolved` — такая же ошибка, как новая сигнатура: «написал так, что проверка не разобрала» — это
не повод её обойти.

### 2.6 Инвентарь — отдельный файл

`apps/web/quality-inventory.json` рядом с `quality-budget.json`. Бюджет читают глазами — там
полтора десятка чисел; инвентарь машинный, на сотни строк, и мешать их в одном файле значит сделать
нечитаемым первый.

## 3. Коммиты

Четыре, каждый самостоятелен и оставляет дерево рабочим.

### К1. Инвентарь методов legacy-API (3 ч)

`apps/web/scripts/lib/api-inventory.mjs` — обход `src/api/**` через `typescript` (`ts.createSourceFile`,
без программы и типов: нам нужны имена, а не разрешение символов).

Собирается: для каждого `export const <имя>Api = { … }` — имена свойств объекта
(`PropertyAssignment`, `MethodDeclaration`, `ShorthandPropertyAssignment`).

Падает, если:

- значение экспорта не объектный литерал (фабрика, вызов, спред) — такую форму инвентарь не
  описывает, и молчать о ней нельзя;
- на верхнем уровне объекта встретился `SpreadAssignment` (сейчас таких нет — проверено);
- файл в `src/api` не разобрался вовсе.

`quality.mjs` получает две новые величины: `legacyApi` (список сигнатур) и `legacyApiFiles`.

**Приёмка** — три искусственных нарушения подряд, каждое краснеет:

1. добавить метод в существующий объект → «новая ручка `vehiclesApi.foo`: заводите её в слайсе»;
2. завести файл `src/api/probe.ts` → «новый файл legacy-API»;
3. переложить объект целиком из `resources.ts` в `users.ts` → **зелено** (это перенос, не рост).

### К2. Инвентарь ключей (4 ч)

`apps/web/scripts/lib/query-keys.mjs` — обход всего `src` тем же способом.

Первый проход: узлы, где ключ употреблён, — свойство `queryKey` в объектном литерале и первый
аргумент `invalidateQueries`, `setQueryData`, `getQueryData`, `removeQueries`, `cancelQueries`,
`prefetchQuery`, `fetchQuery`, `ensureQueryData`.

Для каждого места определяется владелец:

| Что стоит в ключе                          | Вывод                            |
| ------------------------------------------ | -------------------------------- |
| литерал `['waybills', …]`                  | сырой ключ, корень `waybills`    |
| идентификатор → объявление в этом же файле | сырой ключ, корень из объявления |
| вызов/поле из импорта `@entities/*`        | ключ сущности, не считается      |
| что-то иное                                | `unresolved` с файлом и строкой  |

`source-scan.mjs` переводится на этот обход: регулярка удаляется, `rawKeyFiles` начинает считаться
по AST — число вырастет, и это правильный результат, а не регресс.

**Приёмка** — четыре сценария:

1. ключ в переменной (`const X = ['drivers']`) виден (регулярка его не видела);
2. новый корень в уже «грязном» файле краснеет (числовой бюджет этого не умел);
3. массив строк, не употреблённый как ключ, в инвентарь не попадает;
4. `queryKey` из выражения, которого скрипт не понял, попадает в `unresolved`, а рост `unresolved`
   краснеет.

### К3. Дыра в раскладке этапа 2 (30 мин)

`check-stage2-layout`: `PENDING_API` перестаёт быть фиксированным списком и читает `src/api`
целиком. Пока каталог не пуст — заметка; когда опустеет, проверка начинает требовать его
отсутствия, как и было задумано.

**Приёмка:** новый файл в `src/api` появляется в выводе проверки без правки скрипта.

### К4. Первое сокращение инвентаря (3 ч, необязательный)

Три слайса — `counterparty`, `user-account`, `weekly-request` — содержат **только `keys.ts`**: ключи
переехали, API остался в legacy. Дом готов, переносить некуда больше.

Переезжают `counterpartiesApi`, `usersApi`, `weeklyRequestsApi`; `resources.ts` и `users.ts`
реэкспортируют переехавшее, потребители не трогаются. Инвентарь уменьшается на ~40 сигнатур —
первое доказательство, что он умеет сокращаться, а не только запрещать.

Коммит необязателен: этап закрыт и без него.

## 4. Что этап меняет в правилах

После К1–К3 в `pretest` проверяется:

| Правило                                    | Было           | Стало                      |
| ------------------------------------------ | -------------- | -------------------------- |
| Новая ручка в legacy-API                   | не видно       | красный                    |
| Новый файл в `src/api`                     | не видно       | красный                    |
| Новый корень ключа в «грязном» файле       | не видно       | красный                    |
| Ключ, записанный в переменную              | не видно       | учитывается                |
| Конструкция, которую проверка не разобрала | тихо пропущена | `unresolved`, рост красный |

## 5. Риски

**Первый прогон краснеет обильно.** Смягчение — `unresolved` (§2.5) и то, что первый снимок делает
`quality:update`: он фиксирует состояние как есть. Красным становится только то, что появится потом.

**Инвентарь снимается с рабочего дерева, а в нём чужая незавершённая работа.** Так уже было
10.08 с числовыми бюджетами. Порядок тот же: снимать сразу после коммита, а расхождение лечить
`quality:update` с отдельной строкой в диффе.

**AST замедлит `pretest`.** Сейчас все проверки идут 0,14 с. Замер входит в приёмку К2; порог —
10 секунд на все проверки разом. Если не уложится: `src/api` парсится всегда, полный обход `src` —
только при изменении файлов (сверка по `mtime`), но усложнение вводится **после** замера, а не
заранее.

**Проверка начнёт мешать чужой работе.** Это и есть её работа. Важно другое: сообщение обязано
называть не только нарушение, но и куда деть новое, — иначе первым движением будет поднять число.

## 6. Критерии приёмки этапа

| Признак                                     | Проверка                                                                |
| ------------------------------------------- | ----------------------------------------------------------------------- |
| Новое API в legacy невозможно завести молча | сценарии К1, все три                                                    |
| Новый сырой ключ невозможно завести молча   | сценарии К2, все четыре                                                 |
| Проверка не молчит о непонятном             | подложенная неразбираемая форма даёт `unresolved`, не тишину            |
| Скорость не пострадала                      | все проверки `pretest` ≤ 10 с                                           |
| Инвентарь умеет сокращаться                 | `quality:update` убирает исчезнувшие сигнатуры (К4 или ручная проверка) |

## 8. Что этап оставляет следующему

Инвентарь ключей — половина работы Р3 (статическая проверка инвалидаций): обход, который умеет
сказать «в этом файле гасится вот этот корень», и есть та часть, на которой Р3 споткнулась бы
первой. После этапа Р3 сводится к сопоставлению собранного с таблицей эффектов бэка.
