# Протокол выката необратимых миграций

Нормативный документ: единственное описание state-машины выката, форматов состояния и гейтов
отката. Всё остальное на него **ссылается** — [runbook](runbook.md) даёт команды оператора,
[план рейсов](route-trips-plan.md) — параметры своего релиза (номер миграции, свой верификатор,
свой teardown). Двух нормативных описаний быть не должно: они разойдутся при первой же правке.

Заведён под миграцию рейсов (на 13.08.2026 свободен номер `0136`), но написан общим: у следующей необратимой миграции будет свой
teardown и свой верификатор, а протокол — этот же.

---

## 1. Зачем

Штатный `deploy-auto` накатывает миграции **до** перезапуска
([`deploy-auto.sh:795`](../deploy/deploy-auto.sh#L795)) — старый код какое-то время работает на новой
схеме. Для аддитивных миграций это безобидно. Для миграции, меняющей смысл данных, — нет: старый
код пишет по старым правилам, и разобрать потом, где план, а где мусор, бывает нечем.

Отсюда два требования, из которых вырастает весь протокол:

1. **старый код и новая схема не встречаются** — выкат идёт с остановкой записи;
2. **после определённого момента откат назад невозможен**, и этот момент должен быть наблюдаемым,
   переживать перезапуск и не зависеть от того, помнит ли о нём человек.

## 2. Понятия

| Термин               | Что это                                                                                  |
| -------------------- | ---------------------------------------------------------------------------------------- |
| **бандл**            | набор миграций релиза; для необратимого выката — ровно одна **необратимая** (§6)         |
| **верификатор**      | команда релиза, проверяющая данные после миграции; для рейсов — `backfill:trips --check` |
| **teardown**         | обратная миграция релиза, лежащая **вне** каталога миграций (§7)                         |
| **floor**            | граница совместимости: миграция, ниже которой откатываться нельзя (§4)                   |
| **точка невозврата** | атомарная запись floor (§3, шаг 7) — не «начало `up -d`» и не переход фазы               |

## 3. State-машина `--cutover`

Состояние — `$STATE_DIR/cutover.state`, рядом с `release.state`, а не в рабочем дереве: `git pull`
не должен ни стирать его, ни конфликтовать с ним. Пишется атомарно (временный файл + `mv`).

Фазы: `migrating` → `migrated` → `irreversible` → `done` | `superseded`.

Шаги:

1. **сверка бандла** — до всякого действия. Среди неприменённых должна быть ровно одна необратимая
   (узнаётся по teardown в образе); две — отказ, ни одной — отказ с отсылкой к обычному деплою.
   Обычные соседи допускаются и пишутся в `extras`, а окно объявляется широким: откат такого окна
   идёт дампом, а не teardown'ом, и об этом предупреждают сразу, пока сервисы работают (§6);
2. остановка `technic-api` и `technic-worker` — запись прекращена;
3. дамп + `<дамп>.pin` (закрепление от ротации) + `.meta` с **точным набором применённых миграций**
   (§5);
4. `cutover.state` = `migrating` (SHA кандидата, имя миграции, имя дампа) — **до** наката: обрыв
   между применением и записью иначе оставил бы миграцию, о которой состояние не знает;
5. накат миграции → фаза `migrated`;
6. **верификатор**, fail-closed: ненулевой код — сервисы остаются лежать, состояние `migrated`,
   откат ещё возможен;
7. **атомарная запись floor** (§4) — ← **точка невозврата**;
8. фаза `irreversible`;
9. `up -d` → health-гейт;
10. фаза `done`;
11. **архивирование**: `cutover.state` атомарно переименовывается в `cutover-<sha>.state`. Без этого
    шага «активного состояния больше нет» неоткуда взяться, а следующий cutover встретит чужой SHA.

Порядок шагов 7 и 8 обязателен именно такой. Обратный оставлял бы щель, в которой фаза уже
запрещает откат, а постоянной границы ещё нет, — и forward-deploy, успевший заархивировать
состояние, снял бы запрет вместе с ним.

### 3.1. Возобновление

`--cutover` не требует чистого старта: после любого обрыва (упал верификатор, умер контейнер,
Ctrl-C) он сверяет журнал миграций, floor и фазу и пропускает сделанное.

| Миграция в журнале | Во floor | Фаза             | Что делает `--cutover`                                                          |
| ------------------ | -------- | ---------------- | ------------------------------------------------------------------------------- |
| нет                | нет      | файла нет        | обычный ход с шага 1                                                            |
| нет                | нет      | `migrating`      | обрыв до наката: продолжает с шага 3                                            |
| нет                | нет      | `migrated`       | след успешного `--cutover-revert`: чистит состояние, дальше как с чистого листа |
| есть               | нет      | `migrating`      | обрыв между накатом и записью: чинит фазу на `migrated`, идёт к шагу 6          |
| есть               | нет      | `migrated`       | возобновление: сразу шаг 6                                                      |
| **есть**           | **да**   | **`migrated`**   | **обрыв сразу после границы**: фаза чинится на `irreversible`, идёт к шагу 9    |
| есть               | да       | `irreversible`   | доподнимает контейнеры и **повторяет health**; подтвердился — `done`            |
| есть               | да       | `done`           | обрыв на шаге 11: архивирует состояние и завершается успешно                    |
| есть               | да       | архив, файла нет | отказ: релиз завершён, следующий выкат — обычным `deploy-auto`                  |
| есть               | любое    | файла нет        | отказ: миграцию накатили мимо cutover — разбирает человек                       |

Сочетания «фаза `irreversible`, а floor нет» по построению не бывает: floor пишется раньше.

SHA кандидата при возобновлении обязан совпасть с текущим. «Контейнеры подняты» проверяется тегом
образа (`docker inspect` показывает `technic-*:<candidate>`), а не фактом запуска: наполовину
поднятый набор иначе сошёл бы за поднятый.

### 3.2. Что заблокировано и когда

| Фаза                        | `deploy-auto` (другой SHA) | `--previous` / `--restore-db`     |
| --------------------------- | -------------------------- | --------------------------------- |
| `migrating`, `migrated`     | отказ: идёт cutover        | отказ: идёт cutover               |
| `irreversible`, `done`, нет | разрешён (forward-fix)     | только через гейты floor (§4, §5) |

После `irreversible` блокировка обычного деплоя снимается намеренно: схема уже новая, и обычный
релиз ничего не обходит — он выкатывает следующий код на ту же схему. Это единственный путь, когда
health не подтвердился из-за дефекта кода. Завершившись, такой деплой архивирует состояние как
`superseded`.

### 3.3. `--cutover-revert`

Разрешён **тогда и только тогда**, когда выполнены оба условия:

- фаза ровно `migrated`;
- миграции бандла **нет** во floor.

Второе условие и есть закрытие обрыва между шагами 7 и 8: floor уже стоит, фаза ещё нет — откат
запрещён, чинится вперёд. Дополнительно проверяются: окно было узким (`extras` пуст — иначе отказ
с отсылкой к `--restore-db`, §6), сервисы остановлены, применённый набор совпадает с бандлом,
посторонних миграций нет, закреплённый дамп на месте.

Сам revert возобновляем: обрыв между teardown и подъёмом сервисов оставляет базу без миграции и
сервисы лежащими; повтор видит, что миграции в журнале уже нет, teardown пропускает и поднимает
текущий тег. Успешно завершившись, **удаляет** `cutover.state`.

## 4. Граница совместимости — `$STATE_DIR/schema-floor.state`

Запрет отката не может жить в `cutover.state`: тот архивируется при `done`/`superseded`, и вместе с
ним исчез бы запрет. Особенно скверно сразу после успешного выката — `release.state` помнит только
`current` и `previous` ([`deploy-auto.sh:183`](../deploy/deploy-auto.sh#L183)), а `previous` там
предыдущий релиз, который про новую схему не знает.

Формат — документ, а не «файл с дописыванием»:

```json
{ "schemaVersion": 1, "floors": [{ "migration": "0136_route_trips.sql", "sha": "…", "at": "…" }] }
```

**Пустой список — законное состояние, отсутствие файла — авария.** Различать их обязательно, иначе
потерю границы нечем обнаружить: журнал миграций непуст всегда, и «нет файла при непустом журнале»
ничего не значит. Поэтому bootstrap-релиз **создаёт** файл с `floors: []`, и дальше:

| Состояние файла     | Трактовка                                            |
| ------------------- | ---------------------------------------------------- |
| нет файла           | **авария**: fail-closed на все разрушительные режимы |
| нечитаем, повреждён | **авария**: то же                                    |
| `floors: []`        | границ ещё не было — обычная жизнь площадки          |
| непустой `floors`   | границы стоят, действуют гейты §4.1 и §5             |

Запись новой границы — атомарная замена документа целиком (временный файл + `mv`), а не дописывание
строки: половина записи не должна читаться как валидное состояние.

Файл переносится и бэкапится вместе с `release.state`: сейчас `snapshot_config` кладёт в архив
только `prod.env`, CA и vhost ([`deploy-auto.sh:477`](../deploy/deploy-auto.sh#L477)), и оба
state-файла добавляются туда же — потерять «вечную» границу при переносе площадки значит потерять её
навсегда.

Но одного этого мало: `snapshot_config` снимается **до** `pull` и, значит, до миграции
([`deploy-auto.sh:686`](../deploy/deploy-auto.sh#L686)) — после первого же cutover последний снимок
содержал бы `floors: []`, то есть ровно то состояние, от которого граница защищает. Поэтому
**атомарная запись floor (шаг 7) сразу же повторяет снимок состояния**: копия обоих state-файлов
кладётся рядом с закреплённым дампом, под тем же `.pin`. Правило простое — снимок делается после
каждой записи границы, а не только в начале деплоя.

**Инициализация — однократная.** Файл заводит bootstrap, и только он: после успешного bootstrap
отсутствие файла означает потерю, а не «ещё не было», и автоматически не переинициализируется
никогда.

Отличить «ещё не заводили» от «потеряли» по самому файлу **невозможно** — в обоих случаях его нет.
Поэтому у права на создание есть свой след: `$STATE_DIR/schema-floor.bootstrap` — отметка, что файл
на этой площадке уже заводился. Следом считается и любое состояние cutover (`cutover*.state`):
границы пишет только выкат, и раз он здесь был, границе положено существовать. Нет файла, но есть
след — авария с указанием, откуда восстанавливать (снимок `snapshot_config`), а не молчаливое
пересоздание пустого списка. Отметка кладётся в снимок конфигурации рядом с самой границей: потеряв
её вместе с площадкой, мы вернули бы возможность переинициализации.

### 4.1. Гейт `--previous`

Целевой образ обязан содержать **все** миграции из `floors`. Проверяется по самому образу, а не по
журналу базы: журнал говорит, что накатано сейчас, а спрашиваем мы другое — умеет ли этот код жить с
такой схемой.

Спрашивается **состав образа**, поэтому и берётся он у образа: `db:migrate:files` целевым образом
отдаёт список его миграций, и множество `floors` обязано в него вложиться. `db:migrate:check` здесь
не годится, хотя и близок по смыслу: он отвечает про журнал **базы** («что накатано сейчас»), а при
`--previous --restore-db` журнал по ходу операции ещё и меняется — гейт спрашивал бы у движущейся
цели. Отказ называет, ниже какой границы метит откат.

## 5. Гейт `--restore-db`: дамп сверяется составом, а не временем

Время не годится: метка дампа имеет точность в секунду
([`deploy-auto.sh:781`](../deploy/deploy-auto.sh#L781)), а предмиграционный дамп снимается ровно
перед миграцией — «не раньше границы» он выполнит на той же секунде и пройдёт гейт, заведённый
против него. И «снят после границы» не означает «схема совместима»: `pg_restore --clean` не снимает
объекты, которых нет в архиве ([`deploy-auto.sh:609`](../deploy/deploy-auto.sh#L609)).

Поэтому `.meta` дампа несёт **точный набор применённых миграций** (список имён; для короткого
сравнения — количество и хеш списка), и до всякого разрушительного действия проверяется:

1. `.meta` есть и читается — иначе отказ. Прежнее «метки неизвестны» было предупреждением; для гейта
   такого допуска быть не может;
2. все миграции из `floors` присутствуют в дампе — иначе восстановление вернуло бы схему за границу;
3. **набор дампа в точности равен набору целевого образа**. Не «образ содержит всё из дампа»:
   лишние миграции образа после восстановления станут `pending`, `db:migrate:check` вернёт код 3
   ([`migrate.ts:49`](../apps/api/src/db/migrate.ts#L49)), и сервис не поднимется. Контрпример,
   который проходил бы одностороннюю проверку:

   ```text
   дамп и текущая база: 0135
   целевой образ:       0135, 0136   ← код ждёт схему 0136, после restore её нет
   ```

   Накатывать недостающее прямо в откатной команде — соблазнительно и опасно: откат превратился бы в
   миграцию. Для команды отката безопаснее равенство, а «восстановить старый дамп и доехать
   миграциями» остаётся отдельной осознанной процедурой;

4. текущая схема не содержит миграций **новее** дампа — их `pg_restore --clean` не снимет, и
   восстановление оставит гибрид. Тогда отказ, а выходов два: PITR либо явный teardown лишнего.

`created_at` остаётся в `.meta` справочным полем: оно отвечает человеку «когда», а не скрипту
«можно ли».

## 6. Бандл: одна необратимая на выкат

Раннер применяет **все** pending-файлы
([`migration-journal.ts:87`](../apps/api/src/db/migration-journal.ts#L87)). Вся фича поэтому едет
одной миграцией, включая сопутствующие данные (например, запись в журнал обновлений), а
`--cutover` сверяет pending-набор **до** остановки сервисов.

Бандл считается по **необратимым**, а не по всем. Необратимость видна по teardown в образе:
его несёт только то, что снимается протоколом. Необратимая в окне обязана быть одна — две означают,
что teardown снимет первую, а вторая останется в базе без пути назад. Обычные соседи в том же окне
допускаются, и это уступка не удобству, а арифметике: необратимая, уехавшая в ветку не одна,
запирала площадку наглухо — обычный путь отказывался из-за неё, `--cutover` из-за соседей, и
разъехаться можно было только переписав ветку. Состав релиза — не то, чем чинят площадку.

**Ценой широкого окна уходит `--cutover-revert`.** Teardown снимает одну миграцию; остальные
останутся в журнале при том, что в старом образе их файлов нет, — и он не стартует (`missing`).
Поэтому откат широкого окна идёт **только** восстановлением дампа, снятого в начале этого же окна
и закреплённого от ротации (§5), а `--cutover-revert` для такого окна отказывает намеренно, до
остановки чего-либо. Состав окна пишется в `cutover.state` полем `extras` — по нему отказ и
принимается, а не по догадке о том, что застали в журнале.

Дверь при этом обязана быть открыта, и это отдельное исключение в гейте разрушительных режимов.
По общему правилу (§3.2) активный выкат запирает `--previous` и `--restore-db`: откатывать его
положено его же режимом. Для широкого окна это правило оставило бы выход запертым с обеих сторон —
`--cutover-revert` отказывает, а разрушительные режимы не пускает гейт. Поэтому при непустом
`extras` гейт пропускает откат, **требуя оба флага**: `deploy-auto --previous --restore-db`. Одного
`--previous` мало — он посадил бы старый образ на новую схему. По завершении такого отката
состояние выката снимается и закрепление с дампа снимается тоже, ровно как после `--cutover-revert`.

Потери данных этот путь не несёт, пока окно не закрыто: с шага 2 и до подъёма сервисов запись
остановлена, так что дамп шага 3 и есть полное состояние окна. Дороже он не данными, а временем —
восстановление базы против снятия одной миграции.

Узкое окно — по-прежнему лучшее: `extras` пуст, откат идёт teardown'ом, дамп остаётся страховкой,
а не единственной дорогой назад. Широкое — законный, но худший режим, и скрипт говорит об этом
предупреждением в момент сверки бандла, пока сервисы ещё работают.

Сверка бандла отвечает на вопрос «этот ли состав», но не на вопрос «тем ли путём». Обычный
`deploy-auto` применял pending-набор, не спрашивая, нет ли среди него необратимого: раннеру всё
равно, а гейт бандла живёт в другой ветке скрипта. Такой деплой снимает дамп рядовой страховкой,
не зовёт верификатора и не пишет границу совместимости — площадка теряет единственный откат
молча и узнаёт об этом в тот момент, когда откат понадобился. Поэтому обычный путь проверяет
pending на teardown в образе и **отказывает целиком**, не применяя ничего
([`deploy-auto.sh`](../deploy/deploy-auto.sh), шаг «накат новых миграций»).

Отказ этот чинится не повтором, а флагом: необратимое накатывает `--cutover`, и только он.

## 7. Teardown: где лежит и чем вызывается

Раннер берёт из `apps/api/drizzle` каждый `*.sql`
([`migration-journal.ts:37`](../apps/api/src/db/migration-journal.ts#L37)) — teardown там применился
бы ближайшим `db:migrate` следом за миграцией, сняв только что накатанное. Поэтому:

- файл лежит в `apps/api/teardown/`, каталог раннеру неизвестен;
- читает его только команда `db:cutover-down`;
- teardown и удаление записи журнала — **одной транзакцией**;
- запись удаляется по полному имени файла с проверкой «удалена ровно одна»: ноль — миграция не
  применялась, больше — журнал не тот; и то и другое — отказ с откатом транзакции;
- teardown снимает **всё**, что завела миграция, включая данные: забытая строка в справочнике не
  даст накатить миграцию повторно, то есть откат сделает релиз невыкатываемым;
- запускается образом **кандидата** (SHA из `cutover.state`): teardown приезжает вместе с
  миграцией, и в предыдущем образе его ещё нет;
- руками не вызывается — она не проверяет ни фазы, ни границы. Для человека есть
  `deploy-auto --cutover-revert` (§3.3).

  **Это проверено на репетиции, а не предположено.** Запуск teardown напрямую (`psql -f`) не
  оборачивает файл в транзакцию: DDL проходит, а проверка «удалена ровно одна строка журнала»
  падает уже после того, как колонки сняты и таблицы удалены. База остаётся **полуразобранной** —
  каталог откачен, запись в журнале миграций на месте, — и следующий `db:migrate` увидит миграцию
  применённой при отсутствующих таблицах. `db:cutover-down` того же файла на той же базе проходит
  чисто: транзакция там снаружи.

- **Правка уже накатанной миграции ломает её teardown, и это правильно.** Teardown снимает запись
  выпуска по паре «`seq` + версия»; если после наката в файле поправили номер ADR или версию (у
  этого релиза так и вышло — `0107` оказался занят соседним потоком), пара перестаёт совпадать, и
  teardown отказывает словами «удалено 0 строк». Отказ верен: молча снести не ту строку журнала
  выпусков хуже. Но знать об этом надо заранее — **после первого наката файл миграции неизменяем**,
  включая её запись в `app_releases`.

**Верификатор объявляется рядом с teardown и тем же именем**: `apps/api/teardown/<миграция>.sql.verify`
— одна строка команды, которую выкат выполняет в образе кандидата после наката (§3, шаг 6). Место
общее по той же причине, по какой общий и teardown: механика не должна знать SQL конкретного релиза,
а релиз не должен править механику. Отсутствие файла — отказ **до** остановки сервисов, вместе со
сверкой бандла: выкат, которому нечем проверить перенос данных, начинать нельзя. Для репетиции (§9)
объявленную команду перебивает `AUTO_CUTOVER_VERIFY` — на копии базы проверяют и сам верификатор
тоже.

## 8. Что должен уметь bootstrap-релиз

Флаги разбираются до `git pull` ([`deploy-auto.sh:103`](../deploy/deploy-auto.sh#L103)) — значит
`--cutover`, приехавший тем же релизом, которым им собираются пользоваться, не запустится. Поэтому
механика выкатывается **заранее, отдельным обычным релизом**:

- режимы `--cutover` и `--cutover-revert`, сверка бандла, `cutover.state` с атомарной записью;
- `schema-floor.state`, **инициализированный как `{"schemaVersion":1,"floors":[]}`**, и его гейты;
- запись состава миграций в `.meta` дампа, `.pin` и его исключение в `rotate_dumps` **до**
  применения `keep-2`;
- `release.state` и `schema-floor.state` в `snapshot_config`;
- обобщённый запускатель teardown (без SQL конкретного релиза);
- строки в [runbook](runbook.md).

## 9. Чек-лист репетиции

Прогоняется на копии базы до релиза; без него необратимый выкат не начинается.

1. `pre-dump → миграция → db:cutover-down → db:migrate:check` показывает миграцию неприменённой →
   она накатывается **повторно без ошибок** → верификатор чист;
2. каталог БД после teardown совпадает с исходным — сверяется запросами: новых таблиц и колонок нет,
   снятые ограничения и индексы восстановлены. **Порядковый номер колонки в счёт не идёт**:
   снятая и возвращённая колонка встаёт в конец таблицы, и `scheduled_time_unspecified`, стоявшая
   девятой, после круга окажется третьей. На данные это не влияет (проверяется сверкой значений
   **явным списком** колонок, а не `SELECT *`), и восстановление дампа тоже не ломает — `pg_dump`
   пишет `COPY` со списком колонок. Требовать совпадения порядка значило бы требовать пересоздания
   таблицы там, где хватает `ALTER`;
3. teardown не виден раннеру: `listMigrationFiles()` его не возвращает, `db:migrate` после миграции
   не находит pending;
4. повторный `db:cutover-down` отказывает («удалено 0 строк»), а не чистит журнал молча;
5. посторонний pending блокирует `--cutover` **до** остановки сервисов;
6. `--cutover` возобновляем: обрыв после наката (фаза `migrated`) — повтор продолжает с
   верификатора; фаза `migrating` при накатанной миграции чинится; чужой SHA — отказ;
7. **граница crash-safe**: обрыв между записью floor и переходом фазы (`floor + migrated`) —
   `--cutover-revert` отказывает, `--cutover` чинит фазу; повреждённый и отсутствующий floor роняют
   разрушительные режимы; `floors: []` разрушительных режимов не роняет;
8. health упал — выкат не заперт: повтор `--cutover` прогоняет health заново; обычный `deploy-auto`
   с новым SHA при `irreversible` проходит и архивирует состояние (`superseded`); обрыв между
   успешным health и `done` лечится повтором;
9. **граница держится без активного `cutover.state`**: после `done` и после `superseded`
   `--previous` на образ без floor-миграции отклоняется, на образ с ней — проходит; две границы
   подряд (вторая необратимая миграция) проверку не ломают;
10. **restore-гейт**: отклоняются дамп до границы, дамп той же секунды, что и граница, дамп без
    `.meta`, дамп с набором, не равным набору целевого образа, и дамп старше текущей схемы (с
    предложением PITR); проходит дамп, совпадающий с образом по составу;
11. `--cutover-revert` после `irreversible` отклоняется;
12. **архивирование `done`**: обрыв между записью `done` и переименованием лечится повтором
    `--cutover` — он архивирует и завершается успешно; после архивирования повтор отказывает;
13. **однократная инициализация floor**: первый bootstrap при отсутствии файла создаёт `floors: []`;
    после успешного bootstrap отсутствие файла даёт fail-closed и файл не пересоздаётся;
14. **снимок после границы**: копия `release.state` и `schema-floor.state` появляется рядом с
    закреплённым дампом сразу после записи floor и переживает ротацию.
