# ADR 0021. Единая модель прав: матрица разрешений вместо списков ролей

- Статус: Принято
- Изменяет: способ проверки доступа во всех модулях; п. 2 [ADR 0014](0014-waste-price-directory.md)
  («ведут администратор и менеджер», `REFERENCE_MANAGER_ROLES` → право `directories.write`,
  которое теперь есть и у диспетчера)
- Связано: `packages/contracts/src/permissions.ts`, `apps/api/src/auth/plugin.ts`,
  `apps/api/src/lib/access.ts`, все `apps/api/src/routes/*.ts`,
  `apps/web/src/auth/AuthContext.tsx`, `apps/web/src/auth/ProtectedRoute.tsx`,
  `apps/web/src/components/AppLayout.tsx`, `apps/api/test/route-authorization.test.ts`

## Контекст

Доступ проверялся четырьмя независимыми способами сразу:

- `app.requireRoles('admin', 'manager')` в `preHandler` — одиннадцать справочников, каждый со
  своей копией списка;
- предикаты `canManageRequests` / `canChangeStatus` / `assertNotOperator` в `lib/access.ts` —
  ещё один набор ролей, уже в теле обработчиков;
- сравнения вида `p.role === 'admin'` прямо в маршрутах — около двадцати мест (архив,
  восстановление, удаление машины насовсем, удаление файла);
- на портале — свои перечни: `RequireRole roles={[...]}` в маршрутах и `hasRole('admin',
'manager')` в меню.

Константы, заведённые ровно для того, чтобы списки не расходились (`REFERENCE_MANAGER_ROLES`,
`STATUS_CHANGE_ROLES`), не использовались нигде, кроме соседней функции в том же файле.

Хуже разнобоя было другое: модуль «Вывоз мусора» защищался запретами, а не разрешениями. На всех
его маршрутах стоял только `app.authenticate`, а роли ограничивались проверками «не оператор» и
«штаб — свой объект». Такая схема разрешает по умолчанию: любая новая роль — и любая учётка, чью
роль забыли или сняли, — получала права заказчика (создание, правка и удаление заявок) молча, без
единой строки в диффе. Забытая проверка на новом маршруте выглядит точно так же, как намеренно
открытый маршрут, и ни один тест на это не реагировал.

Отдельный вопрос — роль «Диспетчер»: он ведёт заявки всех объектов, но справочники, из которых
эти заявки собираются (техника, типы ТС, контрагенты), были ему недоступны даже на чтение
страницей — правки приходилось просить у менеджера.

## Решения

1. **Право, а не роль, — единица доступа.** `packages/contracts/src/permissions.ts` объявляет
   перечень прав (`directories.write`, `wasteRequests.status`, `archive.restore`, …) и матрицу
   `ROLE_PERMISSIONS`. Код спрашивает `can(role, permission)` и нигде не перечисляет роли: новая
   роль заводится строкой матрицы, а не правкой пятнадцати файлов.

2. **Матрица живёт в общем пакете, а не на сервере.** Портал скрывает недоступное по той же
   таблице, по которой API запрещает. Разъехавшиеся копии давали либо кнопку, ведущую в 403, либо
   действие, видимое в интерфейсе и запрещённое на сервере.

3. **Права перечислены полностью, без наследования.** «Диспетчер = менеджер + N прав» прячет
   расширение доступа: новое право у базовой роли расходится по производным незаметно. В матрице
   каждое расширение видно строкой в диффе.

4. **Право и область видимости — разные слои.** Право («что роль может делать») проверяется до
   запроса в БД, в `preHandler`. Область («над какими строками») — по конкретной записи:
   `assertShtabScope`, `assertOperatorScope`, `requestVisibilityWhere`, `assertShtabEditable`.
   Смешение слоёв даёт либо 403 на собственной заявке, либо доступ к чужой.

5. **Разрешение по умолчанию отменено.** Каждый маршрут объявляет право явно, включая «Вывоз
   мусора»: `wasteRequests.read` на чтение, `.create` / `.update` / `.delete` / `.status` /
   `.assignOperator` — на действия. Запреты для отдельных ролей (`assertNotOperator`) исчезли:
   у оператора просто нет соответствующих прав.

6. **Маршрут без проверки роняет тест.** `app.requirePermission()` помечает страж именем права,
   `app.authorizeInHandler(причина)` — случаи, где доступ зависит от самой записи (файл виден
   тому, кому видна его заявка). `test/route-authorization.test.ts` собирает маршруты из готового
   приложения и требует пометку у каждого. Ради этого `buildApp` принимает наблюдателя `onRoute` —
   из собранного приложения Fastify список `preHandler`'ов больше ниоткуда не достать.

   Страж ловит только полностью забытую проверку: правильность привязанного права он не знает.
   За это отвечает `test/access-matrix.test.ts` — запросы под каждой ролью к каждому значимому
   маршруту, с ожиданием 403 ровно у тех, кому запрещено.

7. **Правила статусов выведены из прав.** Откат закрытой заявки — право
   `requests.rollbackStatus`, а не сравнение с `admin`; коридор оператора описан таблицей
   `ROLE_STATUS_TRANSITIONS`, куда добавляется следующая такая роль. `allowedStatusTransitions`
   переехала к матрице: «кто может» — это право, а таблицы переходов описывают только «что за чем
   идёт».

8. **Диспетчер ведёт справочники наравне с менеджером** — все вкладки, включая «Стоимость вывоза
   мусора» и «Контрагенты». Решение заказчика: диспетчер собирает заявки из этих же данных, и
   ожидание менеджера ради строки в справочнике останавливает работу.

9. **Архив справочника открыт тем, кто его ведёт.** Удалённая техника показывается по
   `directories.write` (раньше — любому, кто мог читать список), удалённые контрагенты и заявки —
   по `archive.read` (администратор). Восстановление — `archive.restore`, удаление насовсем —
   `records.purge`.

10. **Право нельзя обойти соседним маршрутом.** Право на действие проверяется везде, где это
    действие выполняется, а не только там, где оно названо:
    - назначение исполнителя (`wasteRequests.assignOperator`) спрашивается и в форме создания, и
      в правке заявки — поля `operatorCounterpartyId` в общих схемах достаточно, чтобы штаб
      назначил оператора мимо `PATCH /:id/operator`. Право требуется по факту присутствия поля:
      сравнивать со старым значением значило бы проверять его после загрузки заявки, а решение
      от её содержимого не зависит;
    - удалённая запись отдаётся только по `archive.read` — не только в списках, но и в карточке,
      истории и карточке справочника (`assertArchiveVisible`). Список скрывает архив фильтром, а
      выдача по прямому id обходила его при известном UUID;
    - восстановление техники — `archive.restore`, как и у контрагентов и заявок, а не
      `directories.write`.

11. **Доступ к файлу выводится из связанной заявки, а не из факта загрузки.** Авторство открывает
    только ещё не привязанный файл — так работает форма: файл грузится до сохранения заявки.
    После привязки файл живёт по правилам своей заявки, иначе загрузивший сохранял бы доступ и
    после смены роли, объекта или контрагента. Связи ищутся только по модулям, доступным роли
    (`wasteRequests.read`, `vehicleRequests.read`): ограничения видимости написаны про штаб и
    оператора и роль без прав ничем не сужают — без проверки права учётка без роли скачивала бы
    вложение любой заявки вывоза по известному id. Решение вынесено в чистую `decideFileAccess`,
    чтобы правило проверялось тестом, а не только читалось.

## Последствия

- «Менеджер» и «Диспетчер» сейчас совпадают по правам полностью: заявки они вели одинаково и
  раньше, а справочники сравнялись решением 8. Роли оставлены раздельными — они различаются
  организационно и разойдутся при первом же новом праве. Пока это так, любое правило вида «только
  менеджер» нужно вводить правкой матрицы, а не кода.
- Учётка без роли теперь не может ничего явно (`can(null, …) === false`). Раньше она проходила
  в «Вывоз мусора» как заказчик; активировать такую учётку API и так не давал, но защита была
  косвенной.
- Оператор больше не видит удалённую технику через `includeDeleted` — сужение доступа, заметное
  только при обращении к API напрямую.
- Страж авторизации требует, чтобы приложение собиралось без БД и S3. Сейчас это так; если
  появится плагин, который ходит в сеть при регистрации, тест придётся чинить вместе с ним.
- Матрица не заменяет проверку прав по записи: `records.purge` у администратора не отменяет
  проверку `assertShtabScope` для штаба. Оба слоя обязательны, и тест на маршруты видит только
  первый.
