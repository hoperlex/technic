# ADR 0136. Ширина раскрытого списка — правило портала, а не свойство поля

- Статус: Принято (реализовано). Схему не трогает: работа целиком во фронте. Миграцией уезжает
  только запись выпуска (ADR 0077 §4) — `0203`, выпуск `0.1.44.0136`
- Уточняет: [ADR 0135](0135-waste-request-completed.md) — фильтр площадки в вывозе мусора получил
  широкий список первым и поимённо; теперь это следствие общего правила, а не его собственная
  настройка
- Связано: [ADR 0030](0030-responsive-layout.md) (режимы устройства — почему правило одно на оба),
  [ADR 0069](0069-address-directory-pick.md) (выбор адреса из справочника — самый длинный список
  портала), [ADR 0028](0028-vehicle-classification-selection.md) (классификатор техники — единственная
  двухколоночная опция);
  `apps/web/src/main.tsx`, `apps/web/src/pages/waste/requestFilters.tsx`,
  `apps/web/src/pages/waste/WasteHistoryTab.tsx`

## Контекст

Раскрытый список antd по умолчанию ровно той же ширины, что и поле. Для короткой подписи это
незаметно, а для длинной — губительно: «С-12 — Корпус 3 — г. Москва, ул. Ленина, д. 14, стр. 3» в
поле шириной 240 px превращается в «С-12 — Корпус 3 — г. Мос…», и список перестаёт отвечать на
вопрос, ради которого его открывают: та ли это площадка. Расширять само поле нельзя — полоса
фильтров над таблицей разъедется, а поле стоит на экране всегда, в отличие от списка.

Лечили это поимённо. К августу 2026 правило имели ровно два поля из 186 (128 `<Select>`,
57 `<AutoSelect>`, один `<AutoComplete>` в 77 файлах) — фильтр площадки в рабочем списке заявок на
вывоз и такой же фильтр в журнале «История». Оба несли по две строки настроек и по абзацу
объяснения, почему у них так. Остальные 184 обрезали подписи молча — в том числе выбор адреса,
самый длинный список портала.

## Решение

**Правило одно, живёт в корневом `ConfigProvider` (`apps/web/src/main.tsx`):**

```tsx
popupMatchSelectWidth={false}
select={{ styles: { popup: { root: { maxWidth: '90vw' } } } }}
```

Инвариант, который из этого следует:

- список **не уже поля** — нижнюю границу antd растягивает по полю сам;
- поле уже 90 % ширины окна → список растёт **по содержимому** до 90 % ширины окна;
- поле шире 90 % ширины окна → нижняя граница выигрывает (в CSS `min-width` сильнее `max-width`), и
  список равен полю. Так работает мобильный шит фильтров, где поле во всю ширину экрана: там
  правило даёт ровно прежнее поведение, и для шита это правильный ответ;
- что не влезло — многоточие: `text-overflow: ellipsis` у пункта списка antd ставит сам.

Ветвления по режиму устройства нет намеренно: инвариант описывает оба режима одной формулой, а
не двумя ветками, которые пришлось бы держать в согласии.

### Почему в провайдере, а не обёрткой над `Select`

Флаг antd читает из контекста провайдера, а вложенные провайдеры его наследуют — своя тема кабинета
водителя и тема истории заявки правило не сбрасывают. Одно место покрывает `Select`, `AutoSelect`
(он на нём построен), `AutoComplete` (тоже) и списки внутри самой antd. Обёртка потребовала бы
перевести 56 файлов на неё и не дала бы ничего сверх.

Потолок задан **стилем, а не классом**: контекстные `styles` сливаются с локальными, локальные
побеждают — точечное переопределение остаётся возможным. Правило в CSS с `!important` эту дверь
закрыло бы.

## Цена: виртуализация списка выключается — и иначе не выходит

`popupMatchSelectWidth={false}` выключает виртуализацию (`realVirtual = virtual !== false &&
popupMatchSelectWidth !== false` в `@rc-component/select`), и локальный `virtual={true}` этого не
отменяет. Обход искали и проверили на стенде: при живой виртуализации попап шириной по содержимому
**не получается в принципе**. Виртуальный список рисует пункты в контейнере с `overflow: hidden` и
шириной 100 % родителя, поэтому `width: max-content` схлопывается до нижней границы — стиль долетает
до попапа целиком (это видно в inline-стиле), а ширина остаётся равной полю. Ширина по содержимому и
виртуализация в этой библиотеке несовместимы.

Значит вопрос был не «как обойти», а «сколько это стоит». Замер сделан **до** решения, на
производственной сборке, headless Chromium, 20 повторов на каждое действие после прогрева; интервал
— от клика (ввода символа) до следующего отрисованного кадра. Пороги задавались заранее: открытие
≤ 100 мс и ввод ≤ 50 мс на обычном CPU, ≤ 250 мс и ≤ 120 мс при торможении в 4 раза (офисная машина
медленнее машины разработчика).

| Случай | Открытие, ×1 | Ввод, ×1 | Открытие, ×4 | Ввод, ×4 |
| --- | --- | --- | --- | --- |
| 1000 пунктов, простые подписи | 33,6 / 45,7 | 18,5 / 21,6 | 159,2 / 188,5 | 98,1 / **122,8** |
| 500 пунктов | 23,7 / 29,0 | 12,4 / 17,2 | 94,8 / 109,4 | 58,6 / 74,9 |
| 1000 пунктов, множественный выбор | 26,0 / 27,8 | 15,9 / 18,8 | 137,0 / 161,5 | 93,2 / 104,5 |
| 100 пунктов, двухколоночная опция | 16,6 / 18,8 | 11,0 / 17,5 | 81,9 / 98,7 | 49,9 / 65,3 |
| 200 пунктов, двухколоночная опция | 28,3 / 34,3 | 15,3 / 21,1 | 131,3 / 150,0 | 76,8 / 84,7 |

Числа — медиана / p95 в миллисекундах. До правила (с виртуализацией) любой из этих случаев стоил
13–14 мс на открытие и ~17 мс на ввод при ×1; то есть на худшем списке портала правило добавляет
около 120 мс к открытию на медленной машине.

Размеры взяты не с потолка: `pageSize` в контракте ограничен рядом 50/100/200/500, а выбор адреса
складывает два справочника по 500 и группу «выбранное ранее» — это и есть 1000+. Двухколоночная
опция живёт только в классификаторе техники, где позиций порядка сотни (в деве 21 тип + 46
категорий), поэтому сочетание «1000 пунктов + двухколоночная опция» не мерялось как рабочее: его в
портале нет.

**Одна величина порог не прошла**: p95 ввода символа на списке в 1000 пунктов при ×4 — 122,8 мс
против 120 мс. Превышение на 2 %, на худшем сочетании из возможных, и медиана там 98 мс. Правило
принято с этим, а не вопреки: разница между «список читается» и «список обрезан» дороже трёх
миллисекунд в хвосте распределения.

Если однажды станет дорого — лечить надо будет не ширину, а длину: выгрузку справочника целиком
заменяет поиск на сервере. Это отдельная работа, и правило ширины её не блокирует.

## Последствия

- **Персональные настройки ширины сняты.** В `requestFilters.tsx` и `WasteHistoryTab.tsx` от них
  остались только комментарии о том, почему поле узкое; ширину списка эти файлы больше не знают.
  Новое поле получает правило само, ничего не прописывая.
- **`AutoComplete` подсказок адреса** правило получает вместе со всеми (он построен на `Select`).
  Подсказок там не больше восьми — разницы в цене нет.
- **Размер страницы у пагинации** antd задаёт `popupMatchSelectWidth: false` сам и всегда задавал;
  от правила он получает только потолок. Фильтры колонок таблиц построены на `Dropdown` и правила
  не касаются.
- **`TreeSelect` потолка не получит.** Флаг он берёт из корневого контекста, а `styles` — из
  собственного конфига провайдера. В коде портала его сегодня нет; появится — ему нужна своя строка
  рядом с `select`.
- **Ширина списка теперь зависит от содержимого**, то есть от данных. Самый длинный адрес в
  справочнике задаёт ширину всему списку; при поиске состав пунктов меняется, и ширина меняется
  вместе с ним. Это цена читаемости, и она видна на экране.
