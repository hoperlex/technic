# ADR 0231. Durable receipts for ordinary request creation

- Статус: Принято (15.10.2026); implementation staged, migration pending
- Домены: заказ-тс, вывоз-мусора, механизация, оргтехника, схема-и-выкат
- Развивает: [ADR 0230](0230-request-local-drafts.md) (a draft also retains one exact submitted body and key)
- Связано: [ADR 0101](0101-backdated-correction.md) (backdated Vehicle Request uses its correction journal), [ADR 0085](0085-weekly-vehicle-request.md) (weekly object/week uniqueness), [ADR 0226](0226-client-floor-seven-and-deploy-preflight.md) (old clients remain valid)
- Область: [receipt service](../../apps/api/src/services/request-create-attempt.ts), [pending SQL](../../apps/api/drizzle/pending/request-create-idempotency.sql), [draft store](../../apps/web/src/shared/lib/localFormDraftStore.ts), [Vehicle Request](../../apps/api/src/routes/vehicle-requests.ts), [Vehicle Request validation](../../packages/contracts/src/vehicle-requests.ts), [Waste Removal](../../apps/api/src/routes/waste-requests.ts), [Mechanization](../../apps/api/src/routes/mech-requests.ts), [Service Request](../../apps/api/src/routes/service-requests.ts)

## Context

An ordinary create can commit and lose its HTTP response. Repeating the same POST then creates a second Vehicle, Waste Removal, Mechanization or Service Request. Local drafts preserve entered fields but cannot prove whether the first POST committed. Weekly Vehicle Request creation already has a unique active object/week pair and a reconciliation flow. Backdated Vehicle Request creation already uses the correction journal, and the Service Request candidate branch already has a separate candidate intake receipt.

## Decision

1. The four ordinary create routes accept an optional UUID `Idempotency-Key`. A missing header keeps old API behavior. The route hashes the validated body using canonical object-key order. One key belongs to one request kind, actor and body; reuse for another combination returns 409.
2. The server reserves a shared receipt row in the same transaction that inserts the request, its child rows, file links and mail outbox entries. A concurrent retry waits on the receipt primary key and cannot repeat those writes. The receipt retains the request ID without a foreign key so later hard deletion never frees the key.
3. Before the first 201, the server freezes the response JSON in the receipt. A retry returns it with 200. If the process dies after committing the request and before freezing the response, the next retry completes it from the saved request ID and metadata. A request deleted in that gap yields 409 instead of creating another. Existing best-effort audit writes remain after the request transaction; a retry never duplicates them, while a crash in that gap can leave them absent.
4. The browser stores the key and exact first submitted body synchronously in its local draft before every send or retry. It keeps both after **any** HTTP error, including 400/422. A later retry may fail validation while the first POST is still in flight and later commits; that refusal cannot prove the original operation failed. Changed form fields do not alter the frozen body. Storage failure prevents sending because a reload could otherwise lose the only safe retry token. Restored drafts retain the attempt; a restored fork writes its own envelope but reuses the same key and body. The UI shows the key, explains that a retry sends the original body, and blocks discarding a pending attempted draft until the result is reconciled outside the form.
5. Backdated Vehicle Request creation remains with its correction operation ID and journal. The candidate intake branch retains its own receipt and response semantics. Weekly creation remains protected by its object/week uniqueness and list reconciliation; no second receipt is added. Uploaded file references remain in the submitted body, but unuploaded binary data still requires reattachment after a tab closes.
6. Vehicle Request and Waste Removal receipt replays pass stable structural validation before their clock-dependent new-request date gates. Otherwise a request created just before Moscow midnight could fail validation on an exact retry after midnight before the route sees its receipt. The SQL is additive and can run while the old API is live; `SET LOCAL lock_timeout = '10s'` bounds waiting on the users FK. The code must be released after this pending SQL is numbered and applied. The migration number is assigned by the release train.
7. An ordinary create client that may reconcile an uncertain result sends it to `POST /api/v1/<request-kind>/_create-with-receipt`, which requires `Idempotency-Key`. The four exact routes are absent on older API releases, so an API rollback rejects a cached new client instead of silently ignoring its key. Old root POST routes remain available for headerless tabs. Vehicle Request backdated creation stays on its root route and correction journal; Service Request candidate intake stays on its root route and own receipt. The new routes reject those two special bodies. New local attempts carry `protocol: receipt-v1`; an unmarked old attempt may have reached a root route and cannot be retried or reconciled automatically. After checking the request list, a user can explicitly reset that legacy attempt with a warning that the first POST may still finish and a new send may duplicate the request. This preserves draft fields but assigns a fresh key.
8. `POST /api/v1/<request-kind>/_create-attempts/reconcile` accepts the original validated body and key for an ordinary versioned-route attempt. It authenticates the actor but does not recheck create permission or current object scope: those may have changed after the first POST, while the receipt binds the actor, request kind and body fingerprint. A committed receipt returns `created` with its request ID. If no receipt exists, the endpoint inserts a permanent tombstone under that key and returns `not-created` with one server-generated replacement key. Its `INSERT ... ON CONFLICT` waits on the same primary key as an in-flight create; a create reaching the key later is rejected. Concurrent or restored tabs receive the same replacement key. An actor/body mismatch, Vehicle Request correction body, Service Request candidate body, or indeterminate state is blocked with an error; the client keeps its frozen attempt. A confirmed `not-created` allows the client to release the old body, edit the form and use the replacement key for a new attempt.
9. A `not-created` response replaces the frozen body with the server's next key in one checked local storage write. A Vehicle Request `created` response is followed by the ordinary request GET under current permissions; if that read fails, the UI still shows the committed request ID. The Vehicle Request draft carries earlier attempt keys across a release or manual reset. Confirmed creation clears restored forks and original local envelopes for those keys as well as the new key; failed storage removal leaves the active attempt available for another cleanup. Network failures and 409, 400 and 422 responses never release the first body. The submitted body is a private JSON snapshot so later mutations of nested form values or file IDs cannot change a retry.
10. Backdated Vehicle Request creation stays on the correction route and never uses this barrier. After checking the request list, the operator may explicitly start a new correction attempt. The confirmation warns that the first POST may commit late and the new operation can create a duplicate. One checked local storage write preserves the visible fields and trips while assigning a new correction operation ID and client key; this action does not send a POST. This manual exception is not a `not-created` proof and is not offered for ordinary versioned attempts.
11. An unlabelled ordinary attempt from a root-route client also has no valid barrier proof. After checking the request list, the operator may explicitly start a new versioned attempt. Its confirmation warns that an old API may have ignored the key and the first POST may commit late, creating a duplicate. One checked local storage write preserves visible fields and trips while replacing the client key; it does not send a POST. A failed write keeps the old body and key frozen. This manual route never presents `not-created` as a server result and is not offered for `receipt-v1` attempts.
12. Mechanization `Duplicate` is a separate create command. The new `POST /api/v1/mech-requests/:id/_duplicate-with-receipt` requires a key and uses the same receipt table and `mech` kind. Its fingerprint binds the command marker, source request ID and validated empty body, never the mutable source DTO. A committed replay returns only the copy ID before reading the source; the client uses ordinary GET under current permissions for a display number. Reconciliation at `/:id/_duplicate-attempts/reconcile` returns only the committed ID or a permanent `not-created` tombstone and replacement key. The old `/:id/duplicate` route remains for older tabs. A new browser attempt is durably saved before POST, and Web Locks serialize first-key selection across tabs; without that browser capability the action fails before sending. Every error preserves the key. A confirmed copy leaves a per-source completion marker after attempted draft cleanup; a later click displays its ID. Only an explicit "create another copy" action reserves a fresh key for a second rental unit. A late response for an older key cannot overwrite a newer marker or pending key. A confirmed `not-created` does not send automatically; the operator must explicitly start the next attempt. The shared pending SQL covers this command and must be applied before its code release.

## Consequences

- Retrying an uncertain ordinary create is safe while the draft and its attempted body remain available. A deliberately new Vehicle Request needs a confirmed `not-created` reconciliation through the versioned protocol or a new form opening that does not release the frozen attempt; the form never infers failure from a 400/422.
- Receipt rows remain after request deletion and need storage monitoring.
- The old clients continue to create without a header; protection requires a client that sends one.
- The reconciliation proof applies to all four ordinary forms only when their attempts were sent through versioned routes. The candidate intake and backdated Vehicle Request protocols remain separate. A keyed UI that still posts to a root route is unsafe on API rollback because an older server may ignore the header.
- Mechanization `Duplicate` shares the receipt barrier but has a separate command fingerprint and client intent. A cached client reaches a missing versioned route after API rollback, leaving its saved key available for a safe retry when the new API returns.
- The receipt and duplicate flows increase two measured first-screen closures: Mechanization to 619151 gzip bytes and the Waste Removal blind-check tab to 604391 gzip bytes. `apps/web/bundle-budget.json` records these deterministic `BUILD_ID=quality-check` measurements as the new limits.
