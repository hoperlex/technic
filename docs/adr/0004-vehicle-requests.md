# ADR 0004. Модуль «Заказ ТС» — заявки на технику (каркас)

- Статус: Принято
- Основано на: [ADR 0003](0003-vehicle-types-directory.md) (классификатор ТС), модуль «Вывоз мусора»
- Связано: `apps/api/drizzle/0012_vehicle_requests.sql`, `apps/api/src/routes/vehicle-requests.ts`,
  `apps/api/src/services/request-files.ts`, `packages/contracts/src/vehicle-requests.ts`,
  `apps/web/src/pages/VehicleRequestsPage.tsx`

## Контекст

Раздел заявок на технику двух типов — заказ спецтехники и грузоперевозки. Реализован как
законченный вертикальный срез поверх классификатора ТС. Согласованная установка: это **каркас**
системы — приоритет рабочей сквозной структуре, отдельные функции дорабатываются итеративно.

## Решения

1. **Модель данных.** Единая base-таблица `vehicle_requests` + две detail-таблицы
   (`special_equipment_request_details`, `freight_transport_request_details`). Общие статус,
   права, история, файлы; без широкой NULL-таблицы.
2. **Целостность деталей — сервисом, не триггером (на этапе каркаса).** «Ровно одна деталь
   нужного типа» обеспечивает сервисная транзакция. Deferred constraint-триггер (§9 плана) —
   в бэклоге; добавляется аддитивной миграцией без изменения формы таблиц.
3. **Тип заявки — отдельный enum** `vehicle_request_type` (`special_equipment|freight_transport`),
   неизменяем после создания (PATCH сверяет и отдаёт 422 при попытке смены).
4. **Классификатор.** Заявка ссылается только на конечный подтип (`vehicle_type_id`); backend
   валидирует, что это выбираемый активный подтип нужного вида. В API — `vehicleSubtypeId`,
   `parentTypeId` (через JOIN).
5. **Даты.** Спецтехника — период date-only `YYYY-MM-DD` (без JS Date, непрерывный, включительно;
   пусто = один день). Грузоперевозка — `scheduled_at timestamptz`; бизнес-таймзона Europe/Moscow:
   frontend шлёт ISO с offset, отображает в МСК; фильтр диапазона — день в МСК → UTC.
6. **Числа.** `numeric(12,3)` для объёма/массы; в DTO приводятся `Number()` + `Number.isFinite`.
7. **Статусы/версии/удаление** — как в «Вывозе мусора»: enum `request_status`, optimistic
   `version`, hard-delete для «Новая» (иначе soft), restore (admin), `includeDeleted` (admin),
   история `NULL→new` в транзакции создания. Аудит — после commit (best-effort).
8. **Номер.** `num` identity, отображается «ТС-000123» (`formatVehicleRequestNumber`); поиск
   принимает `123`/`ТС-123`/`ТС-000123`. Своя последовательность (независимо от «Мусора»).
9. **Общий файловый сервис** `services/request-files.ts` — оба модуля: привязка/отвязка,
   S3-outbox задачи, **кросс-модульная уникальность** (файл максимум в одной заявке) через
   `FOR UPDATE`. `requestVisibilityWhere`/`assertShtabScope` вынесены/параметризованы в
   `lib/access.ts`; `canAccessFile` учитывает оба модуля; `DELETE /files/:id` → 409, если файл
   прикреплён (исправлен латентный баг). Поведение «Мусора» сохранено.
10. **Frontend.** Раздел `/vehicle-requests`, три вкладки с `?tab=`: две отдельные формы/таблицы
    (спецтехника/грузоперевозки) + пустая «На объекте» (`Empty`, без запросов). Зависимый
    Тип→Подтип Select, раздельные query-keys.

## Последствия

- (+) Сквозной рабочий модуль от БД до UI; переиспользование классификатора и файловой
  подсистемы; «Мусор» и «ТС» ведут файлы единообразно.
- (−) Кросс-модульная уникальность файла — не чисто-БД гарантия (две типизированные link-таблицы
  ради FK-каскада), а сериализация в сервисе; достоверность — за конкурентным PG-тестом.
- (−) Отсутствие constraint-триггера деталей на этапе каркаса — теоретически допускает
  некорректную деталь при обходе сервиса (в бэклоге).

## Отложено (backlog)

- **PG-интеграционные тесты** (§34): deferred trigger, файловая конкурентность/кросс-модульная
  уникальность, timezone-фильтр, регрессия «Мусора» после рефакторинга. Тестовой БД-инфраструктуры
  нет; логика покрыта контракт/unit-тестами. См. `docs/reports/vehicle-requests-summary.md`.
- Deferred constraint-триггер целостности деталей.
- Snapshot исторических названий типов не делается: старые заявки показывают актуальные названия.
- Учёт техники на объекте (вкладка «На объекте») — следующий этап.
