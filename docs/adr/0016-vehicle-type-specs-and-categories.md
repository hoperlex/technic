# ADR 0016. ТТХ типов ТС и категории (условные подтипы)

- Статус: Принято
- Развивает: [ADR 0005](0005-vehicle-types-flatten.md) (плоский классификатор типов),
  [ADR 0007](0007-vehicle-models-and-vehicles.md) (марки/модели и техника)

  `apps/api/src/db/schema.ts`, `packages/contracts/src/vehicle-specs.ts`,

## Контекст

После ADR 0005 справочник типов ТС плоский: 13 типов, у типа нет ничего, кроме наименования и вида.
Реальная техника внутри одного типа различается измеримыми характеристиками — грузоподъёмностью,
длиной стрелы, объёмом кузова, — и заявка «нужен автокран» без этих чисел не адресна.

Подтипы из ADR 0001/0003 были отменены именно потому, что их приходилось выдумывать и вести руками
как отдельный список наименований. Нужен другой механизм: не второй уровень наименований, а набор
**значений характеристик**, из которого подтип получается сам.

## Решения

1. **ТТХ — глобальный справочник (`vehicle_specs`), а не поле типа.** Одна характеристика =
   наименование + единица измерения + масштаб. «Грузоподъёмность, т» — одна запись, общая для
   автокранов и самосвалов. Ведение ТТХ внутри типа дало бы дубли с разными единицами и сделало бы
   невозможным кросс-типовой отбор («вся техника с г/п ≥ 20 т»).
2. **Привязка = обязательность (`vehicle_type_specs`).** Тип обладает 0..N ТТХ; колонки
   `is_required` нет намеренно: раз ТТХ привязан к типу, **каждая** категория этого типа обязана
   иметь по нему значение. Ключ `(vehicle_type_id, spec_id)` — одновременно PK и цель составного FK
   из значений.
3. **Категория — кортеж значений, а не наименование (`vehicle_categories`).** Идентичность
   категории — набор значений всех ТТХ типа; наименование производно и служит отображению.
   Технически идентичность материализована в `spec_signature` + `UNIQUE (vehicle_type_id,
spec_signature)`: «одна комбинация значений = одна категория». Тип без ТТХ категорий не имеет
   вовсе — в этом случае тип и есть конечная классификация.
4. **Значения — реляционная таблица (`vehicle_category_spec_values`) с парой составных FK.**
   `(category_id, vehicle_type_id) → vehicle_categories (id, vehicle_type_id)` и
   `(vehicle_type_id, spec_id) → vehicle_type_specs (vehicle_type_id, spec_id)`. Это приём
   `vehicles_model_type_fk` из ADR 0007: физически, а не соглашением в коде, запрещены значение по
   непривязанному ТТХ, значение у категории чужого типа и отвязка ТТХ, по которому есть значения
   (RESTRICT). Денормализованный `vehicle_type_id` рассинхронизироваться не может — его держит
   первый FK. Вариант «весь кортеж в jsonb-колонке категории» отклонён: он лишает отбора и
   агрегации по ТТХ и не проверяется ключами.
5. **Канонизация — одна IMMUTABLE-функция `vehicle_category_signature(jsonb)`.** Приложение
   сигнатуру не считает само, а вызывает функцию в INSERT/UPDATE — тот же принцип, что с
   `vehicle_model_normalize` (ADR 0007 §2): расхождение канонизации между кодом и уникальным
   индексом сделало бы дубли неотличимыми. Формат — `code=value` через `;`, отсортировано по коду,
   число через `trim_scale` (`21.0` и `21` дают одну сигнатуру).
6. **Полнота набора — сервис + отложенный constraint-триггер.** Ключи закрывают «нет лишних и
   чужих значений», но не «нет пропущенных». Сервис проверяет полноту в транзакции с
   `SELECT … FOR UPDATE` строки типа (идиома ADR 0003 §8); `vehicle_category_assert_consistent`
   на `DEFERRABLE INITIALLY DEFERRED` триггерах трёх таблиц перепроверяет на COMMIT полноту и
   совпадение сигнатуры с фактическими значениями. Триггер — страховка от прямого SQL мимо API,
   пользовательские ошибки ловит и объясняет сервис.
7. **Генератора категорий нет.** Комбинации не порождаются перебором: активные категории заводит
   человек в справочнике либо приносит seed-миграция из выверенных данных. Декартово произведение
   создало бы десятки несуществующих в парке комбинаций, которые потом пришлось бы вычищать.
8. **Только числа в v1.** `value_kind` заведён колонкой с CHECK `IN ('number')` — расширение до
   перечислений/флагов аддитивно (снять CHECK, добавить таблицу опций и текстовое значение).
   Значение — `numeric(14,4)`, границы `min_value`/`max_value` и масштаб `decimals` — в справочнике ТТХ.
9. **`unit` и `decimals` замораживаются после первого значения.** Они входят в смысл канонизации:
   смена единицы у используемого ТТХ молча переопределила бы все категории. `code` неизменяем всегда.
10. **Правка значений категории — смена её сущности.** Пока на категорию никто не ссылается,
    значения править можно (пересчитываются сигнатура и авто-имя). Когда появятся ссылки от техники
    и заявок, правка значений должна быть запрещена: заводится новая категория, машины переводятся.
    Заложено правилом здесь, чтобы не обнаружилось на проде.
11. **Наименование категории генерируется, но хранится.** `{тип}, {ТТХ} {значение} {ед}, …` в
    порядке `vehicle_type_specs.sort_order`; хранится материализованно (имя в отчётах и истории не
    должно «плыть» задним числом) и перегенерируется при смене значений/состава ТТХ только при
    `is_auto_name = true`. Уникальность имени внутри типа проверяет сервис, а не индекс: инвариант
    БД — сигнатура, имя же массово перезаписывается при отвязке ТТХ, и уникальный индекс по нему
    ловил бы мнимые конфликты внутри одного UPDATE.
12. **Жизненный цикл привязки.** Добавление ТТХ типу с категориями требует `backfillValue` —
    значение проставляется всем существующим категориям в той же транзакции; уникальность при этом
    не может нарушиться (одинаковая координата, добавленная ко всем кортежам, не создаёт коллизий).
    Отвязка ТТХ, наоборот, может **схлопнуть** две категории в одинаковый кортеж: сервис заранее
    считает будущие сигнатуры и при коллизии отдаёт 409 со списком конфликтующих пар. Отвязка
    последнего ТТХ у типа с категориями запрещена (категория без значений невозможна).
13. **Категорию можно удалить, пока на неё никто не ссылается.** Осознанное отступление от принципа
    «удаления нет»: категории заводятся пачками при наполнении, ошибочная запись должна вычищаться,
    а не оставаться неактивным мусором в выпадающих списках. При появлении ссылок — 409 и
    деактивация через `is_active`.
14. **У конкретной машины собственных ТТХ нет.** Машина получит ссылку на категорию (следующий
    этап); хранение фактических значений («г/п 24.7 т» при категории «25 т») отложено до появления
    потребителя.

## Последствия

- (+) Подтип перестал быть выдуманным наименованием: он выводится из измеримых значений и не может
  разойтись с ними.
- (+) Дубли категорий невозможны физически: одна комбинация значений — одна строка.
- (+) Отбор техники по ТТХ — обычный join, без разбора jsonb и без денормализации.
- (−) Появился plpgsql (три constraint-триггера и функция), которого в проекте раньше не было, а
  PG-инфраструктуры для интеграционных тестов нет — триггеры выкатываются без автотестов.
- (−) Смена состава ТТХ у типа с категориями — не рутинная операция: требует либо значения для
  заполнения, либо ручного разбора схлопывания.
- (−) `unit`/`decimals` используемого ТТХ править нельзя — ошибка в единице лечится заведением
  нового ТТХ и переносом.

## Отложено (backlog)

- `vehicles.vehicle_category_id` + составной FK `(vehicle_category_id, vehicle_type_id)` — категория
  машины не сможет разойтись с её типом.
- `vehicle_requests.vehicle_category_id` (или требования диапазоном по ТТХ) — адресная заявка
  «нужен автокран 25 т».
- Запрет правки значений у категории, на которую есть ссылки (п. 10) — включается вместе с первой
  ссылающейся сущностью.
- Перечислимые и логические ТТХ (`value_kind`), фактические ТТХ конкретной машины.
- PG-интеграционные тесты миграций и триггеров — тестовой БД-инфраструктуры в проекте нет
  (см. ADR 0005, 0007).
