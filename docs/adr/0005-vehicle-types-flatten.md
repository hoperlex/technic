# ADR 0005. Плоский классификатор ТС (отмена подтипов)

- Статус: Принято
- Заменяет: иерархическую модель из [ADR 0001](0001-vehicle-classification.md),
  наполнение и source-mappings из [ADR 0002](0002-vehicle-classification-population.md),
  справочник типов/подтипов из [ADR 0003](0003-vehicle-types-directory.md)
- Связано: `apps/api/drizzle/0013_vehicle_types_flat_expand.sql`,
  `apps/api/drizzle/0014_vehicle_types_flat_contract.sql`, `apps/api/src/db/schema.ts`,
  `packages/contracts/src/vehicle-types.ts`, `packages/contracts/src/vehicle-requests.ts`,
  `apps/api/src/routes/vehicle-types.ts`, `apps/api/src/routes/vehicle-requests.ts`,
  `apps/web/src/pages/directories/VehicleTypesTab.tsx`, `apps/web/src/pages/vehicle/shared.tsx`

## Контекст

Двухуровневый классификатор (тип → подтип в одной таблице `vehicle_types` + таблица правил
`vehicle_type_source_mappings`) оказался слишком громоздким: подтипы, производная активность
родителя, source-mappings и разбор неоднозначных групп усложняли и справочник, и «Заказ ТС».
Утверждён **плоский** список типов ровно из присланной таблицы «Тип ТС» (13 значений).

## Решения

1. **Плоская модель.** `vehicle_types` — один уровень: `kind_id` (вид) + `code` + `name` +
   описательные поля + `is_active`/`sort_order`. Колонки `parent_id`/`is_selectable`, самоссылочный
   FK, CHECK уровня и таблица `vehicle_type_source_mappings` удалены. Заявка ссылается на тип
   напрямую (`vehicle_requests.vehicle_type_id`); в API — `vehicleTypeId`/`vehicleTypeName`
   (поля `vehicleSubtypeId`/`parentType*` убраны).
2. **Виды сохраняются.** `vehicle_kinds` (Спецтехника / Грузоперевозки) и деление «Заказа ТС» на две
   формы / две detail-таблицы / enum `vehicle_request_type` — без изменений. Каждый тип относится к
   одному виду. **«Вид ПЛ» (ЭСМ2/4П/3) не хранится** — это справочная колонка исходника.
3. **13 типов (seed 0013).** Спецтехника (8, ЭСМ2): Автокраны, Вилочные погрузчики и минипогрузчики,
   Кран пневмоколесный, Кран самоходный, Фронтальные погрузчики, Экскаватор колесный, Экскаваторы
   гусеничные, Экскаваторы-погрузчики. Грузоперевозки (5, 4П+3): Грузовые малотоннажные автомобили,
   Самосвалы, Тягачи с полуприцепами, Тяжелые манипуляторы, Легковые автомобили. Это **стартовый
   seed**; CRUD-создание типов в справочнике остаётся.
4. **Самосвалы включены.** Отменяет п.3 ADR 0002 (полное исключение `dump_truck`/«Самосвалы»): теперь
   `dump_trucks` — активный тип вида `freight_transport`.
5. **Выкат — expand/contract, без простоя.**
   - **0013 (expand, аддитивно):** снят CHECK `vehicle_types_level_selectable_check`; добавлены 13
     плоских типов (дискриминатор сосуществования — `parent_id IS NULL AND is_selectable = true`,
     ранее запрещённая комбинация); существующие заявки ремапнуты со старых подтипов на плоские типы
     со **stop-guard** (RAISE при подтипе без сопоставления). Старые строки/колонки/mappings остаются.
     Backend двусторонний (`vehicleTypeId | vehicleSubtypeId`, `view='flat'`), старый фронт совместим.
   - **0014 (contract, необратимо):** guard (нет заявок на неплоские строки) → снос source-mappings,
     старых типов/подтипов, колонок `parent_id`/`is_selectable`. Backend/контракты — только плоская
     модель. Применять после выката Фаз 1–2.
6. **Справочник.** Плоская таблица «Справочники → Типы ТС»: колонки **Вид → Тип → Активен →
   Действия**; инлайн-`Switch` активности; создание плоского типа проверяет активность вида и
   уникальность `code`; удаления нет. В формах заказа — единый `VehicleTypeSelect` (без Тип→Подтип).

## Последствия

- (+) Модель и код заметно проще: нет иерархии, производной активности, source-mappings, разбора
  неоднозначных групп.
- (+) Нулевой простой при выкате (две фазы миграций + двусторонний backend).
- (−) Разбор конкретных ТС по неоднозначным исходным группам (был в source-mappings) переносится на
  этап импорта техники.
- (−) `0014` необратим; откат — restore из бэкапа (см. `docs/reports/`).
