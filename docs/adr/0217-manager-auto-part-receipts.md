# ADR 0217. Менеджер ведёт чеки автозапчастей

- Статус: Принято (30.09.2026). Реализовано целиком; схема БД и версия клиентского контракта не
  меняются
- Домены: доступ, автозапчасти
- Изменяет: аудиторию `autoParts.manage` из
  [ADR 0154](0154-auto-part-receipts.md) — роль `manager` получает ведение чеков наряду со
  службой главного механика; граница необратимого удаления не меняется

  сервера и портала)

## Контекст

`manager` — временная роль-заглушка. Ею уже пользуются реальные сотрудники, которым нужен
расширенный доступ к рабочему функционалу. Один из недостающих сценариев — добавление чеков
автозапчастей в гараже.

Раздел уже виден менеджеру по `garage.read`, однако кнопка «Принять чек» и серверный
`POST /api/v1/auto-part-receipts` закрыты `autoParts.manage`. Локально открыть кнопку нельзя:
портал пообещал бы действие, которое сервер завершит отказом 403, а два источника правила
разошлись бы при следующей правке.

Существующее право ведения неделимо: оно открывает создание, правку документа целиком,
распознавание сканов, постановку пометки на удаление и её снятие. Отдельного права только на
создание нет. Необратимое удаление уже отделено в `autoParts.delete` и остаётся
неназначаемым — его получает только администратор.

## Решение

### 1. Менеджер получает существующее право ведения ролью

`ROLE_PERMISSIONS.manager` разворачивает `AUTO_PARTS_PERMISSIONS`, то есть сегодня
`autoParts.manage`. Серверные стражи и портал продолжают спрашивать одно право; специальных
проверок роли в маршруте или разметке не появляется.

Право приходит ролью по той же причине, что круг заявителя оргтехники в ADR 0181: роль временная,
а доступ нужен всем её реальным держателям. Поимённый набор оставил бы выдачи после снятия роли и
потребовал бы отдельной уборки.

### 2. Граница удаления не расширяется

`autoParts.delete` менеджеру не выдаётся. Он может исправить чек и попросить удалить его,
указав причину, но не может уничтожить документ и отвязать его сканы насовсем. Эта граница
по-прежнему выражена отдельным правом, а не проверкой роли.

### 3. Диспетчер не получает ведение автоматически

Решение относится к временной роли `manager`, а не к офисным ролям вообще. `dispatcher`
сохраняет `garage.read`: видит список, карточку и суммы, но мутации чека получают 403 без
поимённого полномочия.

## Совместимость и выкат

Миграция не нужна: роль и право уже существуют, а принципал собирает права из матрицы на каждом
запросе. Тела и ответы API не меняются, поэтому пол версии клиента поднимать не нужно. Для
появления кнопки нужна новая статика, для успешной записи — новый API; любой порядок обновления
безопасен: старый портал не показывает новое действие, старый API отклоняет его.

## Последствия

- менеджер видит «Принять чек», может сохранить чек и выполнять остальные штатные действия
  ведения;
- постоянное удаление остаётся только у администратора;
- диспетчер остаётся читателем чеков;
- при будущем удалении временной роли доступ исчезнет вместе с её строкой в матрице.
