# ADR 0007. Марки/модели и конкретные ТС

- Статус: Принято
- Развивает: [ADR 0005](0005-vehicle-types-flatten.md) (плоский классификатор типов)
- Связано: `apps/api/drizzle/0015_vehicle_models.sql`, `apps/api/drizzle/0016_vehicle_types_rollers.sql`,
  `apps/api/drizzle/0017_vehicles.sql`, `apps/api/src/db/schema.ts`

## Контекст

После ADR 0005 в системе есть плоский справочник типов ТС (13 типов) и заявки «Заказ ТС», которые
ссылаются на тип. Не хватает двух уровней ниже: марки/модели и конкретной машины — без них нельзя
назначать технику на заявку.

Источники данных: список техники по типам (2 листа, 137 строк, колонки «Вид ПЛ / ТС / Тип ТС») и
бухгалтерская выгрузка «Список автотехники» (176 записей с инвентарным и заводским номерами, ПТС,
изготовителем, датой выпуска). Обе выгрузки заполнены людьми и содержат смешение кириллицы с
латиницей, описательные префиксы («Погрузчик телескопический …»), машины без марки
(«Манипулятор на шасси JAC c КМУ Fassi») и без госномера («Linde S30»).

## Решения

1. **Единая сущность «Марка/модель».** `vehicle_models`: одна запись = одно наименование
   («Mustang 2700V», «МАЗ 6501В5»). Таблица `vehicle_makes` **не создаётся** — изготовитель хранится
   текстом в `manufacturer_name`. Модель принадлежит плоскому типу ТС; одинаковое имя в разных типах —
   разные записи (`UNIQUE (vehicle_type_id, normalized_name)`).
2. **Нормализация — в БД, одной функцией.** `vehicle_model_normalize` и `vehicle_reg_normalize` объявлены
   IMMUTABLE и используются в GENERATED-колонках `normalized_name` / `registration_number_normalized`.
   Приложение не дублирует нормализацию, а вызывает ту же функцию в запросах — иначе поиск разошёлся бы
   с уникальным индексом. Нормализация **механическая** (регистр, ё→е, схлопывание разделителей; для
   госномера — гомоглифы АВЕКМНОРСТУХ → латиница). Транслитерация («Мустанг» → «Mustang») в неё не
   входит: это знание, а не функция от строки, и решается человеком при заведении записи.
3. **Алиасов нет.** `vehicle_model_aliases` отложены: их единственным потребителем было
   автосопоставление при импорте, а импорт из скоупа исключён (п. 5).
4. **`vehicles` хранит тип явно, модель — опционально.** Тип известен всегда (прямая колонка источника),
   марка/модель — не всегда. Согласованность обеспечивает составной внешний ключ
   `(vehicle_model_id, vehicle_type_id) → vehicle_models (id, vehicle_type_id)`: при NULL-модели он не
   проверяется (MATCH SIMPLE), при заполненной — физически запрещает состояние «ТС одного типа, а его
   модель другого». Денормализация типа при этом не может рассинхронизироваться.
5. **Импорта и парсера нет.** Исходные строки не разбираются кодом: соответствие
   «строка источника → тип / марка-модель / госномер» готовится один раз человеком в выверенной
   таблице, из неё генерируется seed-миграция. Staging-таблица `vehicle_import_rows`, эвристики разбора
   и статусы `needs_review` не создаются. **Неоднозначные строки не сидируются вовсе** — добавить машину
   позже дешевле, чем чистить ошибочно заведённую.
6. **Реквизиты из бухгалтерской выгрузки** хранятся в `vehicles`: `inventory_number` (1С),
   `serial_number` (заводской/VIN), `passport_number` (ПТС/ПСМ), `manufacturer_name`, `manufactured_on`.
   Поле `internal_number` отменено: числовой хвост в строках вида `Мустанг-2700V-4344` оказался не
   внутренним номером, а цифрами госномера спецтехники (`ХО 4344 50`).
7. **Уникальность госномера включена сразу** — частичный уникальный индекс по
   `registration_number_normalized` (живые записи). Таблица создаётся пустой, поэтому конфликт при
   сидировании — это сигнал об ошибке разбора, а не блокирующая проблема выката. Инвентарный и
   заводской номера уникальными **не** объявляются: в выгрузке встречаются кириллические гомоглифы
   внутри VIN и незаполненные значения.
8. **Тип «Катки» добавлен** (вид ПЛ ЭСМ2 → вид «Спецтехника»). Тип «Бункеровозы, мультилифты»
   (вид ПЛ «3С (спец. автомобили)») **не** добавлен: принадлежность к виду не определена, машины этого
   типа не сидируются до решения.
9. **Квалификационные требования — вне скоупа этого ADR.** Люди, документы и категории квалификаций
   заводятся параллельно в ADR 0008 (`persons`, `credential_types`,
   `qualification_categories`, миграции `0018`/`0019`). Связка «тип/марка-модель ТС → требуемая
   категория» лежит на стыке двух моделей и делается отдельным шагом после обеих фаз — вместе с
   назначением техники и работника на заявку. Здесь ни одной таблицы требований не создаётся.

## Последствия

- (+) Цепочка `вид → тип → марка/модель → ТС` замкнута тремя таблицами без иерархий и mappings.
- (+) Рассогласование типа между машиной и её моделью невозможно на уровне БД, а не соглашений в коде.
- (+) Нет кода разбора исходных строк — нечему ломаться на новых форматах наименований.
- (−) Первичное наполнение техники — ручная выверка (137 строк): дороже разово, зато без ошибочных
  записей в справочнике.
- (−) Повторная загрузка из обновлённой выгрузки потребует такой же ручной сверки; автоматического
  сопоставления по алиасам нет.

- Назначение техники на заявку (связь `vehicle_requests` ↔ `vehicles`).
- Квалификационные требования к типу/марке-модели — стык с ADR 0008.
- Тип «Бункеровозы, мультилифты» и его машины; прицепы/полуприцепы из бухгалтерской выгрузки —
  отдельная категория, в классификаторе типов её нет.
- `vehicle_model_aliases` — если появится повторяющийся импорт.
- PG-интеграционные тесты миграций (тестовой БД-инфраструктуры в проекте нет — см. ADR 0005).
