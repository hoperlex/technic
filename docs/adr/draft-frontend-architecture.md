# ADR (черновик): структура фронтенда — слои, границы, публичные API слайсов

Статус: черновик. Номер не присвоен: основной поток ADR идёт быстрее, чем пишется документ (за
31.07.2026 он прошёл с 0043 до 0050), поэтому номер берётся в момент коммита — последний числовой
ADR плюс единица:

```bash
ls docs/adr | grep -E '^[0-9]{4}-' | sort -V | tail -1
```

## Контекст

Фронтенд рос вместе с разделами и к 31.07.2026 пришёл к состоянию, где размер файла перестал
что-либо значить: пять крупнейших занимают около трети кода, а страница списка заявок держит в себе
форму, колонки, карточки, четыре модальных окна, пять мутаций и десяток запросов. Причина не в
объёме, а в отсутствии слоёв: `pages/` содержит бизнес-правила, `components/` — вперемешку ui-kit и
доменные блоки, справочные запросы копируются из файла в файл (22 копии в 12 файлах), а ключи
запросов живут строковыми литералами в 29 файлах.

Полный разбор с цифрами — [docs/frontend-fsd-plan.md](../frontend-fsd-plan.md), базовые замеры —
[docs/reports/frontend-baseline.md](../reports/frontend-baseline.md).

## Решение

Принимается Feature-Sliced Design с шестью слоями. Импорт разрешён только вниз:

```text
app/        провайдеры, маршруты, глобальные стили, точка входа
pages/      композиция экрана: вкладки и виджеты, без бизнес-логики
widgets/    самостоятельные блоки: список заявок, шапка и навигация, карточка
features/   пользовательские сценарии: создать заявку, сменить статус, завизировать
entities/   бизнес-сущности: api, ключи, queryOptions, доменный ui
shared/     ui-kit, утилиты, http-клиент и сессия, конфигурация
```

Слой `processes/` не заводится: сквозных многошаговых сценариев поверх страниц в портале нет.

Правила, которые из этого следуют:

1. **Импорт только вниз.** `entities` не знает о `features`, `features` — о `widgets`.
2. **Слайсы не видят соседей.** `entities/object` не импортирует `entities/user` напрямую: общее
   выносится вниз, в `shared`, либо связывается уровнем выше.
3. **Вход в слайс — только его `index.ts`.** Внутренние модули (`api/`, `model/`, `ui/`) снаружи не
   видны, поэтому перестроить слайс можно, не трогая тех, кто им пользуется.
4. **Ключи запросов живут в своей сущности** (`entities/<e>/api/keys.ts`), а не в `shared`: иначе
   нижний слой знал бы обо всех доменах портала.
5. **Ключ описывает запрос, а не сущность.** Варианты («только активные объекты» и «все объекты»)
   различаются параметром в ключе: сливать их — значит менять поведение форм, которые эти варианты
   и завели.

## Как это удерживается

Правила проверяются линтером, а не договорённостью:

- `eslint-plugin-boundaries` (7.x, правило `boundaries/dependencies`) — направление импортов и точка
  входа слайса одним правилом: разрешение выдано на `fileInternalPath: index.ts`, поэтому импорт
  внутреннего модуля под него не подпадает;
- сами правила проверяются фикстурами `apps/web/test/fixtures/boundaries` — четыре случая
  (импорт вниз, вверх, к соседу, вглубь чужого слайса), каждый по конкретному `ruleId`;
- алиасы `@app`, `@pages`, `@widgets`, `@features`, `@entities`, `@shared` объявлены в
  `tsconfig.json`; Vite и Vitest читают их через `resolve.tsconfigPaths`.

## Последствия

Что становится нельзя:

- импортировать вверх по слоям и вбок по слайсам;
- лезть внутрь чужого слайса мимо `index.ts`;
- держать доменные ключи запросов и доменный ui в `shared`;
- заводить справочный запрос копипастой: у него есть место — `entities/<e>/api/queries.ts`.

Чем платим:

- в слайсе появляется `index.ts`, который нужно поддерживать;
- перенос кода между слоями требует думать, а не двигать файл: если модуль не подходит ни одному
  слою, обычно он делает две разные вещи;
- линт границ добавляет к прогону несколько секунд.

Что это даёт: страница перестаёт быть местом, где живёт всё сразу; правка сквозного поведения
(фильтр, статус, инвалидация) делается в одном месте, а не в пяти; запросы и справочники
переиспользуются вместо копирования.

## Порядок внедрения

Этапами, каждый — отдельные короткие ветки с мержем в `main`, от холодного кода к горячему
(подробно — [docs/frontend-fsd-plan.md](../frontend-fsd-plan.md) §7, этап 0 —
[docs/frontend-fsd-stage-0.md](../frontend-fsd-stage-0.md)). До окончания переезда в `src/` живут
и разложенные по слоям файлы, и ещё не перенесённые: `boundaries/no-unknown-dependencies` включается
последним этапом, когда нераспределённых не остаётся.
