# План: кабинет водителя — правки после первого показа

Рабочий план, не ADR. Продолжение [driver-portal-plan.md](driver-portal-plan.md) (ADR 0102, 0103):
кабинет выкачен коммитом `da79d30`, и это первые правки по итогам показа. Решения помечены **Р**,
развилки — **У**; нумерация своя, чтобы не путать с решениями основного плана (там они Р1–Р34).

Шесть правок из постановки. Три косметические и три меняют модель — их и разбираем подробно.

| Правка                                            | Задевает                                          |
| ------------------------------------------------- | ------------------------------------------------- |
| крупный шрифт в мобильном кабинете                | только стили                                      |
| убрать горизонтальную прокрутку                   | только стили                                      |
| кнопки передачи всегда внизу экрана               | только вёрстка листа                              |
| **убрать переключатель «нет возможности снять»**  | Р18 основного плана: чем закрывается строка дня   |
| **только задания с действительным листом**        | Р11, Р16: из чего собирается задание              |
| **предупреждения о падении и невероятных числах** | Р20: где живут пороги и что делает предупреждение |

---

## 1. Крупный шрифт (Р1)

Кабинет читают с телефона в кабине, часто в перчатках и на солнце. Масштаб задаётся **одной
переменной на каркасе**, а не правкой каждого компонента:

```css
.driver-shell {
  --driver-scale: 1.15;
  font-size: calc(16px * var(--driver-scale));
}
```

Числовые поля ввода — отдельно и крупнее прочего (`1.35`): в них водитель попадает пальцем и
сверяет с прибором, и это единственное место, где ошибка стоит денег. Мелкие подписи
(`fontSize: 12` в двух компонентах) уезжают на `0.85em` — относительная величина, чтобы масштаб
менялся в одном месте.

Переменная живёт рядом с прочими константами кабинета (Р5): подобрать её на живом телефоне —
работа одного значения, а не поиска по файлам.

> **Пересмотрено 21.08.2026** ([driver-readings-typography-plan.md](driver-readings-typography-plan.md)):
> масштаб поднят до `1.25`, а сама переменная перестала быть единственной дорогой размера — то,
> что рисует antd (поля, кнопки, календарь), берёт величину из токена темы кабинета и переменной
> каркаса не подчиняется вовсе. Числовые поля получили свой множитель (`1.4`), обещанный здесь же
> и до кода тогда не доехавший.

## 2. Горизонтальная прокрутка (Р2)

Причина всегда одна — содержимое, которое не переносится: длинная подпись машины, номер листа,
адрес заявки. Лечится в каркасе кабинета, а не в каждом блоке:

```css
.driver-shell {
  overflow-x: clip;
}
.driver-shell * {
  min-width: 0;
  overflow-wrap: anywhere;
}
```

`min-width: 0` существенен: во flex-строке потомок по умолчанию не сжимается меньше содержимого —
именно это и растягивает страницу вбок. Проверка — тестом: ширина `document.body` не превышает
ширину окна на узком экране.

## 3. Кнопки всегда внизу (Р3)

Сейчас подвал листа липкий, но уезжает вместе с прокруткой содержимого. Становится закреплённым:

```css
.driver-sheet__footer {
  position: fixed;
  inset-inline: 0;
  bottom: 0;
  padding-bottom: max(var(--safe-bottom), 8px);
}
```

Клавиатура уже учтена через `visualViewport` (правка есть в коде) — она поднимает подвал над
полосой ввода. Содержимое листа получает нижний отступ на высоту подвала, иначе последний блок
прячется под кнопкой.

## 4. Переключатель «нет возможности снять показания» (Р4, развилка У1)

**Что просят:** убрать переключатель из формы водителя.

**Чем он был:** единственный способ ЗАКРЫТЬ строку дня, когда счётчик неисправен, машину увёл
сменщик или кабина опечатана. Приёмка требует, чтобы по каждой строке ожидания было показание —
любого вида (ADR 0103, Р22). Уберём переключатель молча — водитель, у которого сломан одометр, не
сможет закрыть день вовсе: числа он не введёт, а другого пути нет.

Поэтому правка не «удалить чекбокс», а «решить, кто и как закрывает такую строку» — У1.

**Решение (Р4): закрывает только персонал.** У водителя переключателя нет — он не заполняет строку
и отправляет остальные; строка остаётся `pending`, день висит в гараже как «частично», и диспетчер
закрывает её видом `no_data` с причиной. Так исчезает поле, которым водитель мог отписаться от
ввода, а учётная дыра не появляется: причина неввода записана человеком, который её знает.

Что меняется в коде: вид `no_data` остаётся в модели и в API, но `driverCabinet.submit` его больше
не принимает — отправка водителя с таким видом отвечает отказом. Это не косметика формы, а правило
доступа, и живёт оно на сервере: спрятать переключатель и оставить ручку открытой значило бы
запретить кнопкой то, что разрешено ручкой.

Цена: пока диспетчер не закрыл строку, день не принимается. Это не потеря — именно так «частично»
и должно работать.

## 5. Только задания с действительным листом (Р5, развилка У2)

**Что просят:** показывать в кабинете только те задания, по которым выписан действительный
путевой лист.

**Как сейчас:** задание собирается из рейсов дня (независимо от того, выписан ли лист) плюс
недельные ЭСМ-2. Лист выписывают с рейса отдельным действием, когда состав собран, — иногда уже
после выезда.

**Что меняется по существу.** Показания — это то, что переносят в путевой лист. Нет листа — нет
документа, в который они лягут, и строка ожидания повисает. С этой стороны правка верная.

Но у задания две работы, и вторая — сказать водителю, **куда ехать**: адреса, время, контакты
погрузки и выгрузки. Эта работа нужна ДО выписки листа, а не после. Отсюда развилка У2: фильтр
применяется ко всему заданию или только к передаче показаний.

**Решение (Р5): фильтр применяется ко всему заданию.** Рейс, по которому нет действительного
листа, в кабинете не показывается вовсе — ни карточки ввода, ни адресов. Кабинет становится строго
документальным: водитель видит ровно то, на что у него есть бумага.

**Цена решения названа прямо, потому что она реальная.** Лист выписывают с рейса отдельным
действием, когда состав собран; выехавший до выписки водитель не увидит в кабинете ни адреса
погрузки, ни телефона встречающего. На практике это не пробел, а требование к порядку работы:
бланк строгой отчётности и так обязан быть у водителя до выезда (ADR 0037), и кабинет теперь
показывает то же, что показывает бумага. Но если выписка задерживается, задание пропадает именно
тогда, когда оно нужнее всего.

**Следствие, которое надо держать в голове: письмо и кабинет разошлись.** Рассылка «Задание
водителю» шлёт рейсы независимо от листа (ADR 0102, Р11) — теперь водитель может получить письмо о
рейсе, которого в кабинете нет. Выравнивать их этой правкой не будем: письмо уходит вечером
накануне, когда листа обычно ещё нет, и лишать водителя единственного канала с адресами накануне
выезда — хуже расхождения. В плане это записано как осознанное различие каналов, а не как забытый
край.

**Что считается действительным листом:** выписан на этот рейс, не аннулирован (`status <>
'cancelled'`) и выписан на этого же работника (`driver_person_id`). Недельный ЭСМ-2 сам себе лист —
он и так входит в задание по своему периоду.

Условие по работнику добавлено на сверке реализации: без него переназначенный рейс показывался бы
новому водителю по бумаге, выписанной на другого человека. Цена — при переназначении без коррекции
листа день пропадает из кабинета у обоих, пока лист не перевыпишут (ADR 0101).

## 6. Предупреждения при вводе (Р6, развилка У3, У4)

**Что просят:** предупреждать о показаниях ниже предыдущих (одометр, моточасы) и о нереалистичных
значениях по всем полям; пороги — константами рядом с компонентом, чтобы разработчик правил их
быстро.

**Как сейчас:** сервер проставляет аномалии `counter_reset` (значение меньше предыдущего) и
`implausible_jump` (прирост выше порога `1500 × max(1, d)` км и `24 × max(1, d)` часов), водитель
узнаёт о них **после** отправки и подтверждает следующей.

**Что добавляется.** Предупреждение показывается **во время ввода**, до отправки: как только в
поле появилось число, блок сравнивает его с предыдущим показанием этой машины. Для этого API
задания начинает отдавать предыдущий снимок по каждой строке — значение, дату и сколько суток
прошло:

```ts
previous: { odometerKm: 145_320, engineHours: 9_812.5, measuredOn: '2026-08-10', daysAgo: 2 } | null
```

Три вида предупреждений:

| Вид                 | Условие                                  | Текст                                   |
| ------------------- | ---------------------------------------- | --------------------------------------- |
| ниже предыдущего    | значение меньше снимка                   | «меньше предыдущего (145 320 от 10.08)» |
| невероятный прирост | прирост больше порога за прошедшие сутки | «прирост 3 200 км за 2 дня — проверьте» |
| вне здравого смысла | значение вне абсолютных границ поля      | «столько в бак не входит»               |

Третий вид новый: он ловит опечатку в разряде там, где предыдущего снимка нет вовсе (первое
показание машины) — а таких строк много в первые недели.

**Решение (Р6): мягкое предупреждение — галочка, грубое — запрет.**

| Что                   | Условие                                         | Что делает портал                    |
| --------------------- | ----------------------------------------------- | ------------------------------------ |
| ниже предыдущего      | значение меньше снимка                          | предупреждение + галочка «всё верно» |
| невероятный прирост   | прирост больше суточного порога × прошедшие дни | предупреждение + галочка «всё верно» |
| вне абсолютных границ | миллион моточасов, тысяча литров, отрицательное | **отправить нельзя**                 |

Граница между «странно» и «невозможно» проведена по одному признаку: странное число бывает правдой
(счётчик заменили, машина неделю стояла в поле), а невозможное — всегда опечатка в разряде.
Требовать подтверждения у опечатки бессмысленно: водитель подтвердит её так же, как набрал.

**Константы (Р7): файл рядом с компонентом.** `apps/web/src/pages/driver/readingLimits.ts` — все
числа в одном месте, каждое с русской подписью: суточные пороги прироста, абсолютные потолки
одометра, моточасов и заправки, масштаб шрифта кабинета (Р1). Разработчику, которого попросят
«сделать помягче», не придётся искать по файлам.

Серверные пороги (`ODOMETER_JUMP_PER_DAY_KM`, `ENGINE_HOURS_JUMP_PER_DAY` в контрактах) остаются
своими, и это записано в комментарии обоих файлов: **клиентские предупреждают, серверные
записывают аномалию**. Числа могут совпадать, но роли разные — выровняй их «для порядка» в один
источник, и первая же попытка сделать подсказку помягче начнёт менять учётные пометки в базе.

## Предложения по логике сверх постановки

**П1. Показывать предыдущее показание прямо в поле.** Подпись под полем «предыдущее: 145 320
(10.08)» стоит дешевле любого предупреждения: водитель сверяет два числа глазами до того, как
ошибётся. Это же снимает половину поводов для предупреждений.

**П2. Число прописью не нужно, а разряды — нужны.** Группировка разрядов при выводе (не при
наборе, он ломает курсор): «145 320» читается с телефона, «145320» — нет.

**П3. Кнопка «как вчера» для моточасов не нужна.** Соблазн есть, но это ровно тот случай, когда
портал подсказывает число вместо человека: подставленное значение уедет в учёт как снятое.

**П4. Строка «не сдано» в шапке кабинета.** Если у водителя есть незакрытые дни в окне записи —
показать это на экране дня одной строкой со ссылкой. Сейчас он узнаёт о долге только от диспетчера.

**П5. Порядок блоков в оверлее — по позиции смены**, а не по порядку загрузки: первая смена дня
сверху. Сейчас порядок приходит с сервера и совпадает, но зафиксировать это тестом стоит.

## Решения по развилкам

Все четыре закрыты при постановке 13.08.2026:

| Развилка                               | Решение                                                                                       |
| -------------------------------------- | --------------------------------------------------------------------------------------------- |
| У1. Кто закрывает строку без показаний | Только персонал: у водителя переключателя нет, сервер его отправку с `no_data` отклоняет (Р4) |
| У2. К чему применяется фильтр по листу | Ко всему заданию: рейса без действительного листа водитель не видит (Р5)                      |
| У3. Что делает предупреждение          | Мягкое — галочка, вне абсолютных границ — запрет отправки (Р6)                                |
| У4. Где живут пороги                   | Файл рядом с компонентом; серверные отдельно и с названной разницей ролей (Р7)                |

## Этапы работ

**Этап 1. Стили кабинета.** Масштаб шрифта переменной, крупные числовые поля, запрет горизонтальной
прокрутки, закреплённый подвал листа. Тест: ширина страницы не превышает ширину окна на узком
экране; подвал остаётся в поле зрения при прокрутке содержимого.

**Этап 2. Фильтр задания по действительному листу.** Правка `driver-assignment.ts`: рейс входит в
задание, только если у него есть живой лист. Тесты: рейс без листа не виден; рейс с аннулированным
листом не виден; выписали лист — рейс появился; ЭСМ-2 по-прежнему входит по периоду.

**Этап 3. Запрет `no_data` водителю.** Переключатель убирается из формы, сервер отклоняет вид
`no_data` от `driverCabinet.submit`. Тесты: водитель получает отказ; персонал закрывает строку с
причиной; день с незакрытой строкой не принимается.

**Этап 4. Предупреждения при вводе.** API задания отдаёт предыдущий снимок по каждой строке; блок
показывает подпись «предыдущее: …» и три вида предупреждений; мягкие требуют галочки, грубые
блокируют отправку. Тесты: каждое из трёх предупреждений, галочка уезжает в отправку, значение вне
границ не отправляется.

**Этап 5. Мелочи из П1–П5.** Разряды при выводе, строка «не сдано» в шапке, порядок блоков по смене.

Порядок выбран по риску: стили ничего не ломают, фильтр меняет состав задания (и должен пройти
первым, чтобы дальше проверять уже новый состав), запрет `no_data` меняет правило доступа,
предупреждения расширяют API.
