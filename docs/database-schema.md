# Схема БД (этап 1)

SQL-first миграции: `apps/api/drizzle/*.sql`, применяются `apps/api/src/db/migrate.ts` с журналом `_migrations`. Drizzle-схема (источник типов приложения): `apps/api/src/db/schema.ts`.

## Таблицы

- **users** — пользователи. ФИО по частям (ADR 0034, миграция `0055`): `last_name` (CHECK not-blank), `first_name`, `middle_name` (default `''`), `full_name` (GENERATED STORED — как у `persons`, но выражение схлопывает пробелы через `regexp_replace`, а не только обрезает края: имя здесь может быть пустым у учёток, заведённых до миграции одним словом, и простой `btrim` дал бы двойной пробел внутри строки; CHECK на непустое имя не ставится по той же причине — требование живёт в контрактах). Колонка `full_name` осталась на месте и остаётся единственной точкой правды для чтения: `actor_name` в истории и аудите, `created_by_name`, поиск и сортировка не менялись. `role` (`admin|manager|dispatcher|shtab|rukstroy|commandant|operator|observer`, nullable до активации; `rukstroy` добавлена миграцией `0049`, ADR 0025; `observer` — `0054`, ADR 0033: только просмотр обоих модулей заявок, ни объекта, ни контрагента у роли нет; `commandant` — `0067`: заказчик на объекте по одному модулю, вывозу мусора, — область та же, что у штаба, а заказ ТС закрыт правом), `counterparty_id` (ADR 0010, миграция `0022`: контрагент учётки — область видимости роли `operator`; CHECK `users_operator_counterparty_check` в `0023` требует его при `role='operator'`; в drizzle-схеме без `.references()`, чтобы не создавать цикл `users ↔ counterparties`), `is_active` (default false), `must_change_password`, `auth_version` (отзыв токенов), `person_id` (ADR 0008, миграция `0018`: физлицо учётки; nullable, частичный UNIQUE — одна учётка на человека; в drizzle-схеме без `.references()`, чтобы не создавать цикл `users ↔ persons`), `deleted_at` (soft-delete). Уникальный `email` (citext). Пожелание из заявки на регистрацию (ADR 0034, миграция `0057`): `requested_role` (enum `registration_role_request`: `dispatcher|rukstroy|site_staff|commandant|waste_operator|vehicle_lessor|other` (`commandant` — миграция `0067`, CHECK на обязательный объект расширен `0068`: значение enum и ссылка на него разведены по файлам, иначе CHECK читал бы значение в транзакции, которая его добавила); `NULL` — учётку заводил администратор), `requested_object`/`requested_company` — **свободный текст**, а не FK: справочники неаутентифицированному не отдаются, сопоставляет их администратор. Права из пожелания не следуют — их даёт только `role`, назначаемая при активации. CHECK `users_requested_object_check` / `users_requested_company_check` требуют уточнения там, где без него заявку не рассмотреть (объектные роли — объект, операторы — компания); учёток без пожелания не касаются. Частичный индекс `users_pending_registration_idx (created_at DESC) WHERE deleted_at IS NULL AND is_active = false AND role IS NULL` — под вкладку «Ожидают активации» и бейдж в меню.
- **refresh_sessions** — opaque refresh-токены: `token_hash`, `family_id`, ротация (`replaced_by`, `revoked_at`), reuse detection.
- **construction_objects** — справочник объектов: `code` (unique), `name`, `address`, `is_active`. GIN-trgm по `name`.
- **counterparties** — контрагенты (ADR 0010, миграции `0022`, `0032`): `type` (enum `counterparty_type`: `general_contractor|contractor|operator|vehicle_lessor`; `vehicle_lessor` — арендодатель ТС, добавлен `0032`), `name` + `normalized_name` (GENERATED из `counterparty_name_normalize`: регистр, ё→е, кавычки и разделители схлопываются; ОПФ не отбрасывается), `inn` (CHECK формата — 10 или 12 цифр; контрольную сумму проверяет сервис), `comment`, `is_active`, `created_by/updated_by/deleted_by`, `deleted_at` (soft-delete). Частичный UNIQUE по `inn` среди живых записей — ИНН и есть идентичность контрагента, поэтому **тип у записи один**: организация в другой роли меняет тип, а не заводит вторую запись. ИНН обязателен у всех ролей, включая арендодателей ТС: недостающие реквизиты разыскиваются в ЕГРЮЛ, а не заменяются заглушкой (решение 14 ADR 0010). GIN-trgm по `name`. CRUD `/api/v1/counterparties` (запись — admin/manager), `GET /resolve?name=` — сопоставление наименования из документа по нормализованной форме. Первичное наполнение арендодателями ТС — `0033` (идемпотентно по ИНН).
- **counterparty_synonyms** — альтернативные наименования контрагента (миграция `0022`): `counterparty_id` (каскад), `name` + `normalized_name` (GENERATED). Основное наименование здесь **не дублируется**. UNIQUE по `normalized_name` **глобальный**, а не внутри контрагента: синоним отвечает на «чьё это наименование», и два владельца одного текста сделали бы сопоставление недетерминированным. API принимает синонимы полным списком (замена набора).
- **organizations** — свои юрлица-владельцы транспорта (ADR 0037, миграция `0060`, создаётся **пустой**): `name` (CHECK not-blank), `address`, `phone`, `okpo`/`ogrn`/`inn` (CHECK формата; пустая строка = не заполнен, контрольные суммы проверяет сервис — приём `counterparties.inn`), `is_primary`, `is_active`, `comment`. Реквизиты для шапки путевого листа; отдельно от `counterparties` — там внешние стороны, здесь те, от чьего имени выписывается документ. Частичные UNIQUE: `organizations_primary_unique WHERE is_primary` (основная ровно одна — «чей это лист по умолчанию» обязано иметь единственный ответ) и `organizations_inn_unique WHERE inn <> ''`.
- **construction_object_operators** — операторы вывоза, обслуживающие объект (ADR 0010, миграция `0027`), **многие-ко-многим**: PK `(construction_object_id, counterparty_id)`, каскад с обеих сторон, `created_by`/`created_at`. Отдельный индекс по `counterparty_id` — под обратный проход «объекты этого оператора» (PK покрывает только проход от объекта). Требование «тип контрагента = `operator`» держит сервис — то же решение, что и с `waste_requests.operator_counterparty_id`. Набор правится **с обеих сторон** и передаётся полным списком: `operatorIds` в `/objects`, `objectIds` в `/counterparties` (непустой список у типа, отличного от `operator`, отклоняется; смена типа при живых привязках — 409). Замена набора со стороны объекта не трогает привязки к удалённым контрагентам: в карточке их не видно, и снимать невыбранное нельзя.
- **user_construction_objects** — объекты учётки (ADR 0039, миграция `0063`), **многие-ко-многим**: PK `(user_id, construction_object_id)`, каскад с обеих сторон, `created_by`/`created_at`; отдельный индекс по объекту — под обратный проход «кто работает на площадке». Заменила колонку `users.construction_object_id`: один штаб ведёт несколько площадок, а руководитель строительства отвечает за куст объектов, и вторая учётка на того же человека была бы вторым входом ради одной строки справочника. Набор передаётся полным списком (`constructionObjectIds` в `/users`), сервер считает разницу. Вместе с колонкой снят CHECK `users_rukstroy_object_check` (миграция `0050`): он читал колонку своей строки, а набор лежит здесь — требование «объектной роли обязателен объект» держит теперь API (`resolveObjectIds`) и тест. Смена набора поднимает `auth_version` и гасит сессии: это смена области видимости.
- **departments** — справочник отделов (ADR 0040, миграция `0066`): `code` (unique), `name`, `is_active`, GIN-trgm по `name` — устроен как `construction_objects` и отвечает на тот же вопрос с другой стороны: от чьего имени идёт заявка. Отделы с объектами не пересекаются (офис, а не площадка), поэтому это вторая ось области, а не её продолжение. Сид: «Отдел1», «Отдел2» — без пары отделов не проверить ни роли, ни визирование.
- **user_departments** — отделы учётки (ADR 0040, миграция `0066`), **многие-ко-многим**: PK `(user_id, department_id)`, каскад с обеих сторон, `created_by`/`created_at`, индекс по отделу («кто в отделе» — вопрос карточки справочника). Заполнен ровно один из наборов области — этот или `user_construction_objects`: инвариант кросс-табличный и CHECK'ом невыразим, держит его API. Отсюда же выводятся **руководители отдела** в карточке справочника: это учётки с ролью `department_head`, привязанные к отделу, — второго хранилища у связи нет. Правка набора с любой стороны поднимает `auth_version` и гасит сессии затронутых учёток.
- **container_types** — справочник типов контейнеров/машин (управляется менеджером): `code` (unique), `name`, `type` (`cont|truck`), `volume_m3` (вместимость, ADR 0009 — база расчёта стоимости и кратности объёма; nullable), `sort_order`, `is_active`. Состав (миграции `0001`, `0003`, `0041`): контейнеры 8, 20, 27 и 38 м³ и самосвалы 25 и 36 м³; «Контейнер 25 м³ для тяжёлых грузов» выведен из обихода деактивацией — удалять его нельзя, на него ссылаются заведённые заявки (FK restrict).
- **vehicle_kinds** — виды ТС (верхний уровень): `code` (unique), `name`, `sort_order`, `is_active`. Seed — «Спецтехника», «Грузоперевозки». Таблицей, а не enum (расширяемо).
- **vehicle_types** — **плоский** справочник типов ТС (один уровень, ADR 0005): `kind_id` (FK, restrict), `code` (unique), `name`, `description`, `default_qualification_category_id` (FK на `qualification_categories`, restrict; ADR 0037, миграция `0059`: категория прав по умолчанию — подставляется при заведении машины, отбор водителей по ней не идёт), `waybill_form_code` (ADR 0037, миграция `0060`: какой бланк путевого листа выписывается — `4p` у пяти типов грузоперевозок, NULL у спецтехники и легковых; CHECK допускает `4p|leg3|esm2`, чтобы расширение области было значением, а не второй схемой), `sort_order`, `is_active`. CHECK `vehicle_types_code_format_check` — `code ~ '^[a-z][a-z0-9_]*$'`. Seed — 13 типов (миграция `0013`): 8 спецтехника (ЭСМ2) + 5 грузоперевозки (4П+3), включая «Самосвалы». CRUD `/api/v1/vehicle-types`: структурные ключи (`code`/`kind_id`) неизменяемы; удаления нет (деактивация через `is_active`). Переход с иерархии тип→подтип — expand/contract (миграции `0013` expand → `0014` contract, снявшая `parent_id`/`is_selectable` и `vehicle_type_source_mappings`). Обоснование — `docs/adr/0005-vehicle-types-flatten.md` (заменяет `0001`–`0003`).
- **vehicle_specs / vehicle_type_specs / vehicle_categories / vehicle_category_spec_values** — ТТХ типов и категории как комбинации их значений (ADR 0016, миграции `0034`–`0035`, seed `0045`–`0046`): ТТХ — глобальный справочник (`code` unique, `unit`, `decimals`, границы); привязка `(vehicle_type_id, spec_id)` означает обязательность значения у каждой категории типа и служит целью составного FK из значений; идентичность категории — `spec_signature` (IMMUTABLE `vehicle_category_signature(jsonb)`) + UNIQUE `(vehicle_type_id, spec_signature)`, наименование производно и хранится материализованно; полноту набора перепроверяют DEFERRABLE constraint-триггеры. У типа без ТТХ категорий не бывает.
- **Классификатор ТС** (ADR 0028, `GET /api/v1/vehicle-classifications`) — не таблица, а представление двух справочников: у типа с категориями позициями идут его категории, у типа без категорий — сам тип. Правило «общий тип при наличии категорий не выводится» живёт только здесь; им заполняются списки выбора в заявке и в справочнике техники и строки самого справочника типов.
- **vehicle_models** — справочник «Марка/модель» (ADR 0007, миграция `0015`): `vehicle_type_id` (FK, restrict), `name`, `normalized_name` (GENERATED из `vehicle_model_normalize(name)`), `description`, `manufacturer_name` (текст; отдельной таблицы марок/производителей нет), `is_active`. UNIQUE `(vehicle_type_id, normalized_name)` — дубли внутри типа; UNIQUE `(id, vehicle_type_id)` — цель составного FK из `vehicles`. Нормализация только механическая (регистр, ё→е, схлопывание разделителей); транслитерация («Мустанг»→«Mustang») в неё не входит.
- **vehicles** — конкретные ТС (ADR 0007, миграция `0017`): `vehicle_type_id` (FK, restrict; хранится явно — тип известен всегда), `vehicle_model_id` (**nullable** — в источнике есть машины без марки), `registration_number` + `registration_number_normalized` (GENERATED из `vehicle_reg_normalize`, гомоглифы АВЕКМНОРСТУХ→латиница), `inventory_number` (1С), `garage_number` (ADR 0037, миграция `0060`: своя графа бланка, отдельная от инвентарного; CHECK not-blank при непустом), `owner_organization_id` (FK на `organizations`, restrict; NULL = за основной организацией портала), `serial_number` (заводской/VIN), `passport_number` (ПТС/ПСМ), `manufacturer_name`, `manufactured_on`, `required_qualification_category_id` (FK на `qualification_categories`, restrict; ADR 0037, миграция `0059`: какая категория прав нужна, чтобы сесть за эту машину — требование стоит у машины, а не у типа, потому что его задаёт разрешённая максимальная масса; NULL = не заведено, и отбор водителей по нему не сужается; частичный индекс `vehicles_required_category_idx`), `status` (enum `vehicle_status`: `active|inactive|maintenance|retired`), `source_name` (исходная строка выгрузки), `note`, `deleted_at` (soft-delete). Составной FK `(vehicle_model_id, vehicle_type_id) → vehicle_models (id, vehicle_type_id)` — MATCH SIMPLE: при NULL-модели не проверяется, иначе запрещает расхождение типа машины и типа её модели. Частичный UNIQUE по `registration_number_normalized` (живые записи); инвентарный/заводской — только индексы (в выгрузке кириллица внутри VIN). Импорта/парсера нет: наполнение — выверенным seed'ом.
- **waste_types** — типы мусора (ADR 0009, миграция `0021`): `code` (unique, формат `^[a-z][a-z0-9_]*$`), `name`, `description`, `sort_order`, `is_active`. Seed — 7 значений из прайса; миграция `0040` (ADR 0026) переименовала «ОССиГ» в «Тринити» (`code` остался `ossig` — он неизменяем) и удалила «Строительные отходы» вместе с их ценами и ссылающимися заявками (пробными; их файлы, история статусов и машины уходят каскадом), так что остались 6: строительный мусор, бетонный бой, чистый/замусоренный грунт, Тринити, древесные отходы. Вариации написания одного типа запрещены (ADR 0017, миграция `0036`): `name_key` — GENERATED-колонка `waste_type_name_key(name)` (регистр, «ё» и любые разделители значения не имеют) под UNIQUE `waste_types_name_key_unique` + CHECK на непустоту; нормализацию считает та же SQL-функция, которую зовёт сервер в проверке, а её двойник в контрактах (`wasteTypeNameKey`) нужен форме для мгновенной подсказки. Отдельной вкладки у справочника нет: тип заводится **вместе с первой ценой** одной транзакцией `POST /api/v1/waste-tariffs` (`wasteTypeName` вместо `wasteTypeId`; `code` выводит сервер из названия), а переименование и деактивация — из строки тарифа. API `/api/v1/waste-types`: читают все, `PATCH` — администратор и менеджер, `POST` нет; `?hasActiveTariff=true` оставляет только типы с действующей ценой (список для формы заявки). `code` неизменяем, удаления нет — деактивация через `is_active`.
- **waste_tariffs** — прайс вывоза (ADR 0009, миграция `0021`; цены по операторам — ADR 0026, миграция `0040`): `operator_counterparty_id` (FK → `counterparties`, restrict, NOT NULL — чья это цена; тип «operator» проверяет сервис), `waste_type_id` (FK, restrict), **либо** `container_type_id` (точный тариф), **либо** `container_kind` (`cont|truck` — тариф на вид техники); CHECK `waste_tariffs_target_check` требует ровно одно из двух. `price_per_m3` (всегда за 1 м³), `price_per_container` + `is_per_container` — если в прайсе цена объявлена за контейнер (15 000 ₽ за 8 м³ → 1875 ₽/м³ и объём заявки обязан быть кратен 8), `note` (пункт прайса), `is_active`. Частичные UNIQUE по `(operator_counterparty_id, waste_type_id, container_type_id)` и `(operator_counterparty_id, waste_type_id, container_kind)` — считают и отключённые позиции, поэтому цену меняют в существующей строке, а не заводят вторую; цена другого оператора на ту же пару дублем не считается. Подбор (`/api/v1/waste-tariffs/resolve`): внутри оператора точный тариф побеждает тариф вида, между операторами выбирает исполнитель заявки — а пока он не назначен, берётся минимальная цена с пометкой `isMinimum` («от»); неактивный оператор из подбора выпадает вместе со своими ценами. Ведение (ADR 0014, вкладка «Стоимость вывоза мусора» — сводная таблица «пара × операторы»): `POST`/`PATCH` для администратора и менеджера, `POST` с `wasteTypeName` заводит вместе с ценой и сам тип мусора (ADR 0017), кросс-полевые инварианты — `validateWasteTariff` из контрактов, `price_per_m3` у позиции «за контейнер» считает сервер из `container_types.volume_m3`, правка пишется в `audit_log` («было → стало»); суммы оформленных заявок не пересчитываются — в них снимок тарифа, и меняется он только при смене исполнителя.
- **waste_requests** — заявки: `num` (identity, отображается «М-123» — миграция `0064`, по образцу «ТС-123» у заявок на технику: счётчики двух модулей свои, и одно число без префикса называло две разные заявки), `legacy_num_format` (`boolean NOT NULL DEFAULT false`, миграция `0064`: заявка заведена до префикса и показывается прежним номером «123-ВМ» — число плюс буква типа; её номер уже в талонах и переписке. Флагом на строке, а не порогом номера: порог пришлось бы зашить константой, своей в каждой базе). Счётчик при смене формата не сбрасывался — «М-» относится к отображению, а не к нумерации. FK `object_id`, `container_type_id` (только контейнерные операции: у `waste_removal` техники нет — ADR 0022, у заявок вывоза до этого решения колонка заполнена и очищается при первой правке); `request_type` (`container_install|container_replace|container_removal|waste_removal`), `delivery_at` (UTC), `comment`, `status` (`new|confirmed|done|cancelled`), `version` (optimistic lock), `created_by/updated_by/deleted_by`, `deleted_at` (soft-delete). Тарификация (ADR 0009, миграция `0021`): `waste_type_id`, `volume_m3`, `waste_tariff_id` + `price_per_m3` (снимок цены на момент сохранения; тариф вывоза подбирается по виду техники «Самосвал», ADR 0022), `amount` (GENERATED `round(volume_m3 * price_per_m3, 2)`). Все четыре поля заполняет **только `waste_removal`** (ADR 0019): контейнерные операции — установка, замена, снятие — не тарифицируются, и сервер их обнуляет. CHECK `waste_requests_install_no_pricing_check` держит это для установки; на замену и снятие он не расширен — у заявок, заведённых до ADR 0019, тип мусора и сумма сохранены как есть (миграции нет), а очищаются они при первой же правке. CHECK `waste_requests_price_snapshot_check` — тариф и цена только вместе. Исполнитель (ADR 0010, миграция `0022`): `operator_counterparty_id` (FK, restrict; nullable — оператор ещё не назначен). Эта же колонка задаёт видимость заявки для роли `operator`; требование «тип контрагента = operator» держит сервис. Назначение — отдельной ручкой `PATCH /waste-requests/:id/operator`, чтобы не пересчитывать предмет заявки и тариф. Исполнитель обязан обслуживать объект заявки (`construction_object_operators`, миграция `0027`); объект **без единой привязки** назначению не мешает — иначе первая заявка на новом объекте встала бы до заполнения справочника. Проверка повторяется и при переносе заявки на другой объект: пара «оператор — объект» может разойтись без смены исполнителя. Контакт ответственного (миграция `0062`): `responsible_name`, `responsible_phone` (`text NOT NULL DEFAULT ''`) — кто принимает машину на площадке; обязательность держит сервер.
- **request_files** — связь заявка↔файл (PK `(request_id, file_id)`, каскад) + `kind` (миграция `0031`): `attachment` — документ заявки, `ticket` — талон, приложенный при её закрытии (ADR 0013). С ADR 0024 талоны так лежат у заявки **любого** типа — общим пулом, без деления по машинам (миграция `0042` перенесла сюда талоны из `waste_request_vehicle_files`, после чего та таблица удалена). Талон обязателен: без единого живого `kind='ticket'` заявка в «Выполнена» не переводится (ADR 0020) — проверяет сервер, ограничения в БД нет (талон приходит в той же транзакции, что и статус). Видимость талона равна видимости его заявки, включая ограничение роли `operator` своими заявками.
- **waste_request_completions** — факт выполнения заявки на вывоз (ADR 0035, миграция `0056`): PK=FK `request_id` (каскад; одна заявка — одно закрытие, повторное после отката строку переписывает), `volume_m3` (`numeric(12,3)`, CHECK >0 — **фактически вывезено**: цифра из талона и весовой квитанции, вводится руками и с заявленным `waste_requests.volume_m3` расходится законно; сверка — подсказка человеку, а не запрет), `price_per_m3` (`numeric(12,2)`, CHECK >0 — **снимок цены** на момент закрытия: сначала снимок самой заявки, а если его нет, подбор по виду «Самосвал» у прайса оператора, ADR 0022/0026) и `waste_tariff_id` (CHECK `waste_request_completions_price_snapshot_check`: тариф только вместе с ценой — обратное законно, цена без тарифа означает «взяли не из прайса»), `total_cost` (`numeric(14,2)`, CHECK >=0 — считается `volume_m3 × price_per_m3`, но приходит от клиента и **правится свободно**: счёт оператора включает подачу и недогруз; NULL — цены в прайсе нет и сумму не ввели, ноль — вывоз в счёт другой работы), `completed_by` (RESTRICT), `completed_at`, `updated_at`; индекс `waste_request_completions_completed_at_idx (completed_at DESC)`. Незаданная цена закрытию **не мешает** (ADR 0035): заявка выполнена, и отказ означал бы «сначала заполните справочник». Факт есть только у `waste_removal` — контейнерные операции объёма не несут и закрываются одним талоном; «Выполнена» без объёма сервер не проводит, а при повторном закрытии хватает уже предъявленного. Приходит вместе со сменой статуса (`PATCH /waste-requests/:id/status`, `completion`) и правится только повторным закрытием — через `PATCH /waste-requests/:id` факт не меняется.
- **waste_request_vehicles** — состав техники прошлых закрытий (ADR 0011, ADR 0024; миграции `0029`, `0042`, `0056`), **только чтение**: с ADR 0035 закрытие предъявляет объём и стоимость, а не перечень машин, и новых строк здесь не появляется. Форма прежняя: `request_id` (каскад), `container_type_id` (FK, restrict — техника чужая, конкретное ТС из `vehicles` здесь не при чём; допустимы **оба вида**, `truck` и `cont`), `volume_m3` (`numeric(12,3)`, CHECK > 0 — снимок вместимости одной машины), `vehicle_count` (CHECK 1..99), `waste_tariff_id` + `price_per_m3` (снимок цены по прайсу для пары «тип мусора × тип техники» и оператора заявки; CHECK — только вместе), `amount` (GENERATED `round(volume_m3 * vehicle_count * price_per_m3, 2)`), `created_by`, `deleted_at`/`deleted_by` (пометка на удаление: такая строка в факт не входила). Миграция `0056` перенесла факт этих заявок в `waste_request_completions`: объём — суммой активных строк, сумма — ровно той, что показывал портал, цена — только если она одна на все строки (у разных типов техники она разная, и одним числом её не выразить). Сами строки остаются: по ним заявки принимали, и в карточке они видны в истории закрытия. У строк, заведённых до ADR 0024, `vehicle_count = 1` и снимка цены нет — сумма по факту у таких заявок не переносится.
- **request_status_history** — история смены статусов (+ `comment`, миграция `0024`): при переходе в `cancelled` комментарий обязателен и хранит причину отмены (её требует сервер, не CHECK). Статус `confirmed` отображается как «В работе»: переименовалась подпись, значение enum осталось. Переход с `from_status IS NULL` — заведение заявки; из него и складывается событие «создана» в её истории (ADR 0012).
- **vehicle_requests** — заявки на технику (модуль «Заказ ТС», миграция `0012`): `num` (identity, отображается «ТС-123»), `request_type` (`special_equipment|freight_transport`, enum `vehicle_request_type`), FK `object_id`, `vehicle_type_id` (плоский тип классификатора, ADR 0005), `vehicle_category_id` (категория заказанного типа, ADR 0028, миграция `0052`: nullable — у типа без ТТХ категорий не бывает, у заявок старше миграции их не проставляли; составной FK `vehicle_requests_category_type_fk (vehicle_category_id, vehicle_type_id) → vehicle_categories (id, vehicle_type_id)` RESTRICT — категория чужого типа невозможна, а заказанную из справочника не удалить; частичный индекс `vehicle_requests_vehicle_category_idx`. Обязательность решает сервер: категория требуется, когда у типа есть активные категории — состав справочника меняется, и CHECK этого не выражает), `status` (общий enum `request_status`), `comment`, `approved_by/approved_at` (виза руководителя строительства, миграция `0049`, ADR 0025: заполнены обе или ни одной — CHECK `vehicle_requests_approval_check`; частичный индекс `vehicle_requests_awaiting_approval_idx` под вопрос «что ждёт согласования»), `version` (optimistic lock), `created_by/updated_by/deleted_by`, `deleted_at` (soft-delete). Без визы заявка не переводится в «В работе» (422), виза ставится и снимается, пока заявка «Новая». Целостность «ровно одна деталь нужного типа» — сервисной транзакцией (constraint-триггер в бэклоге). Тип заявки выбирается в форме явно и из вида ТС не выводится (ADR 0004 §3): на объект (`special_equipment`) заказывают технику **любого** вида, грузоперевозку — только вида `freight_transport`. Пару «тип заявки × вид ТС» сверяет сервер (`isVehicleKindAllowedForRequest`, 422); ограничения в БД нет — вид лежит через `vehicle_types.kind_id`. Заказчик заявки (ADR 0040, миграция `0069`): `object_id` (**nullable** с 0069) или `department_id` (FK → `departments`, restrict) — CHECK `vehicle_requests_customer_check` требует ровно одного из них, CHECK `vehicle_requests_department_freight_check` запрещает отделу спецтехнику (она выходит на площадку). Частичные индексы по `department_id` — список заявок отдела и «что ждёт визы» с его стороны.
- **special_equipment_request_details** — детали заказа спецтехники (PK=FK `request_id`, каскад): `date_from`, `date_to` (date-only; CHECK `date_to >= date_from`). Контакт ответственного (миграция `0062`): `responsible_name`, `responsible_phone` (`text NOT NULL DEFAULT ''`) — кто встречает технику на объекте. CHECK на непустоту нет: у заявок, заведённых до колонки, контакта не было; обязательность держит сервер — новую заявку без контакта не завести, а правка не даёт сохранить пустое.
- **freight_transport_request_details** — детали грузоперевозки (PK=FK `request_id`, каскад): `scheduled_at` (timestamptz), `volume_m3`/`weight_tons` (`numeric(12,3)`; CHECK >0 и хотя бы одно задано), `loading_location`/`unloading_location` (CHECK not-blank). Метаданные верификации адреса (миграция `0013`, ADR 0006): `loading_address`/`unloading_address` (`jsonb NULL`; `source|fiasId|fiasLevel|geoLat|geoLon`; CHECK формы: `jsonb object` + ключ `source`). `NULL` = адрес введён вручную (не верифицирован); заполняется подсказками DaData на фронте. Контакт на концах маршрута (миграция `0062`): `loading_responsible_name`/`loading_responsible_phone` и `unloading_responsible_name`/`unloading_responsible_phone` (`text NOT NULL DEFAULT ''`) — грузят и принимают разные люди в разных местах, поэтому контакт свой у каждого конца; обязательность, как и у спецтехники, за сервером.
- **vehicle_request_assignments** — техника, которой заявку взяли в работу (ADR 0027, миграция `0051`): PK=FK `request_id` (одна заявка — одна машина: заявка заказывает одну позицию классификатора на один срок), `vehicle_id` (конкретное ТС из `vehicles`), `vehicle_type_id` (**служебная копия** типа заявки — существует только ради двух составных FK), `price_per_hour`/`price_per_shift` (`numeric(12,2)`, CHECK >0) и `shift_hours` (CHECK 1..24) — **снимок договорённости** по этой заявке: подставляется из предложения аренды, но правится свободно, и правка прайса его не переписывает, `assigned_by` (RESTRICT), `assigned_at`. Совпадение «машина того же типа, что заказан» держат FK `(request_id, vehicle_type_id) → vehicle_requests (id, vehicle_type_id)` (каскад; **без** `ON UPDATE` — смена типа ТС у заявки с назначенной машиной отклоняется, сервер отвечает 422) и `(vehicle_id, vehicle_type_id) → vehicles (id, vehicle_type_id)` (RESTRICT — назначенную технику из справочника не удалить). Обе цели уникальности добавлены той же миграцией: `vehicles_id_type_unique`, `vehicle_requests_id_type_unique`. Категорию (ADR 0028) сверяет сервер: машина **другой** категории не принимается, машина без категории — принимается («не разнесли» ≠ «не подходит»). «Хотя бы одна цена у аренды» — тоже правило сервера: принадлежность лежит в `vehicles`, и CHECK её не видит. Назначение приходит вместе со сменой статуса (`PATCH /vehicle-requests/:id/status`, `assignment`), «В работе» без машины сервер не проводит; повторный перевод (после отката) строку переписывает.
- **vehicle_request_completions** — факт выполнения заявки ТС (ADR 0029, миграция `0053`): PK=FK `request_id` (каскад; одна заявка — одно закрытие, повторное после отката строку переписывает), `worked_unit` (enum `vehicle_work_unit`: `hours|shifts` — единица хранится рядом с числом: «8» без неё не значит ничего), `worked_amount` (`numeric(10,2)`, CHECK >0), `rate` (`numeric(12,2)`, CHECK >0 — **снимок ставки** назначения по выбранной единице на момент закрытия: сумма обязана объясняться сама, а ставку назначения повторный перевод в работу переписывает), `total_cost` (`numeric(14,2)`, CHECK >=0 — считается `rate × worked_amount`, но приходит от клиента и правится свободно: счёт арендодателя включает перегон и простой), `completed_by` (RESTRICT), `completed_at`, `updated_at`; индекс `vehicle_request_completions_completed_at_idx (completed_at DESC)` — под журнал вкладки «История». `rate`/`total_cost` пусты у своей машины без ставки: внутреннюю технику не всегда считают в деньгах. «Аренду без суммы не закрывают» — правило сервера (принадлежность лежит в `vehicles`, CHECK её не видит); факт обязателен при назначенной технике и не требуется у заявок, взятых в работу до ADR 0027. Приходит вместе со сменой статуса (`PATCH /vehicle-requests/:id/status`, `completion`).
- **vehicle_request_files** — связь заявка ТС↔файл (PK `(vehicle_request_id, file_id)`, каскад; UNIQUE `file_id` — файл не в двух заявках ТС; кросс-модульную уникальность с «Мусором» держит общий файловый сервис `services/request-files.ts`).
- **vehicle_request_status_history** — история статусов заявки ТС (+ `comment`).
- **persons** — физические лица (ADR 0008, миграция `0018`): `last_name`/`first_name`/`middle_name` (CHECK not-blank на фамилию и имя), `full_name` (GENERATED STORED из трёх частей — единственная точка правды по ФИО), `birth_date` (CHECK `>= 1900-01-01`; верхняя граница — в сервисе, `CURRENT_DATE` в CHECK запрещён как не-IMMUTABLE), `phone`, `email` (citext), `created_by/updated_by/deleted_by`, `deleted_at` (soft-delete), `version` (optimistic lock). `snils` (ADR 0037, миграция `0058`): обязательный реквизит путевого листа, 11 цифр без разделителей (CHECK `persons_snils_format_check`; форматирование «XXX-XXX-XXX YY» — на выводе, контрольную сумму проверяет сервис — приём ИНН контрагента). Частичный UNIQUE `persons_snils_unique WHERE snils <> '' AND deleted_at IS NULL` — один живой человек на номер; пустая строка = не заполнен, обязателен номер только водителю, и держит это сервис. GIN-trgm по `full_name` — поиск и подсказка о дублях; жёсткого UNIQUE по ФИО нет (однофамильцы-ровесники), надёжно человека различает СНИЛС. Должность/специализация/работодатель/категории прав здесь **не хранятся**.
- **person_employments** — трудовые отношения, история (миграция `0018`): `person_id` (каскад), `employment_type` (enum `employment_type`: `staff|contractor|temporary`), `employer_name` (текст; справочника организаций пока нет), `personnel_no`, `job_title`, `started_on`/`ended_on` (CHECK порядка). Активность работника выводится отсюда (`ended_on IS NULL`), отдельного флага в `persons` нет. Частичный UNIQUE `(employer_name, personnel_no)` среди действующих отношений — табельный переиспользуем после увольнения.
- **specializations** — справочник специализаций (миграция `0018`): `code` (unique, формат `^[a-z][a-z0-9_]*$`), `name`, `description`, `sort_order`, `is_active`. Отвечает на «какую работу человек может выполнять» — это не право по документу. Миграция `0058` (ADR 0037) завела единственную запись — `driver` («Водитель»): ею и выражается водитель, отдельной таблицы для него нет.
- **person_specializations** — специализации человека, несколько одновременно (миграция `0018`): `person_id` (каскад), `specialization_id` (restrict), `is_primary`, `started_on`/`ended_on`, `comment`. Частичные UNIQUE: одна действующая запись на пару (человек, специализация) и не более одной действующей основной. **Водитель — это выборка по `code='driver'`**; таблиц `drivers`/`driver_profiles` нет.
- **credential_types** — справочник видов документов (ADR 0008, миграция `0019`): `code` (unique), `name`, `has_categories` (false — медзаключение и подобные), `expiry_required` (false — бессрочный), `sort_order`, `is_active`. Уровень «система квалификации» не заводится — вид документа и система совпадают один-к-одному. Миграция `0058` (ADR 0037) завела `driver_license` («Водительское удостоверение», с категориями, со сроком).
- **qualification_categories** — категории (квалификации) вида документа (миграция `0019`): `credential_type_id` (restrict), `code`, `name`. UNIQUE `(credential_type_id, code)` — «C» водительского и «C» тракториста не смешиваются; UNIQUE `(id, credential_type_id)` — цель составного FK. Миграция `0058` (ADR 0037) завела 16 категорий водительского удостоверения по ст. 25 ФЗ «О безопасности дорожного движения»: `code` в нижнем регистре (этого требует CHECK формата), `name` — сама буква («B», «CE»), расшифровка — в `description`, `sort_order` — порядок граф на бланке удостоверения.
- **person_credentials** — документы конкретных людей (миграция `0019`): `person_id` (каскад), `credential_type_id` (restrict), `series`/`number`, `issued_on`/`expires_on` (NULL = бессрочный; CHECK порядка), `issued_by`, `verification_status` (enum `credential_verification_status`: `unverified|verified|rejected`) + `verified_by`/`verified_at` (CHECK: отметка времени есть у всего, что не `unverified`), `revoked_at`/`revoke_reason` (аннулирование ≠ истечение ≠ удаление), `deleted_at`, `version`. Новый документ не перезаписывает старый. Частичный UNIQUE `(credential_type_id, series, number)` среди живых; индекс по `expires_on` — под отчёт по истекающим и напоминания через `jobs`.
- **person_credential_categories** — категории, открытые конкретным документом (миграция `0019`): `credential_id`, `qualification_category_id`, денормализованный `credential_type_id`, `valid_from`/`valid_to` (сужают срок документа, не продлевают), `restrictions`. Два составных FK — на `person_credentials (id, credential_type_id)` и `qualification_categories (id, credential_type_id)`: чужая категория в документе физически невозможна (приём из `0009`/`0017`).
- **person_credential_files** — сканы документа (миграция `0019`): PK `(credential_id, file_id)`, каскад, UNIQUE `file_id` — паттерн `vehicle_request_files`; у одного документа может быть несколько файлов.
- **waybill_series** — серии бланков путевых листов (ADR 0037, миграция `0061`): `code` (unique, формат `^[a-z][a-z0-9_]*$`), `name`, `prefix` (печатается в графе «серия»: «260604-646-»), `next_number` (счётчик), `number_width` (ведущие нули, CHECK 1–12), `organization_id` (NULL = серия основной организации), `is_active`. Счётчик строкой, а не sequence: sequence не откатывается вместе с транзакцией и оставляет дыры, а журнал строгой отчётности читают как непрерывный. Миграция заводит серию `main`.
- **waybills** — сам путевой лист (ADR 0037, миграция `0061`): `series_id` + `number` (UNIQUE — это и есть номер бланка), `form_code` (снимком, не join'ом: тип машины могут переклассифицировать, а лист уже выдан; CHECK `4p|leg3|esm2`), `status` (enum `waybill_status`: `issued|cancelled` — черновика нет, лист рождается переводом заявки в работу сразу выданным), `organization_id`, `vehicle_id`, `driver_person_id` (все restrict), `issued_for_date` (день листа и граница правки — до этой даты лист аннулируют и выписывают заново, начиная с неё нет; держит сервис, `CURRENT_DATE` в CHECK запрещён), `with_trailer` + реквизиты прицепов (CHECK: без прицепа они пусты), `garage_number`/`communication_kind`/`transportation_kind` (графы шапки, наследуются от прошлого листа машины), `data` (jsonb-снимок значений: лист печатается из него, а не из справочников), `issued_by/at`, `cancelled_by/at` + `cancel_reason` (CHECK: у аннулированного есть и время, и причина), `version`. Частичный UNIQUE `waybills_vehicle_date_unique (vehicle_id, issued_for_date) WHERE status <> 'cancelled'` — один лист на машину и дату, разные заказчики идут талонами; аннулированный дату освобождает.
- **waybill_requests** — талоны заказчиков (миграция `0061`): PK `(waybill_id, request_id)`, `slot` (CHECK 1–4 — столько талонов держит бланк 4-П), UNIQUE `(waybill_id, slot)`. UNIQUE по `request_id` намеренно нет: аннулированный лист сохраняет строку, а заявку после него выписывают заново — условие «лист не аннулирован» живёт в соседней таблице и держит его сервис.
- **files** — метаданные файлов в S3: `object_key` (unique), `filename`, `content_type`, `size`, `status` (`pending|active|deleted`), `scan_status` (резерв под ClamAV, этап 2), `uploaded_by`, `deleted_at`.
- **jobs** — outbox фоновых задач (§16): `type`, `payload`, `status`, `attempts/max_attempts`, `next_run_at`, `locked_by/locked_until`, атомарный захват `FOR UPDATE SKIP LOCKED`.
- **audit_log** — append-only аудит критичных действий (§22). Индекс `audit_log_entity_idx (entity_type, entity_id, created_at DESC)` (миграция `0030`) — под историю одной сущности: карточка заявки на вывоз читает отсюда правки, назначение исполнителя и архив/восстановление (ADR 0012). У правок в `metadata.changes` лежит снимок изменённых полей готовым текстом (`{field, from, to}`) — справочник могли переименовать позже, а история показывает то, что было.

## Правила удаления заявок

- Статус **«Новая»** (смены статуса не было) → **hard delete**: строка и связанные файлы удаляются; объекты S3 чистятся задачей `delete_s3_object` (немедленно).
- После первой смены статуса → **soft delete** (`deleted_at`); файлы сохраняются; восстановление — только администратор (`/waste-requests/:id/restore`).
- Отдельно удалённый файл (через редактирование заявки) — soft-delete + физическое удаление из S3 через 30 дней (job).
- Orphan upload-сессии (pending-файлы старше 24ч) чистит worker.

## Индексы

Уникальные: email, коды объектов/типов, `object_key`, `token_hash`. Обычные: статусы, FK, `delivery_at`, `created_at`, `jobs(status,next_run_at)`. GIN-trgm: `construction_objects.name`, `users.full_name`, `persons.full_name`, `counterparties.name`, `counterparty_synonyms.name` (полнотекстовый поиск). Частичные UNIQUE (действующие записи / живые строки): `users.person_id`, табельный номер, специализации человека, номер документа, `counterparties.inn`, `persons.snils`. Глобальный UNIQUE: `counterparty_synonyms.normalized_name` (см. ADR 0010).
