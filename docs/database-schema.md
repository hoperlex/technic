# Схема БД (этап 1)

SQL-first миграции: `apps/api/drizzle/*.sql`, применяются `apps/api/src/db/migrate.ts` с журналом `_migrations`. Drizzle-схема (источник типов приложения): `apps/api/src/db/schema.ts`.

## Таблицы

- **users** — пользователи. `role` (`admin|manager|dispatcher|shtab|operator`, nullable до активации), `construction_object_id` (обязателен для `shtab`), `counterparty_id` (ADR 0010, миграция `0022`: контрагент учётки — область видимости роли `operator`; CHECK `users_operator_counterparty_check` в `0023` требует его при `role='operator'`; в drizzle-схеме без `.references()`, чтобы не создавать цикл `users ↔ counterparties`), `is_active` (default false), `must_change_password`, `auth_version` (отзыв токенов), `person_id` (ADR 0008, миграция `0018`: физлицо учётки; nullable, частичный UNIQUE — одна учётка на человека; в drizzle-схеме без `.references()`, чтобы не создавать цикл `users ↔ persons`), `deleted_at` (soft-delete). Уникальный `email` (citext).
- **refresh_sessions** — opaque refresh-токены: `token_hash`, `family_id`, ротация (`replaced_by`, `revoked_at`), reuse detection.
- **construction_objects** — справочник объектов: `code` (unique), `name`, `address`, `is_active`. GIN-trgm по `name`.
- **counterparties** — контрагенты (ADR 0010, миграция `0022`): `type` (enum `counterparty_type`: `general_contractor|contractor|operator`), `name` + `normalized_name` (GENERATED из `counterparty_name_normalize`: регистр, ё→е, кавычки и разделители схлопываются; ОПФ не отбрасывается), `inn` (CHECK формата — 10 или 12 цифр; контрольную сумму проверяет сервис), `comment`, `is_active`, `created_by/updated_by/deleted_by`, `deleted_at` (soft-delete). Частичный UNIQUE по `inn` среди живых записей — ИНН и есть идентичность контрагента, поэтому **тип у записи один**: организация в другой роли меняет тип, а не заводит вторую запись. GIN-trgm по `name`. CRUD `/api/v1/counterparties` (запись — admin/manager), `GET /resolve?name=` — сопоставление наименования из документа по нормализованной форме.
- **counterparty_synonyms** — альтернативные наименования контрагента (миграция `0022`): `counterparty_id` (каскад), `name` + `normalized_name` (GENERATED). Основное наименование здесь **не дублируется**. UNIQUE по `normalized_name` **глобальный**, а не внутри контрагента: синоним отвечает на «чьё это наименование», и два владельца одного текста сделали бы сопоставление недетерминированным. API принимает синонимы полным списком (замена набора).
- **construction_object_operators** — операторы вывоза, обслуживающие объект (ADR 0010, миграция `0027`), **многие-ко-многим**: PK `(construction_object_id, counterparty_id)`, каскад с обеих сторон, `created_by`/`created_at`. Отдельный индекс по `counterparty_id` — под обратный проход «объекты этого оператора» (PK покрывает только проход от объекта). Требование «тип контрагента = `operator`» держит сервис — то же решение, что и с `waste_requests.operator_counterparty_id`. Набор правится **с обеих сторон** и передаётся полным списком: `operatorIds` в `/objects`, `objectIds` в `/counterparties` (непустой список у типа, отличного от `operator`, отклоняется; смена типа при живых привязках — 409). Замена набора со стороны объекта не трогает привязки к удалённым контрагентам: в карточке их не видно, и снимать невыбранное нельзя.
- **container_types** — справочник типов контейнеров/машин (управляется менеджером): `code` (unique), `name`, `type` (`cont|truck`), `volume_m3` (вместимость, ADR 0009 — база расчёта стоимости и кратности объёма; nullable), `sort_order`, `is_active`. Seed — 6 значений (8/20/27/25 м³ контейнеры, 25/36 м³ самосвалы).
- **vehicle_kinds** — виды ТС (верхний уровень): `code` (unique), `name`, `sort_order`, `is_active`. Seed — «Спецтехника», «Грузоперевозки». Таблицей, а не enum (расширяемо).
- **vehicle_types** — **плоский** справочник типов ТС (один уровень, ADR 0005): `kind_id` (FK, restrict), `code` (unique), `name`, `description`, `sort_order`, `is_active`. CHECK `vehicle_types_code_format_check` — `code ~ '^[a-z][a-z0-9_]*$'`. Seed — 13 типов (миграция `0013`): 8 спецтехника (ЭСМ2) + 5 грузоперевозки (4П+3), включая «Самосвалы». CRUD `/api/v1/vehicle-types`: структурные ключи (`code`/`kind_id`) неизменяемы; удаления нет (деактивация через `is_active`). Переход с иерархии тип→подтип — expand/contract (миграции `0013` expand → `0014` contract, снявшая `parent_id`/`is_selectable` и `vehicle_type_source_mappings`). Обоснование — `docs/adr/0005-vehicle-types-flatten.md` (заменяет `0001`–`0003`).
- **vehicle_models** — справочник «Марка/модель» (ADR 0007, миграция `0015`): `vehicle_type_id` (FK, restrict), `name`, `normalized_name` (GENERATED из `vehicle_model_normalize(name)`), `description`, `manufacturer_name` (текст; отдельной таблицы марок/производителей нет), `is_active`. UNIQUE `(vehicle_type_id, normalized_name)` — дубли внутри типа; UNIQUE `(id, vehicle_type_id)` — цель составного FK из `vehicles`. Нормализация только механическая (регистр, ё→е, схлопывание разделителей); транслитерация («Мустанг»→«Mustang») в неё не входит.
- **vehicles** — конкретные ТС (ADR 0007, миграция `0017`): `vehicle_type_id` (FK, restrict; хранится явно — тип известен всегда), `vehicle_model_id` (**nullable** — в источнике есть машины без марки), `registration_number` + `registration_number_normalized` (GENERATED из `vehicle_reg_normalize`, гомоглифы АВЕКМНОРСТУХ→латиница), `inventory_number` (1С), `serial_number` (заводской/VIN), `passport_number` (ПТС/ПСМ), `manufacturer_name`, `manufactured_on`, `status` (enum `vehicle_status`: `active|inactive|maintenance|retired`), `source_name` (исходная строка выгрузки), `note`, `deleted_at` (soft-delete). Составной FK `(vehicle_model_id, vehicle_type_id) → vehicle_models (id, vehicle_type_id)` — MATCH SIMPLE: при NULL-модели не проверяется, иначе запрещает расхождение типа машины и типа её модели. Частичный UNIQUE по `registration_number_normalized` (живые записи); инвентарный/заводской — только индексы (в выгрузке кириллица внутри VIN). Импорта/парсера нет: наполнение — выверенным seed'ом.
- **waste_types** — справочник типов мусора (ADR 0009, миграция `0021`): `code` (unique, формат `^[a-z][a-z0-9_]*$`), `name`, `description`, `sort_order`, `is_active`. Seed — 7 значений из прайса (строительные отходы, строительный мусор, бетонный бой, чистый/замусоренный грунт, ОССиГ, древесные отходы). API `/api/v1/waste-types`: читают все, заводят и правят администратор и менеджер (ADR 0014, вкладка «Типы мусора»); `code` неизменяем, удаления нет — деактивация через `is_active`.
- **waste_tariffs** — прайс вывоза (ADR 0009, миграция `0021`): `waste_type_id` (FK, restrict), **либо** `container_type_id` (точный тариф), **либо** `container_kind` (`cont|truck` — тариф на вид техники); CHECK `waste_tariffs_target_check` требует ровно одно из двух. `price_per_m3` (всегда за 1 м³), `price_per_container` + `is_per_container` — если в прайсе цена объявлена за контейнер (15 000 ₽ за 8 м³ → 1875 ₽/м³ и объём заявки обязан быть кратен 8), `note` (пункт прайса), `is_active`. Частичные UNIQUE по `(waste_type_id, container_type_id)` и `(waste_type_id, container_kind)` — считают и отключённые позиции, поэтому цену меняют в существующей строке, а не заводят вторую. Подбор: точный тариф побеждает тариф вида (`/api/v1/waste-tariffs/resolve`). Ведение (ADR 0014, вкладка «Стоимость вывоза мусора»): `POST`/`PATCH` для администратора и менеджера, кросс-полевые инварианты — `validateWasteTariff` из контрактов, `price_per_m3` у позиции «за контейнер» считает сервер из `container_types.volume_m3`, правка пишется в `audit_log` («было → стало»); суммы оформленных заявок не пересчитываются — в них снимок тарифа.
- **waste_requests** — заявки: FK `object_id`, `container_type_id`; `request_type` (`container_install|container_replace|container_removal|waste_removal`), `delivery_at` (UTC), `comment`, `status` (`new|confirmed|done|cancelled`), `version` (optimistic lock), `created_by/updated_by/deleted_by`, `deleted_at` (soft-delete). Тарификация (ADR 0009, миграция `0021`): `waste_type_id`, `volume_m3`, `waste_tariff_id` + `price_per_m3` (снимок цены на момент сохранения), `amount` (GENERATED `round(volume_m3 * price_per_m3, 2)`). CHECK `waste_requests_install_no_pricing_check` — установка нового контейнера не тарифицируется; CHECK `waste_requests_price_snapshot_check` — тариф и цена только вместе. Исполнитель (ADR 0010, миграция `0022`): `operator_counterparty_id` (FK, restrict; nullable — оператор ещё не назначен). Эта же колонка задаёт видимость заявки для роли `operator`; требование «тип контрагента = operator» держит сервис. Назначение — отдельной ручкой `PATCH /waste-requests/:id/operator`, чтобы не пересчитывать предмет заявки и тариф. Исполнитель обязан обслуживать объект заявки (`construction_object_operators`, миграция `0027`); объект **без единой привязки** назначению не мешает — иначе первая заявка на новом объекте встала бы до заполнения справочника. Проверка повторяется и при переносе заявки на другой объект: пара «оператор — объект» может разойтись без смены исполнителя.
- **request_files** — связь заявка↔файл (PK `(request_id, file_id)`, каскад).
- **waste_request_vehicles** — машины, вывезшие заявку (ADR 0011, миграция `0029`): `request_id` (каскад), `container_type_id` (FK, restrict — техника чужая, конкретное ТС из `vehicles` здесь не при чём; принимаются только типы вида `truck` — вывоз выполняется самосвалами), `volume_m3` (`numeric(12,3)`, CHECK > 0; **снимок вместимости типа** на момент закрытия — клиент объём не присылает, его подставляет сервер из `container_types.volume_m3`; тип без вместимости выбрать нельзя), `created_by`, `deleted_at`/`deleted_by`. `deleted_at` — **пометка на удаление**: строка выпадает из сверки объёма, но остаётся в истории; ставить и снимать её может любой, кто правит заявку, а удалить запись насовсем — только администратор. Машины передаются вместе со сменой статуса (`PATCH /waste-requests/:id/status`), и «Выполнена» без единой активной машины сервер не проводит; сверка суммы с `waste_requests.volume_m3` — подсказка, а не запрет. Машинами отчитывается **только `waste_removal`**: контейнерные операции (установка, замена, снятие) считаются по контейнерам, окно закрытия им не показывается, а машины у них отклоняются.
- **waste_request_vehicle_files** — талоны машины (миграция `0029`): PK `(vehicle_id, file_id)`, каскад, UNIQUE `file_id` (паттерн `vehicle_request_files`). Талон необязателен. Видимость талона равна видимости его заявки, включая ограничение роли `operator` своими заявками.
- **request_status_history** — история смены статусов (+ `comment`, миграция `0024`): при переходе в `cancelled` комментарий обязателен и хранит причину отмены (её требует сервер, не CHECK). Статус `confirmed` отображается как «В работе»: переименовалась подпись, значение enum осталось. Переход с `from_status IS NULL` — заведение заявки; из него и складывается событие «создана» в её истории (ADR 0012).
- **vehicle_requests** — заявки на технику (модуль «Заказ ТС», миграция `0012`): `num` (identity, отображается «ТС-000123»), `request_type` (`special_equipment|freight_transport`, enum `vehicle_request_type`), FK `object_id`, `vehicle_type_id` (плоский тип классификатора, ADR 0005), `status` (общий enum `request_status`), `comment`, `version` (optimistic lock), `created_by/updated_by/deleted_by`, `deleted_at` (soft-delete). Целостность «ровно одна деталь нужного типа» — сервисной транзакцией (constraint-триггер в бэклоге).
- **special_equipment_request_details** — детали заказа спецтехники (PK=FK `request_id`, каскад): `date_from`, `date_to` (date-only; CHECK `date_to >= date_from`).
- **freight_transport_request_details** — детали грузоперевозки (PK=FK `request_id`, каскад): `scheduled_at` (timestamptz), `volume_m3`/`weight_tons` (`numeric(12,3)`; CHECK >0 и хотя бы одно задано), `loading_location`/`unloading_location` (CHECK not-blank). Метаданные верификации адреса (миграция `0013`, ADR 0006): `loading_address`/`unloading_address` (`jsonb NULL`; `source|fiasId|fiasLevel|geoLat|geoLon`; CHECK формы: `jsonb object` + ключ `source`). `NULL` = адрес введён вручную (не верифицирован); заполняется подсказками DaData на фронте.
- **vehicle_request_files** — связь заявка ТС↔файл (PK `(vehicle_request_id, file_id)`, каскад; UNIQUE `file_id` — файл не в двух заявках ТС; кросс-модульную уникальность с «Мусором» держит общий файловый сервис `services/request-files.ts`).
- **vehicle_request_status_history** — история статусов заявки ТС (+ `comment`).
- **persons** — физические лица (ADR 0008, миграция `0018`): `last_name`/`first_name`/`middle_name` (CHECK not-blank на фамилию и имя), `full_name` (GENERATED STORED из трёх частей — единственная точка правды по ФИО), `birth_date` (CHECK `>= 1900-01-01`; верхняя граница — в сервисе, `CURRENT_DATE` в CHECK запрещён как не-IMMUTABLE), `phone`, `email` (citext), `created_by/updated_by/deleted_by`, `deleted_at` (soft-delete), `version` (optimistic lock). GIN-trgm по `full_name` — поиск и подсказка о дублях; жёсткого UNIQUE на человека нет. Должность/специализация/работодатель/категории прав здесь **не хранятся**.
- **person_employments** — трудовые отношения, история (миграция `0018`): `person_id` (каскад), `employment_type` (enum `employment_type`: `staff|contractor|temporary`), `employer_name` (текст; справочника организаций пока нет), `personnel_no`, `job_title`, `started_on`/`ended_on` (CHECK порядка). Активность работника выводится отсюда (`ended_on IS NULL`), отдельного флага в `persons` нет. Частичный UNIQUE `(employer_name, personnel_no)` среди действующих отношений — табельный переиспользуем после увольнения.
- **specializations** — справочник специализаций (миграция `0018`, **пустой**): `code` (unique, формат `^[a-z][a-z0-9_]*$`), `name`, `description`, `sort_order`, `is_active`. Отвечает на «какую работу человек может выполнять» — это не право по документу.
- **person_specializations** — специализации человека, несколько одновременно (миграция `0018`): `person_id` (каскад), `specialization_id` (restrict), `is_primary`, `started_on`/`ended_on`, `comment`. Частичные UNIQUE: одна действующая запись на пару (человек, специализация) и не более одной действующей основной. **Водитель — это выборка по `code='driver'`**; таблиц `drivers`/`driver_profiles` нет.
- **credential_types** — справочник видов документов (ADR 0008, миграция `0019`, **пустой**): `code` (unique), `name`, `has_categories` (false — медзаключение и подобные), `expiry_required` (false — бессрочный), `sort_order`, `is_active`. Уровень «система квалификации» не заводится — вид документа и система совпадают один-к-одному.
- **qualification_categories** — категории (квалификации) вида документа (миграция `0019`, **пустой**): `credential_type_id` (restrict), `code`, `name`. UNIQUE `(credential_type_id, code)` — «C» водительского и «C» тракториста не смешиваются; UNIQUE `(id, credential_type_id)` — цель составного FK.
- **person_credentials** — документы конкретных людей (миграция `0019`): `person_id` (каскад), `credential_type_id` (restrict), `series`/`number`, `issued_on`/`expires_on` (NULL = бессрочный; CHECK порядка), `issued_by`, `verification_status` (enum `credential_verification_status`: `unverified|verified|rejected`) + `verified_by`/`verified_at` (CHECK: отметка времени есть у всего, что не `unverified`), `revoked_at`/`revoke_reason` (аннулирование ≠ истечение ≠ удаление), `deleted_at`, `version`. Новый документ не перезаписывает старый. Частичный UNIQUE `(credential_type_id, series, number)` среди живых; индекс по `expires_on` — под отчёт по истекающим и напоминания через `jobs`.
- **person_credential_categories** — категории, открытые конкретным документом (миграция `0019`): `credential_id`, `qualification_category_id`, денормализованный `credential_type_id`, `valid_from`/`valid_to` (сужают срок документа, не продлевают), `restrictions`. Два составных FK — на `person_credentials (id, credential_type_id)` и `qualification_categories (id, credential_type_id)`: чужая категория в документе физически невозможна (приём из `0009`/`0017`).
- **person_credential_files** — сканы документа (миграция `0019`): PK `(credential_id, file_id)`, каскад, UNIQUE `file_id` — паттерн `vehicle_request_files`; у одного документа может быть несколько файлов.
- **files** — метаданные файлов в S3: `object_key` (unique), `filename`, `content_type`, `size`, `status` (`pending|active|deleted`), `scan_status` (резерв под ClamAV, этап 2), `uploaded_by`, `deleted_at`.
- **jobs** — outbox фоновых задач (§16): `type`, `payload`, `status`, `attempts/max_attempts`, `next_run_at`, `locked_by/locked_until`, атомарный захват `FOR UPDATE SKIP LOCKED`.
- **audit_log** — append-only аудит критичных действий (§22). Индекс `audit_log_entity_idx (entity_type, entity_id, created_at DESC)` (миграция `0030`) — под историю одной сущности: карточка заявки на вывоз читает отсюда правки, назначение исполнителя и архив/восстановление (ADR 0012). У правок в `metadata.changes` лежит снимок изменённых полей готовым текстом (`{field, from, to}`) — справочник могли переименовать позже, а история показывает то, что было.

## Правила удаления заявок

- Статус **«Новая»** (смены статуса не было) → **hard delete**: строка и связанные файлы удаляются; объекты S3 чистятся задачей `delete_s3_object` (немедленно).
- После первой смены статуса → **soft delete** (`deleted_at`); файлы сохраняются; восстановление — только администратор (`/waste-requests/:id/restore`).
- Отдельно удалённый файл (через редактирование заявки) — soft-delete + физическое удаление из S3 через 30 дней (job).
- Orphan upload-сессии (pending-файлы старше 24ч) чистит worker.

## Индексы

Уникальные: email, коды объектов/типов, `object_key`, `token_hash`. Обычные: статусы, FK, `delivery_at`, `created_at`, `jobs(status,next_run_at)`. GIN-trgm: `construction_objects.name`, `users.full_name`, `persons.full_name`, `counterparties.name`, `counterparty_synonyms.name` (полнотекстовый поиск). Частичные UNIQUE (действующие записи / живые строки): `users.person_id`, табельный номер, специализации человека, номер документа, `counterparties.inn`. Глобальный UNIQUE: `counterparty_synonyms.normalized_name` (см. ADR 0010).
