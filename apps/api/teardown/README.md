# Teardown — обратные миграции необратимых выкатов

Каталог намеренно **не** `apps/api/drizzle`: раннер миграций берёт оттуда каждый `*.sql`
(`listMigrationFiles()`), и лежи обратная миграция там, ближайший `db:migrate` применил бы её
следом за прямой — сняв только что накатанное, молча и без единой ошибки в выводе. Здесь его не
видит никто, кроме команды `db:cutover-down`.

Нормативное описание — [протокол выката](../../../docs/schema-cutover-protocol.md) §7. Коротко:

- **имя файла = полное имя файла миграции**: `0135_route_trips.sql` откатывается файлом
  `teardown/0135_route_trips.sql`. По этому же имени снимается запись журнала `_migrations`;
- **teardown и удаление записи журнала — одна транзакция** (`db:cutover-down`), с проверкой
  «удалена ровно одна строка»: ноль и больше одной — отказ с откатом транзакции;
- **снимает всё**, что завела миграция, включая данные: забытая строка в справочнике не даст
  накатить миграцию повторно, то есть откат сделает релиз невыкатываемым;
- **запускается образом кандидата**: teardown приезжает вместе со своей миграцией, и в предыдущем
  образе его ещё нет;
- **руками не вызывается** — команда не проверяет ни фазы выката, ни границы совместимости. Для
  человека есть `deploy-auto --cutover-revert`; прямой запуск остаётся у репетиции на копии базы
  (протокол §9).

Рядом с teardown релиз кладёт **верификатор** — файл `<миграция>.sql.verify` с одной строкой:
командой, которая проверяет данные после наката и возвращает ненулевой код на любом нарушении
(например `pnpm --silent --filter @technic/api backfill:trips --check`). Она выполняется внутри
образа кандидата на шаге 6 протокола, до записи границы, и её отсутствие — отказ: «проверять
нечего» релиз обязан написать явно (файл со строкой `true`), а не оставить пустым местом.

Файлы отсюда не удаляются после выката: сам факт, что у миграции был обратный ход, — часть истории
релиза, а стоимость хранения нулевая.
